# Spec: edge's tree builds and passes its checks under main's Omarchy pin

## Design

### 0. One signal for "this is an edge pin"

The checks that need to know which pin they run under take one fact:
`omarchy.version` begins with `edge-`. `omarchyVersion` is
`edge-<date>-<sha>` on edge and the release tag (`4.5.0`) on `main`, and
`tests/review-pins.nix:133` already relies on that. It is passed to a Python
check as `--edge` or nothing, and read in Nix as
`lib.hasPrefix "edge-" omarchy.version`.

Why not "is it a commit", and why this holds when `main` moves to a quattro
tag: on that day `omarchyVersion` becomes a tag again, so every edge-only
marker below stops being honoured. Each one then fails loudly: an
unclassified name, or a group that no row allows. Nothing is silently
skipped. That is the prompt to promote the marked rows in the same merge,
which is what §8 already asks of that merge.

### 1. The package builds under both pins

`pkgs/omarchy/default.nix` gains
`hasScreensaverPackage = builtins.elem "omarchy-screensaver" basePackages`.
The fact is independent of the needle: quattro's base list names the Arch
package and v4.5.0's does not (checked: 1 against 0). The
`omarchy-launch-screensaver` `--replace-fail` is spliced in with
`lib.optionalString hasScreensaverPackage`, so it is decided at evaluation
time and stays `--replace-fail`. Under quattro the install phase text is
unchanged, so the `omarchy` drvPath is unchanged. That is the strongest
proof that edge ships the same thing, and the plan checks it. So under quattro, an upstream rewording of the
launcher still fails the build. This is the intent's constraint against
`--replace-quiet` in disguise.

### 2. The migration test decides applicability from the pinned source

`tests/user-migrations/run` decides per migration, not per case:

- **The source.** A helper `applicable <ids…>` prints the ids whose
  `$ORACLE_SOURCE/migrations/<id>.sh` exists. `ORACLE_SOURCE` is the
  immutable pinned tree. `$oracle` is not used, because `run:648` reassigns
  it to a scratch tree that holds one migration.
- **Running.** A case computes `ids=$(applicable …)` and passes only those to
  `run_ids`. Its assertions loop over the same set: the marker loop at
  `run:316`, and any check about one id's effect, which is guarded by that
  id being in the set.
- **An empty set.** A case whose set is empty prints
  `skip <case>: none of its migrations are in this pin` and returns. A case
  with some applicable ids still runs them.
- **Coverage.** Under quattro, every applicable id still goes through
  `run_ids`. So one missing from the runner's list still fails at `run:49`
  (`… is not in the runner's list`).

### 3. The coexistence fixture asserts what each pin owes

`tests/coexistence/default.nix:494` (edge). The user's own `/lib/qt-6/plugins` must
be present under both pins (count ≥ 1). The count must be exactly 2 when the
package `hasQtengine`, and exactly 1 when it does not. The fixture keeps
asserting the user's half on v4.5.0, and both halves on quattro.

### 4. Ledgers: an `edge` marker, per row or per field

| ledger | how it is read | the marker |
|---|---|---|
| `data/bin-ledger.nix` | a regex over quoted strings (`check-bin-ledger.py:450`) | two string fields. `edge = "only"` means the row applies only under an edge pin. `edge_allow = "<groups>"` holds groups allowed only under an edge pin |
| `data/menu-actions.nix` | `builtins.toJSON (import …)`, values are strings (`check-menu-actions.py:123` rejects anything else) | a value may also be `{ reason = "…"; edge = "only"; }`. `check-menu-actions.py` takes `--edge` and skips such rows without it. A bare string is unchanged |
| `data/user-migrations.nix` | evaluated in Nix (`tests/user-migrations-ledger.nix`) | `edge = "only";` on a row: without an edge pin, the row is not counted as stale. With one it is checked as now |
| `data/omarchy-packages.nix` | evaluated in Nix (`tests/omarchy-package-ledger.nix:24` requires exactly one decision key) | the same `edge = "only";`. It is removed before the exactly-one-decision check, which still applies |

**Validation comes before filtering, in all four.** Every row is validated
under both pins, active or not:

- the marker's value is exactly `"only"`;
- no unknown field: the bin-ledger parser lists every `key =` in a row body
  and refuses any that is not a quoted string of a known key, and refuses a
  duplicate key, which the dict at `check-bin-ledger.py:453` would otherwise
  collapse silently;
- `edge_allow` groups are checked against `PATTERNS` even when inactive;
- a menu value that is an attrset has exactly `reason` and `edge`.

Only then are inactive rows set aside.

**One effective allowance.** Under `--edge` it is `allow` plus `edge_allow`,
otherwise `allow` alone. Both places that read allowances use it: the
behaviour biconditional ("allows X and no longer matches it",
`check-bin-ledger.py:384-397`), and the vendor-row guard, which refuses a
vendor row with neither `allow` nor `pacman` (`check-bin-ledger.py:311`). So
a stale `edge_allow` group fails under edge, and a vendor row carrying only
`edge_allow` is valid under edge.

`edge_allow` is used for the three commands whose classification holds on
both pins and whose allowances differ: `omarchy-agent-local`,
`omarchy-install-dictation-hex` and `omarchy-keyboard-toprow`. A row is
`edge = "only"` when its subject exists only on quattro:
`omarchy-launch-screensaver`'s patch row, `install.ai.herdr`, the nine
migration rows, and the quattro-only package rows.

Which rows get a marker is decided by the checks under `main`'s pin, not
from memory (§4, a hand-kept list fails open). The plan runs each check
there and marks exactly what it names.

### 5. The both-pins job (phase 2, a workflow PR to `main`)

Promotion is a step inside `verify` (`omarchy-edge.yml:546`), so a job that
runs after `verify` would be too late. `omarchy-edge.yml` therefore gains a
hosted job, `main-pin`:

- it `needs: prepare`, and runs beside `wait-idle`;
- `verify` gains `needs: main-pin`;
- the promote step's condition adds `needs.main-pin.result == 'success'`;
- `verify`'s `failed` output (`:484`) gains `main-pin` when that result is
  not success;
- `report` gains `needs: main-pin` and reports a `main-pin` failure the way
  it reports the others (`:568`).

The main-pin build needs neither VMs nor p620, so it stays off the
self-hosted runners. The job does:

1. Restore `main`'s pin: both copies in `flake.nix`, read from
   `origin/main:flake.nix`, plus `nix flake lock --update-input omarchy`.
2. Build `.#omarchy`, the cheap tier (`generated-checks.sh` minus VM checks),
   `vm-toplevel`, `reference-toplevel`, the four `options-*` shards, and
   statix.
3. Run `readme-counts.sh --fix` and leave its diff uncommitted. README counts
   are pin-derived (#1537), and the merge regenerates them, so this only
   proves the counts can be computed.

A failure there leaves `edge` where it was, and the report names
`main-pin`.

Phase order: phase 1, steps 1 to 4 above, lands on `edge` through
`edge-candidate` and a `from_candidate=true` dispatch. Phase 2, this job, is
a PR to `main` that the owner merges (§11). It is proven before that against
a deliberately broken carry, so it can be shown to fail (§1).

## Alternatives rejected

- **A list of rows the merge drops.** Nothing checks it between merges (§4),
  and the next main→edge merge would delete the rows on edge.
- **Gating the screensaver patch on `hasInfix needle launcher`.** That is
  `--replace-quiet` under another name.
- **Skipping the migration cases by the runner's list.** That hides a
  migration missing from the list, which is the one regression the case
  exists for.
- **A `checks.<name>` for the both-pins property.** A check cannot swap a
  flake input, and it would run on every `main` PR, where the property
  means nothing.
- **Nightly only.** It finds the break a day later. And it is not cheaper:
  edge's job already has the tree and a warm store.

## Risks

- **Marker rot.** `edge = "only"` rows build up between merges. They expire
  loudly when `main` moves to a quattro tag (§0), but not before, so a row
  whose subject has left quattro is still caught as stale under the edge
  pin, as today.
- **Job cost.** The `main-pin` job adds a second package build and the cheap
  tier to every edge run. That is about one `omarchy` build plus the options
  shards on a hosted runner, against edge's existing VM checks. The PR gives
  the measured minutes.
- **Coverage moved, not lost.** Each marker narrows what one pin checks.
  The plan's §1 breaks prove each still fails under the pin it claims.

## Verification

- **What ships is unchanged.**
  - Under quattro, `omarchy`'s drvPath on the carry equals the base's, by
    §1's `optionalString`.
  - Under v4.5.0, the baseline is the base edge tree with only the
    screensaver substitution made non-fatal, which is the build that
    otherwise cannot exist. The carry's `share/omarchy` is diffed against
    it, and so is the `vm-toplevel` package list.
  - Both diffs must be empty.
- **The signal's expiry.** The quattro tree, with `omarchyVersion` set to a
  release-style `4.6.0` in a scratch tree, must fail
  `bin-ledger`, `omarchy-package-ledger` and `user-migrations-ledger`
  loudly, not pass. That is §0's claim, measured.
- **Under both pins, on the carry:**
  - `.#omarchy`;
  - `bin-ledger`, `menu-actions`, `user-migrations`,
    `user-migrations-ledger`, `omarchy-package-ledger`, `coexistence`,
    `patched-files`;
  - `options-shards`, statix;
  - `vm-toplevel` and `reference-toplevel`.

  `main`'s pin comes from a scratch tree. Each pin's built
  `share/omarchy/bin` is diffed against the same pin's build before the
  change. It must be identical except for the gated screensaver line, which
  is unchanged under quattro, and absent from the v4.5.0 build that could
  not build before.
- **§1 breaks, each shown red and then green:**
  - a stale `edge_allow` group under `--edge`;
  - an `edge = "only"` row whose subject is gone, under `--edge`;
  - an unknown marker value;
  - the screensaver gate inverted, under quattro;
  - a migration that runs after `case_1672` (where `$oracle` is reassigned)
    removed from the runner's list under quattro, which `user-migrations`
    must still fail;
  - a mixed case under v4.5.0: its quattro-only id is dropped, and its
    applicable ids still run and are asserted;
  - an unknown bin-ledger field, a duplicate field, a non-string value and
    a bad `edge_allow` group, each refused under both pins;
  - a vendor row with only `edge_allow`, which is valid under `--edge` and
    refused without it;
  - the qtengine count forced to 1 under quattro (coexistence).
- **Phase 2:** the workflow runs on a branch against a carry that re-breaks
  the screensaver gate. `main-pin` must fail and `edge` must not move:
  `git ls-remote origin edge` reads the same before and after. It then
  passes once restored.
- **Done** means:
  - phase 1 is green on edge, and the dispatched run passes;
  - the phase 2 PR is open, with its proof;
  - #1752 closes when the phase 2 PR merges.
