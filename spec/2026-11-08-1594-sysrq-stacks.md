# Spec: a hung test guest says what it is waiting for

## Design

The approved intent settles three questions: SysRq is enabled through the test
instrumentation only, by kernel parameter, and the detector sends `w`, then
`t` when `w` showed no blocked task. This spec says where each piece goes.

### 1. The kernel parameter, in the instrumentation text

`tests/lib/installed-target.nix:106-112`, `etcInstrumentation`, gains one body
line:

```nix
boot.kernelParams = [ "sysrq_always_enabled" ];
```

- **Why it works.** The kernel's `sysrq_on_mask()` returns true when
  `sysrq_always_enabled` is set, whatever `kernel.sysrq` says. So the shipped
  `kernel.sysrq` that `systemd-sysctl` applies later cannot turn it off, and
  nothing nixarchy ships changes.
- **The output reaches the console.** nixpkgs' `test-instrumentation.nix:252`
  already sets `boot.consoleLogLevel = 7`, so the `pr_info` task lines reach
  `ttyS0`. The handler restores the log level before it runs the operation, so
  this setting is what lets the lines through.
- **List merge.** `boot.kernelParams` is a list, so this line adds to the
  instrumentation's own `console=` parameters rather than replacing them (§7).
- **Who gets it.** Every caller of `etcInstrumentation`: `install`,
  `free-space`, `install-encrypted` and `install-seed-shape`. The seed imports
  the same text (`targetSystemFor`), so the reinstall stays a copy and not a
  build. `checks.install-seed-shape` is what proves that, and it must stay
  green.

### 2. The check's own nodes

`tests/boot-hang-detect.nix`: `nodes.frozen` and `nodes.healthy` each get
`boot.kernelParams = [ "sysrq_always_enabled" ]`. They are plain test nodes
and never go through `etcInstrumentation`. Without the parameter, case C
could not see an enabled key.

### 3. The pokes (`tests/vm-cleanup.py`, `_poke` and `_diagnose`)

The sequence is `nmi`, then `sendkey alt-sysrq-w`, then `sendkey alt-sysrq-t`.
The `t` poke is skipped when the `w` output already contains a `state:D` task
line.

- **When `t` still runs.** A `w` that printed nothing at all still gets `t`. A
  guest that answers neither key has its silence recorded twice, which is the
  "did not answer" evidence the intent asks for.
- **Watch windows.**
  - `nmi` and `w` keep the fixed `watch`.
  - `t` watches until the console has been quiet for 3 s, capped at
    `TASK_DUMP_MAX_S = 90`. A full task dump at 115200 baud is tens of seconds
    for a few hundred tasks, so a fixed window would either cut the dump or
    waste time.
- **Output cap.**
  - `new[:20]` (`vm-cleanup.py:109`) becomes a cap of
    `POKE_MAX_LINES = 3000` per poke.
  - When lines are cut, the poke's text ends with `(N more console lines not
    shown)`, so a cut is never silent.
  - The full serial log is still in the job log either way. The cap keeps the
    exception text bounded.
- **Time budget.** `_diagnose`'s `30 + 2 * poke_watch` (`:159`) becomes
  `30 + 2 * poke_watch + TASK_DUMP_MAX_S + 5`, so the `t` dump is not
  abandoned halfway.

### 4. The assertions

**`tests/boot-hang-detect.nix`**

- Case C stops asserting the refusal.
  - After `w`, it now asserts `Show Blocked State`, which the kernel prints
    only when the operation is enabled.
  - After `t`, it asserts at least one `task:` line, unless `w` already
    printed a `state:D` task.
- Case A adds `poke sendkey alt-sysrq-t:` to its expected headers, because the
  stopped guest prints nothing for `w`, so `t` runs.
- Case A's 60 s limit includes the pokes, which run inside `_diagnose`
  before the raise. "Quiet" means no new line for 3 s, counted from the send
  or the last line, so a guest that prints nothing ends `t`'s wait after
  3 s, not 90. Case A (`poke_watch=2`) grows by about 3 s.

**`tests/boot-diagnostics.py`** (stub machines)

- The poke order becomes `nmi`, then `w`, then `t`.
- A new stub case whose `w` reply contains `state:D` asserts that `t` is not
  sent.
- A case with 3,500 console lines asserts the cap and its
  `(500 more console lines not shown)` line.

### 5. Documentation

`tests/AGENTS.md`, under "Reading the pokes", and the paragraph at `:790`:

- the disabled line no longer appears in tests;
- how to read `w` (blocked tasks) and `t` (every task, looking for the one in
  a wait that never ends);
- `:790`'s sentence becomes what is true now: enabled in the test
  instrumentation only.

## Alternatives rejected

- **`kernel.sysrq = 1` as a sysctl in the instrumentation.** It is applied by
  `systemd-sysctl`, which is not guaranteed to run before the hang's 5 s
  mark, and it
  merges by priority with whatever else sets `kernel.sysrq` (§7: sysctls sit
  at `mkOverride 1250`). The parameter needs neither.
- **Enabling it in nixarchy's default configuration.** Rejected in the intent:
  it is a security-relevant default.
- **`l` (backtraces of all CPUs).** It shows only the idle loop that the
  registers already show.
- **Always sending `t`.** It costs up to 90 s on every hang, and a `D`-state
  stack already names the wait.
- **No cap on lines.** It would make an unbounded exception message. The
  serial log keeps everything anyway.

## Risks

- **The install closure changes** (one kernel parameter), so the first run
  rebuilds the target's toplevel. Seed parity is guarded by
  `install-seed-shape`.
- **A long dump on a healthy guest in case C** makes `boot-hang-detect`
  slower, by tens of seconds at most.
- **A guest whose key really is lost reads as silence.** That is the same
  weak evidence as today, and it is now recorded for both keys.
- **`w` and `t` are read-only operations**, but `sysrq_always_enabled` allows
  every operation on these test guests. Only the detector sends keys, and it
  sends these two.

## Verification

| check | tier | expect |
|---|---|---|
| `boot-diagnostics` | cheap | order `nmi`/`w`/`t`, `t` skipped on `state:D`, cap line |
| `boot-hang-detect` | VM | case A has the `t` header; case C has `Show Blocked State` and `task:` |
| `install-seed-shape` | eval/cheap | the seed still matches the instrumented target |
| `install`, `free-space` | VM | pass; the target's `/proc/cmdline` holds `sysrq_always_enabled` (one assertion in `install`) |

§1 breaks:

1. Drop the node parameter → case C fails on `Show Blocked State`.
2. Drop the `t` poke → case A fails on its header.
3. Skip the `state:D` test → the `boot-diagnostics` case fails.
4. Restore `[:20]` → the cap case fails.
5. Drop the `etcInstrumentation` line → `install`'s cmdline assertion fails.

Not provable before a real hang: that a halted, hung guest answers the key.
The next CI hang is that proof, as the intent says.
