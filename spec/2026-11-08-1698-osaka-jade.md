# Spec: a machine on Osaka Jade keeps a working theme after Omarchy dropped it

## Design

### 1. Osaka Jade ships as a bundled theme again (intent decision 1)

`pkgs/omarchy/default.nix` fetches the theme's own repository, pinned:

```nix
osakaJadeTheme = fetchFromGitHub {
  owner = "omacom";
  repo = "omarchy-osaka-jade-theme";
  rev = "bc18781cdd0102f86cbc3e82c6bd6d420c8025b9";
  hash = "sha256-4BGYncJ7a0/qHNTAs91x3C9ciEx+9/tioGMg5fR+siQ=";
};
```

The install phase copies it to `$out/share/omarchy/themes/osaka-jade`, with
a `# Why:` pointer to a short section in `pkgs/AGENTS.md`. That keeps
`checks.install-phase-budget` from growing past one line plus the pointer.

That one directory is the whole integration, because every theme path
already reads it:
- `omarchy-theme-list` lists every directory under `$OMARCHY_PATH/themes/`
  (`bin/omarchy-theme-list:8`), so the theme menu offers it again;
- `omarchy-theme-set osaka-jade` stages a bundled theme from
  `$OMARCHY_THEMES_PATH` with `cp -r --no-preserve=mode`
  (`pkgs/omarchy/default.nix:481-482`), the same path every stock theme
  takes, so staging, refresh and the theme's `neovim.lua` work as for the
  other 23;
- a machine whose `theme.name` reads `osaka-jade` names a theme that
  exists again, with no migration and no network.

The repository has the layout of a bundled theme (`colors.toml`,
`icons.theme`, `neovim.lua`, `backgrounds/`, previews), and is MIT, as
Omarchy is. A `LICENSE` and a `README.md` come with it, as harmless extras.

### 2. Interaction with the migrations

- Quattro's `1787481314` begins with
  `[[ -f $OMARCHY_PATH/themes/osaka-jade/colors.toml ]] && exit 0`, so with
  the theme bundled it is a no-op on edge. Its row stays `declined`,
  with the reason updated: the theme is bundled, so there is nothing to
  clone.
- v4.5.0's `1787481315` stays in `predates`; #1705 decides it.
- No user migration is added. The fix is the theme existing.

### 3. Pinning and refreshing

The pin lives beside the other `fetchFromGitHub` sources in
`pkgs/omarchy/default.nix`. The theme moves rarely (last push
2026-10-26). It is refreshed by hand, by bumping `rev` and `hash`.
The nightly review reports pins in `flake.lock`, not `fetchFromGitHub`
revisions, so this one is not watched. That is stated in the AGENTS.md
section.

## Alternatives rejected

- **A flake input** for the theme: it would be watched by the nightly review,
  but adds a top-level input for 13 files that rarely change. Each input
  also enters `inputSources` and the ISO.
- **Porting `1787481314` with `git` on the hook's PATH**: a network clone at
  login, and a silent theme change on failure (intent constraints).
- **Jade Horse with a notification**: the user loses the theme they chose.

## Risks

- **Upstream ships its own `osaka-jade` again.** The `cp` would then
  collide with a directory upstream provides. So the copy refuses if
  `themes/osaka-jade` already exists, and the build fails with a message
  saying to drop this carry.
- **The theme's `neovim.lua` and `vscode.json`** are applied as for any
  bundled theme. Upstream reviewed them as a bundled theme until
  2026-10-25.
- **Size:** about 13 files, mostly the backgrounds. Measured in the plan
  with `du`.

## Verification

- A new cheap check, `checks.osaka-jade-theme` (`tests/osaka-jade-theme.nix`),
  takes the built tree and asserts `themes/osaka-jade/colors.toml` exists.
  It then runs the shipped `omarchy-theme-list` with an empty `HOME` and
  asserts `osaka-jade` is in its output.
  §1: with the copy line removed, both assertions fail. With the refusal
  test forced (a pre-existing `themes/osaka-jade`), the build fails with
  the carry message.
- `checks.user-migrations-ledger` still passes (only a reason changes).
- `checks.install-phase-budget` still passes.
- On edge, the next carry confirms `1787481314` exits 0 with the theme
  bundled. Its row's reason is updated there.
