# Intent: stable moves from Omarchy v4.5.0-rc1 to v4.5.0-rc2

## Problem

Omarchy v4.5.0-rc2 shipped on 2026-10-27. `main` is on rc1 (#1403,
#1405), and the owner chose the RC track, so the nightly bump proposed
rc2 as draft #1473. It does not build. Every build job and the install
check fail on the same `substituteInPlace`, and the scheduled `omarchy`
run (40630476736) fails the same way:

    ERROR: pattern \ \ \ \ lua\ -E\ -\ \<\<\'LUA\' doesn't match anything
    in file '.../bin/omarchy-menu-keybindings'

That error is only the first one. rc2 has moved past what `main` carries
in three ways:

- **rc2 has caught up with edge.** It (tag 5978d93) is strictly ahead
  of edge's quattro pin 58858ae, by 30 commits. Edge already carries the
  NixOS ports of four quattro moves since rc1: #1423, #1428, #1431 and
  #1447. That is 143 commits over 33 files, and `main` has none of them.
  Retargeting the failing patterns by hand reproduces edge's
  `pkgs/omarchy/default.nix` line for line: upstream adopted the
  keybindings Lua timeout, the launchers walk `XDG_DATA_DIRS`, and the
  version-channel grep became `grep -Eq`. The rebuilt package then stops
  on #1447's nine new agents, which edge already handles.
- **The 30 commits past edge.** They are mostly i18n, tests and the
  manual. They also add `etc/mkinitcpio.conf.d/i2c_hid_of_module.conf`
  and `etc/sudoers.d/omarchy-locale-generate`, which
  `nixarchy-etc-overlay`'s ledger does not list. That ledger is exactly
  what has kept edge's own quattro red since this morning (#1475, run
  40641876382). The rest are new `bin/` scripts (n1x GPU memory,
  clamshell, speedtest, dev-font, bar-text-color), shell QML and four
  migrations.
- **rc2's release notes move shortcuts.** Calculator, Activity,
  Network, Nightlight, notifications and `Super + Tab`. Anything
  nixarchy names by key, such as menus, the demo scenes and the manual,
  may now name the wrong one.

## Proposed outcome

- `main` carries Omarchy **v4.5.0-rc2**, pinned to the tag, built from
  edge's proven carries plus the fixes the 30 later commits need. All of
  `build`, `install check` and the `omarchy` workflow are green.
- Edge then differs from `main` by its quattro pin alone, as after #1405.
- The rc2 fixes reach edge through its normal `main` merge, so they also
  clear #1475 for the part of quattro that rc2 shares.
- Installed machines on `release` are untouched, as with rc1.
- Draft #1473 is closed as superseded, pointing at this PR.

## Affected users and systems

- `main`: `flake.nix` (both pin copies) and `flake.lock`, plus edge's
  33 files: `pkgs/omarchy/`, `data/{bin-ledger,etc-overlay,menu-actions}.nix`,
  `modules/{apps,nixos}.nix` and `tests/` (session, coexist, coexistence,
  plugin, menu-*, demo, review-pins, provision-launchers).
- Whatever the 30 later commits need: at least the etc-overlay ledger,
  and maybe `bin-ledger.nix` and `pkgs/omarchy/default.nix`.
- The owner and the eager users who follow `main` or the RC tag.

## Constraints

- **Pin the tag** `v4.5.0-rc2`, not a sha, as #1403 decided.
- **Keep edge's history.** Merge edge into the task branch for real, and
  merge the PR with `gh pr merge --merge`, never a squash (CLAUDE.md §8,
  and the lesson #1405 left).
- **Do not push to `update/omarchy-v4.5.0-rc2`.** The bump workflow owns
  that branch.
- **§1** for every check that changes, including the etc-overlay ledger
  check, which has to show its failing case first.
- **§6 build tiers.** The `omarchy` package build waits for the install
  and edge-verify VM jobs (`vm-host-free.sh`). VM checks run in CI only.
- No workflow edits are expected. If one turns out to be needed, it is a
  §11 change for the owner.

## Open questions

1. **Order of the work.**
   - **(a)** One task branch. Merge edge, pin rc2, then fix whatever rc2
     still breaks. That is the #1405 route, and it unblocks stable
     fastest.
   - **(b)** Fix edge first: #1475, then quattro HEAD, which contains
     most of rc2. Then merge edge into `main` and pin rc2. Each fix is
     proven on edge first, but stable waits on quattro, which moves daily.

   I propose **(a)**. rc2 is the target the owner chose. Its fixes flow
   back to edge through the next `main` merge anyway.
2. **Shortcut moves.** Should this PR re-check every nixarchy file that
   names a moved key, or only those a check or a build trips on? I
   propose a grep pass over `data/`, `docs/manual/` and `tests/demo/` for
   the moved keys, with the fixes in this PR. The demo scenes have no
   check (CLAUDE.md §4).
