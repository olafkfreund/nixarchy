# Intent: the NIXARCHY banner fits the window it is printed in

Closes #764.

## Problem

Every window started by `omarchy-launch-floating-terminal-with-presentation`
prints the banner first. That covers the Install menu's apply, rollback, boxes,
VMs, secrets and most other nixarchy menu actions. Ours
(`pkgs/omarchy/branding/logo.txt`, installed at `pkgs/omarchy/default.nix:474`)
is 87 columns wide. Upstream's is 81, and upstream sizes that window at 875x600
(`default/hypr/apps/system.lua:4`) to fit it. The extra six columns clip or wrap
the banner, and everything the command prints lands below where the window
ends. The owner found it on the rebuild window after enabling an app.

Nothing checks the width, so the day the banner was widened was also the day it
stopped fitting, and nothing noticed.

## Proposed outcome

- The banner still reads NIXARCHY and is at most 81 columns wide, the width the
  upstream window was sized for.
- The floating windows show the whole banner with room for the command below
  it.
- A check fails if the banner ever grows past upstream's width again.

## Affected users and systems

Every nixarchy desktop, through the omarchy package's `logo.txt`. The Plymouth
frames are generated from the same file (`pkgs/omarchy/default.nix:1728`), so
the boot splash changes shape too.

## Constraints

- Do not change the shared floating-window rule. It sizes every floating window,
  not just this one, and a wider window still breaks at a larger font.
- The ARCHY half is sliced from upstream's logo and stays untouched. Only NIX is
  ours to redraw.
- The width assertion goes into an existing check. A new `checks.<name>` would
  need a workflow edit, which is a human change (AGENTS.md §4, §11).
- Prove the assertion fails against today's 87-column file before it counts
  (§1).

## Open questions

- The Plymouth splash is generated from this file. Is a narrower banner at boot
  acceptable, or should Plymouth keep its own copy? The default is one file for
  both.
