# Spec: Chrome gets Omarchy's bundled extensions and policy on edge

## Design

Quattro's `install/helpers/browser-policy.sh` (`browser_policy_install_defaults`)
puts two files into `/etc/opt/chrome/policies/managed`: `omarchy.json` (the
same defaults as Chromium's) and `omarchy-extensions.json` (a copy of
`default/chromium/policies/chrome-extensions.json`). nixarchy writes both
declaratively, as it already does for Chromium (#1491, `modules/nixos.nix`
about line 1723):

- **Package, edge only** (`pkgs/omarchy/default.nix`, inside
  `lib.optionalString isEdge`): rewrite `file:///usr/share/omarchy/` to
  `file://$out/share/omarchy/` in
  `default/chromium/policies/chrome-extensions.json` and
  `default/chromium/crx/updates.xml`, with `--replace-fail` on each side.
  Expose `passthru.chromeExtensionsPolicy = isEdge`.
- **Module** (`modules/nixos.nix`, beside the Chromium entry): when
  `cfg.package.passthru.chromeExtensionsPolicy or false`, add
  `environment.etc."opt/chrome/policies/managed/omarchy.json"` and
  `"opt/chrome/policies/managed/omarchy-extensions.json"`. Each is built
  from the package's file by a small `runCommand` with `jq` that deletes
  every policy the user sets in `programs.chromium.extraOpts` (the names are
  known at evaluation, so there is no import-from-derivation). The Chromium
  file `chromium/policies/managed/omarchy.json` (#1491) is built the same
  way, because `programs.chromium` writes `extra.json` into that directory
  too. These files do nothing until Chrome is installed, the same
  way the Chromium file behaves with Chromium absent; that matches upstream,
  which installs them whenever Chrome is present.
- **Native hosts:** nothing to add. `home.activation.nixarchyChromiumHosts`
  already runs `omarchy-install-chromium-{copy-url,ytdlp}`, which write into
  `~/.config/google-chrome`, and quattro's host templates admit the CRX ids.
- **The theme colour** keeps working: `omarchy-theme-set-browser` writes
  `color.json` into the same directory, which the existing tmpfiles rule
  makes writable, and `environment.etc` only adds symlinks beside it (the
  Chromium directory works this way today).

**Not shipped**, each documented in `pkgs/AGENTS.md`:

- `config/chrome-flags.conf`: nixpkgs' `google-chrome` wrapper never reads
  it (it adds Ozone flags itself through `NIXOS_OZONE_WL`), and Chrome
  ignores its `--load-extension` line, which the policy replaces.
- Migration `1794210626`: the module above does its job declaratively, and
  activation already rewrites the hosts; its `/etc` writes cannot run here.
  #1763 lists it (it runs `omarchy-install-chromium-copy-url`), and its row
  there is `not-needed`, citing this issue.
- Migration `1794391847`, which copies 1Password's external-extension stub
  from Chromium's `/usr/share` directory to Chrome's. `programs._1password-gui`
  does not write that stub, and nixarchy never writes Chromium's: its
  1Password installer replaces the `sudo` stub with a message naming
  `programs.chromium.extensions` (`data/bin-ledger.nix`), and nixpkgs writes
  that option's `ExtensionInstallForcelist` for Chrome too. So there is
  nothing to copy. Documented, not ported.
- `omarchy-dev-pack-chrome-extensions`: a maintainer tool that re-signs the
  CRXs, with nothing to do on a user's machine (already excluded from the
  session scan by #1760).

## Coexistence

A user's own `programs.chromium` writes `default.json` and `extra.json` into
`/etc/opt/chrome/policies/managed` (and into `/etc/chromium/policies/managed`).
Different file names keep `environment.etc` from colliding, but Google
documents a policy set to different values in two Linux policy files as
undefined behaviour. So our files never carry a policy the user sets: the
module drops every name in `programs.chromium.extraOpts` from ours. Our
policies (`ExtensionSettings`, `DefaultBrowserSettingEnabled`, the privacy
and promotion keys) do not overlap the ones nixpkgs derives from its other
options (`ExtensionInstallForcelist`, `HomepageLocation`, the
`DefaultSearchProvider*` keys), and `extraOptsRecommended` is a lower level
that a managed value is meant to beat.

The fixture in `tests/coexistence/fixtures.nix` sets
`programs.chromium.extraOpts.DefaultBrowserSettingEnabled = true` and
`programs.chromium.extensions`, and the check that reads it,
`tests/coexistence/default.nix` (the Chromium block at about line 155), gains
assertions: all four Chrome files and both Chromium files exist, and neither
of our files contains `DefaultBrowserSettingEnabled`.

## Alternatives rejected

- **Gate on Chrome being installed** (scan `environment.systemPackages` for
  `google-chrome`): Chrome also comes from Home Manager, a flatpak or a user's
  own package list, and the files are inert without it. The extra eval
  coupling buys nothing.
- **A wrapper reading `chrome-flags.conf`:** an override of an unfree
  package the user installs, for flags the wrapper already covers or Chrome
  ignores.
- **Run the migration's scripts:** they write `/etc` as root at runtime,
  which is exactly what a declarative system does not do.

## Risks

- A wrong `--replace-fail` target fails the edge package build, loudly.
- Updates: the policy's `update_url` serves the first install only; Chrome
  then updates from the extension's own manifest, and the three CRXs carry no
  `update_url`, so a later Omarchy release with a newer CRX does not reach an
  installed copy without `override_update_url`. Upstream ships the same
  policy, so this behaves as it does on Arch, and it is a fix for upstream
  rather than a patch here (pkgs/AGENTS.md routing rules). Recorded in
  `pkgs/AGENTS.md`; the store path changing with each build is harmless for
  the same reason. Not measurable here: Chrome is unfree and no check runs it.
- `main` is untouched: `passthru.chromeExtensionsPolicy` is false on v4.5.0.

## Verification

- New `checks.chrome-policy` (runCommand on the package): on edge, both
  JSON files parse; neither they nor `updates.xml` contain `/usr/share`;
  every `codebase` in `updates.xml` exists; every extension id in the policy
  has an `appid` in `updates.xml` with an `update_url` pointing at it. On a
  non-edge package it asserts that `passthru.chromeExtensionsPolicy` is false.
- An evaluation assertion in `tests/options.nix` style, or the coexistence
  fixture, that `environment.etc` has both entries on edge and neither on
  v4.5.0.
- Break proofs: drop a substitution (the `/usr/share` assertion fails);
  delete a CRX from the tree (missing codebase); remove the module entry
  (the eval assertion fails); stop filtering `extraOpts` (the coexistence
  assertion on `DefaultBrowserSettingEnabled` fails).
- Not run anywhere: Chrome itself loading the extensions. Named in the PR.
