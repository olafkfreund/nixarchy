# Spec: Bump nixi to 0.10, the Omarchy overlay card

## Design

Two changes land in **nixi** first (its PR olafkfreund/nixi-nixarchy#9, before
it merges), because they fix behaviour every nixi user has, not only nixarchy's.
Then **nixarchy** pins the resulting commit on nixi's `main` and brings its
checks and docs to the 0.10 layout.

### In nixi (PR #9)

**D1. Claude Code is the default agent** (the approver's answer to intent
question 1). Two parts:
- *Harness.* With no Omarchy default agent and no selection in the card, the
  bridge uses `claude` instead of stopping with "No default agent is
  configured" (`bridge/harness-policy.js` `resolveHarness`). razer showed that
  error on a fresh card because `~/.config/omarchy/defaults/agent` did not
  exist. An explicit Omarchy default or card selection still wins.
- *Adapter.* `services.nixi.agents` keeps `claude` first in its default. It is
  pinned only when unfree is allowed: the default becomes
  `lib.optional (pkgs.config.allowUnfree or false) "claude" ++ [ "codex" ]`,
  because `claude-agent-acp` pulls in the unfree `claude-code` and pinning it
  unconditionally would make evaluation fail for anyone with unfree off.
  nixarchy runs Home Manager with `useGlobalPkgs = true`
  (`installer/host.nix:190`) and allows unfree by default
  (`modules/nixos.nix:411`), so a default nixarchy desktop pins it; with
  unfree off, Claude is still the default agent and its adapter is found on
  PATH if installed.

**D2. The card is enabled for you, once** (the approver's answer to intent
question 2 — an explicit exception to "installed, not enabled"). Measured in
Omarchy's `shell/services/PluginRegistry.qml` `isEnabled()`: a third-party
plugin is enabled when its id is referenced anywhere in `shell.json` — an
entry in `plugins[]` (overlays) or in `bar.layout.*` (bar widgets). Measured on
p620: toggling a plugin that is not enabled exits 0 and prints nothing, so
without this SUPER+H, the Help row and `nixi` silently do nothing on a fresh
desktop.

A Home Manager activation step in **nixi's module**
(`services.nixi.autoEnable`, default `true`; nixarchy leaves the default):
- Only if `~/.local/state/nixi/enabled-once` does not exist. Then: the card's
  id belongs in `plugins[]` (it is an overlay); if it is already there, leave
  it; if it is referenced only in `bar.layout.*` (0.9's bar-widget slot, which
  p620 has), move that reference to `plugins[]`; if it is nowhere, add
  `{"id": "io.github.olafkfreund.nixi"}`. When `barWidget.enable`, the button
  is added to its manifest's default bar section unless already in the bar.
  Then create the marker. Once per home, so a user who later turns the card
  off in Setup > Plugins stays off.
- When the shell is running it is asked over IPC
  (`omarchy-shell shell setPluginEnabled <id> true`, the call `omarchy plugin
  enable` makes) so it picks the change up live; otherwise `shell.json` is
  edited as JSON (python3, atomic replace, keeping every other key), and the
  shell reads it at its next start. A missing or unparsable `shell.json` is
  left alone and reported, never recreated.
- `bin/nixi` still checks `omarchy-shell shell listPlugins` before toggling,
  and if the card is off (the user turned it off, or `autoEnable = false`)
  sends `omarchy-notification-send` "Nixi is turned off — enable Nixi in Setup >
  Plugins" and exits 1, instead of the silent no-op.

Why the move matters: on p620 the stale `bar.layout.right` entry is the only
thing keeping the card enabled, so a user tidying the bar later would disable
the card without knowing it.

### In nixarchy

**D3. Pin.** `flake.nix` `nixi.url` → the merge commit of nixi PR #9 on `main`
(a commit, per the rule above it); update the comment's description of nixi
(no server, an overlay card). `nix flake lock` changes only `nixi`.

**D4. `tests/options.nix`, same on/off shape, 0.10 layout.**
- `nixiTracesIn`: drop `systemd.user.services ? nixi` and
  `xdg.configFile ? "nixi/ui.html"` (0.10 has neither); keep the
  `nixi-manual` timer and the package; add the plugin directory link
  `"omarchy/plugins/io.github.olafkfreund.nixi"` and the grounding asset
  `"nixi/KNOWLEDGE.md"`. Still five mechanisms.
- `nixiUnit`: removed — there is no unit to be on. Its job ("a machine that
  says no has nothing listening") is now vacuous and stated in the comment.
- `nixiPluginFile` → `nixiPluginDir = "omarchy/plugins/io.github.olafkfreund.nixi"`;
  `nixiBarWidget` asks about `"${nixiPluginDir}-button"`, the separate button
  plugin that `barWidget.enable` now controls.
- `nixiLeavesMenuAlone` unchanged.
- New `nixiEnablesCard`: on = the default home has nixi's enabling activation
  step (`home.activation ? nixiEnableCard`), off = `nixiOff` does not. It pins the
  approved exception so a nixi bump that drops it fails here, by name.

**D5. Words.** `modules/home.nix` comments that call the bar widget nixi's front
door and mention "a server on 8642"; `docs/manual/getting-started.md` "The
guide" (overlay card, SUPER+H / Help / snowflake, enabled on first switch and
yours to turn off in Setup > Plugins, Claude Code as the default agent, no
server, `services.nixi.port` no longer exists);
`README.md` row. `tests/plugin.nix` needs no change (it only sets
`enable = false`).

**D6. Write-back.** `AGENTS.md` gains the two general traps found here: an
Omarchy IPC toggle for a disabled plugin is a silent success, and a Home
Manager module that moves from per-file links to a whole-directory link fails
`checkLinkTargets` on the old real directory.

## Alternatives rejected

- **Pin `claude-agent-acp` unconditionally.** Honours "Claude default" but
  makes every unfree-off configuration fail to evaluate.
- **nixarchy sets `agents` or writes `shell.json` itself.** Works for nixarchy
  only; both belong to the module that owns the plugin ids.
- **Enable on every activation.** Re-enables a card the user turned off, at
  every rebuild.
- **Only document "enable it in Setup > Plugins".** The approver chose
  enabling, and the silent no-op made documentation-only a trap.
- **Track nixi's branch until PR #9 merges.** `flake.nix` forbids it, and every
  nixarchy user would follow a moving target.

## Risks

- **Existing desktops on upgrade.** A 0.9 real plugin directory fails Home
  Manager activation unless removed first; nixi's module does that when it
  holds only Home Manager links (unit-tested, ordered before
  `checkLinkTargets`, seen working by hand on p620 and razer). A directory with
  anything else in it (an old plugin-manager checkout) still fails, with Home
  Manager's collision message — correct, but a user sees a failed switch.
- **`allowUnfreePredicate` users** who allow only `claude-code` have
  `allowUnfree = false`, so the adapter is not pinned by default and must be
  on PATH or listed in `agents`. Documented.
- **Writing `shell.json`, which the shell owns.** Mitigated by IPC when the
  shell runs, a once-only marker, JSON-preserving atomic edits, and leaving a
  missing or broken file alone. A concurrent write by the shell at the same
  instant could still be lost; the IPC path avoids that on a running desktop.
- **Anyone who set `services.nixi.port` or `voice`** gets an evaluation error
  naming the removed option (intended; nixarchy sets neither).
- **CI cost.** The install check runs on p620's runners (37-90 min) and p620
  hard-resets after some switches (nixos_config#1820).

## Verification

- nixi PR #9: the checks below pass and CI is green.
- nixarchy: `nix build .#checks.x86_64-linux.options` (and `doc-options`) pass
  with the new pin; the updated cases fail when put back to the 0.9
  expectations against the 0.10 pin (mutation); `nix flake check` evaluates;
  the install check passes in CI.
- On p620: with nixos_config's override removed and nixarchy bumped, the p620
  toplevel's closure diff against the running system shows no nixi change
  (same nixi commit), then the override is dropped (nixos_config PR).
- nixi tests for D2: the enable step against fixture `shell.json` files
  (id nowhere → added, marker written, every other key kept; id only in
  `bar.layout` → moved to `plugins[]`; id already in `plugins[]` → unchanged;
  marker present → untouched; missing or broken file → untouched and
  reported), and `bin/nixi` against a stub `omarchy-shell`
  (enabled, disabled, missing, no answer); D1: `resolveHarness` with no
  Omarchy default returns `claude`, and activation packages build with and
  without unfree. Each mutation-checked.
- On p510 (the first desktop to get it from main, when its owner deploys): the
  card is enabled without a manual step and SUPER+H opens it.
- By hand: turn the card off in Setup > Plugins, rebuild, confirm it stays off
  and SUPER+H shows the "turned off" notification.
