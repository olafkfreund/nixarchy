# Spec: Correct stale hypr-rdp and snapshot descriptions

## Design

1. Replace the conflicting release and migration comments in `modules/services/hypr-rdp.nix:26-54` and `:382-399` with one accurate account of the pinned release. `flake.nix:127-129` and `flake.lock` pin v0.1.6. Its pinned `src/config.rs` implements `password_file` and fails for a missing or empty **named** password file, but `RuntimeConfig::load` still logs warnings and permits unauthenticated service when no credentials are named. State both boundaries and retain the reason for the module's guard at `modules/services/hypr-rdp.nix:122-148`. Remove advice to delete that guard merely because `password_file` exists. Preserve the current runtime design; migration to `password_file` is a separate change.
2. Correct `data/bin-ledger.nix:552-555` to say that `omarchy-snapshot create` manually snapshots `/home` and `restore` points the user to files from a `/home` snapshot. `pkgs/omarchy/nix-bin/omarchy-snapshot:147-197` shows both actions. The installer also takes a **boot-time root** snapshot (`installer/host.nix:347-356`), which includes `/var/lib`; the command can list it (`pkgs/omarchy/nix-bin/omarchy-snapshot:155-162`) but does not create or restore that snapshot. Keep the distinction in the ledger's one-line reason.

## Alternatives rejected

- Migrate the unit to upstream `password_file` now: the owner chose a docs-only correction. A migration changes secret rendering and service startup behavior and needs separate design and verification.
- Describe the command as snapshotting `/var/lib`: the root snapshot covers it at boot, but the command's manual create and restore paths operate on `/home` only.
- Add a permanent wording check for these two comments: it would mostly assert the chosen prose, rather than compare behavior, and would need editing on a legitimate upstream pin or command change. The red/green proof below checks the two claims directly during this correction.

## Risks

- An inaccurate statement about upstream's no-credential behavior could encourage removal of a guard and expose a Hyprland session. The revised comments must distinguish a missing or empty **named** file from no credentials configured at all.
- The ledger is a single-line Nix string; careless quoting can break evaluation. Run formatting and syntax checks after editing.
- Upstream behavior may change on a later pin. The source claims here apply to the locked v0.1.6 revision, not every future release.

## Verification

- Inspect the locked v0.1.6 `src/config.rs` for `password_file`, `read_password_file`, `ConfigCredentials::from_parts`, and `startup_warnings`; compare the comments with that code and `flake.nix:127-129`.
- Run a cheap shell check that asserts the hypr-rdp comments name v0.1.6 and its remaining no-credentials fail-open case, rejects the stale “no tag”, “no PR”, and “upstream now refuses on an empty password” claims, and asserts the ledger distinguishes manual `/home` create/restore from boot-time root snapshots. Use `rg` on files directly, with no `producer | grep -q` pipeline.
- Prove each assertion can fail: copy each changed file aside outside the worktree, temporarily restore its stale statement, run the check and capture its nonzero output, then restore with `cp` and show it passing. Never use `git checkout` to restore a break proof.
- Run `nix fmt`, inspect `git diff --stat`, `nix fmt -- --ci`, `nix run nixpkgs#statix -- check .`, and `nix run nixpkgs#deadnix -- --fail .` after editing `.nix` files. No VM or options checks are needed for documentation-only changes.
