# Spec: agents on nixarchy can look up nixarchy's own options and manual

## What was measured (2026-10-03, `nixosConfigurations.reference`, main `5ab63ea5`)

- **The catalogue is cheap.** `pkgs.nixosOptionsDoc` over
  `options.programs.nixarchy`, plus the Home Manager options, evaluates in
  **1.4 s at 230 MB RSS** (`--no-eval-cache`). It builds a **180 KB**
  `options.json` with **300 options**: 287 NixOS, 13 Home Manager. This is
  nothing like `checks.options`' 11.5 GB, which evaluates every *config*, not
  the option declarations.
- **Three defects surfaced, each a fix in this task:**
  1. **One option cannot be rendered at all.**
     `modules/services/microvm.nix:166`,
     `shares.*.tag`, has `default = baseNameOf config.mountPoint` with no
     `defaultText`, so the build aborts. *"The option
     `…shares.*.mountPoint' was accessed but has no value defined"*. With a
     `defaultText` it builds. (nixd's option hover over the same subtree hits
     the same throw.)
  2. **269 of 300 options are declared in an unnamed store path.** The flake
     exports `nixosModules.nixarchy = import ./modules/nixos.nix inputs` and
     `homeManagerModules.nixarchy = import ./modules/home.nix inputs`: bare
     functions with no `_file`, so every option declared in those two files
     is attributed to whoever called the evaluation. That is nixpkgs'
     `flake.nix` for NixOS, home-manager's `nixos/common.nix` for HM. The
     same misattribution shows in every "defined in" / "declared in" a user
     reads in an error trace today.
  3. **The HM options need their real prefix.** `getSubOptions [ ]` yields
     `<name>.programs.nixarchy.*`; `getSubOptions [ "home-manager" "users" ]`
     yields `home-manager.users.<name>.programs.nixarchy.*`. The type supplies
     the `<name>` segment itself.
- **The manual is small:** `docs/` is 23 MB, almost all images and video.
  `docs/manual` (35 pages) plus `docs/llms.txt` is **about 430 KB**, which is
  exactly what mcp-nixarchy reads (`manual/*.md`, `llms.txt`).
- **The server swap needs no new plumbing.** mcp-servers-nix's `nixos` module
  is `mkServerModule { name = "nixos"; packageName = "mcp-nixos"; }`. Its
  `package` option takes any package, and the command is
  `lib.getExe package`. mcp-nixarchy's `meta.mainProgram` is
  `mcp-nixarchy`, and the flake exposes `packages.<system>.mcp-nixarchy` and
  `overlays.default`. It carries its own fastmcp 4 stack, scoped to itself,
  so following our `nixpkgs` does not touch our Python set.

## Design

### D1. The server is mcp-nixarchy

- **`flake.nix`:** a new input
  `mcp-nixarchy = { url = "github:olafkfreund/mcp-nixarchy/<commit>"; inputs.nixpkgs.follows = "nixpkgs"; }`.
  It is pinned to a commit (the repository has tags only from release-please;
  bump deliberately, as the `mcp-servers-nix` comment says), with a comment in
  the same register as the neighbouring inputs. Any other inputs it has
  (`flake-parts`, `devshell`) follow ours where we have one.
- **`modules/home.nix` `mcpConfig`** (`:203`): add
  `programs.nixos.package = inputs.mcp-nixarchy.packages.${pkgs.stdenv.hostPlatform.system}.mcp-nixarchy;`
  beside `programs.nixos.enable = true;`. The server key stays `nixos`, so
  `mcp__nixos__*` and every permission granted to it are unchanged.

### D2. `/etc/nixarchy/options.json`

- **One builder, a package output:** `packages.<system>.nixarchy-options`,
  built in `flake.nix` from the reference machine's option tree:
  - `options.programs.nixarchy`;
  - `(options.home-manager.users.type.getSubOptions [ "home-manager" "users" ]).programs.nixarchy`.
    The same expression `modules/nixos.nix:227` already gives nixd.
  - Built with `pkgs.nixosOptionsDoc`.
  - **`transformOptions`** rewrites every declaration under the flake's own
    `outPath` to
    `{ name = "<repo-relative path>"; url = "https://github.com/olafkfreund/nixarchy/blob/<rev>/<path>"; }`,
    where `<rev>` is `self.rev or "main"`. Declarations from other inputs are
    left as store paths.
  - The option tree is the same on every machine (options do not depend on
    config), so one build serves all.
- **`modules/nixos.nix`:** under `mkIf cfg.enable`,
  `environment.etc."nixarchy/options.json".source = "${…nixarchy-options}/share/doc/nixos/options.json";`.
  The package reaches the module the way the module already receives flake
  outputs (`inputs.self.packages`).
- **The three fixes measured above:**
  - `defaultText = lib.literalExpression "baseNameOf mountPoint";` at
    `modules/services/microvm.nix:166`;
  - the two exports become
    `{ _file = ./modules/nixos.nix; imports = [ (import ./modules/nixos.nix inputs) ]; }`,
    and likewise for `home.nix`;
  - the HM prefix as above.

### D3. `/etc/nixarchy/docs`

- **A small derivation** holding `docs/manual` and `docs/llms.txt`, by path
  from the flake source, not the 23 MB `docs/`.
- **`modules/nixos.nix`:** under `mkIf cfg.enable`,
  `environment.etc."nixarchy/docs".source = <it>;`.

### D4. The release carries `options.json` (owner signed off, intent answer 1)

- **`.github/workflows/release.yml`,** in the step that assembles `out/`
  (`:262-290`):
  - `nix build .#nixarchy-options`, then copy its `options.json` into `out/`;
  - add it to `SHA256SUMS`, so the existing "every promised asset is
    attached" check (`:479-500`) covers it with no change.
- **The name stays `options.json`.** mcp-nixarchy's fallback URL is
  `releases/latest/download/options.json`.

### D5. Skills and the manual

- **`pkgs/omarchy/skills/nixos/SKILL.md`,** "Finding the right name"
  (`:174-182`) and the error list (`:271`):
  - first, the `nix` MCP tool, with the channel matching the machine;
  - `source=nixarchy` for `programs.nixarchy.*`, `source=nixarchy-docs` for
    the manual;
  - then `nixarchy-search` and `nix search` as fallbacks, for agents without
    MCP;
  - `/etc/nixarchy/options.json` named for `jq`.
- **`pkgs/omarchy/skills/nixos-binaries/SKILL.md:93`:** the MCP tool first,
  then search.nixos.org.
- **`docs/manual/ai.md:113-128`:** the server is mcp-nixarchy, a fork of
  mcp-nixos that also answers nixarchy's options and manual from
  `/etc/nixarchy`.

### D6. Checks

- **`tests/options.nix:5702`** greps the generated MCP configs for
  `mcp-nixos`. Retarget it to `mcp-nixarchy`, so it proves the package swap
  reached all three agents. Its message names the new binary.
- **`tests/ai-mirror-mcp-remove.nix`:** **no change.** Its `mcp-nixos` strings
  are fixture data for a neighbouring server the script must leave alone. Any
  command name serves.
- **New: `checks.nixarchy-options` (cheap, `runCommand`), over the built
  package and the reference machine's `/etc` entries:**
  - it parses, with more than 250 entries;
  - it contains `programs.nixarchy.enable` and
    `home-manager.users.<name>.programs.nixarchy.enable`;
  - **no declaration of an option under `programs.nixarchy` is a bare store
    path** (catches a lost `_file`);
  - `environment.etc."nixarchy/options.json"` and `"nixarchy/docs"` are set
    on `reference` and **absent** with `programs.nixarchy.enable = false`
    (Mode A);
  - the docs tree has `llms.txt` and at least 30 `manual/*.md`.

## Coexistence (§14)

- **A user's own `environment.etc."nixarchy/…"`:** a conflicting `source` is
  an evaluation error that names both files, never a silent shadow. Nobody
  sets these paths today, and it is not worth a fixture. To override, use
  `lib.mkForce`.
- **A user's own `nixos` MCP server:** `mergeJson` already replaces the
  `nixos` key in the agent configs today (unchanged by this task). A user who
  wants their own server turns off `programs.nixarchy.mcp`.
- **The new input** follows our `nixpkgs`, and its Python stack is scoped to
  itself (measured in its own `fastmcp4-overlay-check`), so no package in the
  user's set changes.

## Alternatives rejected

- **Reusing NixOS's `system.build.manual.optionsJSON`:** built with
  `includeAllModules = false`, it has no nixarchy options. Turning that on
  makes the whole NixOS manual unsubstitutable and re-renders every option on
  each build.
- **Building `options.json` per machine from `config`-dependent options:**
  the option tree is machine-independent. One build is cacheable and is the
  same file the release ships.
- **Installing all of `docs/`:** 23 MB of images an MCP server never reads.
- **Overlaying `mcp-nixos` with mcp-nixarchy:** it would change the package
  for anything else that names `mcp-nixos`, and hides the swap behind a name.
- **Two PRs:** the owner chose one (intent answer 3).

## Risks

- **mcp-nixarchy may not build against our nixpkgs** (it pins its own
  `nixos-unstable`). It is checked by building it in the plan's first step.
  If it fails, stop and report rather than drop the `follows`.
- **The `_file` wrap changes every option's "declared in" text.** That is
  the intended effect, but anything that greps those strings would move.
  The plan's step greps `tests/` for `flake.nix` in expected output.
- **`self.rev` is absent on a dirty tree:** the URLs then say `main`, which
  is right for a dev build and never ships (the installer requires a
  committed tree, AGENTS.md §5).
- **The release step grows by one `nix build`** of a 1.4 s evaluation. It is
  negligible.

## Verification

1. **`checks.nixarchy-options` passes, and §1 shows it can fail:**
   - with the `_file` wrap removed, it names a store-path declaration;
   - with the `/etc` entry ungated, the Mode A row fails.
2. **`checks.options` passes with the `mcp-nixarchy` grep,** and fails with
   the `package` line removed (in CI; it is the 11.5 GB check, §6).
3. **`nix build .#nixarchy-options` succeeds,** and the reference toplevel
   evaluates.
4. **By hand, on an installed machine after merge:** in Claude Code, a query
   with `source=nixarchy` for `programs.nixarchy.owe.enable` answers from
   `installed (/etc/nixarchy/options.json)`.
5. **The release workflow** is checked by `actionlint` (with `-shellcheck=`
   and a timeout). The asset itself is seen at the next release, and the PR
   says so.
6. fmt, statix, deadnix.
