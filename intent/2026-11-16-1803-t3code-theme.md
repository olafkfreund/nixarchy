# Intent: T3 Code follows the Omarchy theme when nixarchy installs it

## Problem

On Arch, `omarchy-install-ai-t3-code` sets T3 Code up to follow the theme
in three steps:

1. it creates `~/.t3/userdata` (`$T3CODE_HOME/userdata`);
2. it publishes the palette with `omarchy-theme-set-t3code`;
3. it selects that palette with `t3 theme set omarchy --base-dir
   "$T3CODE_HOME"`.

With `programs.nixarchy.apps.t3-code.enable`, nixarchy installs nixpkgs'
`t3code` (`data/apps.nix:506`), which ships `t3` and `t3code-desktop`.
Enabling the app performs none of that initialisation:

- **No state directory.** `omarchy-theme-set-t3code` exits early while
  `$T3CODE_HOME/userdata` is missing, deliberately, so it creates nothing
  on machines that do not run T3 Code. Until that directory exists, theme
  switches publish nothing.
- **No selection.** Nothing selects the `omarchy` theme, so even with the
  palette published, T3 Code shows its built-in theme until the user picks
  `omarchy` by hand.

Whether a given machine is affected depends on its state: whether T3 Code
has been started and has created the directory, and whether the user has
already picked a theme. The spec measures what starting T3 Code creates.

The owner's own configuration works around it (olafkfreund/nixos_config#2973)
with a Home Manager activation entry after `nixarchySeed`:

- it creates the state directory;
- it runs `omarchy-theme-set-t3code`;
- it runs `t3 theme set omarchy` whenever the selected theme differs,
  bounded with `timeout -k`.

The CLI works headless inside `home-manager-<user>.service` (about 0.4 s).
The workaround's "whenever it differs" rule re-selects `omarchy` at every
activation, overriding any theme the user picks in T3 Code.

## Proposed outcome

These are two separate outcomes, with separate rules:

- **The palette is published and kept current.** With the app enabled,
  activation ensures the state directory exists and publishes the current
  palette. Later theme switches retint it through the existing theme hooks,
  as on Arch.
- **The palette is selected once.** On the first activation that finds no
  record of nixarchy having selected it, the `omarchy` theme is selected,
  and nixarchy records that it did, in a marker under
  `~/.local/state/nixarchy/`. After that it never selects again, so a theme
  the user picks later, including T3 Code's own default, stays.
  - A machine where the user already chose a theme before this change gets
    `omarchy` selected once. That is the one overwrite this design makes.
    The spec measures whether `t3` can tell an untouched configuration from
    a chosen one. If it can, the first selection also skips a configuration
    that already has a user choice.
- **Without the app:** nothing changes. No `~/.t3` and no marker are
  created, and nothing runs (Mode A).
- **Activation never blocks or fails on T3 Code.** Every step (creating the
  directory, publishing, querying, selecting, writing the marker) is
  non-fatal. A failure is reported on stderr and the step is skipped. Every
  call that can hang (`t3`) is bounded with `timeout -k`.
- **No wider theme work.** Activation does not run `omarchy-theme-refresh`
  or touch other applications. If the current theme has no `t3code.json`
  yet, publishing is skipped. The next theme switch, which the hooks
  already handle, publishes it.
- The downstream workaround can then be deleted from the owner's
  configuration. That is the owner's change, not part of this one.

## Affected users and systems

- Anyone with `programs.nixarchy.apps.t3-code.enable`, on both `main` and
  edge.
- **Files:** `modules/home.nix` (a new `home.activation` entry, gated on
  `appEnabled "t3-code"`, ordered after `nixarchySeed` so the current theme
  is seeded first), and a check under `tests/`.
- Standalone Home Manager (no `osConfig`): `appEnabled` reads false there,
  as for every app, so nothing runs.

## Constraints

- **Mode A:** off unless the app is enabled.
- **One T3 Code profile:** every step uses the same
  `${T3CODE_HOME:-$HOME/.t3}` the Omarchy scripts use, so creating the
  directory, publishing and selecting all address one profile. The spec
  says whether a user-set `T3CODE_HOME` reaches activation, and if not,
  names that limit.
- **Pinned:** `t3` comes from the same nixpkgs package the app installs,
  not from `PATH`.
- **§1:** the check covers the behaviour, not a guard's text:
  - a fresh profile gets the palette and the selection, and the marker;
  - a profile with the marker and a different theme keeps that theme, with
    no `theme set` call;
  - a second activation makes no `theme set` call;
  - each assertion fails when the activation entry is removed, and the
    "keeps a later choice" assertion fails when the marker test is removed.
- **Hermetic checks (§4):** the check runs `t3` (or a recording stub where
  the real CLI needs a display) against a temporary `T3CODE_HOME`, never a
  real home.

## Open questions

1. **The once-only rule.** The proposal above selects once, recorded by a
   marker, rather than "whenever it is still the default". A default value
   cannot show whether the user chose it. Is the single overwrite on
   machines that already chose a theme acceptable, if `t3` cannot tell the
   difference?
