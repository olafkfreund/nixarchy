# Intent: Removing a fingerprint removes the fingerprint

## Problem

*Remove > Security > Fingerprint* deletes nothing. The biometric data stays
where it was, and the route we print leaves it behind with no visible way to
remove it.

**What the shipped script does.** `pkgs/omarchy/default.nix:1461` splices
`pkgs/omarchy/1304-guidance-remove-fingerprint.sh` directly after `set -e`,
above upstream's first statement, and that file ends in `exit 1`. Upstream's
two deletions come after it, at `bin/omarchy-remove-security-fingerprint:72`
(`sudo fprintd-delete "$fingerprint_user"`) and `:84` (`sudo rm -rf --
"/var/lib/fprint/$fingerprint_user"`). `fprintd-delete` is the only route to a
reader's own storage, and for a connected reader it also removes that reader's
templates on disk (`src/device.c:2437`, `src/file_storage.c:239`). The `rm`
takes what is left: no reader attached, or templates from an earlier one.
Measured on a built `omarchy-4.5.0` whose guidance text matches this tree, with `sudo`,
`rm`, `fprintd-delete`, `omarchy-cmd-present`, `omarchy-pkg-drop` and
`omarchy-lifecycle-dispatch` stubbed to a log: exit 1, zero stub calls.

This was deliberate. #1304's decision 7
(`plan/2026-10-17-1304-menu-arch-only-actions.md:103`) stopped the script
reaching `rm /etc/pam.d/omarchy-lock-fingerprint` and `omarchy-pkg-drop`, both
wrong on NixOS. The two deletions were not among its reasons. They went with
the rest because they sit below the same line. #1398 then fixed the splice
above the account lookup (`default.nix:1460`), because
`/run/current-system/sw/bin/id` does not exist in the build sandbox. A deletion
needs that lookup, so the fix has to run it and `checks.menu-guidance` has to
reach it.

**Following our message makes it worse.** It says to turn off
`services.fprintd` and Apply. After that:

- `fprintd-delete` is gone: only the module's `environment.systemPackages`
  provides it, not Omarchy's runtime list. fprintd is the only thing that can
  reach a match-on-chip reader. Upstream's comment says why it deletes first: "while
  it still runs". The reader's copy is now out of reach unless fprintd is
  turned back on.
- `/var/lib/fprint/<user>/<driver>/<device>/<finger>` remains (layout from
  fprintd's `src/file_storage.c`). The unit creates it through
  `StateDirectory=fprint`, and systemd does not delete a state directory when a
  unit goes away. The NixOS module declares nothing else about it.
- The row disappears, because its `when` is `command -v fprintd-enroll`
  (`modules/apps.nix:909`). Widening that to look for leftovers does not work:
  `StateDirectoryMode=0700` means an unprivileged test cannot see them.

**The privacy expectation.** Someone pressing Remove on a fingerprint expects
the fingerprint to be gone. That is upstream's promise too: "Fingerprint
authentication and $user's local saved fingerprints have been removed." Our
message is honest that nothing changed, but it does not say prints remain, and
the instruction it gives reads as the complete way to remove them. A template
cannot be rotated like a password, and it is stored unencrypted unless the disk
is.

**Two other copies, which matter to what we may claim.**

- *Boot snapshots.* Installer-managed machines snapshot `/` at every boot
  (`installer/host.nix:356-362`), and `/var/lib` is a plain directory in `@`.
  Each snapshot taken after enrolment holds the templates, so deleting the live
  directory does not delete them until that snapshot goes. That holds however
  long they are kept. How long is not measured: they use the `number` cleanup
  algorithm (nixpkgs `snapper.nix:329`), and a cleanup timer exists, but
  `NUMBER_CLEANUP` defaults to "no" (`snapper-configs(5)`) and neither nixarchy
  nor the module sets it, so they appear to be kept indefinitely. If that holds
  on a machine, it is also a disk problem in its own right, outside this task.
- *Factory reset.* Upstream's `rm` is in `omarchy-system-factory-reset-finish:89`
  (omacom/omarchy#13049). It is only on the degraded path, never touches the
  reader, and the whole script is inert here. Ours
  (`pkgs/omarchy/nix-bin/omarchy-system-factory-reset`, `installer/host.nix:408`)
  never names fingerprints: the templates move to
  `/var/lib.before-reset-<date>/fprint`, and the reader is not touched. Its
  warning does say this is "not a wipe", and that covers the disk. It does not
  cover the reader, whose storage a disk wipe from the ISO cannot reach either.
  It was read only, never run.

**Why nothing noticed.** `checks.menu-guidance` asserts "Nothing on this machine
was changed", so it passes because of this bug. `checks.menu-actions` classifies
the row as guidance and, by its own documentation, cannot see an `rm "$VAR"`.

## Proposed outcome

Pressing Remove, with fprintd still on:

1. deletes the invoking user's prints from the reader, then their templates in
   `/var/lib/fprint/<user>`, in that order;
2. still reaches no NixOS-managed file and drops no package;
3. says what it deleted, what it could not reach (no reader, a failed delete),
   and what remains, including any boot snapshots, and then gives the
   `services.fprintd` route for the login side;
4. says so plainly when pressed again with nothing enrolled, since the row stays
   until fprintd is off.

A person who already turned fprintd off has a documented way to clean up. No
message claims more was removed than was.

## Affected users and systems

- Anyone with fprintd on who has enrolled, on stable and on edge, which carries
  the same guidance file. Mode A included: the row is there, and pressing it is
  the request.
- Machines that already followed the old message: templates and possibly reader
  prints remain, with no row.
- Files that describe today's behaviour: `checks.menu-guidance`'s marker, the
  `guidance:` reason in `data/menu-actions.nix:30`, `data/bin-ledger.nix:518`,
  `docs/manual/security.md`, and the factory-reset warning if decision 3 says so.

## Constraints

- Only the invoking user's prints. Other accounts' prints stay.
- Must not reach `rm /etc/pam.d/omarchy-lock-fingerprint`, `omarchy-pkg-drop` or
  anything else decision 7 closed. Removing the early exit outright would reach
  them, so that is not the fix. `omarchy-lifecycle-dispatch disable-fingerprint`
  has no reason to run either: its ledger row says only aarch64-apple registers
  an operation.
- Must not lock anyone out. With fprintd left on, `pam_fprintd` answers
  `PAM_AUTHINFO_UNAVAIL` for `NoEnrolledPrints` (`pam_fprintd.c:376`), other
  errors differ, and `omarchy-lock-fingerprint` has `unixAuth = false`, so that
  stack has no password fallback. The password lives on the separate
  `omarchy-lock-password` stack, and the shell gates the fingerprint method on
  `fprintd-list` (`modules/nixos.nix:1803-1816`). This is read from code and
  comments only, so the spec has to prove it on the real stacks.
- The exit status is for the spec to settle: login is still declared after a
  successful delete, so neither 0 nor 1 is obviously right.
- A deletion that fails is reported, not swallowed. `fprintd-delete` exits 1
  with "No devices available" when there is no reader (`utils/delete.c:153`),
  and that case must stay distinct from a real failure.
- Tests read no real fingerprint data, and no run here touches a real reader.
- Check-writing rules: AGENTS.md §1 (the check must be seen to fail, with the
  deletions removed) and §3 (vary the reader state).

### What can prove this

No machine in this repository has a reader, and `pkgs/verify.sh` has no
fingerprint section. So, honestly:

| layer | can see | cannot see |
|---|---|---|
| Stubbed `runCommand` against the built script | which commands run, their order and arguments; the named cases: no reader, a failed delete, no `fprintd-delete`, sudo refused; forbidden writers not reached | whether anything is erased. A stubbed `rm` proves the argument, and `/var/lib/fprint` and `/run/current-system/sw/bin/id` are absolute paths the sandbox lacks, so a fixture directory going and another user's staying needs the path rewritten, as upstream's own test does with `sed`. That tests a rewritten copy, and the check must say so. Also real D-Bus and polkit |
| Evaluation | the configured PAM stacks with fprintd on and off; the snapper config | runtime behaviour, including whether a password fallback really fires |
| VM with real fprintd and libfprint's virtual reader | a real delete of a real `/var/lib/fprint` over D-Bus, if it works. The nixpkgs libfprint is built with its virtual drivers for fprintd's tests (`package.nix:70`), and the library contains `FP_VIRTUAL_DEVICE_STORAGE` | a physical chip honouring the delete. **Unproven that this runs in a NixOS test, or that its storage mode covers on-device delete**: the spec must try it or say why not |
| Hardware, by hand | a real match-on-chip reader | nothing, but only a person can run it. Needs a sentence in `tests/AGENTS.md` naming the hole |

A green stub proves we asked for the deletion, not that the reader obeyed. The
PR must say that.

## Open questions

The owner approved every recommendation below on 2026-11-05.

1. **Does pressing the row delete, or only print the commands?** Recommended:
   delete. It is the row's name and upstream's behaviour, and the reader can
   only be cleared while fprintd runs. The cost is reversing a #1304 outcome
   ("Nothing on this machine was changed"), and the user must re-enrol if they
   change their mind.
2. **Boot snapshots: report or remove?** Recommended: report, naming them in the
   message and the manual. Editing read-only snapshots or deleting whole ones
   destroys unrelated rollback state as a side effect of a fingerprint row.
3. **Factory reset: in scope?** Recommended: its warning gains a sentence saying
   the retained `/var/lib` includes any fingerprint templates, the reader keeps
   its prints, and Remove clears both first, with no change to the reset itself.
   It already declares it is not a wipe, and it is a whole-machine action where
   the row is per-user. The alternative is real: the command runs in the live
   session, where fprintd still works, so it could offer the delete itself.
4. **Machines already switched off: what is enough?** Recommended: the manual and
   the release notes give `sudo rm -rf -- /var/lib/fprint/<user>` with the account
   written out, not `$USER`, which is wrong in a root shell, and say the reader
   needs fprintd on, once, to be cleared. A row cannot detect them.
