# Intent: the config writers take apply's lock and keep the files they edit

## Problem

nixarchy-pkg#59 (merged as nixarchy-pkg#65) made the package panel's adapter
take `nixarchy-apply`'s lock, `${XDG_STATE_HOME:-$HOME/.local/state}/nixarchy/applied/lock`,
for every write. The adapter also exports `NIXARCHY_LOCK_HELD=1` and closes
fd 9 for the writers it runs. That covers writes the panel makes. The same
writers also run directly, from a terminal, a menu row or another writer, and
there they take no lock. Only `nixarchy-apply` takes the lock today.

Twelve commands write the user's configuration files and have this problem:

- **The nine #1789 names:** `nixarchy-app-enable`, `-app-disable`,
  `-service-enable`, `-service-disable`, `-pkg-add`, `-pkg-remove`, `-pkg-new`,
  `-pkg-undraft` and `-opt-remove`.
- **Three found in review:**
  - `nixarchy-catalogue-diff --add`/`--add-one`, which `service-enable` calls;
  - `nixarchy-search`, which inserts `#@opt` rows and restores a backup on
    failure;
  - `nixarchy-language-select`.

All are in `modules/apps.nix`, except that `pkg-new`'s body is
`pkgs/pkg-new.sh`. Between them they edit `apps.nix`, `services.nix`,
`advanced.nix` and pkg-new's draft packages. None of the twelve edits
`flake.nix`.

Three things go wrong today:

- **Races.** Run directly, a writer can change one of those files while
  `nixarchy-apply` is copying and staging it, or while the panel or another
  writer is changing it. `nixarchy-search`'s backup restore can then overwrite
  another writer's successful change.
- **Replaced files.** Each of the twelve replaces the file it edits rather
  than writing into it, through `mv "$tmp" "$file"` or `sed -i`. A symlinked
  `apps.nix` (a dotfiles checkout) becomes a regular file, and on the paths
  that do not copy the mode back, mode and owner become the temp file's.
  nixarchy-pkg fixed this in its own writers (nixarchy-pkg#39).
- **Wrong message.** When `nixarchy-apply` finds the lock held, both of its
  messages say "another apply is running", the `--yes` refusal and the
  interactive "waiting". Now that a writer can hold the lock, that names the
  wrong cause.

## Proposed outcome

- **One exclusion.** Run directly, each of the twelve takes `applied/lock`
  for its edit, waits a bounded time, and refuses with a message naming the
  cause if it cannot get it.
  - **Nested and panel calls:** a writer that holds the lock passes it to the
    writers it runs (`NIXARCHY_LOCK_HELD=1`, fd 9 closed). A writer started
    with `NIXARCHY_LOCK_HELD=1` does not take the lock again, matching what
    nixarchy-pkg already does.
  - **No stray holders:** nothing it leaves running, such as a notification
    waiter or an `exec`'d picker, keeps the lock past the edit.
  - **Short hold:** the lock covers reading, editing and writing the file. It
    does not cover pickers (`fzf`, `gum`), `[Y/n]` prompts, network fetches or
    Nix evaluations and builds. A writer that asked something first re-reads
    the file under the lock, so it edits what is there now.
  - **Fail closed:** if the lock cannot be set up (the directory cannot be
    created, or the file cannot be opened), the writer refuses and changes
    nothing. It never writes unlocked.
- **The file is kept.** After any write, the target keeps its inode: a
  symlink stays a symlink to the same file, and mode and owner are unchanged.
  - **A whole file or none:** a write to one file either completes, or leaves
    that file's previous content, including when interrupted (Ctrl-C) or when
    the disk is full.
  - **Partial batches stay partial:** `pkg-add` keeps the names that
    succeeded when others fail. That is not a failure of the file.
  - **Unwritable targets:** a symlink into a read-only location (a Home
    Manager link into `/nix/store`) is refused with a message. It is not
    replaced.
- **The message.** Both `nixarchy-apply` messages say that a write or
  another apply holds the lock.

## Affected users and systems

- Everyone who runs these commands directly (the manual documents them),
  everyone who uses the menu rows that run them, and everyone who uses the
  package panel, whose guarantee this completes.
- **Files:** `modules/apps.nix` (eleven writers and `nixarchy-apply`),
  `pkgs/pkg-new.sh`, and the checks that run these writers.
- **Not covered:** `nixarchy-channel`, `-unfreeze` and `-flatsnap` edit
  `flake.nix` and `flatsnap.nix`, and are not defined in this repository.
  They are named here as the remaining hole, not fixed.
- No host deploy is needed to verify it: the checks run the scripts.

## Constraints

- **nixarchy-pkg#65's contract:** the same lock path and `NIXARCHY_LOCK_HELD`
  handshake, and a bounded wait (5 s there), never an unbounded one.
  `nixarchy-apply` holds the lock through prompts and a whole build.
- **A fresh machine works:** a writer must work when `applied/` does not
  exist yet.
- **Mode A is unaffected:** nothing here runs unless the user runs a writer.
- **Checks are hermetic (§4, #802):** they point `XDG_STATE_HOME` at a
  temporary directory, never the caller's real state.
- **Every check proves it fails (§1):**
  - a writer with its lock removed turns a check red;
  - so does one that still replaces the inode;
  - so does one whose interrupted write loses content.
- **`flock` comes from a declared input:** `util-linux` goes in each
  writer's `runtimeInputs` (§7).

## Open questions

1. **Wait length.** Proposal: 5 s, the same as the adapter. A writer run by
   hand during an apply refuses and says to retry when the apply finishes.
2. **Should `nixarchy-apply` honour `NIXARCHY_LOCK_HELD`?** Proposal: no.
   Nothing runs apply under the lock: `nixarchy-default-install` lets
   `app-enable` exit before it `exec`s apply, and the panel refuses "apply in
   terminal" while busy.
3. **Menu rows.** `app-disable`, `service-enable` and `service-disable` run
   from menu rows with no terminal, and only `app-enable` notifies the
   desktop when it fails. A lock refusal there would be silent. Proposal:
   all four notify on a refusal, as `app-enable` already does on failure.
