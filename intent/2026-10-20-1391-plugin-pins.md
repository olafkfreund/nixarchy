# Intent: the five held-back plugins are current, and Hyprland Settings' new id reaches users without breaking their bar

## Problem

#1381 (PR #1390) pinned five plugins to **their previous commit plus only
the Qt 6.12 fix**, cherry-picked onto `nixarchy/qt612-on-pin` branches,
because their default branches carry work that was out of that scope:

| plugin | commits ahead | what is in them |
|---|---|---|
| nixarchy-hyprsettngs | 91 | a deliberate **plugin-id rename**, `aziz.hyprforge` → `nixarchy.hyprlandsettings` (its plan `2026-09-29-rename-plugin-id`), plus shell-restart safety and docs |
| nixi-nixarchy | 26 | unreleased nixi work |
| nixarchy-voice | 13 | unreleased voice work |
| nixarchy-distrobox | 10 | unreleased distrobox work |
| nixarchy-microvm | 2 | unreleased microvm work |

Two consequences:

- **Users run plugins that are behind their source,** on pins that exist
  only on side branches. A side branch can be deleted, and with it the
  commit a pin needs. #1391 asks that the branches stay until this lands.
- **The hyprsettngs id rename cannot be a plain bump.** nixarchy names the
  plugin `aziz.hyprforge` in 48 places: `modules/home.nix:2084`'s
  default-plugin entry, `tests/options.nix`'s assertions, and the demo.
  The build guard already refuses the new manifest ("Menu rows and key
  binds name it 'aziz.hyprforge'"). More important, the id is **user
  state**: each user's `~/.config/omarchy/shell.json` names it in the
  enabled-plugin list and in bar layouts. A user whose config still says
  `aziz.hyprforge` after the switch would lose the panel from their bar.
  hyprsettngs' plan describes a manual migration (disable the old id,
  enable the new one); nixarchy users should not have to run it by hand.

## Proposed outcome

- **All five pins are on their repositories' default branches**,
  verified like any bump: `checks.qml-color-qualified`, `checks.session`
  and the panels' own checks. The five `nixarchy/qt612-on-pin` branches
  are then deleted.
- **Hyprland Settings carries its new id everywhere nixarchy names it.**
- **An existing user's `shell.json` moves from `aziz.hyprforge` to
  `nixarchy.hyprlandsettings` automatically, once,** keeping its bar
  position and settings. A user who never had it is untouched. This
  follows the shape of upstream Omarchy's own Omapager retirement
  migration, which rewrites `shell.json` with `jq`.
- The four plain bumps do not wait on the rename. They can land first.

## Affected users and systems

- Everyone with these default plugins: hyprsettngs (Hyprland Settings),
  nixi, voice, distrobox and microvm.
- `flake.nix` and `flake.lock` (five pins), `modules/home.nix` (the
  default-plugin id, plus a one-time `shell.json` migration in the home
  activation or the existing post-boot default-plugins hook),
  `tests/options.nix`, the demo shots, and docs naming the old id.

## Constraints

- **User state is migrated, never lost.** The `shell.json` edit backs
  the file up, is idempotent, is atomic (temp file plus rename), and
  touches only the plugin's own entries. A malformed `shell.json` is
  left alone, with a message. The same care as `home-activation-writes`'
  existing guarantees.
- **Mode A (§7):** a user who imports nixarchy but disabled the default
  plugins, or never had hyprsettngs enabled, sees no change.
- **§1:** the migration is proved red/green with fixtures: a `shell.json`
  with the old id in the plugin list and in a bar layout, one without it,
  and a malformed one. Each bump is proved by the existing checks on its
  new pin.
- The other four repos' 51 commits are reviewed by their changelogs. Any
  behaviour change a user would notice is named in the PR.

## Open questions

- **One PR or two?** I propose two: the four plain bumps first (fast,
  low risk), then hyprsettngs with its id migration.
- **Where does the migration live?** I propose nixarchy's existing
  post-boot default-plugins hook (`modules/home.nix`, the
  `omarchy/hooks/post-boot.d/default-plugins` file), because it already
  edits plugin enablement in `shell.json` at the right moment, rather
  than a new activation script.
