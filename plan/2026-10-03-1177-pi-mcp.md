# Plan: pi gets the MCP servers the other three agents already get

## The approved decisions, in full

Implementable without opening the intent or the spec.

**What changed in the world.** `pi-coding-agent` 0.99.2 documents
`~/.pi/agent/mcp.json` (`pi mcp --help`: *"Reads `~/.pi/agent/mcp.json` and, in
trusted projects, `.pi/mcp.json`"*). `pi mcp add ai-mirror -- ai-mirror mcp`
writes `{"mcpServers":{"ai-mirror":{"command":…,"args":["mcp"]}}}`. What
`mcp-servers-nix` produces for `flavor = "claude-code"` carries the same server
entry — same nesting, same `command` and `args` — plus `"env": {}` and
`"headers": {}`, which pi does not write. Not byte-identical, and the earlier
wording overstated it. What was actually checked is behaviour: `pi mcp list`
against the generated file reports the server connected with its tools. So:
**no new flavor, no new helper.** `mergeJson` carries pi unchanged.

**pi's writers are gated; pi's removal is not.** The three existing agents are
ungated, but `mcp` defaults **true** and `mergeJson` creates the file it merges
into, so an ungated pi writer would land `~/.pi/agent/mcp.json` on every
nixarchy machine, almost none of which have pi. Removal stays ungated so that
dropping pi from `localAi.agents` cannot strand an ai-mirror entry nixarchy
wrote with no switch left to remove it.

**Do not gate the other three in this change**, and do not touch `~/.agents`:
it still has no documented MCP file and its exclusion must stay documented.

## Steps

1. **`modules/home.nix` (~line 55, beside `mcpEnabled` / `aiMirrorMcp`): add
   `piOn`.**
   ```nix
   # pi is installed only through programs.nixarchy.localAi.agents -- it has no
   # apps catalogue entry -- so that is the only predicate for "this machine has
   # pi". The two pi writers below already compute it inline.
   piOn = localAi.enable && builtins.elem "pi" localAi.agents;
   ```
   Then replace the inline copies at `nixarchyPiProvider` (`:1795`) and
   `nixarchyPiSettings` (`:1832`) with `piOn` — same expression, one name.
   → verify by `nix flake check`
   Traps: `localAi` is defined at `:29-36` with `enable = false; agents = [ ]`
   as the no-`osConfig` fallback, so `piOn` is `false` for a standalone Home
   Manager user. Keep that; do not reach into `osConfig` directly.

2. **`modules/home.nix` (#623 block, after `nixarchyMcpCodex` at `:1469`): the

     what = "the NixOS MCP server";

   existing pi writers use (`:1798`), not `config.home.homeDirectory` — both

   `"claude-code"`, NOT a new `"pi"`.

## Tests

```sh
nix flake check          # options, writers, dry-run, remover fixtures
```

Expected: green. The remover's existing three-argument calls must still pass,
which is what proves `${4:-}` did not break its callers.

On a machine with pi (`localAi.enable = true`, `"pi"` in `localAi.agents`),
after a rebuild:

```sh
pi mcp list              # reports the servers, rather than erroring
jq . ~/.pi/agent/mcp.json
```

`pi mcp list` is the check that matters: everything else proves the file is
well-formed, only this proves it is acceptable to the tool that reads it.

On a machine without pi: `~/.pi/agent/mcp.json` does not exist, and neither
activation appears in `home-manager build` output.

## Rollback

Each step is a commit on `feat/1177-pi-mcp`; the branch reverts whole. Nothing
here changes an existing file's contents for the three current agents, so a
revert returns pi to having no MCP config and leaves the others untouched.

A user who wants it gone without a revert deletes the `ai-mirror` entry from
`~/.pi/agent/mcp.json`, or sets `programs.nixarchy.mcp = false`; the file itself
is theirs and is never replaced, only merged into.
