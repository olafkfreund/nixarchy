# Intent: pi gets the MCP servers the other three agents already get

## Problem

nixarchy writes MCP server configuration into the agents it installs, so that
the NixOS server (#623) and — when the switch is on — ai-mirror (#773) are
reachable without anyone hand-editing a config file. It does this for three
agents and deliberately not for a fourth, and `modules/home.nix` says why:

> Three agents, not the four this module seeds skills into. `~/.agents` and
> `~/.pi/agent` have no documented MCP configuration file, and a path invented
> for them would be a feature that writes a file nothing reads — the shape §2
> of AGENTS.md is about. Named here so the gap is a decision rather than an
> oversight; close it the day either tool documents one.

That reasoning was right and is now out of date for pi.

`pi-coding-agent` 0.99.2 ships `pi mcp add|remove|list|login|logout`, and its
own `--help` states: *"Reads `~/.pi/agent/mcp.json` and, in trusted projects,
`.pi/mcp.json`."* Run in a throwaway `HOME`, `pi mcp add ai-mirror -- ai-mirror
mcp` writes:

```json
{ "mcpServers": { "ai-mirror": { "command": "ai-mirror", "args": ["mcp"] } } }
```

which is byte-for-byte the shape `mcp-servers-nix` already produces for
`flavor = "claude-code"` — both were generated and compared, not assumed.

So the condition the comment set for closing the gap is met, and the cost of
closing it is small: `mergeJson` already merges a JSON file with an
`mcpServers` object, and the remover's Claude jq path
(`.mcpServers["ai-mirror"]`) applies to pi's file unchanged.

Left as it is, a machine that installs pi has an agent that can reach neither
the NixOS server nor — where the user asked for it — ai-mirror, while the other
three can. The user is given no sign that pi is the odd one out.

## Proposed outcome

On a machine where pi is installed:

1. pi reaches the NixOS MCP server on the same terms as Claude, codex and
   opencode.
2. With `programs.nixarchy.aiMirror.mcp` on, pi reaches ai-mirror too; with it
   off, pi's entry is taken back out, exactly as the other three are. Turning
   the switch off must not leave pi still able to drive the desktop.
3. A user who wrote their own `~/.pi/agent/mcp.json`, or their own `ai-mirror`
   entry inside it, keeps it. Nothing of theirs is replaced or removed.
4. `~/.agents` stays excluded, and the comment still says why — for that one.

Observable: on a machine with pi, `pi mcp list` shows the servers; with the
ai-mirror switch off, it does not show ai-mirror.

## Affected users and systems

- **`modules/home.nix`** — the two groups of MCP activations, and the comment
  that records the exclusion.
- **`pkgs/ai-mirror-mcp-remove.nix`** and its caller — a fourth file to clean.
- **The tests that pin the three-agent set**: the activation-name assertions in
  `tests/options.nix`, `tests/ai-mirror-mcp-remove.nix` and its fixtures,
  `tests/home-writers-dry-run.nix`, `tests/home-manager-writers.nix`.
- **Docs that say "three agents"** or enumerate which agents get MCP config.
- **Every machine that installs pi**, on the next rebuild: a file appears in
  `~/.pi/agent/` that was not there before.

## Constraints

- **Add, never replace.** The existing helpers merge or append and refuse a
  symlinked file; pi's path must go through the same ones rather than a new
  writer with its own rules.
- **Reversible.** The off state is the removal, not the absence of a write. An
  entry is removed only when its command is a nixarchy store path; a
  hand-written one is the user's.
- **No file for a tool that is not installed.** The editor blocks nearby are
  gated on `appEnabled` for a stated reason: an orphan config file is
  indistinguishable, to whoever finds it, from one they wrote themselves. If
  the three existing agents are not gated this way, that inconsistency should be
  named rather than quietly copied.
- **No new flavor, no new helper** unless the spec shows the existing ones
  genuinely cannot carry pi.
- **`~/.agents` is untouched** and its exclusion stays documented.
- **No new runtime dependency.**

## Open questions

1. **Gate on pi being installed?** Recommend yes, on the same predicate the
   editor blocks use, for the orphan-file reason above. This needs checking
   against what the three existing agents actually do — if they write
   unconditionally, the spec should say whether that is deliberate.

2. **One issue or two?** The NixOS server (#623) and ai-mirror (#773) are
   separate features with separate switches that happen to share a gap.
   Recommend one change for both: the same four files, the same helpers, and
   splitting them would mean touching the same lines twice.

3. **Does anything else read `~/.pi/agent/mcp.json`?** pi also reads a
   project-level `.pi/mcp.json` in trusted projects. Nothing here writes one,
   and nothing should — but it is the same shape as the `<cwd>/.codex` layer
   that #74 is about, and worth a sentence in the spec so the next person does
   not reach for it.

4. **Should pi's exclusion from nixi follow?** No. pi is not an ACP agent — its
   modes are `text`, `json`, `rpc`, with no `agent-client-protocol` in the
   package — so it cannot be a nixi harness, and this change does not make it
   one. Recommend stating that in the spec so the two axes are not conflated.
