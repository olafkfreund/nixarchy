# Spec: a hung test guest says what it is waiting for

## Design

The approved intent settles three things:

- SysRq is enabled through the test instrumentation only.
- It is enabled by a kernel parameter.
- The detector sends `w`, then sends `t` when `w` showed no blocked task.

This spec says where each piece goes.

### 1. The kernel parameter, in the instrumentation text

`tests/lib/installed-target.nix:106-112`, `etcInstrumentation`, gains an
inline module in its `imports`:

```nix
imports = [
  "''${modulesPath}/testing/test-instrumentation.nix"
  { boot.kernelParams = [ "sysrq_always_enabled" ]; }
];
```

It goes in `imports`, not as a body line. `install-encrypted`'s
`extraInstrumentationText` is spliced into that same attribute set and already
sets `boot.kernelParams = [ "console=ttyS0,115200" ]`
(`tests/lib/installed-target-cases.nix:48-51`). A second
`boot.kernelParams` line there would be a duplicate attribute and fail to
evaluate. As separate modules, the two lists merge (agy review).

Why the parameter works, and why its output reaches the console:

- The kernel's `sysrq_on_mask()` returns true when `sysrq_always_enabled` is
  set, whatever `kernel.sysrq` holds. So the shipped `kernel.sysrq`, which
  `systemd-sysctl` applies later, cannot turn it off.
- Nothing nixarchy ships changes.
- nixpkgs' `test-instrumentation.nix:252` already sets
  `boot.consoleLogLevel = 7`. The task lines are `pr_info`, and the SysRq
  handler restores the log level before it runs the operation, so this
  setting is what lets them reach `ttyS0`.

Every caller of `etcInstrumentation` gets the parameter: `install`,
`free-space`, `install-encrypted` and `install-seed-shape`.

The seed reads the same `etcInstrumentation` binding, so the seed and the
installed target agree by construction:

- `checks.install`'s rebuild, which must build nothing, is the run-time
  proof.
- `checks.install-seed-shape` compares only `system.path`, so it cannot see a
  kernel parameter. It catches only an evaluation error in the text (Codex
  and agy reviews).

### 2. The check's own node

`tests/boot-hang-detect.nix`: `nodes.healthy` gets
`boot.kernelParams = [ "sysrq_always_enabled" ]`, because it never goes
through `etcInstrumentation`.

`nodes.frozen` does not get it. Its vCPUs are stopped, so it never runs the
key handler, and a setting on it could never fail a check (agy review).

### 3. The pokes (`tests/vm-cleanup.py`)

**The sequence** is `nmi`, then `sendkey alt-sysrq-w`, then
`sendkey alt-sysrq-t`. `t` is skipped only when `w`'s new console lines
contain `state:D`. A `w` that printed nothing still gets `t`, so a guest that
answers neither key has that silence recorded twice.

**Waiting.**

- `nmi` and `w` keep the fixed `watch`.
- `t` waits until the console has been quiet for `quiet` seconds (default 3),
  counted from the send or from the last new line. The wait is capped at
  `task_max` seconds (default 90).
- The wait polls with `abandoned.wait(0.2)`, so an abandoned diagnosis stops
  at once.
- `t`'s header reads
  `poke sendkey alt-sysrq-t: N console lines within S s (quiet Q s)`.
- `quiet` and `task_max` are keyword parameters of `_poke` and `_diagnose`,
  and `wait_for_multi_user` passes them through. That lets the stub check use
  `quiet=0.1`.

**Output cap.**

- `new[:20]` (`:109`) becomes `POKE_MAX_LINES = 3000` per poke.
- A cut ends the entry with `\n  (N more console lines not shown)`, so a cut
  is never silent.
- The serial log in the job log is complete either way.

**Time budget.** `_diagnose`'s budget (`:159`) becomes:

- `30` when `poke_watch is None`, as now. The non-`BootHang` path at `:87`
  passes no pokes (agy review).
- `30 + 2 * poke_watch + task_max + 5` otherwise.

### 4. The assertions

**`tests/boot-hang-detect.nix`.** Case C indexes `_poke`'s returned list
instead of partitioning one joined string (Codex and agy reviews):

- `entries[0]` holds the NMI line, as now.
- `entries[1]` holds `Show Blocked State`, which the kernel prints only when
  the operation is enabled. It replaces the `This sysrq operation is
  disabled` assertion.
- Unless `entries[1]` contains `state:D`, `entries[2]` is the `t` entry and
  holds at least one `task:` line.

**Case A.**

- Case A adds `poke sendkey alt-sysrq-t:` to its expected headers.
- It passes `task_max=10`.
- Its stopped guest prints nothing, so `t` ends after `quiet` (3 s), not at
  the cap. Case A grows by about 3 s, against its 60 s limit.
- A monitor that stalls can now take up to `30 + 4 + 10 + 5 = 49` s, against
  34 s today. Case A already fails in that event, on its register and reply
  assertions (`IP=`, `dumping local APIC state`), so the wider budget makes no
  failing case pass (Codex review).

**`tests/boot-diagnostics.py`** (stub machines, `quiet=0.1`):

- Pass 4's order becomes `nmi`, then `w`, then `t`.
- A stub whose `w` produces a `state:D` line asserts that `t` is not sent.
- A stub producing 3,500 lines after one poke asserts the cap and
  `(500 more console lines not shown)`.
- An abandoned event set during `t`'s wait returns within a second.

**`tests/install.nix`.** Beside the target checks at `:649`, add
`target.succeed("grep -qw sysrq_always_enabled /proc/cmdline")`. `grep -q`
reads a file here, not a pipe.

### 5. Documentation

`tests/AGENTS.md` changes in every place that describes the old pokes:

- `:734-735`: three pokes, and `t`'s quiet wait.
- "Reading the pokes", `:764-774`:
  - `Show Blocked State` replaces the disabled line;
  - how to read `w` (each `state:D` stack names its wait);
  - how to read `t` (look for the task whose wait never ends).
- `:790`: SysRq is now enabled in the test instrumentation only.
- `:802-805` and `:813-814`: case C's new assertions and the new stub cases.

## Alternatives rejected

- **`kernel.sysrq = 1` as a sysctl in the instrumentation.**
  `systemd-sysctl` applies it, and is not guaranteed to run before the hang's
  5 s mark. It also merges by priority with whatever else sets
  `kernel.sysrq`. The parameter has neither problem.
- **Enabling SysRq in nixarchy's default configuration.** Rejected in the
  intent: it is a security-relevant default.
- **`l` (backtraces of all CPUs).** It shows only the idle loop the
  registers already show.
- **Always sending `t`.** It costs up to 90 s on every hang, and a `D`-state
  stack already names the wait.
- **No line cap.** The exception message would be unbounded. The serial log
  keeps every line anyway.
- **A body line in `etcInstrumentation`.** It is a duplicate attribute
  wherever `extraInstrumentationText` also sets `boot.kernelParams` (§1).

## Risks

- **The install closure changes** (one kernel parameter), so the first run
  rebuilds the target's toplevel. Parity holds by construction, and
  `install`'s rebuild-builds-nothing step checks it.
- **`boot-hang-detect` gets slower**, by tens of seconds at most, because of
  the healthy guest's `t` dump in case C.
- **A hung guest whose key is lost still reads as silence.** That is as weak
  as the evidence today, and it is now recorded for both keys.
- **`sysrq_always_enabled` allows every SysRq operation** on these test
  guests. Only the detector sends keys, and it sends `w` and `t`, which only
  read.

## Verification

| check | tier | expect |
|---|---|---|
| `boot-diagnostics` | cheap | order `nmi`/`w`/`t`; `t` skipped on `state:D`; cap line; prompt stop when abandoned |
| `install-seed-shape` | cheap | evaluates, including install-encrypted's case |
| `boot-hang-detect` | VM | case A has the `t` header; case C has `Show Blocked State`, and `task:` in `entries[2]` |
| `install`, `free-space` | VM | pass; the target's `/proc/cmdline` holds `sysrq_always_enabled` |

§1 breaks, each shown failing:

1. Drop `healthy`'s parameter → case C fails on `Show Blocked State`.
2. Drop the `t` poke → case A fails on its header.
3. Skip the `state:D` test → the `boot-diagnostics` skip case fails.
4. Restore `[:20]` → the cap case fails.
5. Drop the inline module from `etcInstrumentation` → `install` fails on
   `/proc/cmdline`.
6. Put the parameter back as a body line → `install-seed-shape` fails to
   evaluate install-encrypted's case.

Not provable before a real hang: that a halted, hung guest answers the key.
The next CI hang is that proof, as the intent says.

## Spec review (Codex gpt-6-sol, agy model not reported)

Each finding below was checked against the files, and each confirmed one is
fixed above:

- The duplicate `boot.kernelParams` in install-encrypted's text (agy).
- `install-seed-shape` compares `system.path` only (both).
- The budget with `poke_watch=None` (agy).
- `frozen` cannot use the parameter (agy).
- Case C's single partition (both).
- The stalled-monitor budget for case A (Codex): the budget is widened, and
  that case already fails case A, as described in §4.
- `t`'s header, the quiet wait in stubs, `abandoned` polling, and the cut
  line's format (agy).
- Three more stale `tests/AGENTS.md` passages (agy).
