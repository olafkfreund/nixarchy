# Spec: Ask-topic aliases, and a Nixi row that cannot double up

## The open question, answered

The intent asked whether a generated Nixi row would collide with the "Help" row
Nixi's installer writes into the user's extensions file. Read off a live host
rather than inferred:

```
~/.config/omarchy/extensions/omarchy-menu.jsonc:40
  "help": {"icon":"󰙴","label":"Help","description":"Ask anything about nixarchy",
           "action":"nixi","aliases":["how","nixi","ayuda"]}
```

The id is **`help`**, a top-level key. And the generated file's own header states
the merge rule:

> Your own file, `~/.config/omarchy/extensions/omarchy-menu.jsonc`, is untouched
> by nixarchy and **overrides anything here by id**, which is exactly what
> upstream designed it for.

So the user file wins, **by id**. That decides the design.

## Design

### 1. The Nixi row takes the id `help`

Not `setup.nixi`, not `trigger.nixi`. Using `help` is what makes the two rows
mutually exclusive by construction rather than by timing:

| machine | today | with this change |
|---|---|---|
| ran Nixi's installer | one unguarded `help` row (theirs) | **one** row, still theirs -- no regression, no duplicate |
| never ran it | no row at all | **one** row, ours, guarded |
| after nixi-nixarchy stops writing theirs | -- | ours everywhere, guarded |

Any other id produces **two** rows on a machine that ran the installer, both
labelled at the same thing and both running `nixi`, which the intent named as
worse than the status quo. Choosing `help` means that state is unreachable.

The row, in `modules/apps.nix` beside the existing guarded rows:

```nix
"help" = {
  icon = "󰙴";
  label = "Nixi";
  aliases = [ "help" "how" "ask" "nixi" ];
  action = "nixi";
  when = "nixarchy-plugin --enabled io.github.olafkfreund.nixi";
};
```

`when` reuses the mechanism already at `modules/apps.nix:362`, `:374` and `:385`
-- a fourth use, not a new one.

### 2. Aliases on the nine Ask topics

`pkgs/omarchy/default.nix:144-152` gain an `aliases` key each. The field is
already used twice in this file (`trigger.ask:143`, `setup.local-ai:153`), so
this is filling an established key.

Written from the **symptom**, not the topic name, because the palette ANDs query
terms and people type what is wrong rather than what they want:

| row | label | aliases |
|---|---|---|
| `trigger.ask.logs` | What's wrong? | error, errors, broken, crash, logs, journal, failed, why |
| `trigger.ask.optimize` | Make it faster | slow, lag, laggy, faster, speed, performance, why |
| `trigger.ask.security` | Am I exposed? | security, hacked, ports, exposed, firewall, open |
| `trigger.ask.disk` | Disk is full | disk, space, full, storage, free, garbage |
| `trigger.ask.gpu` | GPU not working | gpu, graphics, nvidia, amd, driver, display, why |
| `trigger.ask.update` | What changed? | update, updated, changed, upgrade, generation, rollback |
| `trigger.ask.backup` | Back up my config | backup, back up, save, copy, restore |
| `trigger.ask.install` | Install something | install, add, package, software, app |
| `trigger.ask.anything` | Ask anything | ask, question, chat, anything, ai |

`why` is on the three diagnostic rows deliberately: a query must match every
term, so "why is it slow" fails against *Make it faster* without it.

## Alternatives rejected

| | why not |
|---|---|
| A distinct id for the Nixi row (`setup.nixi`) | Produces two rows wherever Nixi's installer has run. The intent called that the worse outcome and it is avoidable for free. |
| Ask nixi-nixarchy to stop writing its row first | Not ours to change, and filing there unprompted is out (section 11). Taking `help` means we do not need them to move first, and their follow-up still improves things when it lands. |
| Descriptions instead of aliases | The issue proposes both. Descriptions are rendered text; aliases are what the palette matches. Aliases are the fix; a description is cosmetic and can follow. |
| Generating aliases from the topic name | "optimize" is not a word a user types. The whole defect is labels written as answers. |

## Risks

- **The existing menu check.** `pkgs/omarchy/default.nix:1173` parses this file
  and asserts at least ten `trigger.ask*` rows exist and that each action starts
  with `omarchy-launch-floating-terminal`. Adding an `aliases` key touches
  neither, but the check runs on the same file and must be seen still passing.
- **The new row's action is bare `nixi`, not a floating terminal.** Its id is
  `help`, not `trigger.ask*`, so it falls outside that assertion's scope -- but
  if the assertion is ever widened to all rows, this row is the counter-example.
  Worth a line at the row rather than a surprise later.
- **Mode A.** The row is generated into the defaults file that
  `programs.nixarchy` already writes; a machine with nixarchy off generates no
  file at all, so there is nothing new to be off.
- **Aliases are unverifiable.** No check can say whether "lag" is a word your
  users type. Stated in the intent and restated here rather than implied to be
  covered.

## Verification

- **`checks.menu-verbs`** -- the row's action is a command the CLI accepts, and
  the nine Ask actions are unchanged.
- **`checks.options`** -- a case asserting the `help` row is present with its
  `when` guard, and **absent** from a machine where the Nixi plugin is not
  enabled. Section 1: it must go red with the `when` line removed, and that
  output goes in the PR. The trap to avoid is asserting on row *presence* alone,
  which the generated file gives for free -- the assertion reads the `when`
  string.
- **The menu build check** at `pkgs/omarchy/default.nix:1173`, seen passing.
- **What no check reaches**: that a user typing "system slow" finds the row.
  The palette is nixarchy-menu's, in another repository, and its matching is not
  exercised by anything here. Checked by hand, and recorded in
  `tests/AGENTS.md` as a documented hole rather than implied coverage.
