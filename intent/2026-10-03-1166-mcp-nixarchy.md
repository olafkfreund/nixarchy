# Intent: agents on nixarchy can look up nixarchy's own options and manual

## Problem

Every coding agent on a nixarchy desktop gets the `nixos` MCP server (#623,
`modules/home.nix` `mcpConfig`, the `mcp-nixos` package from nixpkgs). It
answers questions about NixOS, Home Manager and nixpkgs. It knows nothing
about nixarchy, the layer the user is actually configuring:

- **Options.** `programs.nixarchy.*` (NixOS and Home Manager) are unknown to
  it, so an agent guesses option names, or greps the store.
- **Manual.** `docs/manual` is unreachable unless the agent finds and clones
  the repository.

Nothing installed on the machine would let a server answer either:

- **No nixarchy option catalogue exists on the machine.** The only
  `options.json` there is NixOS's own (`config.system.build.manual.optionsJSON`,
  which `nixarchy-search` reads, `modules/apps.nix:189-194`). It is built with
  `includeAllModules = false`, so it covers NixOS's base modules and not
  ours. That is also why it substitutes from cache.nixos.org (modules/AGENTS.md).
- **The manual is not installed at all.**

[mcp-nixarchy](https://github.com/olafkfreund/mcp-nixarchy) (a fork of
mcp-nixos, merged as its #2) keeps every mcp-nixos feature and adds
`source=nixarchy` (options) and `source=nixarchy-docs` (manual). It reads
`/etc/nixarchy/options.json` and `/etc/nixarchy/docs`, falling back to the
latest GitHub release and to `main`. Until nixarchy installs those, the
options source says "not available", and the docs source reads `main`. `main`
may describe a nixarchy newer than the one installed.

## Proposed outcome

- **The agents' `nixos` MCP server is mcp-nixarchy.** The server key stays
  `nixos`, so `mcp__nixos__*` tool names and every permission a user granted
  are unchanged.
- **An agent asking about `programs.nixarchy.<x>` gets the option** with its
  type, default, description and a link to its declaration, for the nixarchy
  version actually installed. That covers NixOS and Home Manager options alike.
- **An agent can search and read the nixarchy manual** of the installed
  version, offline.
- **The skills nixarchy ships to agents** (`nixos`, `nixos-binaries`) point at
  the MCP tool first for nixarchy questions, and `docs/manual/ai.md` says so.
- **Machines without nixarchy installed** can still get the catalogue: each
  GitHub release carries `options.json`, the server's fallback.
- **A check proves the installed catalogue parses** and contains
  `programs.nixarchy.enable`.

## Affected users and systems

- **Every installer-managed machine with AI agents enabled:** a different
  server package behind the same key; two new paths in `/etc/nixarchy/`.
- **Mode A** (someone importing `nixosModules.nixarchy` into their own config):
  nothing changes unless `programs.nixarchy.enable` is on.
- **Files touched:**
  - `flake.nix`/`flake.lock` (a new input);
  - `modules/home.nix` (`mcpConfig`);
  - `modules/nixos.nix` (`environment.etc`);
  - the release workflow;
  - two skills, `docs/manual/ai.md`;
  - `tests/options.nix` (around the mcp-nixos assertion, `:5702`),
    `tests/ai-mirror-mcp-remove.nix`, and a new check.

## Constraints

- **The server key stays `nixos`** (permissions and tool names).
- **The input follows our `nixpkgs`.** Otherwise a second Python closure
  arrives (the `mcp-servers-nix` comment in `flake.nix` explains why that
  matters). It is pinned to a commit, as with every untagged input.
- **The catalogue is built, not fetched, and costs little.** Evaluating every
  option is the 11.5 GB `checks.options` problem (AGENTS.md §6). The spec must
  measure what building `programs.nixarchy.*` alone costs at system build
  time, and on the `system` CI job.
- **No new external dependency at runtime.** The GitHub fallback is the
  server's, for machines without the files; an installed machine must answer
  offline.
- **Mode A stays inert:** nothing new outside `programs.nixarchy.enable`.
- **§14 coexistence:** a user who already sets `environment.etc."nixarchy/…"`
  or their own `nixos` MCP server must not be broken. The spec answers how.
- **Releases:** attaching an asset changes the release workflow, a CI file
  (§11). The spec names it for owner sign-off.

## Open questions

1. **The release asset (issue step 4):** in this task, or later? It touches
   the release workflow (owner sign-off), and only serves machines without
   nixarchy. The proposal is to include it.
2. **Gate:** install `/etc/nixarchy/{options.json,docs}` whenever nixarchy is
   on, or only when an agent with MCP is enabled? The proposal is whenever
   nixarchy is on: they are small, and also useful to a human (`jq`, `less`).
3. **Separate the server swap from the catalogue?** They could be two PRs.
   The proposal is one: the swap alone gives a source that says
   "not available", which is worse than today.
