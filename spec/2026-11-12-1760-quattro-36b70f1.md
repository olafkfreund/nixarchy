## Design

### The pin gate

The package's own `version` says which pin it was built from, the same
`lib.hasPrefix "edge-"` test #1752 put in the checks. Each patch that differs
between pins goes under `isEdge = lib.hasPrefix "edge-" version`, with a strict
`--replace-fail` on each side. Under `main`'s pin the existing lines are
byte-identical, so `main-pin` proves nothing changed there. When `main` moves
to a quattro tag, the stable side's `--replace-fail` breaks the build, which
is the loud signal to drop the gate.

Rejected: one pin-agnostic `sed` with an assertion afterwards. It is shorter,
but a `sed` that silently matches nothing on one pin is the failure §1 warns
about. Each side has to stay a `--replace-fail` that can fail.

### One ownership test for every guard below

Home Manager can own a file (a link into `/nix/store`) or a whole directory
(`xdg.configFile."hypr".source = ./dir`, so `~/.config/hypr` is the link and
the file inside is not). `[[ -L $file ]]` misses the second case. Every guard
in D1–D5 asks the same question instead: does `readlink -f` of the file, or
of its directory when the file does not exist yet, start with `/nix/store/`?
It is written once, as a sourced helper in the package
(`share/omarchy/lib/nixarchy-store-owned.sh`), and each patched script calls
it. Every fixture below has two variants: a link to the file, and a link to
its directory.

### D1: Chromium stays the default (approved intent decision 1)

On edge:

- **P3:** in `omarchy-provision-user`, replace the whole line
  `env -u BROWSER XDG_CURRENT_DESKTOP= xdg-settings set default-web-browser
  google-chrome.desktop`. The replacement keeps the `env` prefix on both
  calls (`get` with `|| true`), and sets `chromium-browser.desktop` only when
  `get` prints nothing and `~/.config/mimeapps.list` is not store-owned.
  `xdg-mime` writes a new file and renames it over the list, which would
  replace a Home Manager link. The next line, `xdg-mime default HEY.desktop`,
  gets the same ownership guard. Generic `xdg-settings get
  default-web-browser` reads `x-scheme-handler/http` (xdg-utils
  `xdg-settings:797`), so a user who set only that keeps it. Upstream's line sets
  the browser unconditionally, on any home without Omarchy's finalization
  marker (`:59`), so a home with Firefox already chosen would lose it.
  v4.5.0 does the same at `:128`, and `main` keeps it as it is. `provision-user` leaves the `chromium.desktop`
  rename loop on edge. `omarchy-default-browser` and
  `omarchy-remove-browser` still name `chromium.desktop` on both pins, so
  they stay in the loop.
- **P1:** drop the `case` patch; upstream's own line covers it.
- **P2:** replace `browsers=(google-chrome.desktop chromium.desktop)` with
  `browsers=(chromium-browser.desktop google-chrome.desktop)`. Chromium comes
  first because it is the browser nixarchy ships; Chrome follows for a user
  who installed it. The `exec setsid uwsm-app -- "$browser_exec"` quoting
  patch matches both pins and stays outside the gate.
- **P4:** replace the body of `install_browser_extension` with the existing
  declarative message (`programs.chromium.extensions`), then `return`. The
  message text is unchanged.

**Chrome-only additions are not carried in this PR** (open question 1).
Install > Browser > Chrome keeps working as it does on `ceb30ed`. It has never
had upstream's CRXs or flags on nixarchy, so nobody loses anything. Carrying
them means a Chrome policy path under `/etc/opt/chrome` and a flags file that
nixpkgs' `google-chrome` wrapper may not read.

Migrations 1794210626 and 1794391847 touch only system paths, so the triage
grep does not flag them and nixarchy does not run them. No row.

### D2: Adwaita on edge, leaving the user's icon theme alone (decision 2)

**One limit, which needs your call (open question 2).** Omarchy wrote
`Yaru-<colour>` on every theme change. A user who picked `Yaru-blue` by hand
holds the same value, and nothing tells the two apart. So "a `Yaru*` value is
Omarchy's" overwrites that user once, which is also what upstream's migration
does.

On edge, patch `omarchy-theme-set-gnome` line 29 to set Adwaita only when the
current icon theme is a `Yaru*` value, `Adwaita`, `hicolor` or empty: the
values Omarchy or GTK put there. Anything else is a theme the user picked, and
it stays.

`omarchy-theme-set-qt` does the same for Qt (`icon_theme="Adwaita"` at :16,
written unconditionally at :24), so it gets the same guard on
`.theme.iconTheme`, plus the ownership test on `~/.config/qtengine/config.json`.
Both guards compare the real output: `gsettings get` prints GVariant-quoted
strings (`'Yaru-blue'`, `''`), and the GTK guard matches those quoted forms.

Migration 1794397144: `partial`, with a nixarchy port. The `pacman` removal
and the `/usr/share/icons/Yaru` cleanup do not apply (there is no pacman, and
the store is read-only). The two settings changes are the part users need:
`gsettings` when the value starts with `Yaru`, and the Qt config when
`.theme.iconTheme` starts with `Yaru`. The port runs exactly those two
statements, guarded as upstream guards them, plus the ownership test on the
Qt config. It calls `gsettings` and `jq`, so the port names both by store
path.

`yaru-theme` stays in `modules/nixos.nix:1461` on both pins. `main` needs it
for v4.5.0's `Yaru-<colour>`, and on edge it keeps a user who picked a Yaru
variant working. The ledger row `data/omarchy-packages.nix:306`
(`yaru-icon-theme`) gets `edge = "absent"`: the package ledger reports it
stale on the probe tree.

### D3: Super + Ctrl + X (decision 3)

1794387387: `ported`, `run = "edited"`. Upstream's text is kept, with one
guard added: a `bindings.lua` that is a symlink into `/nix/store` is left
alone. The exact-line test alone is not enough. A user can write the legacy
line into a Home Manager file themselves, and `sed -i --follow-symlinks`
then fails on the read-only target.

### D4: shared agent instructions (decision 4)

- Ship upstream's `omarchy-agent-instructions` with two guards:
  - **The shared file itself.** If `~/.agents/AGENTS.md` is a symlink
    (Home Manager or dotfiles), the script does not write the header through
    it (`:94`), and never `mv`s a harness file onto it (`:75`), which would
    replace that link. `blank()` then answers "not blank", so a regular
    harness file goes down upstream's `.bak` path. Otherwise a header-only
    linked file would send it down the adopt path, skip the `mv`, and
    `ln -sfn` would delete the user's file with no backup.
  - **`--edit` on a store-owned shared file** prints which Home Manager
    option holds it, instead of opening a read-only file.
  - **Each harness target.** At the top of `link()`: if the target is a
    symlink that is not already the shared file, print
    `Skipping <target>: a link you manage` and return.

  That covers Home Manager and dotfiles links, as the approved decision says.
  A regular file gets upstream's move or `.bak`.
- nixarchy's `pkgs/omarchy/nix-bin/omarchy-default-agent` calls
  `omarchy-agent-instructions "$agent"` after it records a choice, as
  upstream's does (its line 158). On edge only: the command does not exist
  in v4.5.0. The call is guarded with `command -v`, so the same script holds
  under both pins without a gate.
- `omarchy-provision-user:108` already calls it upstream, and the patch
  covers that call too.
- 1794344676: `ported`, `run = "upstream"`. It calls
  `omarchy-agent-account-state link grok`, whose `link_shared` creates a link
  inside an added account's home only where nothing exists yet
  (`if target.exists() or target.is_symlink(): continue`). It never replaces
  a file or a link.

### D5: the editor's MIME defaults

- Patch `omarchy-cmd-editor-mimetypes`:
  - **At the top, before anything writes:** if `~/.config/mimeapps.list`
    is store-owned, print one line naming the Home Manager option and exit
    0. Upstream writes the list at :29 and :32 before its main write at
    :107. The same test guards `~/.config/hyprland-mimeapps.list` before the
    branch at :112.
  - Drop the block at :19–24 that copies the handler into
    `~/.local/share/applications`. The package installs it system-wide
    (below), and a copy there would shadow every later version of it.
  - Treat `/etc/xdg/mimeapps.list`, where NixOS's
    `xdg.mime.defaultApplications` writes, as one more "older" list for
    `--unless-chosen`. A type set there to anything but Omarchy's own past
    defaults counts as chosen, so a NixOS module's `text/plain =
    kate.desktop` survives. nixarchy's own `text/plain = nvim.desktop`
    counts as Omarchy's.
  - Read aliases from `${shared-mime-info}/share/mime/aliases`.

  An explicit choice (Setup > Default > Editor) still rewrites matching
  associations, as the intent says.

  One limit, kept as upstream wrote it: `--unless-chosen` treats
  `nvim.desktop` and `plain.desktop` as Omarchy's past defaults (`:59`), so a
  user who chose either by hand gets the handler instead. The handler opens
  the default editor (Neovim unless the user changed it). So a user who chose
  `nvim.desktop` and kept Neovim as the editor sees no change, but one who
  chose `plain.desktop` by hand while keeping Neovim as the editor gets
  Neovim. Telling those choices apart would need a record that does not
  exist; this limit is in the release notes.
- Install `omarchy-launch-editor.desktop` unprefixed, beside
  `omarchy-browser.desktop` (:1218): the script and the mimeapps lines name
  it by that ID, and no package ships an entry with Omarchy's name.
- **P6:** the icon guard skips entries with `NoDisplay=true`, because the
  guard exists to stop blank launcher tiles and a hidden handler has no tile.
- 1794390043: `ported`, `run = "upstream"`, now that the script respects
  Home Manager. This matters here: on p620, `~/.config/mimeapps.list` is a
  Home Manager store link, so upstream's migration would fail there.

### Agent menu checks (§1 read backwards)

- **`default-agent-routes`** reads rows by prefix. It takes
  `agent.harness.` when the menu has any and `setup.default.agent.`
  otherwise, and asserts exactly one prefix is present. Then it reads the
  ids as before, so the 24-row count and every route assertion are
  unchanged.
- **`check-menu.py`** keeps the property: a row must not tick for an agent
  that is not installed.
  - In the old layout, `checked` had to run `command -v`.
  - In the new layout, `checked` must call `omarchy-default-agent` and
    compare its output with the row's own id. That alone is weaker: the
    setter records the choice before the rebuild (`nix-bin/omarchy-default-agent:180`),
    and declining the build leaves it recorded (`:199`). So the getter
    (`:53–61`) prints the recorded agent only when `command -v` finds it.
    `default-agent-routes` gains a case asserting that a recorded agent
    whose command is missing prints nothing. That case can fail. The same
    getter is used under both pins; v4.5.0's rows run `command -v`
    themselves, so nothing changes there.

  This holds only because each row id is the command the agent installs.
  The script says so for its `attr_for` rows ("Each package's
  meta.mainProgram is the agent's id"). `default-agent-routes` already
  checks that by stubbing `omarchy-agent` with `command -v "$WANT"`. Ids
  nixarchy names but does not install (`elsewhere_attr_for`) are installed by
  the user, so `command -v` is the only test there is.

  Recording before the rebuild already replaces a previous default when the
  user declines the build. That is today's behaviour on both pins; the getter
  change only stops the menu from ticking something that cannot run.

  The agy-row assertion uses whichever prefix is present. The PR says that
  the check was retargeted, not satisfied.

### The migrations ledger under two pins

`tests/user-migrations-ledger.nix` rejects a row that its triage did not
select (`:39`). That breaks twice:
- v4.5.0 has no 1794* migrations, so `main-pin` would reject all four new
  rows;
- 1794390043 never matches the triage, so it would be rejected on edge too.

So:

- **New rows carry `edge = "only"`.** Two consumers read the ledger, and
  both drop those rows off-edge:
  - the check, the way #1752 did for `data/etc-overlay.nix` and
    `data/mise-allow.nix`, with the same marker validation. A marker on a row
    whose migration the tag also contains is reported as stale.
  - `pkgs/omarchy/user-migrations.nix`, which ships every `ported` or
    `partial` row and runs `test -f` on upstream's script. Without the
    filter, `main-pin` fails on a missing 1794* script, and the ported
    1794397144 would run for `main` users and move them off Yaru, against
    decision 2. It reads `omarchy.version`, which it already receives.

  The filter runs before the `via` test, so `main-pin` never looks for an
  edge-only script.
- **Rows can carry `via = "<command>"`.** The check accepts a row outside
  the triage only when the migration calls that command and the command's
  `bin/` script matches the triage grep. 1794390043 gets
  `via = "omarchy-cmd-editor-mimetypes"`. A `via` naming a command the
  migration does not call, or one that writes no user file, fails.

## Alternatives rejected

- **Follow upstream to Chrome by default.** Chrome is unfree, so the default
  would depend on `allowUnfree`, and `checks.options` would fail with it off.
  Rejected at the intent gate.
- **Widen the migration triage now.** It would add 54 migrations, each
  needing a decision, to a carry about one pin. That goes to its own issue
  instead.
- **Drop `yaru-theme` on edge.** That would break a user who picked a Yaru
  variant, against decision 2, and gate a module line for no gain.
- **Skip `omarchy-agent-instructions` entirely.** Decision 4 adopts it, and a
  regular-file move is upstream's documented behaviour.

## Risks

- **p620 and razer deploy edge.** `~/.claude/CLAUDE.md` is HM-managed on
  p620. A guard that missed would break the next HM switch there. The
  fixture with an identical-content link is what guards that (§1, #1304).
- **The first theme change on edge moves a Yaru user to Adwaita.** That
  follows upstream on purpose, and the release notes say so (§14).
