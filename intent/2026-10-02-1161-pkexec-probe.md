# Intent: the pkexec probe in checks.session either passes or says why it failed

## Problem

`checks.session`'s pkexec probe (`tests/session.nix`, about lines 510-535,
from #776) failed once on 2026-10-02 (run 37042891405, PR #1160). The same
tree passed on `main` and on #1156 the same afternoon.

The test asks Hyprland to start `pkexec env touch /tmp/pkexec-ok`, then waits
90 s for a `polkit-agent-helper@` unit. That unit appears only once the
shell's polkit agent is showing its dialog. Here it never appeared, and the
log cannot say why:

- **The dispatch is unchecked.** `hyprctl dispatch 'hl.dsp.exec_cmd(…)'`
  exits 0 even when Hyprland rejects the command or the instance signature
  (`ls -t /run/user/1000/hypr | head -1`) names the wrong instance. Its reply
  is thrown away. If it failed, pkexec never ran.
- **"Agent ready" is matched anywhere in the boot's journal.** The probe waits
  for `omarchy polkit agent registered`
  (`shell/plugins/polkit/PolkitAgent.qml:186`) in all of
  `journalctl -b -t omarchy-shell`. The shell is supervised and can be
  relaunched during the 75 s settle before the probe. On the failing run the
  wait returned in 0.02 s, which is consistent with matching an earlier
  instance's line while the current shell's agent was not yet registered.
  pkexec with no agent gives up with no dialog.
- **Nothing is captured on failure.** pkexec's own output is not kept, and
  neither is polkitd's journal. A timeout prints only the timeout.

So this is either a real race in the test (the agent check) or something
neither log shows. A re-run that passes does not answer which (AGENTS.md §10).

## Proposed outcome

- **The probe proves each precondition it depends on:** the dispatch was
  accepted, and the agent of the shell *currently running* is registered.
- **When it fails, the failure names its cause:**
  - the dispatch reply;
  - pkexec's own output and exit status;
  - polkitd's journal;
  - the shell's recent journal.
- **If the agent race is the cause, the flake stops;** if not, the next one is
  diagnosable from the CI log alone.

## Affected users and systems

- `tests/session.nix` only. A test change: nothing shipped to machines
  changes.
- CI time is unchanged in the passing case.

## Constraints

- **Do not weaken the probe.** It must still prove the Omarchy dialog
  answers a pkexec started inside the session (#765/#776).
- **No retry-until-green:** no blind retry of the dispatch. A retry is
  acceptable only after a recorded, named failure, and then only if it
  carries that diagnosis into the log.
- **A probe that cannot fail is worse than none (§1).** The change must be
  shown red, and since the flake cannot be summoned, through a staged
  failure: for example, the agent prevented from registering. That red must
  print the new diagnostics.
- **VM runs are CI's** (§6 tiers).

## Open questions

1. **How strict is "the current shell's agent"?** Options:
   - match a registration line after the newest shell start in the journal;
   - ask the running shell over IPC whether its agent is registered, if the
     plugin exposes that (to be checked).

   IPC is more direct, but adds a dependency on an IPC surface the plugin may
   not have. The spec picks after reading `PolkitAgent.qml`.
2. **Should the same hardening go into the second pkexec probe?** It is the
   `systemd-run --user` variant just below (#765 PR 3), which shares the
   pattern. The proposal is yes, in the same change, since it can flake the
   same way.
