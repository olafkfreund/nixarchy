# Intent: Gliff-Manager ships as a default plugin, from a NixOS-ready fork

## Problem

gliff has been a default package since #1227, and #1233 added Setup > Remote
desktop > Connect with gliff. That row opens gliff's own window and nothing
more. Before you connect, nothing tells you which of your machines are ready:
whether ssh lets you in, whether gliff is installed there, whether a Hyprland
session is running, or whether a screen is plugged in.

[Gliff-Manager](https://github.com/28allday/Gliff-Manager) (MIT, by Gavin
Nugent, commit `b39ea9b`) is an Omarchy bar widget that answers exactly that.
It lists your gliff machines, checks each one over ssh, picks headless or mirror
mode per machine, fixes common setup problems, and connects. It is written for
Arch, and on NixOS it breaks in five ways:

1. **The rebuild refuses it.** `modules/home.nix:525-544` fails the build for
   any plugin with a non-comment line that names `pacman`. `gliff-manager.sh`
   names it at :463, :557-564 and :1012-1030.
2. **gliff reads as missing everywhere.** Both the local and the remote version
   checks run `pacman -Q gliff`. So the panel says "gliff is not installed on
   this computer", and every nixarchy machine in the list says "gliff is not
   installed there", with a fix button that runs `sudo pacman` on it.
3. **It never sees a connected window.** `pgrep -x gliff` matches the process
   name, which on NixOS is `.gliff-wrapped` (gliff is wrapped by nixpkgs). So:
   - the bar never shows "Connected";
   - every click opens another window;
   - every connect ends with "gliff did not start", even though the window
     opened.
4. **It never finds which user owns Hyprland.** `ps -C Hyprland` misses
   nixpkgs' `.Hyprland-wrapp`, so the "switch user" fix never appears.
5. **Two of its fixes only work on Arch.** The install fix runs pacman. The
   session fix installs a script that runs `/usr/bin/gliff-server`, and on
   NixOS that file is not part of the gliff package; the binary lives in the
   Nix store. A NixOS machine reached over Tailscale SSH still triggers that
   fix, because such a login has no `XDG_RUNTIME_DIR`.

## Proposed outcome

- **A public fork, `olafkfreund/nixarchy-gliff-manager`, fixes all five.** It
  has:
  - a flake: the plugin package, plus a Home Manager module for NixOS machines
    that run the Omarchy shell without nixarchy;
  - a check that exercises each fix against real processes and fails when any
    fix is reverted;
  - CI, a one-page docs site, and a weekly workflow that opens an issue when
    the original project changes;
  - a README that credits Gliff-Manager and says what the fork changes and why.
- **On every nixarchy machine with gliff, the widget is in the bar from the
  first login.** It is enabled once, like the other default plugins.
  `programs.nixarchy.defaultPlugins.gliff-manager = false` removes it, turning
  it off in Setup > Plugins sticks, and `preinstallsExclude = [ "gliff" ]`
  removes it together with gliff.
- **Between two nixarchy machines, the panel shows each one as "Ready"**, with
  its gliff version. Connecting a second machine adds a tab rather than opening
  a second window, and the bar shows the connection.
- **Setup > Remote desktop gains "Manage gliff machines"**, beside "Connect with
  gliff".
- **Users can find it.** It is in the manual's plugin list and on its remote
  desktop page, on the site's front page and in `llms.txt`, and it is announced
  in Discussions.

## Affected users and systems

- **The new repository** `olafkfreund/nixarchy-gliff-manager`: a GitHub fork of
  28allday/Gliff-Manager, public.
- **nixarchy:**
  - a new flake input and `flake.lock`;
  - the `defaultPluginSet` entry in `modules/home.nix`;
  - `remoteMenuRows` in `pkgs/omarchy/default.nix`;
  - tests: `tests/options.nix`, `tests/plugin.nix`, `tests/remote-tunnel.nix`
    and `tests/demo/screencast/shots.nix`;
  - documentation: the README, `docs/index.md`, `docs/llms.txt`,
    `docs/manual/{plugins,remote-desktop,configuration}.md` and
    `docs/internals/flake.md`.
- **Every nixarchy machine with gliff** gains a bar widget at its next rebuild
  and login, existing machines included. Machines without gliff, and Mode A,
  get nothing.
- **Anyone who already added upstream's copy** with `omarchy plugin add` ends up
  with two widgets, because the fork has a new id. Both share
  `~/.config/gliff-manager/`. The documentation tells them to remove upstream's
  copy.

## Constraints

- **Nothing in the plugin may run pacman or yay.** That keeps nixarchy's scan
  green, and nothing on NixOS can install a package imperatively anyway.
- **Fix the fork rather than patch at build time.** We own the fork, so its
  source is what ships. Upstream's licence and copyright stay as they are.
- **Each fix needs a check that fails without it (§1),** with the failing output
  captured in the pull request.
- **Enable through the running shell's own hook, never by writing `shell.json`
  (#847).** Turning it off has to stick.
- **Mode A gets nothing.** Neither standalone Home Manager nor a machine with
  nixarchy off may gain the plugin. `checks.options` asserts both states.
- **No contribution upstream without asking (§11).** A pull request to
  28allday is offered separately; this work does not open one.
- **No separate tools list in nixarchy.** The plugin's runtime tools (`jq`,
  `ssh`, `pgrep`, `lspci`, `setsid`, `xdg-terminal-exec`, `uwsm-app`) are
  already runtime dependencies of the `omarchy` package.

## Open questions

1. **On by default, or installed only?** The plan takes on, enabled once and
   only where gliff is installed, following the request for "a default
   installed plugin". The trade-off: the plugin is a day old, has one author,
   and opens ssh connections to every machine you list. It only probes machines
   you have listed or connected to, and its checks only read.
2. **The new id.** The fork renames the id to `nixarchy.gliff-manager`, which is
   the fork convention (podman, menu, pkg). Keeping `nosignal.gliff-manager`
   would avoid the duplicate widget for anyone who already has upstream's copy,
   but then one id would name two different programs.
