# Intent: Tolerate brief MicroVM status probes before refusing a mutation

## Problem

Refs #1098, Robustness lock item. The finding still holds on current `origin/main` after #1100 and #1112: `pkgs/microvm.nix:158-166` implements `lock_held` by opening `<vm>/.lock` and trying an exclusive `flock -n`. `vm_status` calls it from both text and JSON `list` (`:180-214`), and the detached-run readiness poll also calls it (`:391`). `pkgs/verify.sh:683-694` repeats the same exclusive probe for each guest. When a VM is stopped, a probe **acquires** the lock briefly before releasing it. A simultaneous normal `run`, `rm`, or `set-template` tries `lock_stopped_vm` with a nonblocking exclusive lock (`pkgs/microvm.nix:316-333,357-359,445-479`) and can spuriously refuse as “already running.” The panel and terminal both consume `list`, so this is a user-facing race, even though the lock window is short. The verifier's wider guest checks also repeat it.

The original claim overstates one part: `stop` runs `microvm-shutdown` directly (`pkgs/microvm.nix:450-459`) and does not take this lock. A `launch_vm` handoff waits for its lock for up to 30 seconds (`:363-370`), so a short probe may delay that path but does not immediately refuse it. No persistent state corruption follows from the probe itself; the demonstrated code-level harm is transient false-busy behavior. `tests/microvm-template.nix:675-695` verifies stopped/running values but does not assert that a brief probe cannot make a mutator falsely refuse.

## Proposed outcome

Status/list and verification keep their existing short lock probes. `run`, `rm`, `set-template`, and detached `run` wait up to two seconds for that transient holder before deciding the VM is busy. A real running VM still refuses with its existing message after the bounded wait; an active or activating detached unit remains busy, and the runner keeps its exclusive lock for its lifetime. A cheap concurrency check proves a brief holder no longer causes a false refusal.

## Affected users and systems

Users of `nixarchy vm list` and its JSON consumer (`nixarchy.microvm`), and users running `nixarchy-verify` while starting or changing a disposable VM. The implementation belongs at the shared mutation-lock call in `pkgs/microvm.nix` and its cheap check. `pkgs/verify.sh` keeps its probe unchanged. The verifier also walks declarative `/var/lib/microvms/<name>` directories; whether those runners use this same lock is separate from this race.

## Constraints

- Keep the lifetime exclusive lock on the real runner. Replace only the mutation path's immediate `flock -n` refusal with `flock -w 2`, preserving the same refusal message when a runner really holds the lock.
- Leave both status probes (`pkgs/microvm.nix`, `pkgs/verify.sh`), the JSON `list` shape, and the `unit_busy` handoff check unchanged. Prove with a cheap fixture that a brief holder fails under `-n` and succeeds under `-w 2`, while a persistent holder still refuses within the bound. No VM boot is needed.
- This is one remaining item of the batch issue. #1097 separately tracks CI hygiene and is still open; a later PR for this item should say **Refs #1098**, not `Closes #1098`. No workflow, settings, or other-issue edits.
- At this gate, only this draft intent is committed locally. No build, implementation, push, or PR.

## Open questions

A real running VM still refuses with the same message after the bound.
2. **Owner decision:** Do not add `lslocks` or `/proc/locks` parsing. Their path and permission behavior add complexity for a race that a bounded wait solves.
