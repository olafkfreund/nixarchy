# Intent: the nine config writers take apply's lock and keep the files they edit

## Problem

nixarchy-pkg#59 (merged as nixarchy-pkg#65) made the package panel's adapter
take `nixarchy-apply`'s lock, `${XDG_STATE_HOME:-$HOME/.local/state}/nixarchy/applied/lock`,
for every write. It also keeps a recoverable backup and refuses to write
while an apply runs. That covers writes the panel makes. Nine of the writers
it calls also run directly, from a terminal or a script, and there they take
no lock at all:

`nixarchy-app-enable`, `-app-disable`, `-service-enable`, `-service-disable`,
`-pkg-add`, `-pkg-remove`, `-pkg-new`, `-pkg-undraft` and `-opt-remove`
(all in `modules/apps.nix`).

Run that way, a writer can edit `apps.nix` or `flake.nix` while
`nixarchy-apply` is copying and staging it, or while the panel is writing the
same file. Only `nixarchy-apply` takes the lock today.

The same nine also replace the file they edit rather than writing into it,
through `mv "$tmp" "$file"` or `sed -i`. That turns a symlinked `apps.nix`
(a dotfiles checkout) into a regular file, and resets its mode and owner to
those of the temp file. nixarchy-pkg fixed the same defect in its own writers
(nixarchy-pkg#39).

And when `nixarchy-apply --yes` finds the lock held, it says "another apply
is running". Now that a few-second panel write also holds the lock, that
names the wrong cause.

## Proposed outcome

- **The lock.** Run directly, each of the nine writers takes `applied/lock`
  before it reads the file it will change, waits a bounded time for it, and
  refuses with a message naming the cause if it cannot get it. Run under
  nixarchy-pkg, which exports `NIXARCHY_LOCK_HELD=1` and already holds the
  lock, it does not take it again: that would deadlock on a second open file
  description.
- **The file.** After any of the nine writes, the target keeps its inode: a
  symlink stays a symlink to the same file, and the file's mode and owner are
  unchanged. A failed write still leaves the original content.
- **The message.** A refused `nixarchy-apply --yes` says that a write or
  another apply holds the lock.

## Affected users and systems

- Everyone who runs these commands directly (the manual documents them), and
  everyone who uses the package panel, whose guarantee this completes.
- `modules/apps.nix` (the nine writers and `nixarchy-apply`), and the checks
  that run these writers.
- No host deploy is needed to verify it: the checks run the scripts.

## Constraints

- **Matches nixarchy-pkg's contract:** the same lock path, the same
  `NIXARCHY_LOCK_HELD=1` handshake, and a bounded wait, as nixarchy-pkg#65's
  spec chose (5 s, then refuse), never an unbounded one. `nixarchy-apply`
  holds the lock through prompts and a whole build.
- **No new failure on a fresh machine:** a writer must work when
  `applied/` does not exist yet.
- **Mode A is unaffected:** nothing here runs unless the user runs a writer.
- **Every check proves it fails (§1):** a writer with the lock removed, and
  one that still replaces the inode, must each turn a check red.

## Open questions

1. **Wait length.** nixarchy-pkg waits 5 s. Should a writer someone runs by
   hand wait longer, say while an apply is building? Proposal: 5 s, the same
   as the adapter, and the message says to retry when the apply finishes.
2. **Does `nixarchy-apply` itself honour `NIXARCHY_LOCK_HELD`?** The panel's
   "apply in terminal" is refused while busy, so nothing calls apply under
   the lock today. Proposal: no change.
