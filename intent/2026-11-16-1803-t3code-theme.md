# Intent: T3 Code follows the Omarchy theme when nixarchy installs it

## Problem

On Arch, `omarchy-install-ai-t3-code` sets T3 Code up to follow the theme
in three steps:

1. it creates `~/.t3/userdata`;
2. it publishes the palette with `omarchy-theme-set-t3code`;
3. it selects that palette with `t3 theme set omarchy --base-dir
   "$T3CODE_HOME"`.

With `programs.nixarchy.apps.t3-code.enable`, nixarchy installs nixpkgs'
`t3code` (`data/apps.nix:506`), which ships `t3` and `t3code-desktop`. None
of the three steps runs:

- `omarchy-theme-set-t3code` exits early while `~/.t3/userdata` is
  missing. The script says so on purpose: it creates no state directory on
  machines that do not run T3 Code.
- Nothing ever selects the theme.

So T3 Code keeps its built-in theme on every nixarchy machine, and theme
switches never reach it.

The owner's own configuration works around it (olafkfreund/nixos_config#2973)
with a Home Manager activation entry after `nixarchySeed`:

- it creates the state directory;
- it runs `omarchy-theme-set-t3code`;
- it runs `t3 theme set omarchy` only when the selected theme differs,
  bounded with `timeout -k`.

The CLI works headless inside `home-manager-<user>.service` (tested, about
0.4 s).

## Proposed outcome

- **With `apps.t3-code.enable`:** after a rebuild, T3 Code shows the Omarchy
  palette, and later theme switches retint it as they do on Arch.
  `omarchy-theme-set-t3code` already runs from the theme hooks once the
  state directory exists.
- **A user's own choice survives.** The theme is selected only when T3 Code
  has no theme of the user's choosing. Overwriting a deliberate choice at
  every activation would be worse than today. The spec decides the exact
  rule (the open question below).
- **Without the app:** nothing changes. No `~/.t3` is created, and nothing
  runs (Mode A).
- **Activation never blocks or fails on T3 Code.** The CLI call is bounded
  in time, and a failure is reported and skipped, never fatal to
  `home-manager-<user>.service`.
- The downstream workaround can then be deleted from the owner's
  configuration. That is the owner's change, not part of this one.

## Affected users and systems

- Anyone with `programs.nixarchy.apps.t3-code.enable`, on both `main` and
  edge.
- **Files:** `modules/home.nix` (a new `home.activation` entry, gated on
  `appEnabled "t3-code"`), and a check under `tests/`.
- Standalone Home Manager (no `osConfig`): `appEnabled` reads false there,
  as for every app, so nothing runs.

## Constraints

- **Mode A:** off unless the app is enabled.
- **Nothing leaves the store unpinned:** the activation calls `t3` from the
  same nixpkgs package the app installs, not from `PATH`.
- **Bounded:** `timeout -k` on the CLI call, so a hung Electron runtime
  cannot stall activation.
- **§1:** the check fails with the activation entry removed, and again with
  the "only when it differs" guard removed (where the spec keeps one).
- **Hermetic checks (§4):** any check runs `t3` against a temporary
  `T3CODE_HOME`, never a real home.

## Open questions

1. **When to select the theme.** Proposal: select `omarchy` only when T3
   Code's current theme is still its built-in default, or unset, so a theme
   the user picked in T3 Code stays. The workaround's rule ("only when
   `defaultTheme` differs from omarchy") would override a user's pick at
   every activation. The spec checks what `t3 theme` can report.
2. **Where the palette comes from at first activation.** If
   `~/.local/state/omarchy/current/theme/t3code.json` is missing (a theme
   staged before the template existed), the Arch installer runs
   `omarchy-theme-refresh`. Proposal: do the same only when that file is
   missing, and the spec measures its cost under activation.
