# Spec: `omarchy agent account copy` works in every direction, and we know why

Part of #1610. The sender does not change, destinations without envfs fail and
that is documented, and an interpreter found through PATH is accepted and
documented. The owner decided all of that in the intent. This spec adds a guard
and docs, and ships no behaviour change.

Upstream citations are v4.5.0: `transfer` and `copy` are
`bin/omarchy-agent-account-transfer` and `bin/omarchy-agent-account-copy`.

## Design

### Two checks, because no single layer can see it all

The receiver depends on three things: `/bin/bash` and `/usr/bin/python3` resolving
(`transfer:352,358`), and `OMARCHY_PATH` being set (`transfer:61-66`).

| Layer (§2) | Can see | Cannot see |
|---|---|---|
| Static (`bin-ledger`) | A vendored script starting to run `ssh` | Whether anything resolves |
| `runCommand` | The real receiver text, its branches, and what it writes | envfs, sshd, PAM, the system PATH |
| `checks.session` | All of it: real envfs, real sshd, the system's PATH and environment | A second machine, an Arch end, envfs off |
| `pkgs/verify.sh` | Nothing extra, and it only runs by hand | |

**A `runCommand` can't have envfs, and that is useful.** Measured in the sandbox:
`/bin` holds only `sh`, and `/usr/bin` doesn't exist. So the unedited receiver
there is a destination without envfs, which is the failure the owner chose to
document. It can't prove the working case: to run the receiver at all, the
interpreter paths have to be rewritten, and rewriting them skips the very thing
that could break. The working case belongs in the VM.

### 1. `checks.account-copy`: the failures, cheap, on every PR

New file `tests/account-copy.nix`, shaped like `tests/agent-account-routing.nix`,
wired in at `flake.nix:2266`. The generated step runs it with no workflow edit
(§4). It takes `omarchy` from the package and makes a fake login through the
shipped `omarchy-agent-account-state begin` and `register`, with stubbed
notification and usage commands. `HOME` and every `XDG_*` point into the build
directory (§4).

| Leg | Run | Must hold | Measured with upstream's scripts |
|---|---|---|---|
| A, no envfs | `receiver-command`'s output, unedited | exit 127, stderr names `/bin/bash`, no file under the destination's `HOME` | exit 127, 0 files |
| B, no `OMARCHY_PATH` | Interpreters rewritten to PATH names, variable unset, receiver on PATH | exit 1, `destination account backend is unavailable`, no file | exit 1, 0 files |
| C, control | As B, variable set | exit 0, `Claude: copied`, credential files mode 600 | exit 0, 4 files, credentials and registry 600, `.claude.lock` 644 |

Three things each leg must assert, because each already gave a false answer while
this was being measured:

- **The command text isn't empty.** With the export broken, `bash -c ""` exited 0
  on all three legs, with 0 files. That reads as a pass for "wrote nothing".
- **The message, not only the status.** With a bad fixture, leg B exited 1 with
  `invalid receiver bundle`: the right status for the wrong reason. Leg C is what
  shows the fixture is good.
- **`/bin/bash` is absent.** Leg A fails unless `test ! -e /bin/bash` holds, so a
  builder without the sandbox goes red rather than testing something else.

### 2. A loopback copy in `checks.session`: the working case

`checks.session` gets `services.openssh.enable = true` on its node
(`tests/session.nix:128`) and one subtest beside the `/usr` scan
(`tests/session.nix:2085`). The subtest is a script from `writeShellScript`,
because `as_user` (`:907`) wraps its command in single quotes:

1. Generate a throwaway key for `omarchy` and authorize it for `localhost`.
2. Run the real sender as `omarchy` with `HOME` and `XDG_*` moved to a temp
   directory holding a fake Claude login. `ssh` finds its key through the passwd
   entry, not `HOME`, so the far side is `omarchy`'s real home and login
   environment.
3. Assert exit 0, `Claude: copied`, and credential files with mode 600 and the
   fake contents, on the far side.
4. Remove the far side's account state and the key, so later steps see the
   machine they expect.

This runs the real sender, `ssh -T`, sshd, the login shell, envfs, the system
`python3` and the installed receiver. Nothing is rewritten. No real credential
exists in a test VM, and the fake values contain no token.

### The `OMARCHY_PATH` gap

`OMARCHY_PATH` is the one that a probe of the interpreters can't see. With it unset
and the receiver installed, the capability probe fails and the copy stops at
`transfer:66`, while `/usr/bin/python3` works perfectly.

**A correction to the intent, which is not edited here.** It says the variable
arrives through PAM. It has two routes, and the second holds with PAM off:

- `environment.sessionVariables` reaches `/etc/pam/environment`, read with
  `UsePAM yes`.
- The same value is merged into `environment.variables`
  (`nixos/modules/config/system-environment.nix:231`). bash built with
  `SSH_SOURCE_BASHRC` (`pkgs/shells/bash/5.nix:75`) reads `/etc/bashrc` under sshd,
  which loads it (`programs/bash/bash.nix:134`). The receiver's own
  `bash --noprofile --norc` inherits it from that shell.

From reading only. So `UsePAM no` is expected to stay green (§1: a property provided
twice) and isn't a valid break. See Verification.

### Failing with no credential written

Legs A and B assert this directly. It covers failure before the importer runs. An
import that fails partway keeps the providers already done (`transfer:389`), which
is upstream's stated behaviour and isn't changed or asserted here. The docs say so.

### The ledger rows, and watching the class

A vendored command only gets a row if it has an `allow` field; otherwise the check
fails it as a rubber stamp (`.github/scripts/check-bin-ledger.py:305-318`). So a row
here needs a behaviour group. Add one, `remote-exec`:

```python
"remote-exec": r"(?<![-\w])ssh\s+-",
```

Run comment-stripped over upstream's `bin/` it matches exactly two files:

- `omarchy-agent-account-copy`: the row names `transfer:352-358`, what they rely on
  at the far end, and `checks.session`.
- `omarchy-theme-set-herdr-machines`: the far end runs `bash -l -s` from PATH
  (`:76-78`), so no fixed path is involved. The row says so.

The lookbehind excludes `GIT_SSH_COMMAND`'s `:-ssh -oBatchMode` in the plugin
scripts. Requiring `-` excludes the `echo "…ssh $USER@…"` in
`omarchy-setup-security-sshd:224`. Add `remote-exec` to the group list at
`data/bin-ledger.nix:44-45`.

**On future bumps, recommend only this.** The dangerous property is "this command
runs on a machine other than the one that built it", and two of 444 scripts do that.
The group costs one line and fires only when upstream adds a third.

- **It is not watertight.** An `ssh "$host"` with no option, or a Python
  `subprocess.run(["ssh", …])`, escapes it. Say that in the group's comment.
- **`/usr/` paths are already watched.** The scan at `tests/session.nix:2102-2117`
  fails on any shipped script with `/usr/` in code. `omarchy-agent-account-transfer`
  is a named exception (`:2085-2087`), so point its comment at the new subtest.
- **Don't watch `/bin/bash`.** That is about 11 rows, for hits that run locally
  through envfs, and the group above already catches the remote case.

### Docs

- `docs/manual/ai.md`: a short section, "Copying subscription logins". It works to
  and from machines with envfs on, which is the default, and the destination needs
  `services.openssh.enable`. With envfs off, or on Mode A and plain NixOS, it fails
  with `/bin/bash: No such file or directory` and writes nothing. Under envfs the
  interpreter is whichever `bash` and `python3` come first on PATH, so a `python3` in
  `~/bin` receives the stream, which crosses no privilege boundary: that code already
  runs as the receiving account. A failure partway keeps providers already copied.
- `tests/AGENTS.md:313`: drop "the session VM runs no sshd", which stops being true,
  and add the holes under Risks.

### Coexistence (§14)

No option, default or package changes for any user. The sshd is on the test node only.
No fixture, because there is no clash to fail on. `services.envfs` stays `mkDefault`
(`modules/nixos.nix:1580`).

## Alternatives rejected

- **Probe `/usr/bin/python3` in `checks.session`.** Stays green with `OMARCHY_PATH`
  missing: measured, exit 0 with it unset on p620.
- **`runCommand` only.** Cheap, but can't reach envfs or sshd, and would pass with
  envfs gone from the module.
- **VM only.** Can't assert the envfs-off failure without a second node, and the
  sandbox already provides that state for free.
- **A dedicated VM check, two nodes, one with envfs off.** Closes the "real second
  machine" and "real envfs off" holes. Rejected as too much for a guard: a whole extra
  VM job, for a failure leg A pins and a hop that is ssh's own.
- **An evaluation check** that envfs is on and `python3` is in `systemPackages`. Proves
  the configuration says so, not that a receiver over SSH resolves them.
- **`pkgs/verify.sh`.** Runs by hand on hardware, and nothing here needs hardware.
- **Patching the sender.** Decided in the intent.

## Risks

- **sshd on the session node** could disturb an assertion further down the 2,967-line
  script. Only a run can tell; if it does, that is the argument for a dedicated VM.
- **Fake state left behind** could change later session steps, hence the cleanup step.
  `omarchy-agent-usage-update` also starts detached after an import (`transfer:390-393`)
  and may write its own state after the cleanup; the first VM run must show this is
  harmless.
- **Holes that remain, to name in `tests/AGENTS.md` (§3):** no real second machine; no
  Arch end in either direction; no real envfs-off machine over SSH (leg A is the same
  failure without sshd); Codex and Grok, which share this transport and differ only in
  which files they carry; login shells other than the session user's.
- **All on default nixarchy.** A red here on a bump means upstream changed the receiver,
  which is what the guard is for. It does not fail a host, since nothing shipped changes.

## Verification

§1, with failing output in the PR. Prove each break landed before reading the result.

| Break | Expected | Layer |
|---|---|---|
| Leg A runs the rewritten command | Red: exit is not 127 | `account-copy` |
| Leg B keeps `OMARCHY_PATH` set | Red: exit 0 | `account-copy` |
| Stub `receiver-command` to print nothing | Red: empty text | `account-copy` |
| A receiver that writes a file and then exits 1 | Red in leg B: a file exists | `account-copy` |
| Forced command `env -u OMARCHY_PATH /bin/sh -c "$SSH_ORIGINAL_COMMAND"` in `authorized_keys` | Subtest red at `backend is unavailable`, **while `/usr/bin/python3 -c pass` on the same machine stays green**; capture both | `session` |
| Forced command with `PATH` lacking `python3` | Subtest red | `session` |
| Delete a `remote-exec` row | Red: unclassified match | `bin-ledger` |

The `authorized_keys` forced command is the session break because it removes the
property only on the SSH path. Turning off envfs or dropping `sessionVariables` makes
earlier session assertions fail first (`tests/session.nix:310`), which would say
nothing about this subtest. Run `UsePAM no` once too, and record whether it stays green:
that tests the correction above rather than the guard.

`python3`-alone probe. Not run: `checks.session`, because CI had runs in flight at
writing time (§6), and `bin-ledger` with the new group, whose regex was only run
standalone. Both are the plan's to run.
