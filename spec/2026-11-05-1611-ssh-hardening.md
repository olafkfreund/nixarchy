# Spec: Turning on SSH from the menu leaves password logins on

## Design

### How a rebuild tells the two lines apart

It does not try to tell two identical lines apart. The two routes write
different options, and the rebuild reads the option.

| how sshd was turned on | line in `services.nix` | passwords |
|---|---|---|
| hand-uncommented old row, or a menu pick before this change | `services.openssh.enable = true;` | on, unchanged |
| own config | `services.openssh.enable = true;` | on, unchanged |
| menu, after this change | `programs.nixarchy.services.openssh.enable = true;` | off |

The openssh entry in `data/services.nix:73-81` becomes `kind = "bundled"`. The
marker stays `#@ openssh`, so the `disabled`, `when` and enable tests
(`modules/apps.nix:900,905,1097`) and `nixarchy-service-disable`
(`modules/apps.nix:1909-1941`) work unchanged.

`nixarchy-service-enable openssh` replaces a commented row that still names
`services.openssh.enable` with the template's row, then uncomments it as it does
today (`modules/apps.nix:1825`). A live row is never rewritten: the command
exits at its "already enabled" test (`modules/apps.nix:1820`) and, for openssh
on the old line, also says passwords are still on and points at the manual. That
is the approved answer to question 3.

Consequences to know:

- A machine enabled from the menu today keeps its line and its passwords.
- That machine turns the row off and on again through the menu: this is a new
  pick, so it goes through the key check and comes out hardened.
- An old file's commented row keeps the false note until the menu rewrites it,
  because nothing regenerates the file (`modules/apps.nix:1800-1802`). Hand-
  uncommenting it gives passwords on under a comment saying otherwise. This
  cannot be fixed without editing a file nixarchy promises not to touch, so the
  release note says it.
- A new file's row is the bundled one, so hand-uncommenting it there gives
  passwords off and no key check. See owner decision 1.

### The module

`modules/services/openssh.nix`, imported at `modules/services/default.nix:78`.
It does not touch `modules/nixos.nix`.

```nix
options.programs.nixarchy.services.openssh.enable = lib.mkEnableOption "...";
config = lib.mkIf cfg.services.openssh.enable {
  services.openssh = {
    enable = lib.mkDefault true;
    settings.PasswordAuthentication = lib.mkDefault false;
    settings.KbdInteractiveAuthentication = lib.mkDefault false;
  };
};
```

`openFirewall` stays at nixpkgs' `true`, as upstream opens the port too. It earns
a module under `modules/services/default.nix:1-10` because the two settings and
the key check are what a newcomer would not find alone, and because nothing else
can carry the difference.

Measured by `extendModules` on `nixosConfigurations.reference`, with that module
inlined:

| extra config | enable | Password | KbdInteractive | PAM `unixAuth` |
|---|---|---|---|---|
| none | false | true | true | no sshd service |
| `services.openssh.enable = true` | true | true | true | true |
| bundled option | true | false | false | false |
| bundled + `PasswordAuthentication = true` | true | true | false | true |
| bundled + `PasswordAuthentication = null` | true | null | false | false |
| bundled + `PasswordAuthentication = lib.mkDefault true` | evaluation error | | | |
| bundled + `services.openssh.enable = false` | false | false | false | no sshd service |

No nixarchy assertion or warning fired in any row that evaluated.

### The key check

It lives in `nixarchy-service-enable`, in an `openssh` branch before the rewrite,
because that command is the one both rows run. `nixarchy-apply` calls it only
for flatpaks (`modules/apps.nix:3511-3517`), so no other caller reaches this.

Facts only evaluation knows are baked into a JSON file, with an environment
override for tests, as `languageRegistry` is (`modules/apps.nix:1849`):

- `declaredUsers`: users with `openssh.authorizedKeys.keys` or `keyFiles`. The
  script cannot read this at run time: `/etc/ssh/authorized_keys.d` is only
  written with sshd on (`sshd.nix:766,777-778`), and the point is to check
  before it is on.
- `homeRead`: `services.openssh.authorizedKeysInHomedir`.
- `otherSources`: `authorizedKeysCommand` when not `none`, and
  `authorizedKeysFiles` minus nixpkgs' two own entries (`sshd.nix:885-887`).
- `sshdOn`: `services.openssh.enable`.

Order, for the running user:

1. `sshdOn` with the marked row not live means sshd comes from their own config,
   the lockout case from the intent. Say that Apply will refuse passwords unless
   their config sets `PasswordAuthentication`, and require a yes. With no
   terminal, refuse.
2. A key is visible if the user is in `declaredUsers`, or `homeRead` and
   `ssh-keygen -lf ~/.ssh/authorized_keys` exits 0. Measured: 255 on an empty,
   comment-only or garbage file; 0 with a key, including one with an options
   prefix. Upstream's `-s` test (`bin/omarchy-setup-security-sshd`,
   `disable_password_auth`) passes a comment-only file. Say which places were
   read.
3. If not visible and `otherSources` is set, name them, since this cannot see
   them, and ask whether they hold a key for this user. Yes continues.
4. If not visible and `homeRead` is false, refuse: a key written to the home file
   would not be read. Name `users.users.<you>.openssh.authorizedKeys`, and say a
   key just declared needs an Apply first.
5. Otherwise ask, in upstream's order: GitHub username or paste, reusing
   `omarchy-i18n sshd.howToAddKey`, `keyFromGithub`, `keyPaste`,
   `githubUserPrompt`, `publicKeyPrompt`, which exist at v4.5.0
   (`default/i18n/en/cli.json`). Validate each key, write it as upstream's
   `authorize_key` does (dir 700, file 600, no duplicates). No valid key, a
   cancel or no terminal: exit 1 with the file unchanged, naming the key
   locations and that sops-only users declare `services.openssh` instead.

`runtimeInputs` gains `pkgs.gum`, `pkgs.openssh` and `pkgs.curl`, each used by
name (§7).

Both rows open a terminal:
`omarchy-launch-floating-terminal-with-presentation 'nixarchy-service-enable openssh'`,
the shape at `modules/apps.nix:891`. Line 899 changes directly. Line 1095 is
generated, so the catalogue gains one field, `terminal = true`, documented with
the others (`data/services.nix:30-40`).

### Coexistence

Fixtures in `tests/coexistence/fixtures.nix`, assertions in
`tests/coexistence/default.nix` beside `agentLocalScripts`. Each asserts the
values measured above and that no assertion fired.

| fixture | user's config | must hold | fails if |
|---|---|---|---|
| `openssh-own-passwords` | bundled + `PasswordAuthentication = true` | Password true, Kbd false | the module uses `mkForce` |
| `openssh-own-null` | bundled + `= null` | Password null | same |
| `openssh-own-mkdefault` | bundled + `= lib.mkDefault true` | `tryEval` fails (question 4) | the module's priority is weakened, which is the departure from §7 this records |
| `openssh-plain-line` | `services.openssh.enable = true` | Password true, Kbd true | the settings leave the `mkIf` |

The `tryEval` was measured to catch the conflict on the reference config. A user
with `lib.mkDefault true` gets a loud error, as approved.

### Release note

The derived notes cover the new option. Their mkDefault scan
(`.github/scripts/release-notes.sh:256-283`) will also print the two settings under
"a machine that never mentioned them follows the new value", which is wrong for
lines inside an `mkIf`. The hand-written text has to say otherwise:

> **SSH from the menu now turns password logins off.** *Setup > Security > SSHD*
> and *Install > Service > OpenSSH* ask for your public key first and write
> `programs.nixarchy.services.openssh.enable = true;`.
>
> Nothing changes on a machine that already has sshd on, from the menu or from your
> own config: `services.openssh.enable = true;` still leaves passwords on, as
> nixpkgs defaults it. To turn them off there, first check you can log in with a
> key, then replace that line in `~/.config/nixarchy/services.nix` with the one
> above and run `nixarchy-apply`.
>
> An older `services.nix` still has a comment on that row saying NixOS defaults to
> keys only. That was wrong. The row is corrected when you enable it from the menu.

## Alternatives rejected

- **Harden every `services.openssh.enable` in nixarchy.** Question 1: changes
  users who rely on the nixpkgs default.
- **Companion lines in `services.nix` with `lib.mkDefault`.** Keeps the upstream
  option, but the file's header is `{ ... }:` (`modules/apps.nix:318`), so `lib` is
  not in scope, and the header is the user's. A plain `= false` collides with a
  user's own `= true`.
- **A rebuild reads a different marker from the file.** A module grepping its own
  input is impure and invisible in the option set.
- **Keep the template's row plain and rewrite only from the menu.** See decision 1.
- **Evaluation-time assertion on no key.** Evaluation cannot see the home file, so
  it would fail builds that have a key.
- **Check `sshd -T` after Apply, as upstream does.** The setting is declarative,
  and `checks.sshd-login` proves it on every pull request.
- **Change the guidance in `data/arch-extras.nix:126-127`.** It is the answer for a
  hand-run upstream script, which the intent leaves as it is.

## Risks

- **Own-config sshd with password logins, picks the row anyway.** After a yes,
  passwords go off at Apply. The check required a key and warned, and an open
  session survives the reload. Hosts: any declaring sshd with the row not live.
- **A pinned or older nixarchy.** A `services.nix` with the new line fails to
  evaluate there with "option does not exist": a fleet sharing a file, or a flake
  pin reverted. Same as every bundled row. Booting an old generation is fine.
- **The baked facts are from the last rebuild.** A key declared and not applied
  reads as absent, and the refusal says to Apply first.
- **A key that sshd will not use.** Wrong `~/.ssh` permissions pass the check, as
  they do upstream. Not checked.
- **Parallel work.** #1612-#1615 touch `modules/nixos.nix`; this does not. Rebase
  after anything merges (§9).

## Verification

Each row: what proves it, and the break that must turn it red (§1).

| outcome | check | break |
|---|---|---|
| Menu line refuses passwords; key works; old line still takes passwords | `checks.sshd-login` (new, VM, below) | remove `PasswordAuthentication` from the module |
| Kbd setting is off | `options-*` case, both states, as `tailscaleTrust` (`tests/options.nix:2346`); `sshd -T` in `sshd-login` | remove `KbdInteractiveAuthentication` |
| Option off changes nothing (Mode A) | same `options-*` case: off plus plain line gives true, true | drop the `mkIf` |
| A user's own value stands | `checks.coexistence`, table above | `mkForce` in the module |
| Old commented row becomes the bundled line, live, with the new note | `checks.sshd-enable` (new, `runCommand`, cheap) | drop the rewrite: line stays plain |
| Live old row is untouched and warned about | `sshd-enable`: byte-identical, message | move the rewrite above the live test |
| No key, no terminal: refused, file byte-identical | `sshd-enable` | delete the gate |
| Comment-only `authorized_keys` is no key | `sshd-enable` | replace `ssh-keygen -lf` with `-s` |
| Declared key passes; `homeRead` false refuses and writes nothing; `otherSources` asks | `sshd-enable`, by facts file | ignore each fact in turn |
| Pasted and GitHub keys land with modes 700/600; bad key refused | `sshd-enable`, stubbed `gum` and `curl` | skip validation |
| Own-config sshd warns, refuses with no terminal | `sshd-enable` | delete step 1 |
| Enable then disable round trip on a new file | existing case, `tests/options.nix:5339`, run on openssh | |
| Rows open a terminal and run the right command | `sshd-enable`, reading the menu spec | revert line 899 |
| False note gone from the template | `sshd-enable`: `grep` the built template | restore the text |
| Docs table matches | `checks.docs-lists` (existing) | leave the old row |

`checks.sshd-enable` drives the built script against fixture files in a sandbox,
with `NIXARCHY_TEMPLATES` and the facts override. Prove each break landed with
`git diff` before reading the result (§1).

`checks.sshd-login`: `runNixOSTest`, importing only `modules/services/openssh.nix`.
Three small nodes, each with a user with a known password and an authorized key:

- `hardened`: the bundled option.
- `plain`: `services.openssh.enable = true`, the control.
- `client`, with `sshpass`.

It asserts:

1. `plain`, password over `PreferredAuthentications=password`: **succeeds**. Without
   this, a broken client makes every refusal look like a pass.
2. `plain`, password over `keyboard-interactive`: succeeds.
3. `hardened`, key: succeeds.
4. `hardened`, password and `keyboard-interactive`: refused.
5. `hardened`, `sshd -T` prints both settings `no`.

Assert 4 for `keyboard-interactive` may stay green with the Kbd line removed,
because PAM `unixAuth` is already false. Assert 5 and the options case are what
catch that, so a green result from this one break is expected, not blindness. Write
down which it was.

**Not run.** No login has been attempted yet: CI had two to three runs in flight on
every check of the §6 gate while this was written, so no VM was started. The plan
must run it first. If assert 4 fails on `hardened`, this spec is wrong and comes
back for review.

Not reachable here: rate limiting (out of scope), and a real menu click in a floating
terminal. `checks.plugin` or a manual step in the PR covers the click, and the PR
says which.

## Owner decisions

1. **The template's row for a new file.** Bundled, or plain with the menu rewriting
   it? Recommended: bundled. It removes the false note outright and a new hand
   uncomment gets the safe line. The cost: "anyone who did not use the menu sees no
   change" holds for everyone with a machine today, not for someone hand-uncommenting
   in a future file, who gets passwords off with no key check. Plain keeps that
   sentence literally true, at the price of a row whose note has to admit passwords
   are on.
2. **`checks.sshd-login` needs KVM,** which the generated step lacks
   (`.github/scripts/generated-checks.sh:37-41`). So it joins `claimed` and gets a
   step beside `wifi-hwsim` (`.github/workflows/build.yml:2040`). That is a CI-gate
   change (§4, §11). Recommended: yes, on pull requests.
3. **Where the hand-written note goes.** `release.yml` builds notes from derived
   sections and has no slot for text (`.github/workflows/release.yml:319-354,441`).
   Recommended: put it in the PR body, and add it to the release and its Discussion
   by hand when the release is cut. Adding a slot is separate work.
