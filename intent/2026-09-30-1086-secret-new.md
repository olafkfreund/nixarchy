# Intent: Keep secret creation safe across flake layouts and host key changes

## Problem

`nixarchy secret new` creates `hosts/<host>` even when the flake uses the older flat layout. `nixarchy-apply` chooses its destination by whether that directory exists, so the new root-owned directory redirects a later apply into a location the user cannot write. The current code confirms this path; it does not show that all flat-layout users have run it.

When `.sops.yaml` already contains a rule for the host, `new` accepts any line containing `hosts/<host>/secrets` without comparing the rule's recipient to the current host key. After a reinstall with the same hostname, that can accept a stale recipient. The existing `enroll` path already detects this mismatch.

For system secrets, the root-side wrapper exports the derived `SOPS_AGE_KEY` and executes `sops edit`. The edit command is called with the user's `EDITOR`; nothing in this code removes the key from the editor's environment. The wrapper keeps the identity out of argv, but the editor inheritance needs direct verification during design.

## Proposed outcome

Creating a system secret on an older flat-layout flake fails before changing its directory layout. An existing policy is accepted only when its rule for this host names the current recipient; a stale rule produces a clear refusal. The host age identity remains available to SOPS while the editor and its child processes do not receive it.

## Affected users and systems

Users running `nixarchy secret new` or `nixarchy secret edit` for system secrets, especially on older flat-layout flakes or after replacing a host key. The affected commands live in `pkgs/secret.nix`; policy comparison already exists in `pkgs/sops-policy-add.nix`, and the apply destination is selected in `modules/apps.nix`.

## Constraints

- Preserve existing encrypted files, creation rules, and user-owned secret flows; do not silently rekey or migrate a flake.
- Keep the host private identity on the root side and out of process arguments, the editor, and its plugins.
- Check the real command behavior, including a negative case for each failure, without depending on a real host key in a build sandbox.
- Do not change the apply destination rule or create host directories merely to make secret creation work.

## Open questions

- Owner decision: refuse on a flat-layout flake before touching anything and direct the user to migrate the flake; do not provide a supported flat-layout system-secret path.
- Confirm from SOPS behavior how it launches `EDITOR`, and verify that the proposed environment boundary removes `SOPS_AGE_KEY` from the editor without preventing SOPS from decrypting and saving.
