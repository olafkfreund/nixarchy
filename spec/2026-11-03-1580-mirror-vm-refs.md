# Spec: `@generation` and `@window` in mirror-vm batches

## Design

### Placeholders

`pkgs/omarchy/skills/ai-mirror/mirror-vm` replaces the single `last` variable
with one table and one dict:

```python
MARKERS = {'frame': '@last', 'generation': '@generation', 'window': '@window'}
refs = {'frame': None, 'generation': None, 'window': None}
why = {'frame': 'before any screenshot',
       'generation': 'no generation seen yet',
       'window': 'before any launch'}
```

Before each step, for every `(key, marker)` in `MARKERS` **whose marker the step
uses** (`args.get(key) == marker`):
- the value becomes `refs[key]`;
- if `refs[key]` is `None`, a `ValueError` is raised:
  `step {i}: "{marker}" {why[key]}`.

That gives exit 1 through the existing handler, and nothing is sent for that
step. A step that doesn't use a marker is never checked against it. The match is
only on a top-level key whose value equals the marker (intent question 2).
Every other value passes through unchanged, and a missing key is never filled
in.

### Where each value comes from

All updates happen only when `not err and isinstance(body, dict)`, including in
the grant loop, which today indexes the tuple without a check. A tool error
stops the batch, as today.

- **`frame`:** a successful `screenshot` result's `frame`, when it is a `str`.
- **`generation`:** the `status` that confirms the grant (today it is
  discarded), then every successful result whose `generation` is an `int` and
  not a `bool` (intent question 1).
  - Every `generation` ai-mirror returns is the same number: the control
    state's current generation. That covers `status`, `screenshot`, `input`
    (`run_batch`), `control`, `windows` and `a11y_*`. The server's own
    instructions tell agents to take it from those.
  - So "any result" is the defined meaning, not a guess. A result after
    ownership is lost carries the new number, and the guest's gate refuses it.
  - `launch` results don't carry it, so they leave it alone.
- **`window`:**
  - **Set** by a successful `launch` that returned a `window` string that is
    not blank after `strip()`.
  - **Cleared** (`None`) by any other successful `launch`, with `why['window']`
    = `'after a launch that did not return exactly one window'`. So a launch
    that returns `candidates` or a note can't leave the earlier app's address
    behind. In `api._launch`, `window` and `candidates` are separate branches,
    so a mixed result can't happen.
  - **Also cleared** by a successful `window` step with `action: close` on that
    address, with `why['window']` = `'after that window was closed'`.
    Hyprland reuses addresses: three foot launches in a row on p620 all got
    `0x5af3adaed4e0` (2026-11-03). Without this, a closed window's address
    could later name a new one.
  - No other tool sets it.
  - **Limit:** a window that exits on its own still leaves `@window` set.
    Typing into it then fails in the guest, because `input` checks focus
    before every keystroke (`wrong_target`). A reused address needs a new
    window, and a new `launch` resets `@window` anyway. Documented in SKILL.md.

### Help and docs

- The `--help` description names the three markers.
- `SKILL.md`'s VM-path example becomes the measured flow, with no values known
  beforehand:

  ```json
  [
    {"tool": "launch", "args": {"argv": ["uwsm-app", "--", "foot"], "timeout": 10, "generation": "@generation"}},
    {"tool": "input", "args": {"generation": "@generation", "window": "@window",
      "actions": [{"type": "type", "text": "echo ok\n"}]}},
    {"tool": "screenshot"}
  ]
  ```

  Plus one line on what clears `@window`.

### Test

The new check is `tests/mirror-vm.nix`, a `runCommand` like
`tests/ai-mirror-mcp-remove.nix`, registered in `flake.nix` checks.

- **Fake `socat`:** a stdlib Python script on `PATH`,
  `tests/mirror-vm-fake-socat.py`, kept as a file because heredocs in indented
  Nix strings break under nixfmt. It acts as the guest server: it answers
  `initialize`, `control` and `status` with `owner: agent, generation: 7`, and
  gives canned `launch`, `input`, `windows` and `screenshot` results chosen by
  an env var. It logs every `tools/call` argument to a JSON-lines file.
- **The VM:** `HOME=$TMPDIR` with a `vsock-cid` file, so the real script runs
  unchanged.
- **Cases.** Each failure case asserts the exact stderr text and which steps
  were logged.
  1. `launch` with `@generation`, then `input` with `@generation` + `@window`
     → the logged args show `generation: 7` and the launched address, and the
     exit code is 0. `launch` carries no generation, so 7 survives it.
  2. `@window` before any `launch` → exit 1, `step 1: "@window" before any
     launch`, the `input` is never logged, and `control off` still is.
  3. A launch with one window, then a launch with `candidates`, then
     `@window` → exit 1, with the "did not return exactly one window" text. The
     second launch is logged, the input is not, and there is no fallback to the
     first address.
  4. Launches returning a note, `"window": ""` and `"window": "  "`, then
     `@window` → each exits 1.
  5. A launch, a `window` close on that address, then `@window` → exit 1, with
     the "closed" text. A close on a *different* address leaves it set.
  6. A literal `generation: 5` and `window: "0xabc"` pass through untouched.
  7. A step without `window` gets none added (no auto-fill).
  8. A `screenshot` result with `generation: 9` → a later `@generation` sends
     9. A mid-batch `control` result with `generation: 11` → a later
     `@generation` sends 11, which is why updates were chosen over the grant
     only.
  9. A grant `status` without `generation`, or with `generation: true`, then
     `@generation` → exit 1, `no generation seen yet`.
  10. `"@last"` still works and is still refused before a screenshot.
- **The check must fail without the change:** run it once against the current
  `mirror-vm`. Cases 1, 5 and 8 must fail. Record that in the plan.

## Alternatives rejected

- **General step references (`@step3.result.window`):** they need a path
  parser and step counting, and solve this case no more safely. Both Codex and
  agy rejected them.
- **Auto-fill** of a missing `generation` or `window`: it hides an action's
  target (intent constraint).
- **`@generation` from the grant only** (Codex): a `control` step inside the
  batch would leave it stale. The server reports the current value, so taking
  the latest is correct. agy recommended this too.
- **`@window` from `windows` or `wait`:** picking one of many windows is a
  guess.
- **Tracking every window close (events, polling `windows`) to clear
  `@window`:** more machinery for a case the guest already refuses
  (`wrong_target`). Only the close that the batch itself sends is tracked.
- **Testing in a real microVM in CI:** too slow and heavy for a string
  substitution. The fake server tests the same code path. A VM run stays a
  manual check (Verification).

## Risks

- **Old batches:** they don't use the new markers, so they behave as before.
  The only change in output is that `@last`'s error text comes from the shared
  `why` table. It keeps the same words.
- **A new check:** if `build.yml` or another CI list enumerates checks, the
  new one may need adding there. The plan checks this.
  - #1574 was bitten by an exact list.
- **Hosts:** the script is packaged into every Nixarchy host's skills, and it
  reaches p620 and razer through the normal nixarchy bump. Nothing changes on
  the host path.

## Verification

- `nix build .#checks.x86_64-linux.mirror-vm`, with the cases above.
- `nix build .#checks.x86_64-linux.session`, which lists the skills.
- The CI checks on the PR pass (no admin merge).
- **Manual, in a VM on p620:**
  1. `nixarchy vm create mirror-test --template nixarchy-desktop`, then run it.
  2. Send one `mirror-vm` batch (launch foot with `@generation`, type with
     `@window`, then a screenshot).
  3. The PNG shows the typed output.
  4. Stop and remove the VM.

Review input: Codex (gpt-6-sol) and agy (model not reported) reviewed the
draft. Taken from it:
- clearing `@window` on close (address reuse);
- checking the grant-loop result;
- nesting the `None` check under the marker match;
- the blank-string check;
- the error-text, `control`, missing- or bool-generation and empty-window
  cases;
- proving the check fails without the change.

Not taken:
- **Narrowing `generation` sources:** the source shows they all mean the same
  number.
- **Testing a mixed `window` + `candidates` result:** the source shows it
  can't happen.
