# Intent: a nightly failure always reaches its issue

## Problem

The nightly of 2026-11-18 (run 44228069452) had a real failure:
`keyboard-boot` timed out (#1855). Its report job then failed to file it:

```
GraphQL: Body is too long (maximum is 65536 characters) (createIssue)
```

So the one job whose purpose is that a 03:00 failure does not cost a day
cost six hours, and the failure was found by hand.

The body carried the digest from `.github/scripts/nightly-digest.sh` (#1711):
83,268 characters against `DIGEST_MAX=50000`, naming **1,899** derivations as
failure roots (`stage0-posix-1.9.1-source`, `mescc-tools-*`, …) for one VM
check. The digest job also ran 4 h 20 min (05:07 → 09:26) on a self-hosted
runner fetching those logs. Two defects:

1. **False roots.** A root is any derivation in the target's build closure
   (`nix-store -qR <drv>`) whose outputs are not in the store and for which
   `nix log` returns text. `nix log` also asks the substituters, and
   cache.nixos.org serves logs of its own builds, so every build-time
   dependency that was substituted past (the whole bootstrap, for one)
   qualifies. Measured on `stage0-posix-1.9.1-source`: output not in the
   store, no local log, `nix log` returns 771 bytes, and
   `nix log --option substituters ''` returns 0.
2. **The cap does not bound the digest.** Only excerpts spend the allowance;
   headings are counted first as fixed text, and `remaining` clamps to 0
   when they exceed it, so the digest grows with the number of roots without
   limit.

`checks.nightly-digest` has a cap case (`c7-cap`) with four roots. It cannot
vary the variable that broke (§3), so it passed throughout.

## Proposed outcome

- The digest names the derivations that actually failed or were cut off
  this run, not every dependency a cache has a log for.
- The digest never exceeds `DIGEST_MAX`, whatever the number of roots: past
  the cap it says how many it left out.
- The report job's issue body or comment always fits GitHub's limit, so a
  failure is always filed, even if the digest misbehaves in a new way.
- `checks.nightly-digest` gains cases that fail on today's code: many roots
  under a small cap, and a closure member whose log exists only remotely.
- The digest job takes minutes, not hours.

## Affected users and systems

- `.github/scripts/nightly-digest.sh`, `tests/nightly-digest.nix` and its
  stubs and cases (`tests/nightly-digest/`).
- Possibly `.github/workflows/nightly.yml`'s `report` step, for a last-resort
  size guard on the body.
- The self-hosted digest runner on p620, which today spends hours on remote
  log fetches.
- Users are not affected: this is CI reporting only.

## Constraints

- `nightly.yml` is a workflow file. A guard in the `report` step is not a
  trigger, a required check or a timeout, but it changes the repository's
  watchdog, so it is called out for review in the PR (§11).
- The digest is evidence that must survive a deleted run (#1711, §13): a
  fix may shorten it, but it must still name the failing job, step and
  derivation, and an excerpt of the real failure.
- Whatever is cut is said to be cut, with a count (§4: a list that silently
  drops entries fails open).
- The new cases must be shown failing on today's script before the fix
  (§1).

## Open questions

1. A last-resort cut in the `report` step (truncate the body under 65,536
   with a note) in addition to fixing the script? The recommendation is
   yes: the digest is generated text, and the step that files the issue
   should not depend on it being well behaved.
2. Should a root be limited to derivations whose local log was written
   during this run (by timestamp), as well as local-only? Local-only is
   enough for today's failure; a timestamp also excludes old local logs of
   collected paths on a long-lived store. For the spec to decide, with a
   measurement of how many such logs p620 has.
