### The migration: the once-marker and the user's choice move with the id

**Design change from the intent.** The intent proposed rewriting
`shell.json` with `jq`, as upstream's Omapager migration does. That would
break the rule stated above the hook (`modules/home.nix:2178-2180`): the running shell
rewrites the whole file from memory, so a second writer loses updates. The
migration goes through the shell's own writer instead, the way the hook's
#946 path already does.

**What actually needs migrating.** The new id is itself a default, so
the enable-once path turns it on for anyone without its marker. A user who
had Hyprforge **on** gets it back with no migration at all. The one who
loses is a user who turned it **off**: they have the old marker and no new
one, so the default enables the new id against their choice.

So the hook (`omarchy/hooks/post-boot.d/default-plugins`) gains a rename
table, `aziz.hyprforge` → `nixarchy.hyprlandsettings`. For each pair,
when the old marker exists and the new one does not:

1. Read `shell.json`, **read-only** with `jq`: is the old id in
   `.plugins[].id`? That is the user's last choice. (On p620 today it is,
   as `{"id":"aziz.hyprforge"}`.)
2. Move the marker: `$state/<old>` becomes `$state/<new>`. The new id
   then leaves `todo`, so the default path does not touch it.
3. If the old id was on: `omarchy-plugin-enable <new>`, then
   `omarchy-plugin-disable <old> || true`. That clears the old entry if
   the shell still knows it, and is harmless if not.
4. If it was off: nothing. It stays off.

This runs after the shell answers `ping`, beside the #946 loop, and counts
toward the hook's "anything to do" test. Settings, profiles and history
carry over by themselves: hyprsettngs' state paths (`~/.config/hypr/
hyprforge*`, `~/.cache/hyprforge`) do not derive from the id (its spec
2026-09-29-rename-plugin-id §1). Hyprforge has no bar placement, so there
is no slot to keep.

**Mode A (§7):** without defaults, the hook does not exist
(`lib.mkIf (resolvedDefaults != { })`). Without the old marker, the
table does nothing.

## Alternatives rejected

- **`jq` edits of `shell.json`:** a second writer beside the running
  shell (above).
- **A new home activation script:** it runs before the shell exists, so it
  cannot use the shell's writer. The hook already runs at the right moment.
- **Keeping the old id through an override patch:** a patch that is
  reapplied at every bump, against hyprsettngs' own decision.
- **A generic rename option:** one rename, in one table. Generalise when a
  second one comes.

## Risks

- **The old entry may stay in `shell.json`.** hyprsettngs' spec records
  that `omarchy plugin disable` fails with "not known" once the plugin's
  files are gone, and after the switch they are. The plan measures it in
  the VM and on p620. An orphan `{"id": …}` for a plugin with no files is
  what the #946 path already leaves; the plan checks the shell loads cleanly beside it.
- **The 92 commits** include hyprsettngs' own fixes (write
  serialisation, `SafeWriter`, baseline parsing). `checks.plugin`,
  `checks.session` and `checks.qml-color-qualified` cover loading; the
  panel's behaviour is the fork's own CI.
