# Spec: a form for every kind of report, not only bugs

## Design

Three new forms beside `bug.yml`, in the same GitHub issue-form YAML, each
carrying `bug.yml`'s versions and existing-issues fields verbatim so reports
are comparable.

- **D1. `install.yml` — "Install or ISO failure".** Label: `iso`.
  Fields, in order:
  1. *What happened, and where it stopped* (required) — the installer's last
     screen or output.
  2. *How you installed* (required dropdown): from a release ISO, from
     `nixarchy-reinstall-iso`, from an existing NixOS with `--from-repo`, or
     other.
  3. *Which image* (required) — the release tag or ISO filename, since an
     image older than the tree is the most common cause.
  4. *Disk mode* (required dropdown): whole disk, or free space beside another
     OS.
  5. *Encrypted?* (required dropdown): yes or no.
  6. *The machine* (required) — firmware (UEFI or BIOS), disk (`lsblk`), and
     whether it is a VM.
  7. *Versions* and *existing issues checked*, `bug.yml`'s wording.

  The minimum disk is 32 GiB as of #708, and the form says so above the disk
  fields, because a too-small disk is now a refusal a user will otherwise
  report as a bug.

- **D2. `request.yml` — "Feature or package request".** Label: `enhancement`.
  1. *What you want, and what you would do with it* (required).
  2. *What Omarchy does today* (required) — whether upstream already has this
     on Arch, which decides whether it belongs here at all.
  3. *Is it in nixpkgs?* (required) — the attribute name, or "not packaged".
     For a package request that is the whole answer.
  4. *Existing issues checked*, `bug.yml`'s wording.

  No versions field: a request is about what does not exist yet.

- **D3. `docs.yml` — "Documentation".** Label: `documentation`.
  1. *Which page* (required) — the manual page, README section or wiki page,
     as a link.
  2. *What it says, and what it should say* (required).
  3. *Existing issues checked*.

  It also carries the note that the wiki is a separate repository no check in
  this one can see (AGENTS.md §12), so a wiki fix may be made there directly.

- **D4. `config.yml` unchanged.** The routing links stay above the forms in the
  chooser, which is where GitHub puts `contact_links`. Each form repeats the
  Arch question in its own markdown header where it applies — `install.yml` and
  `request.yml` do, `docs.yml` does not, because this repository's manual is
  not upstream's.

- **D5. Labels are the ones that exist:** `iso`, `enhancement`,
  `documentation`. No new label is created, which would be a repository setting
  (AGENTS.md §11).

- **D6. Milestones stay a triage step.** GitHub forms cannot set a milestone, so
  §12's "every issue gets a milestone when it is filed" remains on whoever
  triages, and the nightly's `board` row is what catches a miss. Stated here so
  it is a decision rather than an oversight.

## Alternatives rejected

- **One combined "request" form** covering features, packages and docs. Shorter
  chooser, but the three ask different questions, and a docs report does not
  need the nixpkgs question.
- **Markdown templates** instead of forms. They cannot make a field required,
  which is the whole reason for this change.
- **A form that sets a milestone.** Not supported by GitHub.
- **A check that the forms are valid.** GitHub validates them on push and shows
  a broken form as an error in the repository's issue chooser. A local YAML
  lint would assert syntax, not that the chooser works, and there is no
  offline way to assert the latter — see Verification.

## Risks

- **A broken form hides the chooser.** GitHub reports it in the repository
  settings and falls back to blank issues; the fix is a commit. Verified by
  opening the chooser after merge.
- **More forms, more friction.** Mitigated by `blank_issues_enabled: true`,
  which stays: someone who does not fit a form can still file.
- **Label drift.** If a label is renamed later, a form silently sets nothing.
  Named here so the rename is known to touch these files too.

## Verification

Deliberately thin, and the intent says why: this is documentation, and the only
mechanical claim is that GitHub accepts the YAML.

- `yq`/`python -c 'import yaml'` parses each new file (a syntax check, no more).
- After merge, open `https://github.com/olafkfreund/nixarchy/issues/new/choose`
  and confirm four forms and the three routing links appear, and that each form
  submits with its label. That is a human step, stated rather than automated.
- No check is added, so `build.yml`'s coverage guard is untouched.
