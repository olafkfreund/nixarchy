# Intent: Bump nixi to 0.10, the Omarchy overlay card

## Problem

Every nixarchy desktop ships nixi (`services.nixi.enable = lib.mkDefault true`
in `modules/home.nix`), pinned at nixi-nixarchy `a141b16`, which is 0.9.7: a
browser widget served from a loopback server on port 8642, a bar snowflake
that opens it, and push-to-talk voice input.

nixi 0.10 (olafkfreund/nixi-nixarchy#8) replaces all of that with a native
Omarchy overlay plugin built on omarchy-ask's card: no server, no port, no
voice, answers grounded in the local manual, a tour and learning path, Guide
and Mechanic trust enforced in the bridge, and Claude, Codex or OpenCode as
the agent. It already runs on p620 and razer, but only because nixos_config
overrides nixarchy's `nixi` input (nixos_config#1828). Everyone else still
gets 0.9.7, and nixarchy's own checks describe the 0.9 layout:

- `tests/options.nix` expects, with nixi on, `systemd.user.services ? nixi`
  and `xdg.configFile ? "nixi/ui.html"`. 0.10 has neither.
- `nixiBarWidget` looks for the plugin's `manifest.json` as a per-file link;
  0.10 links the plugin as one directory and the bar button as a second
  plugin.
- `modules/home.nix` comments (the bar widget as nixi's "front door", "a
  server on 8642") and `docs/manual/getting-started.md` (which names
  `services.nixi.port`) describe 0.9.

## Proposed outcome

- nixarchy pins a nixi 0.10 commit on nixi's `main`.
- A rebuilt nixarchy desktop has the overlay card and the bar button plugins
  installed (enabling them stays the user's one-time Setup > Plugins action,
  as today), and no `nixi.service`, port or `ui.html`.
- An existing desktop upgrades without a manual step: nixi's module removes
  the 0.9 plugin directory of Home Manager links before `checkLinkTargets`.
- `tests/options.nix` proves nixi is on by default and gone when
  `services.nixi.enable = false`, against the 0.10 layout.
- The docs describe 0.10, including the removed `port`/`voice` options.
- nixos_config#1828's override can then be removed.

## Affected users and systems

- Every nixarchy desktop (Home Manager, via `modules/home.nix`).
- `tests/options.nix`, `tests/plugin.nix` (sets `services.nixi.enable = false`),
  the install check that runs on p620's runners.
- `flake.nix` / `flake.lock` (the `nixi` input), `modules/home.nix` comments,
  `docs/manual/getting-started.md`, `README.md`.
- p620, razer (already on 0.10 through nixos_config) and p510 (not yet).

## Constraints

- Pin a commit on nixi's `main`, never a branch (the rule in `flake.nix`).
  So this waits for nixi PR #9 to merge.
- nixarchy must not start writing `shell.json`: plugins stay installed-not-
  enabled, as `modules/home.nix` already promises.
- `services.nixi.enable = false` must still remove every trace.
- No behaviour change beyond nixi itself.

## Open questions

1. **Agents and unfree.** nixi 0.10 defaults `services.nixi.agents` to
   `[ "claude" "codex" ]`, and `claude-agent-acp` depends on the unfree
   `claude-code`. nixarchy allows unfree by default
   (`programs.nixarchy.allowUnfree = true`), but a user who sets it to false
   would fail to evaluate. Should nixarchy set `services.nixi.agents` to
   exclude `claude` when `allowUnfree` is false, leave nixi's default, or
   default to no pinned adapters at all (agents resolved from PATH)?
2. **Enabling the card.** nixarchy deliberately never enables plugins. The
   0.9 bar widget was reachable without the overlay; 0.10's card must be
   enabled before `nixi`, SUPER+H or the Help row do anything. Keep "installed,
   not enabled" and document it, or is the card an exception?
