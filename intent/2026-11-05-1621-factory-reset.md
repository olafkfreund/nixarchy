# Intent: Factory reset tells the truth, and does all of it or none of it

Everything here comes from reading the source. Neither
`omarchy-system-factory-reset` nor `nixarchy-factory-reset.service` was run.

## Problem

### 1. The menu says there is no snapshot, on every machine that has one

"Reset Computer" (`setup.reset`, line 280 of the installed
`omarchy-menu.jsonc`, 266 upstream) runs the command in a floating terminal
with no `sudo`. `has_baseline`
(`pkgs/omarchy/nix-bin/omarchy-system-factory-reset:96-105`) asks
`btrfs subvolume list -r /` with errors discarded. That command uses the
tree-search ioctl (btrfs-progs 7.1, `cmds/subvolume-list.c:847`), which needs
root, as the script's own `--help` says. So "could not ask" reads as "none".

The user is told there is no snapshot, that it "cannot be created now", and
that the last resort is a reinstall. All untrue. It fails safe: nothing changes.
The "This needs root" message was meant to be reached after the refusals, and an
unprivileged run on a machine with a baseline never reaches it.

Neither check can see this, because neither varies privilege (§3): the fake
`btrfs` in `tests/options.nix:5096` answers any caller, and `tests/install.nix`
runs the script as root.

### 2. The reset can stop half done, and says nothing either way

`installer/host.nix:395` promises "either the whole reset happens or none of it
does". `:453-456` says a failure leaves "the state it was already in", and
`:520` says "at no point is there no @home". None of the three holds. The
request is deleted first (`:469`), so there is no retry, and the unit runs under
`set -e`:

| fails at | what the machine is left with |
|---|---|
| before `:512`, or `cp` at `:512` | nothing changed (at most a stray `/var/lib.factory-new`) |
| `mv` at `:513` | nothing changed |
| `mv` at `:514` | **no `/var/lib` at all** |
| snapshot at `:529`, or `mv` at `:530` | **`/var/lib` reset, `/home` not** |
| `mv` at `:531` | **no `@home`**: `/home` has no `nofail`, so the boot should stop in emergency mode (inferred, not run) |
| receipt at `:537-538` | reset complete, no receipt saying where the files went |

**How likely is the `:529` failure? Low.**

- A missing subvolume cannot cause it: `:487-492` exits before anything changes.
- A name collision would need the same one-second stamp twice.
- No quota is configured in `installer/` or `modules/`, though a user could add one.
- Space is the realistic cause: metadata exhaustion, in the narrow band where
  the small `cp` at `:512` fits and the snapshot does not. Unmeasured. It matters
  because a full disk is a likely reason to want a reset.
- A power cut could also leave this state. The renames at `:530-531` may not be
  durable until the next btrfs commit, and the snapshot may already have
  committed `:513-514`. Inferred from btrfs's commit model, unmeasured.

**Is anything lost? No.** Every step is a rename or a copy. The old `/var/lib`
is at `/var/lib.before-reset-<stamp>`, and `@home` is either in place or at
`@home-before-reset-<stamp>`.

**What the user sees is the real harm.** They typed RESET and rebooted. The
machine boots and `/home` is full, so the reset appears to have done nothing,
while Bluetooth pairings, container images and databases are out of sight.
Nothing reports it: the unit has no `OnFailure`, and the receipt is only written
on success. The only trace is a failed unit. The same silence applies to the
more likely failures that change nothing.

**Recovery is undocumented.** `docs/`, the README and the skills do not mention
factory reset at all. Re-running the command should finish the job, and a second
`before-reset` directory would then hold the near-empty `/var/lib`, beside the
one the user wants. Nothing says so.

**Serious, not urgent:** a broken data-integrity promise with silent failure,
low likelihood, and nothing destroyed.

## Proposed outcome

- From the menu or a shell, the command never claims there is no snapshot unless
  it has asked and been answered. "I could not ask" is a different outcome.
- Any command failure in the unit leaves `/home` and `/var/lib` both reset or
  both untouched, and the comments say only what is true.
- A reset that fails tells the person, with what state the machine is in and
  what to do next.
- Each of these has a check that fails when the behaviour is broken (§1, §2).

## Affected users and systems

- Installer-laid machines with a baseline: the only ones with the unit
  (`installer/host.nix`) and the only ones given the false refusal.
- Older managed machines: same output, and true by accident. Stays correct.
- Mode A: unaffected. `checks.options` asserts the unit is absent there.
- Files: `pkgs/omarchy/nix-bin/omarchy-system-factory-reset`,
  `installer/host.nix`, `tests/options.nix`, `tests/install.nix`, possibly a new
  VM check.

## Constraints

- **Neither the command nor the unit runs anywhere but a disposable VM.** A VM
  is justified only because the kernel's behaviour (the real EPERM, a real
  snapshot failure, the boot with no `@home`) cannot be stubbed. Not during this
  intent.
- Nothing is deleted by the reset. `/etc/nixos` stays untouched.
- A failed reset must not fail the boot or retry on every boot (`:465-468`).
- The unit stays absent from Mode A, and both confirmations stay.
- Tests say which layer proves what:

  | layer | can prove | cannot prove |
  |---|---|---|
  | `tests/options.nix`, with a fake `btrfs` that refuses non-root | the refusal's wording and branches, cheaply | that real btrfs refuses |
  | stubbed `runCommand` over the unit's script | order of steps, only if the paths become injectable | ENOSPC, emergency mode |
  | `tests/install.nix` | the success path on real btrfs today; an unprivileged run could be added | failure paths, without slowing an install slot |
  | VM with a real btrfs root | real EPERM, an injected or real snapshot failure, the resulting boot | hardware |

- §5 applies to `tests/options.nix`: no heredoc inside its indented string.
- A later plan names only codex or agy as coders.

## Open questions

1. **Should the menu row work, or only tell the truth?** It has never worked, so
   making it work opens a destructive path for the first time. Options: elevate
   as upstream does (with its fixes omacom/omarchy#13047, #13316, #16032), or
   stop at a true "run this with sudo". *Recommend elevating:* the row offers a
   reset, and sudo plus both confirmations still guard it.
2. **Does the promise cover power loss?** *Recommend command failures only*,
   with the power-cut state stated honestly. Whether a rename exchange could
   narrow that window is for the spec.
3. **How is a failed reset reported?** *Recommend a failure receipt in
   `/var/lib/nixarchy`, shown by the command when next run*, with no login
   notification and no manual page.
4. **Where does the failure proof live?** *Recommend a small dedicated VM check
   with a real btrfs root*, leaving `install` alone except for one unprivileged
   assertion. It costs about 10-20 minutes per PR, because a new check runs on
   pull requests by default (§4).
