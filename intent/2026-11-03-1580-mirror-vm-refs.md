# Intent: one mirror-vm batch can launch an app and type into it

## Problem

`mirror-vm` runs a whole JSON batch over a single connection. The only value a
step can take from an earlier one is `"frame": "@last"`, the latest screenshot.
Two values that later steps need exist only once the batch is running:

- **`generation`**: `launch`, `window`, `a11y_act` and `clipboard` write
  require it. Each `mirror-vm` call makes a new grant, so the number changes.
  On 2026-11-03 I had to predict it: 2, then 5, then 8.
- **The new window's address**: an `input` that types must name its window,
  and only `launch`'s result gives that address.

So "launch foot, type a command, screenshot" took two batches, with the
address copied by hand between them. Measured: `launch` with a predicted
generation worked, and the `input` step in the same batch failed with
`invalid: typing must name the window...`.

`mirror-vm` already reads the generation (the `status` that confirms the
grant carries it) but throws it away.

## Proposed outcome

A batch can say `"generation": "@generation"` and `"window": "@window"` in a
step's `args`, just as it says `"frame": "@last"` today. The
launch-type-screenshot run works as one call with no values known
beforehand. A placeholder that has no value is refused before anything is sent,
and nothing is ever filled in silently.

## Affected users and systems

- `pkgs/omarchy/skills/ai-mirror/mirror-vm` and its `SKILL.md`, and any test
  that covers the script.
- Agents using the VM path on every Nixarchy host. The host path and
  ai-mirror itself are unchanged.

## Constraints

- **Stdlib Python only**, and the script stays small.
- **Explicit only**: no auto-fill of a missing `generation` or `window`. A
  missing `window` must still reach the server's "typing must name the
  window" refusal.
- **`@window` never guesses.** It is set only by a successful `launch` that
  returned exactly one window. A later `launch` that returns `candidates` or a
  note clears it, so it can't silently point at the previous app. `windows` and
  `wait` never set it.
- **A placeholder with no value is refused before anything is sent**, in the
  way `@last` before any screenshot is refused today.
- **The ownership gate stays in the guest server.** A stale or revoked
  generation is refused there, as now.

## Open questions

1. **Where `@generation` comes from.** Recommended: the grant's `status`, then
   updated from every successful result that carries an integer
   `generation` (`status`, `screenshot`, `input`). The server reports the
   current value, so a `control` step inside the batch stays correct.
   - Codex would take it from the grant only.
   - agy would update it.
2. **How exact the placeholders are.** Recommended: only the exact values in
   their own top-level keys, `args.generation == "@generation"` and
   `args.window == "@window"`, like `@last`. No substitution inside nested
   values.

Design input: Codex (gpt-6-sol) and agy (model not reported) both recommended
fixed placeholders over general step references (`@step3.result.window`: a
parser, fragile step numbering) and over auto-fill (it hides the target). Both
flagged the stale-`@window` case.
