# Intent: a theme change reaches kitty, and survives a rebuild in GTK

## Problem

Two theme bugs, both on `main` and on edge (quattro 81fd2d2). The owner's own
config currently overrides the Omarchy package to work around them
(olafkfreund/nixos_config#2370).

1. **kitty never gets the new theme.** `omarchy-restart-terminal` signals
   kitty with `pgrep -x kitty` / `killall -SIGUSR1 kitty`. nixpkgs' kitty is
   wrapped, so the running process is named `.kitty-wrapped`, and both
   commands match nothing. Measured on p620 on 2026-10-19: the running
   kitty's `/proc/<pid>/comm` is `.kitty-wrapped`, `pgrep -x kitty` finds
   nothing, and `pgrep -x '[.]?kitty(-wrapped)?'` finds both kitty processes.
   So kitty, and herdr inside it, keeps the old theme until restarted. The
   same function signals ghostty with `pgrep -x ghostty`, which has the same
   exposure if ghostty is ever wrapped.
2. **A rebuild undoes the GTK colours.** The `omarchy-theme-gnome` user unit
   (`modules/home.nix:1350`) runs `omarchy-theme-set-gnome` at login and on
   every Home Manager activation, and that sets `gtk-theme` to
   `Adwaita-dark`. With the theme engine (`programs.nixarchyThemeEngine`, from
   the `nixarchy-omatheme` input, on by default) targeting GTK, hyprchroma's
   `gtk.css` colours expect `adw-gtk3`. In a live theme switch hyprchroma runs
   last and wins. After a rebuild or a login, nothing runs it again, so GTK
   apps lose the theme's colours.

## Proposed outcome

- Changing the theme reloads kitty's colours in every running kitty, without
  restarting it. Ghostty gets the same treatment, so a wrapped ghostty does
  not regress later.
- After a rebuild or a login, GTK apps keep the theme engine's colours.
- Each fix has a check that fails without it (§1), at the cheapest layer that
  can see it (§2).
- The owner's config can then drop its Omarchy override.

## Affected users and systems

- Everyone with kitty as a terminal: the bug is in a vendored Omarchy script,
  so it is a carried substitution in `pkgs/omarchy/default.nix`.
- Everyone with the theme engine's GTK target on, which is the default when a
  user is set: `modules/home.nix`'s `omarchy-theme-gnome` unit.

## Constraints

- **Bug 1 is NixOS-specific** (nixpkgs' wrapper renames the process), so the
  fix is carried here with `--replace-fail`, and not reported upstream.
- **The bug-2 fix runs only when the engine's GTK target is on**, so Mode A
  machines (theme engine off) are untouched.
- **Bug 2 depends on the `nixarchy-omatheme` input's options.** The spec
  must read how its GTK target is exposed, rather than assume a name.
- **Edge:** put each change where `main` and `edge` agree, and prove it with a
  trial merge into `edge-candidate` before opening the PR (the #1350 and
  #1368 lesson).

## Open questions

- **Bug 2's hook: on the unit, or in the engine?** The issue proposes an
  `ExecStartPost` that re-runs `hyprchroma --target=gtk` on
  `omarchy-theme-gnome`. Making the engine run after that unit
  (`After=`/ordering on its own unit, inside `nixarchy-omatheme`) would be
  cleaner, but it is a change to another repository. I propose the
  `ExecStartPost` here, guarded by the engine's GTK target, unless the spec
  finds the engine already has a unit to order against.
- **One PR or two?** I propose one, since both are theme-switch bugs reported
  together, and the owner's override goes away only when both land.
