# Intent: T3 Code follows the Omarchy theme when installed through apps

## Problem

On Arch, Omarchy's installer `omarchy-install-ai-t3-code` does three things
after it installs T3 Code (lines 70-82):

1. creates `~/.t3/userdata`;
2. publishes the current palette with `omarchy-theme-set-t3code`, which writes
   `userdata/themes/omarchy.json`;
3. selects that theme with `t3 theme set omarchy --base-dir "$T3CODE_HOME"`.

With `programs.nixarchy.apps.t3-code.enable` (`data/apps.nix:466-475`,
`attr = "t3code"`), none of this runs, so T3 Code keeps its built-in theme:

- `omarchy-theme-set` calls `omarchy-theme-set-t3code` on every theme switch.
- That script exits early while `~/.t3/userdata` does not exist.
- Even once the folder exists, nothing selects the theme.

This was found on a real machine (nixos_config #2973) and fixed downstream with
a Home Manager activation entry. That fix has been live on p620 since
2026-11-16. It covers one user on one flake. Every other Nixarchy user with
`t3-code` enabled has the same gap.

## Proposed outcome

With `programs.nixarchy.apps.t3-code.enable = true`:

- `~/.t3/userdata/themes/omarchy.json` holds the current palette, and T3
  Code's selected theme is `omarchy`. This holds from the first activation on
  a fresh install, because it runs after the first-run theme step
  `nixarchySeed`, and on every later switch or boot, with no manual step.
- The theme id can be changed by an option, so that a richer theme publisher
  (nixos_config #2974, T3 Code Thememaxed's `omarchy-plus`) can be selected
  instead. When that theme's file does not exist yet, the step falls back to
  `omarchy`.
- With `t3-code` off, nothing changes: no activation entry and no `~/.t3`
  folder. This is Mode A's off state.
- Downstream, nixos_config can delete its #2973 module after a nixarchy bump.

## Affected users and systems

- Every Nixarchy user with `apps.t3-code` enabled, in both Mode A and Mode B.
- Files:
  - `modules/home.nix`: an activation entry beside the other per-app entries,
    such as `nixarchyNixdZed`;
  - the theme id option, either in the per-app submodule in `modules/apps.nix`
    (`appModule`, which today has `enable`, plus `package` for apps with an
    `attr`) or at the top level (see open question 1);
  - `tests/options.nix`: the option in both states;
  - a behaviour check;
  - docs, for the manual's lists of options and apps.
- Downstream: nixos_config's
  `hosts/common/nixos/omarchy-t3code-theme.nix` and
  `t3code-theme-script.nix`, removed after the bump.

## Constraints

- **Mode A.** No definition, folder or activation work unless `t3-code` is
  enabled. The theme option needs a `checks.options` assertion in both states.
- **Proven downstream behaviour carries over.** The #2973 work was reviewed
  three times and tested with a 10-case check and on p620:
  - check for missing tools first, then create the folder, then require a
    staged palette;
  - publish with Omarchy's own script, and stop if it fails;
  - select only when the theme differs, so `defaultThemeSetAt` stays put;
  - `timeout -k`, with output written to a file, not a pipe;
  - always exit 0, so a T3 Code problem never fails a switch;
  - go through Home Manager's `run`, so dry runs change nothing.
- **Tools come from packages, not from `PATH` guesses.** Upstream can name
  them directly. `writeShellApplication` takes `runtimeInputs`:
  - `cfg.package`, for `omarchy-theme-set-t3code`;
  - `apps.t3-code.package`, the T3 Code package the apps module installs;
  - `coreutils`, `gnugrep` and `jq`.

  Downstream had to fall back to `/run/current-system/sw/bin`.
- **§1 of `CLAUDE.md`.** The behaviour check must be shown to fail: break each
  rule, show the failure, restore it. Use mutation tests, as downstream did.
- **Ordering.** The step must run after `nixarchySeed`, which stages the
  first-run theme headless. The entry name `nixarchySeed` lives in this repo,
  so renaming it later must not silently lose the ordering.

## Open questions

1. **Option name and place.** The option is a string, default `"omarchy"`.
   - `programs.nixarchy.apps.t3-code.theme` would sit beside the app's
     `enable`. But `appModule` is shared by every app, and its only conditional
     option today is `package`, which applies to every app with an `attr`. A
     sub-option for a single app would be a new pattern.
   - Proposed: a top-level `programs.nixarchy.t3code.theme`, so the shared
     submodule stays the same for every app.
2. **Force or seed.** Downstream forces the theme id back on every activation,
   by the owner's decision. For every Nixarchy user, a theme picked in the
   T3 Code app would then revert at the next switch or boot. Proposed: keep
   forcing, because declarative means the config wins. Users who want an
   in-app choice can set the option to `null`, which only publishes and never
   selects.
3. **Fallback to `omarchy`** when the configured theme's file is missing. This
   was decided in #2974's draft and is not yet implemented downstream.
   Proposed: include it here, so #2974 can build on upstream.
