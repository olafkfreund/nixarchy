# Spec: stable moves to Omarchy v4.5.0-rc1, for the owner's machine and the users who want 4.5 now

Decided in the intent:
1. `main` carries rc1. Installed machines on `release` are untouched, and
   opt-in users follow `main`.
2. Cut v4.0.6-1 first.
3. The nightly bump follows RCs as well as final releases.

## Found while specifying: a `v*` tag moves `release`

`release.yml` fast-forwards `release` to any pushed `v*` tag
(`README.md:750`, "It moves only when a `v*` tag is pushed";
`release.yml:552-576`). Two consequences:

- **Cutting v4.0.6-1 releases Omarchy 4.0.6 to every installed machine.**
  `release` is on v4.0.5 today. This is the release you already had
  pending, and it is a normal one, but it is a release, not only a
  rollback marker. **Approving this spec approves that release.** If you
  would rather not ship 4.0.6 to everyone now, say so: the rollback
  target can be the commit a53f1189 instead, and decision 2 becomes
  "skip".
- **No RC tag is cut.** A `v4.5.0-rc1-1` tag would move `release` and ship
  the RC to everyone, which contradicts decision 1. Opt-in is "follow
  `main`", which the manual already documents
  (`docs/manual/omarchy-channels.md:114`: a bare `github:olafkfreund/nixarchy`
  input is `main`). So `release.yml`, its tag guard and
  `release-candidate.sh` stay **unchanged**. Both reviewing models had
  planned to widen them for a tag.

## Design

### 1. Tag v4.0.6-1 on main's current head

Cut the tag the way the weekly release-candidate issue describes, on
a53f1189, the tip of `main` before anything below lands.
`release.yml`'s guards apply as usual: the tag must not be behind `main`,
and its version must match the build.

### 2. Merge edge into the task branch, then pin the rc1 tag

- `git merge origin/edge` into `feat/1403-stable-4.5-rc1`, as a real
  merge. That brings in edge's 51 carries with their history, so edge's
  nightly merge of `main` does not replay them.
- Then set `flake.nix:81` to `github:basecamp/omarchy/v4.5.0-rc1` and
  `flake.nix:540` to `omarchyVersion = "4.5.0-rc1"`, and update only the
  `omarchy` lock input. The lock must resolve to 03ff1eff.
- **Edge-only machinery stays out:**
  - edge's sha pin and its `edge-YYYYMMDD-rev` version, replaced by the
    lines above;
  - edge's `review-pins` expectation of a rev pin (edge's
    `tests/review-pins.nix` diff), which goes back to main's
    tag-pin form.
- **Edge-only code that is harmless on main stays:** the `edge-*` branch
  of the ISO label (it never matches a release version), and every carry,
  because each one is a quattro adaptation that rc1 needs. #1386's agent
  accounts, #1398's fixes, omasnap, the language picker and the new
  notifications all become main's.
- The one upstream commit between rc1 and edge's pin (0a7beb7) changes
  two keybinding lines (`default/hypr/bindings/{applications,utilities}.lua`)
  and the upstream manual. No nixarchy file names either line, so no
  carry should need a change. The full check list on the pinned tree
  proves it.

### 3. The nightly bump follows the newest release, RCs included, and never goes backwards

`omarchy.yml`'s "Find the newest Omarchy release" step (:49-68) moves
into a script, `.github/scripts/omarchy-newest.sh <current>`. The
script:
- reads `gh api repos/basecamp/omarchy/releases --paginate` (prereleases
  included, drafts excluded);
- keeps the tags that match the existing anchored tag regex (:59);
- prints the newest one. Versions are compared with `sort -V` after
  mapping the first `-` to `~`, so the order is
  `4.0.6 < 4.5.0~rc1 < 4.5.0~rc2 < 4.5.0`. Plain `sort -V` ranks
  `4.5.0` *before* `4.5.0-rc1` (measured), which would block the final
  release;
- prints `changed=false` unless that newest tag is strictly newer than
  `current`;
- refuses an empty list or an empty answer, as the step does today
  (#1268 and the 403 lesson in its comments).

The workflow step calls the script and keeps its outputs (`latest`,
`current`, `changed`), so the rest of `omarchy.yml` does not change.

`checks.omarchy-newest` (new, a `runCommand`) runs the script against a
stubbed `gh` with these cases:

| current | releases | result |
|---|---|---|
| `v4.5.0-rc1` | `v4.0.6` | no change (today's code would downgrade) |
| `v4.5.0-rc1` | `v4.5.0-rc1` | no change |
| `v4.5.0-rc1` | `v4.5.0-rc2` | bump |
| `v4.5.0-rc1` | `v4.5.0` | bump |
| `v4.0.6` | `v4.5.0-rc1` | bump |
| any | an empty list, or a malformed tag | refuses |

### 4. The ISO label accepts an RC version

`installer/cd.nix:588`: the release path becomes
`lib.toUpper (lib.replaceStrings [ "." "-" ] [ "_" "_" ] version)`, giving
`NIXARCHY_4_5_0_RC1` (18 characters) and `NIXARCHY_4_5_0_RC1_NET` (22).
The `edge-*` branch stays. The existing assertions (32 characters,
`[A-Z0-9_]`) stay and are the check.

### 5. Documentation

- `docs/manual/omarchy-channels.md`: one paragraph saying that `main`
  now carries Omarchy v4.5.0-rc1 while `release` stays on the last
  release, how to follow `main`, how to go back (pin `.../release` or
  `.../v4.0.6-1`, then roll back the generation first if already
  switched), and that a generation rollback does not undo what 4.5 wrote
  to `~/.config`.
- The README's channel section gets one matching sentence. Run
  `readme-counts.sh` after the build, because the counts may move with
  the new tree.
- After merge, a Discussions post saying the same.

### 6. Edge afterwards

The next `omarchy-edge` run merges main, keeps quattro's pin, and edge's
carry delta drops to its pin. Edge stays green, which is that run's own
check.

## Alternatives rejected

- **An RC tag for opt-in:** it moves `release` and ships to everyone
  (above). Adding a "do not move `release` for RC tags" rule to
  `release.yml` would work, but it is CI surface nobody needs while
  "follow `main`" exists.
- **Re-porting rc1 onto main by hand:** edge has already done it and is
  green. A re-port would repeat 51 commits of work.
- **Pinning 0a7beb7 instead of the tag:** the nightly bump, `review-pins`
  and the release notes reason in tags.
- **`releases/latest` with a no-downgrade guard only:** it can never see
  rc2, so it contradicts decision 3.
- **Moving `release` to the RC:** that is decision 1's option (b),
  declined.

## Risks

- **`main`'s users get an RC.** Anyone already following bare `main` gets
  4.5 at their next update without asking. The manual has always called
  `main` "every merge, ahead of releases", but the announcement must
  say it.
- **#1400 (087f73d, `appearance.*`)** becomes the next bump's problem
  on `main` too, because rc2 will probably contain it. Its intent should
  be revisited for "main and edge", not edge only.
- **The thin install-phase margin** (3,109 bytes after #1398) carries
  over to main. `install-phase-budget` is on the list.
- **VM checks cannot see** graphics, docking, notifications or firmware
  on real hardware. The owner's machine is the hardware check, and the
  previous generation stays bootable.
