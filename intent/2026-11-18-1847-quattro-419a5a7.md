# Intent: edge adopts quattro 419a5a7 (agent launchers, herdr update check, Pi 4, read-only keyboard sysfs)

## Problem

Edge is held on quattro `3b36b9e` (#1847). Two edge runs tried newer
commits and stopped on the ledgers, not on a broken build:

- run 44144714540 at `3437cfb`;
- run 44168041467 at `92deb43`, which added a third failure.

Upstream has since reached `419a5a7`: 26 commits and 203 files past edge's
pin, 14 of them past `92deb43`. The failures known so far, all at `92deb43`:

- `nixarchy-omarchy-package-ledger`: `raspberry-pi-4-bluetooth-firmware` is
  in `install/omarchy-other.packages` (used by
  `install/hardware/raspberrypi/raspberry-pi-4.sh`) and has no row in
  `data/omarchy-packages.nix`. It is aarch64 Pi hardware, which x86_64
  nixarchy never reaches.
- `nixarchy-user-migrations-ledger`:
  - `omarchy-agent-local-launchers` is a new command a migration runs, with
    no row in `data/user-migration-commands.nix` (a file that exists on
    `edge` only). It writes `.desktop` files
    and SVG icons under `~/.local/share` for each local model set up, and
    removes them when the model goes;
  - `1794931275` gives each agent harness already installed its own launcher
    in `~/.local/share/applications`, then redraws the icon set;
  - `1794938310` appends `[update] version_check = false` to
    `~/.config/herdr/config.toml`, on the grounds that "pacman updates
    herdr". It leaves symlinked configs alone, and any config that already
    has an `[update]` table.
- `nixarchy-bin-ledger`: three allowances no longer match anything and must
  be pruned: `omarchy-keyboard-toprow` (`modprobe`) and
  `omarchy-toggle-hybrid-gpu` (`etc-write`, `systemctl-system`). Upstream
  changed both scripts, the first for read-only sysfs (#19013).

The 14 later commits also touch T3 Code theming, the keyboard and installer
tests, T2 initramfs and boot images, Pi 4 DDC brightness, and help for
local-model themes and apps. Any of them may add failures that the ledger
failures hid. The spec lists the full set from a local build at `419a5a7`,
not from this list.

What this changes for a user, as far as is known:

- **Herdr's update check would be turned off for them.** Nothing in this
  repository sets `version_check` today. `modules/home.nix:2354` takes
  `pkgs.herdr` as it is, and the manual (`docs/manual/plugins.md:143`) says
  only that `herdr update` cannot write to the store. That is not the same as
  the check being off, so adopting upstream's suppression is a policy choice
  (question 2), not a formality.
- **Agent harnesses and local models get launchers of their own** next to
  Agent, written into the user's home.
- Pi 4 and T2 changes are for hardware nixarchy does not install on; the
  question is only how the ledgers classify them.

## Proposed outcome

- An edge run at `419a5a7` (or upstream's newest commit when the spec is
  written) promotes, so `edge` carries the batch and #1847 closes itself.
- Every new package, command and migration has a ledger row that says what
  nixarchy does with it, and the stale bin-ledger allowances are gone.
- What upstream's batch changes for a user works on nixarchy, or is
  deliberately declined, with the reason in the row. The herdr migration's
  fate depends on question 2.
- `main` is not affected: the rows are pin-derived, so they go on the edge
  carry (`edge-candidate`), per §8, with `flake.nix`'s two quattro copies
  and `flake.lock` pinned to the commit the rows describe.

## Affected users and systems

- Edge users (the `edge` branch and its release). `main` users are not
  touched until edge next merges to `main`.
- `data/omarchy-packages.nix`, `data/user-migration-commands.nix`,
  `data/user-migrations.nix`, the bin ledger, and possibly patches under
  `pkgs/omarchy/`.
- p620: the local builds follow the §6 tiers by check: cheap ones any time
  under the lock; the `omarchy` package when no `install` or edge `verify`
  job is in flight; VM checks and options shards only when no self-hosted
  runner is busy.

## Constraints

- A carry that classifies a new quattro commit must also pin it (§8):
  rows, `flake.nix`'s input `url` and `omarchyVersion`, and `flake.lock`.
- Push the carry to `edge-candidate` and dispatch with
  `from_candidate=true`, or check that `edge-carry.sh` picks it up by
  author (§8). Never force-push `edge` (§11).
- A fix to how Omarchy behaves belongs upstream, not in a patch here (§11).
- Every check the carry reaches is built locally before the push (§6), and
  under both pins: quattro, and `main`'s tag pin in a scratch tree with both
  `flake.nix` copies and the lock restored from `origin/main` (§8, "a carry
  is checked under both pins").
- Do not dispatch edge while an edge run is in flight: a newer dispatch
  cancels the running verification (§8).

## Open questions

1. Pin `419a5a7`, or whatever quattro's head is when the spec is written?
   The recommendation is the head at spec time, so this carry is not stale
   on arrival.
2. Herdr's version-check migration: adopt upstream's policy (users' herdr
   stops checking for releases, since `herdr update` cannot install one on
   NixOS anyway), or decline it and leave the check on? If adopted, upstream
   leaves any existing `[update]` table untouched, including a user's
   explicit opt-in, which seems right. Whether nixpkgs' herdr already turns
   the check off is for the spec to establish, before this is decided.
