# Intent: edge's tree builds and passes its checks under main's Omarchy pin

## Problem

`main` pins Omarchy at the tag `v4.5.0`; `edge` pins a quattro commit. A real
edge→main merge restores `main`'s pin on edge's tree (CLAUDE.md §8), so every
line edge carries has to hold under both pins, or be dropped by that merge.
Measured on the unchanged `edge-candidate` (`b654130`) with `main`'s pin
restored, during #1750:

1. **The package does not build.** `pkgs/omarchy/default.nix` (from #1485)
   runs `--replace-fail 'exec /usr/lib/omarchy-screensaver/omarchy-screensaver "$@"'`
   on `bin/omarchy-launch-screensaver`. That line exists in quattro and not in
   v4.5.0 (checked: 1 match against 0), so the build stops there, and every
   check that needs the package stops with it.
2. **Four checks fail once the build is unblocked:**

   | check | failure | where it comes from |
   |---|---|---|
   | `checks.user-migrations` | `1794165002 is not in the runner's list`. The test runs cases for migrations that only quattro has | #1736 and later carries |
   | `checks.coexistence` | `qt-own-platform-theme`, because the fixture assumes qtengine, which v4.5.0 does not ship | #1736 |
   | `checks.menu-actions` | `install.ai.herdr` "reaches no hazard: stale" | a row for a quattro menu entry |
   | `checks.bin-ledger` | `omarchy-agent-local`, `omarchy-install-dictation-hex`, `omarchy-keyboard-toprow`: an allowance "no longer matches" | rows for quattro's versions of those commands |

Nothing is broken on either branch today. The cost arrives at the next
edge→main merge, the one that moves `main` to quattro. That merge would meet
these failures one red check at a time, after the package build is fixed by
hand.

## Proposed outcome

- **Code and tests read the pin.** The package, `checks.user-migrations` and
  `checks.coexistence` derive what they do from the pinned source, the way
  `hasPapers`, `hasQtengine` and #1750's `hasFiles` already do. Under either
  pin, they build and pass.
- **Each ledger row says which pins it applies to.** For `data/menu-actions.nix`
  and `data/bin-ledger.nix`, whose rows describe upstream text that differs
  between pins, a row is either valid under both pins or marked as pin-only,
  in a form the checks understand. A stale row is still an error under the
  pin it claims.
- **The property is checked.** A check proves that edge's tree is clean under
  `main`'s pin, so a new edge carry that breaks it fails on edge, not at merge
  time. This is the §4 "prefer a check to a paragraph" rule.
- #1752 closes.

## Affected users and systems

- No user-visible change on either pin. Edge's package, and `main`'s, build
  the same derivations as before. That is measured, not assumed, because both
  pins are evaluated before and after.
- Edge CI: `omarchy-edge.yml` gains, or reuses, a job that evaluates edge
  under `main`'s pin.
- Files: `pkgs/omarchy/default.nix`, `tests/user-migrations/run`,
  `tests/coexistence/default.nix`, the two ledgers and the checks that read
  them, and a workflow or a check.

## Constraints

- The work lands on `edge` through an `edge-candidate` carry, as #1750 did. The
  artifacts go to `main` by their own PR.
- A change to a workflow is a CI-gate change (§10). It is proposed in the PR,
  and the owner merges it.
- `--replace-fail` stays exact. A pin-gated substitution keeps failing loudly
  under the pin it is meant for (pkgs/AGENTS.md).
- Every new or retargeted check is shown to fail first (§1).

## Open questions

1. **Pin-only ledger rows.** Option A (my recommendation): a `pins = [ "quattro" ]`
   field, or something like it, on the row; the check skips that row under the
   other pin and still fails it when stale under its own. Option B: list the
   rows that the edge→main merge drops, in a file the merge reads.
2. **Where the both-pins check runs.** Option A (my recommendation): a job in
   `omarchy-edge.yml` that restores `main`'s pin and builds the cheap tier plus
   the package. Option B: a nightly-only job, which is cheaper but finds a break
   a day later.
