# Intent: Turning on SSH from the menu leaves password logins on

## Problem

Upstream's v4.5.0 `bin/omarchy-setup-security-sshd` authorizes a key, writes
`PasswordAuthentication no`, and only then starts sshd, so the machine never
listens with passwords on. Ours does none of that.

- `setup.security.sshd` runs `nixarchy-service-enable openssh`
  (`modules/apps.nix:898-899`), and `install.service.openssh` runs the same
  command (`modules/apps.nix:1092`). That command uncomments one line in
  `services.nix` (`modules/apps.nix:1764` onward). It asks for no key.
- The catalogue's openssh row is `kind = "plain"`, so nixarchy adds nothing
  beside `services.openssh.enable = true` (`data/services.nix:11-16,73-81`).
- Nothing in `modules/`, `data/` or `installer/` sets `PasswordAuthentication`.
- nixpkgs defaults it to `true`, and `openFirewall` to `true`
  (`nixos/modules/services/networking/ssh/sshd.nix:312-314,547-549` at the
  locked nixpkgs).

Measured with a minimal evaluation at that nixpkgs, `services.openssh.enable =
true` alone gives `PasswordAuthentication = true` and PAM `unixAuth = true`.
So after Apply, port 22 is open and accepts the account's password, with no
rate limit (`docs/manual/security.md:66-69`).

Two pieces of our text make it worse, because they tell the user the opposite
or describe a route that is gone:

- `data/services.nix:80` says "NixOS defaults to keys only, not passwords". That
  is false, and it is what the menu row shows (`svc.note`, `modules/apps.nix`
  row builder at 1085-1100) on `install.service.openssh`.
- `docs/manual/security.md:55-59` says the menu row is upstream's script and
  cannot finish. #1304 replaced it.

## Proposed outcome

A user who turns on SSH from the menu ends up with a machine that takes key
logins and refuses password logins, and cannot lose remote access to their own
machine by doing so. A user who set their own `services.openssh` options sees
no change.

## Affected users and systems

- Anyone using either menu row. This is opt-in: no default install enables sshd.
- **No key yet.** The documented way to add one is `ssh-copy-id you@desk`
  (`docs/manual/remote-desktop.md:49-50`), which needs a password login. With
  passwords off it fails, so `desk` can only get a key from its own console or
  from configuration. A machine at hand loses nothing: local login is not sshd.
  A machine reachable only by ssh could be cut off.
- **Machines that already turned SSH on** and log in with a password. If their
  behaviour changes on upgrade, the first rebuild is the lockout.
- gliff users. The machine they connect to needs sshd, and the widget already
  requires a key (`docs/manual/remote-desktop.md:50-52`).
- sops users who enable sshd only for its host key (`modules/secrets.md:91-104`).
- MicroVM guests, where `services.openssh.enable` is a default from `sshPort`
  (`modules/services/microvm.nix:296`) and the `dev` account has no password.
- `omarchy-setup-security-sshd` run by hand. It stays vendored unchanged
  (`data/bin-ledger.nix:593-597`). The NixOS `sshd.nix` has no `Include` or
  `sshd_config.d`, so its hardening file would not be read here.

## Constraints

- **Must use `mkDefault`, and never override a user's setting (§7, §14).**
- **`mkDefault` alone does not satisfy "no change".** Measured, with a module
  setting `lib.mkDefault false`:

  | the user's own config | `PasswordAuthentication` |
  |---|---|
  | sets nothing | `false`: beats nixpkgs' option default, so a user relying on the default changes |
  | `= true` | `true` |
  | `= null` | `null` (PAM `unixAuth = false`) |
  | `= lib.mkDefault true` | evaluation error: same priority, conflicting values |

  So where the default applies decides who it reaches. Mode A must stay
  untouched by anything opt-in (§7).
- Evaluation cannot see `~/.ssh/authorized_keys`, which sshd reads
  (`authorizedKeysFiles` is `%h/.ssh/authorized_keys` and
  `/etc/ssh/authorized_keys.d/%u`). A check at evaluation sees only
  `users.users.<name>.openssh.authorizedKeys`.
- Nothing regenerates `services.nix` (`modules/apps.nix`, `nixarchy-service-enable`),
  so a changed template line reaches only rows not yet present.
- Coexistence (§14): the spec answers this with fixtures in
  `tests/coexistence/fixtures.nix` that can fail, covering a user's own
  `PasswordAuthentication = true` and `lib.mkDefault true`.
- A changed default is announced in the release notes and Discussions, with the
  migration step (§14).
- The false note and the stale manual section are corrected in the same change.
- Upstream's `ufw limit` has no equivalent here. Rate limiting is out of scope.

## Open questions

1. **Who gets the hardening?** Everyone with sshd through the nixarchy module,
   or only machines that turned it on through the menu? Recommended: only the
   menu route. The first changes Mode A users who rely on the nixpkgs default.
2. **What happens with no key?** Refuse as upstream does, or turn on with
   passwords off and tell the user how to add a key? Recommended: refuse, and ask
   for a key in the menu flow as upstream does (GitHub username or paste).
   Passwords-off with no key is the lockout this must not cause.
3. **Machines already enabled from the menu:** change them on upgrade, or leave
   them and tell them? Recommended: leave them on passwords and announce the
   one-line change. A silent lockout costs more than a delayed hardening.
