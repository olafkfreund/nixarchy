# Intent: a nixpkgs bump that breaks a commit-pinned input is caught, said out loud, and its fix proposed

## Problem

Nineteen flake inputs are pinned to a commit in `flake.nix`, and most of
them follow our nixpkgs. The nightly bump (`flake-update.yml`) moves nixpkgs
alone, on purpose: the other pins are deliberate. So when a nixpkgs bump
breaks one of those inputs, nothing can move the input. Nothing notices
either, until a pull request's CI goes red, and then a human has to find
both the cause and the fix by hand.

This has happened twice:

- **#1457 (2026-10-26).** nixpkgs 3ec6363 asserts on
  `boot.initrd.systemd.enable`. `microvm` (fdfc182) still set it, so
  `checks.microvm-template` and `.#microvm-agent` failed to evaluate.
  Upstream had removed it five days earlier, and our pin was 42 commits
  behind its `main`.
- **#1030.** `sops-nix` hit the same failure when nixpkgs removed
  `buildGo125Module`. The suite stayed green for 12 days.

Four gaps let this through, each checked against the tree:

1. **The pre-PR gate evaluates only two outputs.** `flake-update.yml:160`
   and the nightly canary (`nightly.yml:526-528`) evaluate only
   `vm-toplevel` and `reference-toplevel`. Neither reaches microvm,
   hypr-rdp/sops-nix or zen-browser.
2. **When that gate fails, it fails silently.** The job exits 0 and opens
   nothing, assuming upstream will fix nixpkgs by tomorrow. For an input
   pinned to a commit that never happens, so the nixpkgs bump would stop
   with no one told. `pkgs/review.sh:548-554` does not watch
   `flake-update.yml` either.
3. **The review misreports tagless pins.** `pkgs/review.sh:438-485` asks
   only whether upstream has a newer tag. microvm's newest tag is v0.5.0
   (2024), so the review printed "commits past v0.5.0" as healthy.
4. **Short-hash pins are filed as branches.** `pkgs/flake-pins.py:40-46`
   does this to zen-browser `ec2c94c95846` and nix-skills `0ef9aeb`, which
   then get the 120-day grace a branch gets.

## Proposed outcome

- **Caught before a PR.** A nixpkgs bump that breaks any output we cache is
  caught before its pull request opens. That covers microvm runners,
  hypr-rdp, box image, apps and the system toplevels. The canary catches
  the same set.
- **Never silent.** A bump that fails that gate opens a draft pull request
  that names the failing output and quotes the error. It never auto-merges.
  The review also notices when the bump workflow stops running or passing.
- **Fix proposed.** Where moving an allowlisted third-party input to
  upstream's newer commit makes the bump evaluate, the job proposes that
  move in the draft PR, with every upstream commit listed. A human marks it
  ready. Nothing that moved an input other than nixpkgs merges itself.
- **Honest review.** The nightly review reports how far a commit pin is
  behind upstream's default branch when tags cannot answer that. It also
  recognises short-hash pins as commits.
- **On record.** The lesson goes into `AGENTS.md`, in the section it
  belongs to, so the next person writing an auto-bump knows it.

## Affected users and systems

- **CI and tooling only:**
  - `.github/workflows/flake-update.yml` and `.github/workflows/nightly.yml`
    (canary);
  - one shared script under `.github/scripts/`;
  - `pkgs/review.sh` and `pkgs/flake-pins.py`, with their checks
    (`tests/review-pins.nix`);
  - `AGENTS.md`.
- **Users' machines:** nothing changes. Users get a nixpkgs bump that keeps
  landing instead of stalling.

## Constraints

- **Owner approval.** Workflow changes are CI-gate changes (§11), so they
  merge only with the owner's approval.
- **No auto-merge.** Never auto-merge a PR in which any input other than
  nixpkgs moved, and never auto-bump the owner's own `olafkfreund/*` inputs.
  Their bumps have a manual checklist (`docs/internals/flake.md`).
- **One list.** Reuse `cache-allowlist.sh` as the list of what to evaluate
  (§4: a hand-kept second list fails open). Reuse `omarchy.yml`'s
  draft-PR-on-failure shape (#1383) rather than inventing another.
- **Within the hosted runner's limits.** Stay inside the job's 30-minute
  timeout and a hosted runner's memory: no `checks.options`, and no
  evaluation of every check.
- **Proven to fail (§1).** Every new check or review rule is shown to fail
  first: the new gate against the old microvm pin, and each review rule
  with a fixture.
- **No noise.** The review must not manufacture work (`review.sh:456`). A
  pin that is behind but healthy is information, not a finding.

## Decisions (owner, 2026-10-26)

1. **Auto-fix allowlist:** `microvm`, `sops-nix`, `mcp-servers-nix`,
   `zen-browser`. The owner's `olafkfreund/*` inputs stay manual.
2. **Drift rule in the review:** third-party commit pins are a finding
   when they are behind upstream's default branch and the pin is older than
   7 days. The owner's own repos get a note, never a finding.
3. **Draft-PR lifecycle:** a later clean night promotes the open draft, as
   `omarchy.yml` does. It updates the branch, marks the PR ready, and arms
   auto-merge only if nixpkgs alone moved.
