# Intent: Superwhisper is packaged and becomes the default dictation engine

## Problem

Omarchy 4.5 makes Superwhisper its default dictation engine. Nixarchy has
decided to follow (#1610, #1613), and today it can't:

- `data/omarchy-packages.nix:721` skips `superwhisper-bin`, and nixpkgs has no
  such package (`nix eval nixpkgs#superwhisper.version` fails).
- The menu still offers `setup.default.dictation.superwhisper`. It leads to
  `omarchy-install-dictation-superwhisper`, which runs `omarchy-pkg-add`, and
  that always exits non-zero here (`data/bin-ledger.nix:390`).
- Alt+Space and Right Alt bind only when `omarchy-default-dictation` names an
  installed command (upstream `default/hypr/bindings/dictation.lua`). So most
  machines have no dictation keys. Voxtype needs
  `programs.nixarchy.dictation.enable` (`modules/home.nix:958`).

Four things found while checking make this more than adding a package.

### 1. First run asks nothing, and the default is cloud

Nothing below was run. It comes from reading upstream's tree, the vendor's
v1.2.0 archive and the vendor's published text.

| Step | What it does | Source |
|---|---|---|
| First login | Installs in `--background`: no settings window, no notification | `install/user/first-run/superwhisper.sh`, `bin/omarchy-install-dictation-superwhisper` |
| Setup | Enables the user service, places a bar panel, seeds shortcuts, and links an agent skill into `~/.agents`, `~/.claude`, `~/.codex` and `~/.pi/agent` | recipe's `setup-user` |
| Mode | Cloud; offline models are not bundled and Offline is about 2.2 GB | panel `status.py:427`, skill `SKILL.md`, `BUILD_INFO.json` |
| First key press | Upstream says "It starts in the cloud, so it works the moment you install" | omarchy.org 4.5 notes |

What leaves the machine, per the vendor's privacy policy (updated 2026-10-08):

- **Cloud dictation:** audio, transcript and any needed context. The vendor
  says these are not stored or used for training.
- **Every API call:** a random device identifier, app and OS version, country
  and word counts.
- **Crash reports:** sent to Sentry. "On Windows and Linux you can turn it off
  in settings", so they're on unless turned off. The binary carries a Sentry
  DSN and `errorLoggingEnabled`.
- **Agreement:** "By using Superwhisper, you agree to the terms". Under
  upstream's first run, nobody is shown those terms.

**Not settled: can audio leave with no account?** The sources disagree:

- **No:** the panel says "without an account it cannot transcribe", and the
  binary has "Cloud needs a Superwhisper account".
- **Yes:** the release notes say it works on install. `SKILL.md` says cloud
  "works on the free tier". The privacy policy says API calls are linked to "your
  license key or device identifier". The binary has "Cannot authenticate S1
  free-tier access" and "A valid device ID is required for cloud authentication".
  The panel's warning only shows when `credentials.available` is false
  (`status.py:429`), so it doesn't show that a new device lacks credentials.

The evidence leans yes, but it isn't measured, so treat audio as able to leave on
the first press. Holding Right Alt starts a recording, and that key is easy to hit
by accident.

Nor does this all wait for a key press. The service starts at login, and the policy
also lists "when onboarding is finished" events and linking a download to "the
first app launch". What leaves at service start isn't known.

### 2. Default-on puts a proprietary binary where we can't ship it

- **Licence:** the archive's `licenses/superwhisper-components.txt` says "All
  rights reserved. Preview binaries are distributed through the official
  Superwhisper Linux release channel." The terms (June 2026) bar redistributing
  the backend services and say nothing granting redistribution of the app. I
  found no permission for us to redistribute it. Upstream's recipe fetches from
  the vendor at build time, and nothing I read forbids a user's machine doing the
  same. That is a reading, not legal advice.
- **What ships:** the installed host sets `allowUnfree = true`
  (`installer/host.nix:593`), and `reference-toplevel` and `vm-toplevel` are
  pushed to the public cache (`.github/scripts/cache-allowlist.sh:40-41`). The
  ISO carries the reference closure (`installer/cd.nix:125`) and deliberately
  has no apps (`installer/cd.nix:633`). The `nixarchy-desktop` MicroVM runner
  also sets `enable = true` and is pushed.
- **The guard doesn't cover this:** the unfree filter at
  `cache-allowlist.sh:62` covers the `apps` group only. Nothing there stops
  unfree paths in `system` or `runners`. This has happened before: keying on
  `allowUnfree` put claude-code "into every closure CI pushes", 651 MiB and 42% of
  the cache (`modules/home.nix:926`, #731). Superwhisper is 41 MB packed and 184 MB
  unpacked, so the licence is the problem here rather than the size.
- **The conflict:** the installed system must be exactly what its own flake
  describes (Invariant 1, `tests/install.nix:795`). If the installed flake enables
  Superwhisper, an install needs the binary, and the ISO can't carry it. If the
  flake doesn't enable it, a later rebuild won't add it. So a default that is
  present at first boot and also absent from the ISO can't both hold on an offline
  install.

### 3. The selection is already seeded, so a package changes behaviour by itself

- The pinned tree's `config/omarchy/defaults/dictation` says `superwhisper`, in
  rc3 (`flake.nix:82`) and v4.5.0.
- `seed_dir` copies it into every home (`modules/home.nix:1195`). This machine
  has it, dated 2026-10-19, and has no Superwhisper.
- Upstream's migration that keeps Voxtype for existing users
  (`migrations/1791479273.sh`) never runs here (`data/bin-ledger.nix:368`), and
  would skip anyway because the file exists.

So the file can't tell a choice from a seed. Once `superwhisper` is on `PATH`,
keys bind to it on any machine with that file, including a Voxtype user's.

On an unfree-off machine, the same file names a backend that can't exist, so
Voxtype would get no keys unless that is handled.

### 4. Upstream's scripts don't work on NixOS as written

- `omarchy-pkg-present` is a command lookup here, so it's true once the binary
  is on `PATH`. First run then reaches `omarchy-pkg-add`, which fails.
- `omarchy-provision-first-run` marks itself done only when every step succeeds,
  so first run would repeat at every login (#278, `tests/session.nix:1348`).
- The scripts also name `/usr/share/superwhisper/setup-user` and
  `/opt/superwhisper`, and `tests/session.nix:2081-2082` excepts both because they
  were unreachable.
- `setup-user` links `~/.local/bin/superwhisper` to `/usr/bin` and
  `~/.local/share/superwhisper/app/current` to `/opt`, and the panel uses the first
  link when it exists (`status.py:53`). None of those targets exist on NixOS.

## Proposed outcome

- Superwhisper is packaged from the vendor's signed archive, and the desktop
  integration upstream ships works here. Its own updater does not run.
- On an `enable = true` machine with unfree on, Superwhisper is the selected
  engine and Alt+Space and Right Alt work.
- With unfree off, evaluation still succeeds and Voxtype is the engine, with the
  same keys.
- A Mode A import is byte-for-byte untouched.
- A machine that has `dictation.enable` on, or has chosen a backend, keeps it.
- Nothing from the microphone leaves the machine, and the app sends no diagnostics
  or usage data, until the user has made a visible choice (see question 1).
- The menu rows work, or say truthfully why not.
- The release notes and the Discussions post announce the changed default and
  how to leave it (§14).

## Affected users and systems

- Every `enable = true` machine, including ones the installer didn't write
  (`modules/AGENTS.md:426`: `enable = true` is "the request for the Omarchy
  desktop"). Alt+Space and Right Alt, which today pass through to apps, get
  captured, and so does `Ctrl+Alt+Space`, the shortcut upstream's installer sets as
  the app's own. A new user service runs.
- Machines with `dictation.enable` on, and machines with unfree off.
- `checks.stable-eval`: Home Manager on release-26.05 has no `services.voxtype`
  (`modules/home.nix:945`), so the fallback can't start a daemon there.
- CI: every check that builds a system could now depend on a vendor download,
  the same exposure as Docker Hub in #788.
- Upstream targets x86_64 and aarch64. This flake only builds x86_64, and the
  v1.2.0 x86_64 archive verified against the recipe's key. The GitHub and
  tux.superwhisper.com copies have the same hash (`28bc5758…`). aarch64 stays out
  of scope.
- `modules/nixos.nix` is also being changed by #1611, #1612, #1614 and #1615.
  #1614 owns the fcitx5 addon list (`modules/nixos.nix:2290`), so the two must
  agree on it. #1606 brings v4.5.0, which this depends on.

## Constraints

- Must not evaluate-fail with unfree off. Prove it with
  `env -u NIXPKGS_ALLOW_UNFREE -u NIXPKGS_ALLOW_INSECURE` (§1).
- Must not put a Superwhisper path in the public cache or on the ISO, unless the
  vendor gives written permission.
- Must not run the vendor's installer, or let its updater replace store paths.
- Must not write into a user's agent directories without a reason we can state.
- A Coexistence section and a fixture are required (§14): a user's own
  portable Superwhisper, a user's binding on any captured key, the
  `x-scheme-handler/superwhisper` association `setup-user` writes, and
  `dictation.enable`.
- The vendor calls this "early access" and shipped five releases between
  2026-10-21 and 2026-11-03. With the updater off, version bumps fall to us, so
  the spec must say how they happen.

## Open questions

The owner approved every recommendation below on 2026-11-05.

**1. May audio or diagnostics reach the vendor before the user has chosen?** Saying
no differs from upstream and from "works the moment you install".

*Recommend no.* Superwhisper stays the default, but the user sees where audio goes
and the vendor's terms, and chooses, before anything is sent. Crash reports stay
off unless the user turns them on, whichever mode they pick. A default on a
microphone should not send anything on a stray key press, and users would otherwise
be held to terms they never saw. The cost is one choice. Offline needs Vulkan for
local transcription and a large download (about 2.2 GB), so it can't be the silent
default on every machine.

**2. What does "default for everyone" mean on an offline install, given the binary
can't go on the ISO or in the public cache?**

*Recommend:* keep it off the ISO and the cache, and accept that Superwhisper isn't
working until the machine has been online. The owner must decide that, since it
narrows "everyone". How it arrives without breaking Invariant 1 is for the spec, and
I haven't found the mechanism yet. Written vendor permission would only remove the
licence blocker: the allowlist also treats a prebuilt binary as "a slower second
mirror" (`cache-allowlist.sh:18-20`), and only a human can ask the vendor (§11).

**3. Should the measurement come before the spec?** What the daemon sends at start
and on a first key press with no account needs a real run with captured traffic. The
binary was not executed for this intent.

*Recommend yes*, as the spec's first step, when CI is idle (§6). The result decides
how much question 1 has to do, not whether it is needed.
