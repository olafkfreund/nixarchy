# Intent: a hung test guest says what it is waiting for

## Problem

Install targets hang about 5 s into their first boot, roughly once every
three days (#1594; at least 12 since 2026-10-19). A re-run passes, so each one
costs a pull request about 30 minutes and leaves no fix behind.

The hang detector (`tests/vm-cleanup.py`, #1597) already captures what it
can. Two dumps exist, from 2026-11-05 and 2026-11-06 (p620's raw logs, named
on #1594), and they agree:

- every vCPU is halted (`HLT=1`) at `pv_native_safe_halt+0xf`, the idle loop,
  in both samples 5 s apart;
- the last console line is `Finished Update is Completed.`, at under 5 s;
- the guest still takes timer interrupts (a clocksource watchdog line 60 s
  into the silence).

So it is neither a spin nor host starvation. The guest is idle, waiting for a
wakeup that never comes: a device completion, an IPI or a timer. The
registers cannot say which.

The kernel may. SysRq `w` prints the stack of every task blocked
uninterruptibly (`D` state), and such a stack names the wait (a virtio
request, a filesystem lock). A lost wakeup on an *interruptible* wait (a
timer, `epoll`, a socket) leaves its task in `S` state, which `w` does not
show; SysRq `t` shows every task and catches that case, at the cost of a far
longer dump (Codex and agy reviews). The detector already sends that key on a hang
(`vm-cleanup.py:93`), but the guests have SysRq disabled, so the reply is
`This sysrq operation is disabled`. `checks.boot-hang-detect` asserts exactly
that reply (`tests/boot-hang-detect.nix:45`). It was kept as proof that the
key's delivery path works (`tests/AGENTS.md`, "Reading the pokes"). The
evidence that would name the cause has been requested on every hang and
refused every time.

Two pieces of evidence have never been captured on a real hang. Both
recorded dumps predate the detector's virtio queue walk, and both met a
disabled SysRq. The next hang should carry all of it.

## Proposed outcome

- The next hung guest's log carries whatever SysRq can give: the blocked
  (`D`) tasks' stacks after `w`, and every task's state after `t` when `w`
  shows none. All of it is kept, not cut to 20 lines as `_poke` does today
  (`vm-cleanup.py:109`). If a hung guest does not answer the key at all, that
  is itself recorded, and is evidence about the interrupt path.
- A healthy guest still proves the key's delivery path, by a reply that now
  carries information rather than a refusal.
- No product behaviour changes for users: what is enabled is enabled in test
  guests only, unless the owner decides otherwise.

## Affected users and systems

- Test guests that use `wait_for_multi_user`: `checks.install`, `free-space`,
  `install-iso-net`, `install-stock-iso`, `boot-hang-detect`.
- The install **target** is the system under test, built from the flake the
  installer writes, so changing its kernel settings for a test changes what is
  tested. That is the open question below.
- `tests/AGENTS.md`'s "Reading the pokes".
- `tests/vm-cleanup.py`'s `_poke`: its 20-line cut and its time budget, which
  a long dump needs raised.

## Constraints

- Never send a monitor command that kills the guest (`info virtio-status`
  segfaults the pinned QEMU, `tests/AGENTS.md`); `sendkey` is already proven
  safe.
- The hung guest is the evidence: nothing here may restart or reset it before
  the dump is taken.
- Not a CI-gate change: no timeout, trigger or required check moves.
- Must not raise the install's cost measurably; this adds a sysctl or kernel
  parameter, not a step.

## Open questions

1. **Where SysRq is enabled.** (a) only in the test's own nodes (installer VM,
   free-space neighbour), which leaves the install target, where the hangs
   happen, refusing; (b) in the target too, through `test-instrumentation.nix`,
   the module `checks.install` already adds to the installed flake before the
   target's first boot ("the serial root shell the driver needs and nothing
   else", `tests/install.nix:563-583`), whose text is this repository's
   `etcInstrumentation` (`tests/lib/installed-target.nix:82-112`), not
   nixpkgs' own `testing/test-instrumentation.nix`; or (c) in nixarchy's
   default configuration, `kernel.sysrq` for all users.
   Recommendation: (b). The instrumentation boundary is already drawn there,
   and a kernel parameter changes nothing a test asserts about the product.
   Nodes that do not go through it, such as `boot-hang-detect`'s `healthy`,
   need the setting of their own. (c) is a security-relevant default (SysRq
   lets anyone at the keyboard kill processes, sync and reboot) and is not
   ours to change for a test.
2. **sysctl or kernel parameter.** `kernel.sysrq=1` applies when
   `systemd-sysctl` runs, which is before 5 s on these boots but is not
   guaranteed; `sysrq_always_enabled` on the kernel command line is processed
   during kernel boot, before `systemd-sysctl` runs. It enables every SysRq
   operation on that test guest, though the detector sends only read-only
   keys. Recommendation: the kernel parameter, for the hang's timing.
3. **Which keys.** `w` (blocked tasks) names a `D`-state wait; `t` (all
   tasks) also catches an interruptible one but is long; `l` (all CPUs'
   backtraces) would only show the idle loop the registers already show.
   Recommendation: `w`, then `t` when `w` printed no task, with the capture
   limit and time budget raised to hold `t`.

## Review findings (Codex gpt-6-sol, agy)

Confirmed and taken: `w` misses interruptible waits (`t` added); `_poke` cuts
console output at 20 lines; a healthy guest's refusal makes delivery to a hung
one plausible, not certain; the setting belongs in this repository's
`etcInstrumentation`, and `healthy` needs its own; `l` adds nothing here; the
kernel parameter's timing was overstated. Neither recorded dump has a virtio
queue walk, which postdates them.
