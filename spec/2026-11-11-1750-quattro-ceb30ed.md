# Spec: edge adopts quattro ceb30ed (Files for Nautilus, Plain as the editor)

The approved intent takes all three recommendations: package Files and Plain,
keep Neovim on machines that already exist, and move Moonlight to
Install > Gaming.

## Where the work lands

The same split as #1736:

- **This branch (`fix/1750-quattro-ceb30ed`)** carries the intent, spec and
  plan, and merges to `main` by its own PR. It changes no code.
- **The carry on `edge-candidate`** carries the code, the pin (both copies in
  `flake.nix` plus `flake.lock`, §8), and the pin-derived rows: the package
  ledger, the user-migrations ledger and the new catalogue row. It is then
  dispatched with `omarchy-edge.yml -f from_candidate=true`.

All code is written to hold under both pins. `main` (tag v4.5.0) picks it up
at the next edge→main merge, and that merge drops any edge-only ledger rows
(§8), as #1736 did.

## Design

### 1. One fact about the pin: the base package list

`pkgs/omarchy/default.nix` already derives `hasPapers` from
`${src}/install/omarchy-base.packages`, without IFD. That read becomes a
`let` binding, `basePackages` (the split list, blank lines and comments
dropped). `hasPapers` becomes `builtins.elem "papers" basePackages`, and the
same binding gives:

- `hasFiles = elem "folio" basePackages`
- `hasPlain = elem "plain" basePackages`

`basePackages` is exported in `passthru`, so `modules/nixos.nix` can ask
`elem "sushi"` without parsing the file a second time. Moonlight is read
from where the module already says it comes from,
`omarchy-install-preinstalls` (`modules/nixos.nix:1562`):
`preinstallsMoonlight = lib.hasInfix "moonlight-qt" (readFile
"${src}/bin/omarchy-install-preinstalls")`, also in `passthru`. Checked on
the three pins: v4.5.0 and `054d75e` name it in that script, and `ceb30ed`
names it nowhere. Two more passthru values:

- `fileManagerDesktop` = `"folio.desktop"` when `hasFiles`, else `null`;
- `editorDesktop` = `"plain.desktop"` when `hasPlain`, else `"nvim.desktop"`.

### 2. Two packages: `pkgs/apps/folio.nix` and `pkgs/apps/plain.nix`

These follow `pkgs/apps/owe.nix`: `fetchFromGitHub` from `omacom/<name>` at
the `v0.2.0` tag, with `nix-update` in `passthru.updateScript`, so
`update.yml`'s pinned-package bump and the nightly review's version row
cover them. Both are `qt6.qmake` builds (`qmake6 <name>.pro && make`, as
upstream's `bin/build` does) wrapped with `qt6.wrapQtAppsHook`. Their
inputs:

| | Qt modules | other |
|---|---|---|
| Files | base, declarative, imageformats, multimedia, wayland | `glib` (gio-2.0, gio-unix-2.0), `zlib`, `libarchive` |
| Plain | base, declarative, wayland | none |

`installPhase` installs what upstream's `pkgbuild/PKGBUILD` installs: the
binary in `bin/`, `pkgbuild/<name>.desktop` in `share/applications/`, the SVG
icon in `share/icons/hicolor/scalable/apps/`, and the licence. Both are MIT
(checked: `LICENSE` in each repository), so neither touches the unfree rule
and both may go on the public cache.

Files' optional dependencies (`qt6-webengine` for PDF previews, `glycin`,
`gvfs`, `tailscale`, `dropbox-cli`) are not added. Most are already in the
system closure through other rows, and WebEngine alone would add hundreds
of MiB for a preview. A missing optional dependency is a feature that does
not show, not a failure.

They are exported as `nixarchy-apps.folio` and `nixarchy-apps.plain`, beside
`owe`. That avoids nixpkgs' unrelated `folio` (GNOME's notes app). That app
installs `bin/com.toolstack.Folio` and `com.toolstack.Folio.desktop`, so
neither our binary nor our desktop file collides with it (checked by
building it).

### 3. The vendored tree uses them only when the pin ships them

In `pkgs/omarchy/default.nix`:

- `runtimeDeps`: `(if hasFiles then folio else nautilus)` replaces `nautilus`,
  and `plain` is added when `hasPlain`. `xdg-user-dirs` is already an
  unconditional runtime dependency (`pkgs/omarchy/default.nix:319`), so
  upstream's new explicit row needs nothing. `ffmpegthumbnailer` stays,
  because Files and the lock-screen poster both use it.
- **The desktop-ID check does not reach these.** The build fails when an ID
  named by `$out/share/omarchy/config/*mimeapps.list` is missing from
  `$out/share/applications` (`pkgs/omarchy/default.nix:1236`). At `ceb30ed`,
  `config/` holds only `hyprland-mimeapps.list`, which names
  `omarchy-browser.desktop`. `folio.desktop` and `plain.desktop` are named
  only in `default/applications/mimeapps.list`, which nixarchy neither
  seeds nor checks: the module's `xdg.mime.defaultApplications` takes its
  place. So the IDs are not copied into the Omarchy output. They are proven
  to resolve where it matters, in the booted system (`checks.session`,
  below).
- The editor patch: `--replace-fail` reads a snippet chosen by
  `hasPlain`. `default-editor-install.upstream.sh` stays for `main`, and a
  new `default-editor-install-plain.upstream.sh` carries quattro's text, with
  the `plain)` row. A copy per pin, rather than one regex, because
  `--replace-fail` on exact text is what makes an upstream rewording fail
  the build (pkgs/AGENTS.md, "Patching upstream").
- `nixarchy-default-install` (`modules/apps.nix:2165`): `editor:plain` joins
  `editor:nvim` in the "already ships in the session" arm. Plain is a runtime
  dependency, so upstream's install branch, which runs only when the command
  is missing, never reaches it on edge. The arm exists for the case where it
  would.

### 4. The module

In `modules/nixos.nix`:

- **MIME defaults.** `"text/plain" = cfg.package.passthru.editorDesktop`
  replaces the literal `nvim.desktop` (decision A below). `"inode/directory"` is added from
  `fileManagerDesktop` with `lib.optionalAttrs (… != null)`, so `main` gains
  no new key. Both are inside the existing `mapAttrs (_: lib.mkDefault)`, so
  a user's own handler wins.
- **Preinstalls.** The set at line 1563 takes `moonlight-qt` only when
  `preinstallsMoonlight`, and `sushi` only when `basePackages` names it. In the `preinstallsExclude` assertion
  (line 970), a name that the pin no longer installs moves from `current` to
  `retired`. It is still accepted and does nothing, so
  `preinstallsExclude = [ "moonlight-qt" "sushi" ]` keeps evaluating on both
  pins, which is the shape the Omarchy 4.5 removals already use.
- **Moonlight under Install > Gaming.** On the carry, a `moonlight` row in
  `data/apps.nix` (`menuId = "install.gaming.moonlight"`, `attr` and `arch`
  `moonlight-qt`, category Gaming, mirroring `lutris`). A row in
  `data/menu-actions.nix` classifies `remove.gaming.moonlight` the way
  `remove.gaming.battlenet` is: `pkg-drop` is inert here. A second row
  classifies `setup.default.editor.plain` the way the other nine editor rows
  are: "owned: its one rm clears its own pending-default-editor marker"
  (`origin/edge:data/menu-actions.nix:94-109`). The retained editor patch
  puts that `rm` in every editor setter. Neither belongs on
  `main`, whose menu has neither row. The new bin
  (`omarchy-remove-gaming-moonlight`) gets whatever classification
  `checks.bin-ledger` names, and none if it ships unchanged.

### 5. The two user-file migrations

Omarchy's migrations are not run here; `omarchy-migrate-user` runs the
ported ones at login, from `post-boot.d/user-migrations`. A fresh home
(`fresh_shell` in `modules/home.nix:1215`) marks every ported id as done
before it can run. That gives "fresh install" and "existing machine" the
meaning the intent asks for, using the machinery that is already there.

**`1794341736`, keep Neovim on existing installs: `ported`, `run = "edited"`.**

- The state half runs as upstream wrote it. It writes `nvim` to
  `~/.local/state/omarchy/defaults/editor` only when that file is missing
  or empty. A saved choice is kept, and a fresh home never runs it, so a
  fresh home falls through to upstream's new `plain` default
  (`omarchy-launch-editor`).
- The MIME half adds `nvim.desktop` lines for the 17 types the user has not
  chosen, and it runs only when `~/.config/mimeapps.list` is a regular file
  or absent. When it is a symlink, Home Manager owns it
  (`xdg.mimeApps`, as on p620 and razer). The upstream write would land in
  the store and fail at every login, and the user's Nix declaration is
  already their choice. The edit is one guard line spliced into a copy of
  the upstream script, the way `1786719479` is edited.

**`1794330979`, Nautilus to Files: `partial`, `run = "edited"`.**

- `omarchy-pkg-add folio` and `omarchy-pkg-drop …` are removed: packages come
  from the rebuild.
- The `~/.config/mimeapps.list` rewrite runs under the same regular-file
  guard. A handler the user set to something other than Nautilus is not
  touched, because upstream's `sed` matches only
  `org.gnome.Nautilus.desktop`.
- The dock rewrite is dropped. Upstream edits
  `~/.config/omarchy/shell.json` with `sed`, and nothing here may write that
  file under a running shell (#847, the `build.yml` step "Nothing we ship
  writes shell.json"). The shell has no IPC call for dock pins (its IPC is
  `ping` and `putBarWidget`), so there is no safe way to do it. A dock the
  user pinned Nautilus to keeps that pin. The pin resolves to nothing once
  Nautilus is gone, and they can re-pin with `omarchy dock pin folio`. A
  dock the user never touched follows the new default pins, which already
  name `folio`. That is why the row is `partial`, and the reason says so.

"Fresh" here means what the activation tests: no `shell.json` before the
seed ran (`modules/home.nix:1215`). A home that existed without ever having
a `shell.json`, such as one that never logged into the Omarchy session, is
treated as fresh and gets Plain. That matches what it has used, which is
nothing.

Running either one a second time changes nothing: upstream's own tests
(`grep -q`, `-s`) are idempotent, and the marker stops a re-run anyway.

**`1794351944`** (install `xdg-user-dirs`) touches no user file. It gets no
row and is covered by the package in step 3.

### 7. The rest of the batch needs no work

The herdr `setsid` autostart, the Spark offer, the notification glyph,

### Decided: text files on Home-Manager-managed machines (A)

Approved 2026-11-11 with the recommendation, A. The reasoning is kept below.

Upstream makes Plain the default in two places: the editor that
`SUPER + SHIFT + N` launches (the state file), and the handler for opening
a text file (`mimeapps.list`). The design above keeps an existing machine
on Neovim for both, except on one kind of machine: one whose
`~/.config/mimeapps.list` is Home Manager's, as on p620 and razer. There
the migration cannot write, and the system default answers for every type
the Home Manager list does not name. If that default becomes
`plain.desktop`, such a machine keeps Neovim from `SUPER + SHIFT + N` but
opens text files in Plain. That falls short of the approved outcome
("keeps Neovim"), so it is flagged here rather than accepted silently. Two
ways to close it:

- **A (recommended): the system default follows the pin, and the PR
  says so.** `text/plain` becomes `plain.desktop` on edge. A Home Manager
  machine that wants Neovim declares it, in the same place it already
  declares its PDF handler (one line). A fresh install then matches upstream
  everywhere, and the only machines affected are the ones that manage their
  own MIME list in Nix.
- **B: the system default stays `nvim.desktop` on both pins.** No existing
  machine changes, but a fresh edge install opens text files in Neovim while
  `SUPER + SHIFT + N` opens Plain, which is the split upstream removed.

## Coexistence (§14)

- A user's own `xdg.mime.defaultApplications."inode/directory"` or
  `"text/plain"` wins over ours, because ours are `mkDefault`. A fixture in
  `tests/coexistence/fixtures.nix` sets both and asserts the user's value.
  The break that proves it can fail is ours set without `mkDefault`.
- A user with nixpkgs' `folio` installed: no file collides (`com.toolstack.*`
  against `folio`). That needs no fixture, because there is no failing case
  (§14 says a fixture that cannot fail is worse than none).
- A Home Manager `xdg.mimeApps` file is never edited by either migration
  (§5). `checks.user-migrations` gets a fixture with the list as a symlink.

## Alternatives rejected

- **Patch edge back to Nautilus and Neovim.** Rejected at the intent gate.
- **One `--replace-fail` snippet that strips the `plain)` row before
  matching.** It would match on both pins, but a regex hides an upstream
  rewording. Two exact files keep the failure loud.
- **Move the dock pin with `omarchy dock`.** That script writes the file
  with `mv` and then asks the shell to reload. That is the write #847
  measured as breaking a running shell.
- **Run `1794341736` on every home, fresh ones too.** Then a fresh install
  would get Neovim, which is the case the Codex review of the intent named.
- **Add Files' optional dependencies (WebEngine for PDF previews).** Too
  large for an optional feature. They can be revisited if someone misses
  them.

## Risks

- **Files and Plain at v0.2.0 are young.** Both build here for the first time,
  and a Qt app can build and still fail to start. `checks.session` launches
  both (below). Like the owe bump, the PR says each was run on p620 before
  edge deploys.
- **The editor flip on Home-Manager-managed machines (p620, razer).** Their
  `~/.config/mimeapps.list` is Home Manager's, so text files open in whatever
  that list declares. Where it declares nothing for `text/plain`, the system
  default, now Plain, applies. The editor launched by `SUPER + SHIFT + N`
  stays Neovim through the state file. Stated in the PR, with the one line to
  pin it.
- **A Nautilus dock pin goes dead** for a user who pinned it themselves
  (§5). It is accepted, written in the ledger row and the release note.
- **Closure size.** Two small Qt apps join the closure, while Nautilus,
  sushi and Moonlight leave it. The net change is expected to be a
  reduction, and `cache-budget.sh` reports the figure on the carry.

§1 breaks, each shown failing and then passing:

- the MIME defaults without `mkDefault` (coexistence);
- the symlink guard removed (user-migrations);
- `editorDesktop` hard-coded to `nvim.desktop` (the session's `text/plain`
  probe);
- `1794341736` dropped from the fresh-home marker loop in `modules/home.nix`
  (the session's state-file probe, which then finds `nvim` written on a
  fresh home). The fresh-home path is activation code, so only a booted home
  can test it;
- `preinstallsMoonlight` forced to `false` (the main-pin evaluation, which
  then loses `moonlight-qt`).
