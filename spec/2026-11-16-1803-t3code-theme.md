# Spec: T3 Code follows the Omarchy theme when installed through apps

## Design

A port of nixos_config #2973, which has been live on p620 since 2026-11-16.
It moves to where every Nixarchy user gets it, takes its tools from packages
rather than `PATH`, and adds the approved option and fallback.

### The option (Home Manager, beside `defaultTheme`)

`modules/home.nix`, under `options.programs.nixarchy` (`:639`, in the Home
Manager module, whose `cfg` is `config.programs.nixarchy`, `:14`), next to
`defaultTheme` (`:719-723`):

```nix
t3code.theme = lib.mkOption {
  type = lib.types.nullOr (lib.types.strMatching "[a-z0-9-]+");
  default = "omarchy";
  example = "omarchy-plus";
  description = ''…'';
};
```

- **Why here.** The owner chose a top-level `programs.nixarchy.t3code.theme`
  rather than an `appModule` sub-option. The Home Manager tree is where the
  other per-user theme choice already lives, and where the activation reads
  it, so the option is declared there. Hosts set it with
  `home-manager.users.<u>.programs.nixarchy.t3code.theme`, the same way
  `defaultTheme` is set (`tests/home-activation-writes.nix:22`).
- **The description says:**
  - the theme is forced back on every activation;
  - `null` publishes the palette but never selects a theme;
  - a missing non-`omarchy` theme falls back to `omarchy`, with a log line.
- **Validation.** `strMatching` is the downstream assert, moved into the type,
  so a bad value fails evaluation with the option's name.

### The script builder

New file `modules/t3code-theme-script.nix`, a function:

```nix
{ lib, writeShellApplication, coreutils, gnugrep, jq }:
{ publisher, t3, theme, timeoutSecs ? 30, killSecs ? 5 }:
writeShellApplication {
  name = "nixarchy-t3code-theme";
  runtimeInputs = [ coreutils gnugrep jq publisher t3 ];
  bashOptions = [ "nounset" ];
  text = ''…'';
}
```

- **Arguments.** `publisher` and `t3` are packages that provide
  `bin/omarchy-theme-set-t3code` and `bin/t3`. In production they are
  `cfg.package` and `osConfig.programs.nixarchy.apps.t3-code.package`. The
  check passes stub packages, so stubs win through `runtimeInputs`, the same
  path production uses.
- **`bashOptions = [ "nounset" ]`.** This turns off the default `errexit` and
  `pipefail`, keeping downstream's failure tolerance, which the intent
  requires. The ShellCheck that `writeShellApplication` runs at build time is
  kept.
- **The script body is downstream's**
  (`nixos_config hosts/common/nixos/t3code-theme-script.nix`). Here "stop"
  means `exit 0`. With `T3CODE_HOME="$HOME/.t3"` and
  `STATE="$T3CODE_HOME/userdata"`:
  0. If `HOME` is empty, log and stop.
  1. Check that both commands are there. They are on `PATH` through
     `runtimeInputs`, so this is a safety net.
  2. If `$HOME/.local/state/omarchy/current/theme/t3code.json` is missing,
     log `no Omarchy palette staged yet; next activation retries` and stop.
     This check comes before step 3, so a home with no Omarchy theme gets no
     `~/.t3` folder (agy).
  3. `mkdir -p "$STATE"`. The publisher needs it.
  4. Run `omarchy-theme-set-t3code`. A non-zero exit is logged, and the
     script stops. If the palette contains `{{`, log that the previous palette
     was kept.
  5. If `theme` is `null`, stop: publish only.
  6. **New, the fallback.** Let `want` be the configured theme. If
     `$STATE/themes/$want.json` is missing:
     - if `want` is not `omarchy` and `omarchy.json` exists, log
       `theme <want> not published; using omarchy`, and set `want=omarchy`;
     - otherwise log `theme <want> not published` and stop.
  7. Read the current theme with
     `jq -r '.defaultTheme // empty' "$STATE/settings.json" 2>/dev/null`. If
     it equals `want`, stop.
  8. Run
     `timeout -k <killSecs> <timeoutSecs> t3 theme set "$want" --base-dir "$T3CODE_HOME"`,
     with output to a `mktemp` file. On a non-zero result, log the code and
     the last 5 lines, each prefixed. Always remove the file.

  Finally, `exit 0`. Every log line goes to stderr, prefixed `t3code-theme:`.

### The activation entry

In `modules/home.nix`, beside the other per-app entries (`:1839-1879`):

```nix
# let:
t3codeOn =
  (osConfig.programs.nixarchy.enable or false)
  && (osConfig.programs.nixarchy.session or true)
  && appEnabled "t3-code";

home.activation.nixarchyT3codeTheme = lib.mkIf t3codeOn (
  lib.hm.dag.entryAfter [ "writeBoundary" "nixarchySeed" ] ''
    run ${t3codeThemeScript}/bin/nixarchy-t3code-theme
  ''
);
```

- `t3codeThemeScript` is a `let` binding: the builder called with
  `cfg.package`, `osConfig.programs.nixarchy.apps.t3-code.package` and
  `cfg.t3code.theme` (the Home Manager `cfg`).
- It is only forced inside the `mkIf`, so with the app off the T3 Code package
  is never evaluated.
- **The gate, `t3codeOn`.** It uses the same terms as `hasOmarchySession`
  (`:1043-1044`) plus the app (agy):
  - Nixarchy itself must be enabled;
  - the Omarchy session must be on;
  - `t3-code` must be selected.

  `appEnabled` (`:137`) and every `osConfig` read use `or`. A standalone
  Home Manager evaluation, or Mode A with no `apps`, therefore evaluates to
  off instead of failing.
- `run` gives the dry-run guard.
- Ordering after `nixarchySeed` (`:1161`) means the first-run theme (`:1417`)
  is staged by the time this runs.

## Alternatives rejected

- **`apps.t3-code.theme` inside `appModule`** (Codex's preference). Rejected by
  owner decision: it would add a single-app branch to a submodule shared by
  every app.
- **A NixOS-level option.** The theme is a per-user choice, the activation is
  per-user, and `defaultTheme` is per-user too.
- **`writeShellScript` with a hand-built `PATH`.** That is what downstream had
  to do. Upstream owns the packages, so `runtimeInputs` is exact and also
  runs ShellCheck.
- **A post-boot hook.** Activation after `nixarchySeed` covers a fresh
  install. This was settled downstream, where agy's review raised races.
- **Keeping the downstream module.** That only fixes one flake. It is removed
  downstream after this ships (follow-up below).

## Risks

- **The T3 Code CLI hangs at activation.** It is bounded by `timeout -k 5 30`
  and tested with a stub that ignores TERM.
- **Forcing reverts an in-app theme choice for every user.** This is the
  owner's decision, the option description says so, and `null` opts out.
- **The fallback hides a broken custom publisher.** It logs a line on every
  activation, and the check asserts that line.
- **`nixarchySeed` is renamed.** `checks.options` asserts that both the entry
  and the dependency exist.
- **Mode A.** With the app off, the only trace is the option declaration.
  `checks.options` asserts the activation entry is absent and that no
  activation text mentions `nixarchy-t3code-theme`, using
  `activationText`, which catches a renamed block (`tests/options.nix:428-433`).

## Verification

- **`checks.options`** (`tests/options.nix`, `hasAll`, `hasAny` and
  `activationText` at `:432-436`):
  - **App on:**
    - `hasAll home [ "nixarchyT3codeTheme" ]`;
    - its `.after` contains `nixarchySeed`, and
      `home.activation ? nixarchySeed`;
    - `t3code.theme` evaluates to `"omarchy"`.
  - **App off,** with `apps.t3-code.package = throw "t3code forced"` (Codex):
    - `! hasAny home [ "nixarchyT3codeTheme" ]`;
    - forcing `activationText` does not throw, which proves the package is
      never evaluated;
    - `activationText` lacks `nixarchy-t3code-theme`;
    - `t3code.theme` still evaluates, so the option exists in both states.
  - **App on, `session = false`:** no entry.
  - `t3code.theme = "omarchy-plus"` changes the generated script.
  - `t3code.theme = "Bad Id"` fails evaluation.
- **Generated-activation behaviour, in the style of
  `tests/home-activation-writes.nix`.** That test takes the evaluated home's
  activation text and runs it with a `run()` shim (`:50`). This part
  exercises the real wiring, not just the builder (Codex). In a `vm` extended
  with `apps.t3-code.enable = true` and `apps.t3-code.package = <stub t3
  that logs a unique marker>`, against a fixture `HOME` that has a staged
  `t3code.json`:
  - The real activation entry runs the real `omarchy-theme-set-t3code` and
    the stub `t3`. The marker appears, which proves the package override
    controls the `t3` that is actually called.
  - With `DRY_RUN=1`, there is no marker and no `~/.t3` is created. A mutant
    without `run` must fail this.
- **A new behaviour check, `checks.t3code-theme`**
  (`tests/t3code-theme.nix`). It calls the builder with stub `publisher` and
  `t3` packages, `timeoutSecs = 2` and `killSecs = 1`, and ports downstream's
  10 cases:
  1. no palette;
  2. the publisher fails;
  3. a `{{` palette with an existing theme file;
  4. a `{{` palette with no theme file;
  5. no `settings.json`;
  6. a different theme;
  7. the same theme;
  8. `t3` fails;
  9. `t3` ignores TERM, which must give 137 with no temporary file left;
  10. no `t3`, using a stub package with no `bin/t3`.

  It adds:

  11. `theme = null`: the publisher is called and `t3` never is;
  12. fallback: `theme = "omarchy-plus"`, no `omarchy-plus.json`, and
      `omarchy.json` present give `t3 theme set omarchy` and the fallback log;
  13. `omarchy-plus.json` present: `t3 theme set omarchy-plus`.
- **§1 of `CLAUDE.md`, for every rule.** Break it, capture the failing output,
  restore it. At minimum:
  - remove the `exit` after a publisher failure;
  - drop `-k`;
  - drop the fallback;
  - drop the `null` guard;
  - in `options.nix`, drop the `mkIf`, and rename the dependency;
  - drop the session term from `t3codeOn`;
  - remove `run`;
  - move `mkdir` before the palette check. Case 1 asserts no `~/.t3` is
    created.

  The failing outputs go in the PR.
- **Docs.** `docs/manual/configuration.md` gets the option beside
  `defaultTheme`, and the T3 Code entry in the manual says that it follows the
  theme.
