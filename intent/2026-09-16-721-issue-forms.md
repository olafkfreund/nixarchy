# Intent: a form for every kind of report, not only bugs

## Problem

`.github/ISSUE_TEMPLATE/` has one form, `bug.yml`, and `config.yml`'s routing
links. Everything else is filed as a blank issue, which skips both the routing
question this project depends on — would this happen on Arch? — and the details
that are expensive to collect afterwards.

Three kinds of report arrive without a form:

- **A failed install or ISO boot.** It needs different questions from a desktop
  bug: which ISO or release, full-disk or free-space, encrypted or not, UEFI,
  the disk, and what the installer printed before it stopped.
- **A feature or packaging request.** The useful version says what upstream does
  today and whether nixpkgs already has the package.
- **Documentation.** Wrong or missing pages currently arrive as a bug with no
  reproduction, or not at all.

#720 is the live example of the cost: a careful report, in prose, that still
needed a code read to place.

## Proposed outcome

- **Someone with an install failure** is asked for the ISO, the disk mode and
  the installer's last output, in the form, before they submit.
- **Someone asking for a package or feature** is asked what upstream does and
  whether nixpkgs has it.
- **A documentation report** names the page and what it should say.
- **Routing still comes first:** the "would this happen on Arch?" links stay on
  the chooser, ahead of the forms.
- **Every form carries the same identifying detail** — versions and the locked
  revisions — in the same words as `bug.yml`, so reports are comparable.
- **Each form arrives with a label**, so nothing lands unlabelled.

## Affected users and systems

- Anyone filing an issue, and anyone triaging one.
- `.github/ISSUE_TEMPLATE/` only. No CI, no labels automation beyond what a form
  sets, no change to the milestone rule (AGENTS.md §12 still puts that on
  whoever triages).

## Constraints

- **Forms, not markdown templates**, matching `bug.yml`, so required fields are
  actually required.
- **Reuse `bug.yml`'s wording** for versions and existing-issues rather than
  inventing a second phrasing.
- **No new label needs creating** unless it already exists in the repository.
- **Routing is not weakened:** `config.yml`'s upstream links stay, and each form
  repeats the Arch question where it applies.
- This is documentation: there is nothing for a check to assert beyond the forms
  being valid YAML that GitHub accepts, so the verification is deliberately
  thin and the spec should say so rather than invent a check.

## Open questions

1. **How many forms?** Three (install, request, docs), or fewer with one
   combined "request" form? More forms means a longer chooser.
2. **Should a form set a milestone?** GitHub forms can set labels and
   assignees, not milestones. So §12's "every issue gets a milestone when
   filed" stays a triage step — worth stating in the spec rather than leaving
   implied.
