# Intent: Read MicroVM running state without taking its mutation lock

## Problem

Refs #1098, Robustness lock item. The finding still holds on current `origin/main` after #1100 and #1112: `pkgs/microvm.nix:158-166` implements `lock_held` by opening `<vm>/.lock` and trying an exclusive `flock -n`. `vm_status` calls it from both text and JSON `list` (`:180-214`), and the detached-run readiness poll also calls it (`:391`). `pkgs/verify.sh:683-694` repeats the same exclusive probe for each guest. When a VM is stopped, a probe **acquires** the lock briefly before releasing it. A simultaneous normal `run`, `rm`, or `set-template` tries `lock_stopped_vm` with a nonblocking exclusive lock (`pkgs/microvm.nix:316-333,357-359,445-479`) and can spuriously refuse as “already running.” The panel and terminal both consume `list`, so this is a user-facing race, even though the lock window is short. The verifier's wider guest checks also repeat it.

The original claim overstates one part: `stop` runs `microvm-shutdown` directly (`pkgs/microvm.nix:451-460`) and does not take this lock. A `launch_vm` handoff waits for its lock for up to 30 seconds (`:363-370`), so a short probe may delay that path but does not immediately refuse it. No persistent state corruption follows from the probe itself; the demonstrated code-level harm is transient false-busy behavior. `tests/microvm-template.nix:675-695` verifies stopped/running values but does not assert that a read-only query leaves the lock free to a concurrent mutator.

## Proposed outcome

Status/list and verification report whether an existing VM lock is held without acquiring it themselves. A query of a stopped VM cannot cause `run`, `rm`, or `set-template` to lose the lock race. The detached handoff still treats an active or activating user unit as busy, and an actual runner still holds its exclusive lock for its lifetime. A cheap concurrency check catches the old probe by failing when a status query briefly owns the lock.

## Affected users and systems

Users of `nixarchy vm list` and its JSON consumer (`nixarchy.microvm`), and users running `nixarchy-verify` while starting or changing a disposable VM. `pkgs/microvm.nix`, `pkgs/verify.sh`, and their checks are the likely implementation area. The verifier also walks declarative `/var/lib/microvms/<name>` directories; whether those runners use this same lock is a separate observation to verify before changing their status semantics.

## Constraints

- Keep the lifetime exclusive lock on the real runner and the nonblocking refusal on mutating operations; those prevent two QEMUs sharing one state directory.
- Prefer a read-only view of the existing advisory lock, such as util-linux `lslocks` (already in both runtime inputs: `pkgs/microvm.nix:89`, `flake.nix:731`) with exact VM-lock identity and lock type matching. Account for path display or permission failures instead of silently treating an unknown state as stopped. Do not use a shared `flock` as the probe: it can still contend with a writer.
- Preserve the JSON `list` shape and the `unit_busy` handoff check. Add a check that is first seen red with the old probe and green with the read-only probe; test both stopped and running answers and overlap with a mutator. No VM boot is needed for this lock behavior.
- This is one remaining item of the batch issue. #1097 separately tracks CI hygiene and is still open; a later PR for this item should say **Refs #1098**, not `Closes #1098`. No workflow, settings, or other-issue edits.
- At this gate, only this draft intent is committed locally. No build, implementation, push, or PR.

## Open questions

1. Is a fix warranted for a brief race with no observed data loss? **Recommendation:** yes. `list` is called by a panel and the lock probe can make `run`/`rm`/`set-template` falsely refuse; a read-only query should not schedule against a mutator.
2. Which read-only source should replace the probe? **Recommendation:** use the already installed util-linux `lslocks` view of `/proc/locks`, matching the exact `.lock` and exclusive `FLOCK` entry, after confirming path identity and permission behavior in the spec. If those cannot be made reliable for both user-owned and declarative paths, use `/proc/locks` device/inode matching rather than another `flock` probe.
3. Should this also redesign declarative-VM detection in `nixarchy-verify`? **Recommendation:** no. First establish whether upstream's declarative runner uses a `.lock`; keep this item to removing probe contention and file any detection gap separately.
