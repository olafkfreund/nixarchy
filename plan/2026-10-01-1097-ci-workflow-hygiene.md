# Plan: Make CI workflow gates honest and keep forks off the install runners

## Approved decisions and owner boundary

All five #1097 findings are in scope. The approved fork rule is: an install-relevant fork PR fails its required `install` check on a hosted runner; an irrelevant fork PR gets the existing green no-op; same-repository PRs keep their normal install gate. For forks, the hosted gate runs the base branch's `.github/scripts/pr-touches-build.sh`, not fork code. Unknown relevance is relevant. This guard must never select a self-hosted runner for a fork; repository-wide fork approval protects against fork-edited workflow YAML.

GitHub's [workflow security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) says `pull_request` uses the PR merge commit's workflow, which a fork can edit. A fork can change **any** workflow to request a self-hosted runner, so the in-workflow guard below is defense in depth, not the repository's security boundary. The owner changes the repository Actions setting to **Require approval for all outside collaborators** and reviews workflow changes before approving a fork run. The current `first_time_contributors` policy is insufficient for returning outside contributors. Moving only `install-check.yml` to `pull_request_target` would leave other workflow paths open and add privileged-checkout, ref and slot risks. The trigger stays `pull_request`, and the branch cannot apply or verify the owner-controlled setting.

This plan's output is a **ready-to-apply branch**, not an automatically merged CI change. Root `AGENTS.md` §11 reserves CI-gate changes for the owner to review and merge. Implementation starts only after this plan is approved. The implementing agent writes and checks the patch locally, then stops for owner review; no deploy, push, PR or merge is authorized by this plan.
