# Spec: The installer's keyboard choice reaches the login screen and the session

Upstream paths are in the v4.5.0 tree. "Measured" means I ran it on 2026-11-05 at this
branch's nixpkgs pin. "Read" means source only. **No VM has run:** CI had 2 to 4 runs in
flight at every check, so §6 forbade one. The LUKS answer below is therefore read, and
the intent's "VM first" is still owed; §5 says what happens if the VM disagrees.

## Design

### 1. One table holds both names

`installer/brand/keymaps.txt` gains two columns: the XKB `layout[:variant]`, and the
characters that type differently at the login screen than at the installer.

```
German	de-latin1	de
English (UK)	uk	gb
Russian	ru	us,ru
Norwegian	no-latin1	no	$^`~
```

`ask_keymap` already reads with `cut -f1` and `cut -f2`, so the extra columns do not
disturb it. It additionally sets `xkb_layout` and `xkb_variant`.

The 43 rows, measured. "Differ" compares the console table (`loadkeys --unicode
--mktable`) with the XKB keymap (`xkbcli compile-keymap`) on plain and Shift of the 47
keys a password uses. A non-Latin row is compared with `us`, which is what leads there.
AltGr is not compared. The comparison was shown to fail first: `uk`→`us` gives 8
differences, `et`→`et` gives 79 (Ethiopic) and `la-latin1`→`la` gives 81 (Lao).

Mostly systemd's `kbd-model-map`, with the intent's 7 missing rows filled in. Two traps
the table closes: `et` is Estonian on the console and Ethiopic in XKB (`ee` is right), and
`la-latin1` is Latin American while XKB's `la` is Lao. `jp106` and `br-abnt2` carry no model,
as `input.lua` sets `kb_model = ""`.

**Four rows change, because the measurement says the old pairing cannot satisfy
outcome 5.** These are owner decision 1:

| Row | Was | Differences | Now | Differences |
|---|---|---|---|---|
| French | `fr` | 12, including `{ } / @` on the digit row | `fr-latin1` | 1 (`²`) |
| Swedish | `se-lat6` | 9, and it types `ø æ` where a Swede has `ö ä` | `fi` | 0 |
| Czech | `cz-qwertz` | 20, including Shift on the digit row | `cz-us-qwertz` | 5, all symbols |
| Lithuanian | XKB `lt` | 30, including digits | XKB `lt:us` | 0 |

`fi` reads oddly in a Swedish `configuration.nix`, and it is what kbd's `fi.map` measures
as. Lithuanian letters move to AltGr; `lt` stays one pick away in Keyboard Layouts.

**Slovak has no good pairing.** No kbd map has Slovak's number row, so a `1` typed at the
installer is `+` at the login screen. Owner decision 2.

**The fourth column is shown.** `ask_password` prints, when the column is not empty: *"On
this layout these type differently at the login screen, so leave them out of your password:
…"*. The same column is what the check compares against (Verification), so the message and the
measurement cannot drift.

**Answers-file keymaps outside the menu.** `xkb_for_keymap` reads the menu's column 2 first, then the
first `kbd-model-map` row (new substitution `@kbdmodelmap@`, a store path, as #1614 does), then
falls back to `us`. A `-` variant means empty. A row's first non-`us` layout in upstream's
non-Latin list gets `us` in front, and a variant moves to `,variant`. The list comes from
upstream's `default/hypr/input.lua` (new substitution `@nonlatin@`, via `builtins.match`,
which breaks the build if upstream reshapes it, §4). A fallback prints in the answers summary
(`install.sh:1513`) and `confirm_summary`: *"Desktop keyboard: us (no XKB equivalent of X)"*.

The two now-unlisted values `se-lat6` and `cz-qwertz` have no `kbd-model-map` row, so an existing
answers file naming them gets `us` on the desktop and says so. That is what they get today.

### 2. The template

`installer/template/host/configuration.nix:15`, beside `console.keyMap`:

```nix
  # The login screen and the desktop. console.keyMap above is the text console and the disk prompt.
  services.xserver.xkb = {
    layout = "@xkblayout@";
    variant = "@xkbvariant@";
  };
```

`substitute_host_files` substitutes both. `services.xserver.enable` stays off (the intent
measured the option changing only `weston.ini`). A US answer writes the option's own defaults,
so it adds no store path.

### 3. `/etc/vconsole.conf`, in `installer/host.nix`

Upstream's session reads `XKBLAYOUT` and `XKBVARIANT` there, and NixOS writes only `KEYMAP=`.
`installer/host.nix`, not `modules/nixos.nix`: Mode A never imports it, and machines already
installed have `xkb` at its default, so neither changes (intent's open question 1).

```nix
environment.etc."vconsole.conf" = lib.mkIf
  (config.console.enable && !config.i18n.imperativeLocale && (xkb.layout != "us" || xkb.variant != ""))
  { source = lib.mkOverride 90 (pkgs.writeText "vconsole.conf" ''…''); };

services.xserver.xkb.options = lib.mkIf (lib.hasInfix "," xkb.layout)
  (lib.mkDefault "terminate:ctrl_alt_bksp,grp:alts_toggle");
```

- The body repeats `console.nix`'s two lines (`KEYMAP=`, `FONT=` when set) and adds the XKB lines.
  It cannot read the option it replaces.
- `mkOverride 90`, not `mkForce`: it beats nixpkgs' literal, and a user's `mkForce` still beats it (§7).
- Only the system's copy changes. The initrd's copy comes from `boot.initrd.systemd.contents`
  (`console.nix:176`) and stays `KEYMAP=` only, which §5 depends on.
- Measured with `hl` stubbed: `us,ru` gives `kb_layout=us,ru` and `grp:alts_toggle`; `de`,
  `ch:fr` and `us:dvorak` come through as written.

No patch to upstream's Lua.

### 4. The greeter: keep weston

Both measured, and weston wins on the intent's own constraints.

| | Weston with `xkb.*` (chosen) | Upstream's `sddm/hyprland.lua` |
|---|---|---|
| Latin layout | `keymap_layout` follows (intent's control) | Reads `vconsole.conf` (stubbed: `de`) |
| Non-Latin | `us,ru` plus `grp:alts_toggle`; compiles with `xkbcli` | `ru` gives the same. **`us,ru` gives no toggle** (stubbed), so it needs a different value from the session's |
| A US install | No change | Changes `CompositorCommand` on **every** machine, so outcome 6 fails, and the first screen of the ISO's closure |
| Option | Public `xkb.*` | Overrides the internal `compositorCommand` |
| Closure | Nothing new | Could drop weston: at most 571 MiB beside Hyprland (measured, unpacked, upper bound, as much of it is shared with the rest of the system) |
| Runs today | Every boot | Never here, and not run for this spec |

The 571 MiB is a real reason to revisit this, on its own issue, with a booted comparison. It
is not a reason to change every machine's first screen to fix a layout. Nothing is deleted.

**Unrun:** weston's group toggle with a real keypress. The VM check covers it.

### 5. The LUKS prompt: expected to work already

Read and partly measured, **not booted**:

- Plymouth takes evdev input through XKB only if it can compile a keymap; otherwise it logs
  "no configure XKB layout" and reads the terminal (`ply-device-manager.c:456`, `:843`).
- The reference initrd holds `libxkbcommon` and **no XKB data** (measured: built it, listed
  2,523 paths, none from `xkeyboard-config`). So the compile should fail and the terminal path
  should run.
- The terminal uses the kernel's keymap. `systemd-vconsole-setup` loads it from the initrd's
  `/etc/kbd/keymaps` with `earlySetup = false` (`console.nix:176-184`), and `plymouth-start` is
  `After=` that unit (measured from the shipped unit).

So the prompt and the installer use the same console map, and only the console column of
§1 decides whether the passphrase matches, with no code change. `ask_recovery` uses the same.

**If the VM disagrees**, the fix is one line: `boot.kernelParams = [ "plymouth.use-legacy-input" ]`
in `installer/host.nix` (`ply-device-manager.c:451`). It adds a kernel parameter on non-US
machines. If that does not work either, this splits into an issue the same day, as the intent
says, with the owner's say on narrowing outcome 5.

Upstream's `omarchy_vconsole.conf` shows a trap to keep out: XKB lines in the initrd's copy
would hand Plymouth a layout, which is why upstream keeps a non-Latin one out. §3 stays clear of it.

### 6. `--from`, and a failed `loadkeys`

**`--from` with an existing host.** The clone has run by then (`clone_repo`, before
`install.sh:3209`), so a `load_repo_keymap` step before `ask_password` reads
`console.keyMap = "x"` from `$hostdir/configuration.nix`. If `validate_keymap` accepts it, it runs
`loadkeys` and says *"Typing with this machine's layout: x"*. If not found, for example in a repository
that sets it in a shared module, it warns: *"Typing with a US keyboard. If this machine uses another
layout, pick a password that types the same in both."*

I rejected `nix eval` here: it is minutes of evaluation on a RAM-backed store for one string, and
the fallback has to exist anyway.

**`ask_keymap`'s `loadkeys … || true`** becomes the same warning. Silently typing a password under the
wrong map is the failure this issue is about.

### 7. Existing machines, and the release note

No migration, as approved. The note, also for the Discussions post (§14):

> **The installer's keyboard choice now reaches the login screen and the desktop.** A machine installed
> before this release has it on the text console only. To fix one, add to `configuration.nix`, using
> your layout, and rebuild:
> `services.xserver.xkb = { layout = "de"; variant = ""; };`
> Non-Latin layouts use `layout = "us,ru";`, so Left Alt + Right Alt switches and your password still
> types. **Change your password first if it uses a key that differs**, because the login screen starts
> using the new layout at the next rebuild. Keyboard Layouts and `~/.config/hypr/input.lua` still win
> in the session.
> Four menu entries changed: French, Swedish and Czech use another console map, Lithuanian starts on `lt(us)`.

### Coexistence (§14)

`xkb.layout` is a scalar, so a clash is an evaluation error or a normal override, not a silent
shadow. Added to `tests/coexistence/fixtures.nix`, asserted in `default.nix` by reading
`vconsole.conf`'s text and the `CompositorCommand` `weston.ini`:

| Fixture | User sets | Asserts | Break that makes it fail |
|---|---|---|---|
| `keyboard-own-xkb` | `xkb.layout = "fr"` | `XKBLAYOUT=fr` and `keymap_layout=fr` | Take the layout from `console.keyMap` |
| `keyboard-own-options` | `xkb.layout = "us,ru"`, own `xkb.options` | Theirs in `weston.ini` | Plain assignment of `options` in §3, which then conflicts |
| `keyboard-own-vconsole` | `environment.etc."vconsole.conf".text` under `mkForce` | Their file | `mkForce` in §3, which ties and refuses to evaluate |
| `keyboard-xkb-console` | `console.useXkbConfig = true`, `xkb.layout = "de"` | `KEYMAP=` is the `xkb-console-keymap` path, and `XKBLAYOUT=de` | Hardcode `KEYMAP` from the template's answer |
| `keyboard-imperative` | `i18n.imperativeLocale = true`, `xkb.layout = "de"` | No `vconsole.conf` entry, as nixpkgs seeds it by tmpfiles | Drop that test from the `mkIf` |
| `keyboard-kwin-greeter` | `sddm.wayland.compositor = "kwin"`, `xkb.layout = "de"` | `CompositorCommand` holds kwin, and `XKBLAYOUT=de` | Set `compositorCommand` in `host.nix` |

- **`console.useXkbConfig` on a generated host** still conflicts with the template's normal-priority
  `console.keyMap` (read, `console.nix:144-149`), as it does today. The error is immediate and the
  fix is to delete one line, so it stays. The fixture covers `host.nix`'s `mkDefault`.
- **`~/.config/omarchy/keyboard-layouts` and `input.lua`** are per-user files, not NixOS modules, so
  they belong in the cheap Lua check below rather than a fixture.
- **`programs.nixarchy.displayManager = false`**: no fixture, because we set nothing there and it
  could not fail.

## Alternatives rejected

- **Derive XKB from `console.keyMap` in the module.** Reaches old machines and changes Mode A, against
  the approved answer, and the mapping would have to run at evaluation.
- **`console.useXkbConfig` everywhere, so the console is compiled from XKB.** Console and XKB would
  match by construction, which also solves Slovak. But it builds with `ckbcomp` on the target, adds it to
  the ISO for the installer's own `loadkeys`, and rewrites the console for every non-US machine. Worth a
  look if the residual column grows.
- **Patch `keyboard.lua` to read another file.** A patch carried at every bump, for a file NixOS can write.
- **Seed `~/.config/omarchy/keyboard-layouts`.** Per user, outranks nothing on rebuild, and leaves the
  greeter unfixed.
- **Use `kbd-model-map` for the menu too.** 7 rows are absent, and it is silent about passwords.
- **A new option, such as `programs.nixarchy.keyboard`.** Nobody asked, and `xkb.*` is the public one.

## Risks

- **A rebuild can lock out a machine that adopts the release note.** Its password was typed under the
  console map, and the greeter moves. The note leads with it. New installs are covered by §1.
- **Weston with two layouts and a toggle is unrun.** If it fails, a non-Latin machine still has Latin at
  the login, which is what outcome 3 needs, and loses only the switch there.
- **Offline ISO with a non-US answer is unmeasured.** The new paths are text files, so I expect no compiler
  or fetch (read). `install-iso` settles it. If it needs a path the ISO lacks, it goes in the seed list,
  and `iso-budget` reads the cost.
- **`cz-us-qwertz` and `fi` are unusual names** on a console nobody else tests. `lt:us` changes where
  Lithuanian letters sit, which is owner decision 1.
- **AltGr is unmeasured** by the comparison, so a password using AltGr symbols may differ on rows the table
  shows clean.
- **`host.nix` repeats two lines of `console.nix`.** If nixpkgs adds a line, it is lost on non-US machines
  until a bump notices.

**`checks.keyboard-boot`: what proves a real boot.** A `nixosTest` on the reference with a LUKS root
(the shape of nixpkgs' `systemd-initrd-luks-password`), Plymouth on, autologin off, two nodes:

- **`de`**, `console.keyMap = "de-latin1"`, password and passphrase `zy`. `send_chars` sends physical keys, so
  it sends `yz`. The boot passes the disk prompt, the greeter logs in, a terminal receives a typed `yz` as `zy`,
  `hyprlock` unlocks with it. `tests/session.nix:2733` already has the wake-then-type sequence.
- **`ru`**: passphrase and password `omarchy`, typed plain. `hyprctl devices` then reports `English (US)`
  first, and Left Alt + Right Alt moves it to `Russian`. The same toggle at the greeter is seen by typing a
  Cyrillic password into a throwaway field and reading the failure, not the success.

Break: delete the template's lines and the `de` node stops at the greeter; set `layout = "ru"` and the `ru` node
cannot log in; remove `console.keyMap` and `de` stops at the disk prompt. That last one is the "VM first" for §5,
and I will run it first, as a throwaway, as soon as CI is idle, before the plan is written if I can.

Serial cannot do this: `install-encrypted` types on the serial line, which never touches a keymap.

It needs KVM, so it is claimed and put in a job, which is a CI-gate change for a human (§4, §11). Owner decision 3.

## Owner decisions

1. **Change four menu rows (§1)?** *Recommended: yes.* French, Swedish and Czech change only the console map a new
   install uses. Lithuanian starts on `lt(us)`, with letters on AltGr, because `lt` differs on the digits. The
   alternative for Lithuanian is `lt` plus the warning.
2. **Slovak.** *Recommended: keep `sk-qwerty` and `sk:qwerty` and show the warning,* which tells a Slovak not to put
   digits or symbols in their password. The alternative is compiling this one console map from XKB, which brings
   `ckbcomp` to the ISO for one entry.
3. **Where `keyboard-boot` runs.** *Recommended: nightly-only, with a pasted run on this PR.* The cheap checks catch a
   wrong row on every PR, and what only the VM sees moves with a nixpkgs bump, which the nightly gate sees. The
   alternative is the `box` job, about ten more minutes per PR. Either way the workflow edit is proposed for you to merge.
