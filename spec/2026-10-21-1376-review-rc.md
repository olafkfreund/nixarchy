# Spec: the nightly review stops asking for a downgrade and an RC release while main is on an RC

Pre-approved by the owner, 2026-10-21 ("I preapprove the spec and the plan
as well. Just finish this").

## Design

`pkgs/review.sh`:

1. **`omarchy` row (:240-248).** Keep `omarchy_latest` as it is: it is
   `releases/latest`, the newest **final**, and the release row needs it. Add
   `omarchy_newest`, the newest by `.github/scripts/omarchy-newest.sh
   "$omarchy_pin"` (RCs included, never backwards). The row then reads:
   - "cannot reach GitHub" if the script fails;
   - "bump" only when the script says `changed=true`;
   - ok otherwise, showing `omarchy_newest` in the upstream column.
2. **The menu-mapping row (:253-268)** checks `omarchy_newest`'s menu, the
   version the bump would adopt. rc1's menu maps cleanly: "all 40 Install
   rows are mapped (3 by a recorded exception)" (measured).
3. **`release` row (:320-337).** Before the "no ISO" finding, add a branch:
   when `pkg_version` is a prerelease (`*-*`) and the newest release's
   Omarchy equals `${omarchy_latest#v}` (the newest final), report ok with
   "newest final; main's <rc> is an RC, never tagged (#1405)". Everything
   else is unchanged.

## Alternatives rejected

- **Tagging an RC:** it ships the RC to every installed machine (#1405).
- **Skipping the rows while on an RC:** they would then miss a newer RC or a
  final that shipped without its ISO.

## Risks

- The review needs `gh` for `omarchy-newest.sh`. It already uses `gh`, and
  `gh` is in its runtime inputs.
