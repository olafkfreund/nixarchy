# Spec: a nightly failure always reaches its issue

Decisions carried from the approved intent: a last-resort cut in the
`report` step as well as the script fix (question 1, yes); the priority
order for a tight cap (question 3, as recommended); question 2 decided here
from a measurement.

## The measurement behind question 2

Tonight's failing target, `checks.x86_64-linux.keyboard-boot` at `125d6f1`
(`rb385i1m…-vm-test-run-nixarchy-keyboard-boot.drv`), replayed on p620's
shared store, the one the digest runner uses:

| closure | count |
|---|---|
| derivations in `nix-store -qR` | 16,745 |
| …with an output not in the store and a **local** log | 169 |
| …whose local log was written after the job started (03:06:47) | **1**, the VM test itself (log written 05:07) |

The other 168 local logs are of earlier builds whose outputs were since
collected, dated 2025-11-18 to 2026-11-13. So "local log" alone would still
have named 168 false roots. "Local log written since the job started" named
exactly the one that failed. The replay, one `nix-store` process per
derivation as the script does today, took over ten minutes even with no
network.

## Design

### 1. Roots: a local log written during the failed job

`.github/scripts/nightly-digest.sh`, the root loop (today lines ~120-140):

- For each `.drv` in the closure, compute its log file path in bash, with no
  process: `${NIX_LOG_DIR:-/nix/var/log/nix}/drvs/<first 2 chars of the
  basename>/<rest>`, with or without `.bz2` (nix writes both forms). Keep
  only those that exist **and** whose mtime (`stat -c %Y`) lies between the
  failed job's `started_at` minus 60 s and its `completed_at` plus 60 s, both
  from the jobs JSON the script already reads (`started_at` confirmed in the
  live API for this job; the 60 s is slack for clock skew between GitHub and
  p620). Nix 2.35 writes the split `drvs/xx/rest` layout (confirmed on p620,
  and in nix's reader, which also accepts a legacy flat layout that no nix
  this repository runs still writes; not supported).
- Only those survivors get `outputs_valid` (today's check, unchanged), so
  the per-derivation processes run for a handful of paths, not 16,745.
- `read_log` becomes `nix log --option substituters '' "$1"`: the excerpt
  can then only come from this machine, for roots and the fallback alike.

A root is therefore labelled honestly: "built during this job, and not in
the store". That is recency, not proof of failure: on a shared store, a
concurrent job could build the same path. The heading says "built during
this job" rather than "failed".

The **target fallback** (today: no roots, so read the target's own log)
stays, and applies the same window. A target log outside it is still shown,
because the target is what the job asked for, but labelled `(log from
outside this job's run: may be an earlier build)`.

### 2. A cap in bytes that bounds everything except the job headings

- The script sets `LC_ALL=C` for its own length arithmetic, so `${#var}`
  and `${var:0:n}` work in bytes. Excerpts themselves are not altered.
- **Every job heading always survives** (the intent's constraint). Each is
  cut to 300 bytes, and `DIGEST_MAX` below 4,096 is refused as invalid
  (the script's existing validation, `digest unavailable: DIGEST_MAX ...`).
  A nightly has 11 reportable jobs, so headings cost at most 3,300 bytes and
  always fit; no `more jobs not shown` line exists.
- After the headings, the budget is spent in this order, with every byte of
  framing (labels, fences, newlines, omission lines) counted before it is
  spent, and one omission line reserved per level before that level starts:
  1. each target's label line;
  2. each target's **first** root with an excerpt. The remaining budget is
     split evenly between the targets that have one, so one large excerpt
     cannot starve another target; a share a target does not use returns to
     the pool for the next level;
  3. the names of further roots, in closure order, then
     `(N more derivations not shown)`;
  4. further excerpts, then `(N more excerpts not shown)`.

  An excerpt is cut at whole lines, and its fence is always closed: the
  closing fence's bytes are reserved before the excerpt's lines are added.
- `emit` keeps a final backstop on any body, the `unavailable` fallback
  included: if a body is still over `DIGEST_MAX` (a bug in the assembly),
  cut at the last whole line within the cap less the note's bytes, close an
  open fence, and append `(digest cut at N bytes: this is a bug in
  nightly-digest.sh)`. The tests assert it never fires in a normal case.
- `DIGEST_MAX` stays 50,000. In bytes it is a hard bound well under both
  GitHub's 65,536 characters and the kernel's 128 KiB limit on one
  environment variable.

### 3. The report step cannot be stopped by the digest

`.github/workflows/nightly.yml`, `report` job, "Open or update an issue":

- One helper inside the step, `fit()`, uses no pipeline (a `head -c` under
  `pipefail` exited 141 in review): under `LC_ALL=C` it takes
  `${s:0:$((60000 - ${#note} - 1))}`, drops the partial last line with
  `${x%$'\n'*}`, and appends `$'\n'$note`, where `note` is `(cut to fit
  GitHub's limit; the run log has the rest)`. A string already within
  60,000 bytes is returned unchanged.
- Both payloads go through it: the new-issue `body` and the `Still failing`
  comment.
- Transport: the digest still arrives as `env: DIGEST`, which is safe once
  the script bounds it in bytes. Not moving it to a file is deliberate:
  outputs between jobs are strings, and the script's cap is the guard there.

### 4. Tests

`tests/nightly-digest.nix` and `tests/nightly-digest/`:

- **Stubs.** `bin/nix`'s `log` takes the derivation as its **last**
  argument and serves, in order, `log/` and `old-log/` always, and
  `remote-log/` only when `substituters` is not disabled on the command
  line. So an old log is readable exactly as a real local one is; only its
  file's mtime differs. The check builds a per-case `NIX_LOG_DIR` in nix's
  `drvs/xx/rest` layout: files from `log/` with an mtime inside the case's
  job window, files from `old-log/` with an mtime a day before it.
  `remote-log/` gets no file there.
- **Fixtures.** Every job in every case's `jobs.json` gains `started_at` and
  `completed_at` (none has them today). The existing ten cases keep their
  meaning; `c7-cap` moves from `DIGEST_MAX=2000` to `4096`, the new floor.
- **New cases**, each shown failing on today's script first (§1):
  - `c11-many-roots`: one target, 300 roots with logs in `log/`, at
    `DIGEST_MAX=4096`. Fails today (over the cap: headings and labels are
    never cut). Passes when the digest is at most 4,096 bytes, holds every
    job heading, the first root's excerpt, and a `more derivations not
    shown` line.
  - `c12-remote-and-old`: one root in `log/`, 50 dependencies only in
    `remote-log/`, 20 only in `old-log/`. Fails today: it names all 71.
    Passes when the digest names the one and none of the 70. A second run
    with the window check removed by hand must name the 20 (the §1 break
    for the timestamp rule specifically).
  - `c13-bytes`: run under `LC_ALL=C.UTF-8`, one excerpt of 1,500
    three-byte characters (4,500 bytes, 1,500 characters) at
    `DIGEST_MAX=4096`. Fails today (counts characters, so it fits); passes
    when `wc -c` is at most 4,096.
  - `c14-fallback-old`: a target with no roots and only an old log. Passes
    when the excerpt is shown with the `outside this job's run` label.
  - Every case asserts the `emit` backstop line is absent.
- **Report step.** A runCommand extracts the step's `run:` with `yq`, then
  replaces each `${{ … }}` with a fixture value by a fixed table (each
  `needs.<job>.result` → `success`, except `needs.keyboard-boot.result` →
  `cancelled`; `contains(needs.*.result, 'cancelled')` → `true`), and fails
  if any `${{` survives the substitution. It stubs `gh` to record the
  `--body` of `issue create` and `issue comment`, and runs the script under
  `bash -euo pipefail` twice with a 100,000-byte `DIGEST`: once with no open
  issue, once with one. The stub must have recorded exactly one call each
  time, and each body must be at most 60,000 bytes and end with the note.
  It fails today with a recorded body over 60,000, not with a harness
  error: the case asserts the call was recorded before it asserts its size.

## Alternatives rejected

- **Local logs only, no timestamp.** Measured: 168 false roots on p620
  tonight.
- **Timestamp only, remote logs allowed.** A remote log has no local mtime;
  it would have to be fetched to be judged, which is the four hours.
- **Ask nix which derivations failed.** Older nix kept a failed-path cache;
  I have not confirmed current nix still offers one, and a build cut off by
  a job timeout is never recorded as failed by anything, which is exactly
  this case.
- **Raise `DIGEST_MAX`.** It moves the cliff and leaves the headings
  unbounded.
- **Pass the digest through a file or artifact.** More moving parts between
  two jobs; with a byte cap the environment variable is safe, and the report
  step's own `fit()` covers the GitHub limit.
- **Cap only in the report step.** The env-var limit is hit before the step's
  shell runs, so the script has to bound itself too.

## Risks

- **A real root missed**: a failing build whose log nix did not write, or
  wrote before `started_at` (clock skew between GitHub's timestamp and
  p620, beyond the 60 s slack). The target-level fallback (today's
  `read_log "$drv"` when there are no roots) still covers the target itself.
- **A concurrent job's build counted as a root.** Labelled "built during
  this job", not "failed", so the reader is not told more than is known.
- **Workflow change.** The `report` step is the repository's watchdog. The
  change adds a size cut and touches no trigger, `needs`, condition or
  timeout; the PR calls it out for review (§11).
- Hosts: the digest runs on p620's self-hosted runners and gets lighter.
  Nothing reaches a user machine.
