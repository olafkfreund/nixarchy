# Intent: The input method's candidate window has no page or menu glyphs

## Problem

`omarchy-theme-set-fcitx5` builds the Omarchy theme for fcitx5's candidate window. It copies the
generated `theme.conf`, then links the stock theme's SVG glyphs beside it, because `Image=` entries
resolve inside the theme's own directory.

`pkgs/omarchy/default.nix:906-908` points the script at
`/run/current-system/sw/share/fcitx5/themes/default`. That directory does not exist:

- fcitx5 is in `environment.systemPackages`, through nixpkgs' input-method module.
- The system profile links only what `environment.pathsToLink` names. Neither nixpkgs' defaults nor
  `modules/nixos.nix:1379` name anything under `/share/fcitx5`.
- Measured on this machine: `/run/current-system/sw/share/fcitx5/themes` is absent. The directory it
  should have reached is in the package, at `share/fcitx5/themes/default`, with the SVGs in it.

The script says nothing. Its loop tests each glob match with `[[ -e $glyph ]]`, so a missing directory
links nothing and it carries on, and `--activate` still selects the Omarchy theme. Upstream's own
stock theme names `prev.svg`, `next.svg`, `radio.svg` and `arrow.svg`, so a user typing with an input
method gets a candidate window with those images missing. Nobody has reported this, and it has not
been seen on screen: the effect is read from the script and the theme file.

## Proposed outcome

On a machine using fcitx5, the Omarchy candidate-window theme has its page and menu glyphs, and they
keep working across rebuilds and garbage collection. A check can see the path go missing.

## Affected users and systems

- Anyone typing through fcitx5 whose candidate window uses the Omarchy theme. A theme the user picked is
  left alone by the script, so they are not affected. #1614 (PR #1634) makes the input methods
  work for the first time, so this becomes visible once that merges.
- Mode A: someone importing `nixosModules.nixarchy` without fcitx5 must see no change.
- Existing machines: `~/.local/share/fcitx5/themes/omarchy` gets the glyphs the next time the script
  runs, which is the next theme change. Nothing runs it on upgrade, so someone who never changes theme
  keeps the missing glyphs.

## Constraints

- **Do not link all of `/share/fcitx5`.** `fcitx5-with-addons` adds its own share directory to the end
  of `XDG_DATA_DIRS`, and the session's search path includes the system profile. Linking the whole
  directory would show every addon's `.conf` to any fcitx5, including a stale addon-less daemon, which
  is the state `checks.session` reproduces for #1614. Its libraries would not be there to load.
- **A store path in the script does not meet "across garbage collection".** The script makes symlinks
  in the user's home. A path into one generation's store dangles once that generation is collected,
  until the next theme change. Through the system profile, the link follows the current system.
- `pathsToLink` is a list, so this is plain assignment (§7). Its condition is the module's existing
  `usingFcitx5`, not `cfg.session`, which is what the neighbouring entry uses. fcitx5 configured only through
  Home Manager has no system profile entry, and stays out of scope.
- A `checks.*` entry that can fail (§1, §2), since this path has been dead with every check green.

## Open questions

1. **Which fix?** Recommended: add `/share/fcitx5/themes` to `pathsToLink` when fcitx5 is in use, and
   leave the patch as it is. It exposes themes only, which is what nothing else searches differently
   for. Rejected above: linking all of `/share/fcitx5`, and a store path in the script.
2. **Should an upgrade repair existing machines?** Recommended: no. The glyphs arrive at the next theme
   change, and the defect is cosmetic, so an activation hook is more to maintain than the bug is worth.
   The cost is that someone who never changes theme stays affected, so the release note gives the one
   command that fixes it.
3. **Land before or after #1634?** Recommended: after, because both edit `tests/input-methods.nix`'s
   neighbourhood, and the check belongs in that file, which only exists once #1634 merges.
