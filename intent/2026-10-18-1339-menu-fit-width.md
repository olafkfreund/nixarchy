# Intent: the Omarchy menu is wide enough to show its labels

## Problem

The menu card has a fixed width. `shell/plugins/menu/Menu.qml` (v4.0.5, line
112) sets `cardWidth` to `Style.space(300)` for every menu, with two
hard-coded 520 exceptions (`trigger.capture.screenrecord`, `style.font`).
Labels are elided with `Text.ElideRight`, so on a real machine the Apps menu
(Super+Alt+Space) shows "Advanced Network …", "AIFactory — freun…" and
"Audiobook Search …". The user cannot tell some apps apart without typing a
filter. Web apps suffer most, because their names carry a "— site" suffix.

No setting reaches this. It is not in `shell.json`, the menu jsonc or any
option, so a user's only way out today is to clone `omarchy.menu`. That
freezes the whole menu against upstream and against nixarchy's own menu
patches (#1301, #1305).

## Proposed outcome

- Opening any menu sizes the card to its widest label, so a name that fits on
  screen is shown in full.
- Short menus look as they do today: the card is never narrower than the
  current width, including the two 520 exceptions and a caller's dmenu width.
- The card has a cap, so one very long label cannot make a huge menu. Labels
  past the cap still elide.
- Typing a filter never makes the card shrink or jump. It only grows, and only
  while the menu is open.
- Users who cloned `omarchy.menu` just for this can delete the clone.

Prototype: a clone on p620 (2026-10-18) did exactly this. Apps grew from 300
to the cap, and the full names showed on screen.

## Affected users and systems

- Every Omarchy session on both channels. It touches only the menu's width,
  not its rows, actions or keybindings.
- `pkgs/omarchy/default.nix`: one more carried `--replace-fail` patch on
  `shell/plugins/menu/Menu.qml`, next to the #1305 patches on the same file.
- `pkgs/AGENTS.md`: a "Why" entry, as the other menu patches have.

## Constraints

- `--replace-fail`, so an Omarchy bump that rewords `cardWidth` fails the
  build rather than silently dropping the patch (pkgs/AGENTS.md, "Patching
  upstream").
- It must not conflict with the #1301 and #1305 patches on the same file.
- No new option. The behaviour is not something a user should have to turn on.

## Open questions

1. **Cap.** The prototype used `Style.space(640)`. Keep that, or make it a
   fraction of the screen width, so it scales better from razer's 1920 to
   p620's 2560?
2. **Upstream.** Should this also go to omacom/omarchy as a PR, so the
   carried patch can be dropped later? (Some carried patches are deliberately
   not reported upstream, e.g. #953.)
