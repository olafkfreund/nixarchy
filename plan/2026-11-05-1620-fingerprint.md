## Decisions carried from the approved spec

**What ships.**

- The row runs upstream's script as far as its deletions and stops. Everything below them
  that is wrong on NixOS is cut from the file, so "must not reach" holds because the text
  is not there, not because an `exit` sits above it. Removing the early exit outright is
  rejected (it reaches `rm /etc/pam.d/omarchy-lock-fingerprint` and `omarchy-pkg-drop`), and
  so are keeping an `exit` above the unwanted lines, and `--replace-fail` line by line.
- Upstream's account lookup and safety check (`:9-22`) and its privilege check (`:66-69`) run
  unchanged. Only the invoking account's prints go; other accounts' stay.
- `fprintd-delete` first, `rm` second. `rm` first orphans a reader's copy: fprintd finds a
  device's prints through the host's files (`src/device.c:2355,2380,2399`).
- **A real `fprintd-delete` failure runs no `rm`** (owner decision 1, departs from upstream).
  It says some may already be gone, because fprintd removes the host file and then reports the
  device error (`src/device.c:2395-2480`), and prints the manual `rm` as a last resort.
- **No confirmation** (owner decision 2). The row is named Remove, `sudo` already prompts, and
  re-enrolling undoes it.
- `sudo` in the floating terminal the row already opens, as upstream. `pkexec` is rejected.
- Snapshots are reported, unconditionally, with no retention period claimed. They are not
  detected, edited or deleted. The factory reset gains one sentence and no behaviour. Machines
  already switched off get a documented route, in this order: fprintd on, Remove, fprintd off
  when the reader might store prints; otherwise the `rm` with the account written out.
- Sets no option and declares nothing, so §14 needs no fixture. Mode A: the row is there, and
  pressing it is the request.

**Exit status** answers "did the deletion the person asked for run?"

| state | `/var/lib/fprint/<user>` | says | exit |
|---|---|---|---|
| prints deleted, reader present | removed | deleted | 0 |
| only leftovers from an earlier reader | removed | deleted | 0 |
| nothing on record (second press) | no-op | none on record, with the reader caveat | 0 |
| no reader (`No devices available`) | removed | deleted if there were files, plus "stay there" | 0 |
| `fprintd-delete` absent | removed | same, plus "fprintd is off" | 0 |
| `fprintd-delete` fails otherwise | row runs no `rm` | the reason, may already be gone, press again, the manual `rm` | 1 |
| `sudo` refused or absent, before or at the delete or the probe | not touched | needs administrator rights | 1 |
| `rm` fails, or `sudo` refuses it | possibly part removed | removal may be incomplete | 1 |

**Four places this plan is more exact than the spec's sketch. The reviewer and the owner should
read these.**

1. **The probe.** The spec sketches `sudo test -e … && had_files=1`, and its table says a `sudo`
   refused at a later prompt reports administrator rights. Those conflict: with
   `timestamp_timeout=0` a refused `test` reads as "no files". The block below returns the answer
   on stdout so sudo's status means only sudo. A refusal at the `rm` itself cannot be told from a
   failed `rm` without capturing `rm`'s stderr, and "may be incomplete" is true of both.
2. **The login line.** The spec prints "Fingerprint login is still declared" always. With fprintd
   off that is false, and the row's job is to claim nothing false, so it is skipped when
   `reader=off`.
3. **The spike's press.** The spec's spike presses the shipped script in step 1, but until step 2
   ships, that script exits 1. The spike runs the same two commands by hand to prove the harness.
   Step 7's permanent check presses the shipped script.
4. **Release notes.** They are derived (`.github/scripts/release-notes.sh`: commit subjects,
   options, pins), so there is no file to put the paragraph in. The commit subject says the row
   now deletes, and the PR body carries the paragraph for the release and Discussions post (§14).

### 2. The shipped script

**New file: `pkgs/omarchy/1620-remove-fingerprint.sh`, exactly:**

```bash
reader=off
if omarchy-cmd-present fprintd-delete; then
  # Only fprintd-delete's output is captured, so a sudo prompt or refusal stays on the terminal.
  if delete_output=$(sudo sh -c 'fprintd-delete "$1" 2>&1' sh "$fingerprint_user"); then
    # It exits 0 for "deleted" and "nothing to delete", and two readers can print one of each.
    if [[ $delete_output == *" deleted on "* ]]; then reader=deleted; else reader=none; fi
  elif [[ $delete_output == *"No devices available"* ]]; then
    reader=absent
  elif [[ -z $delete_output ]]; then
    echo -e "\e[31mDeleting fingerprints needs administrator rights.\e[0m"
    exit 1
  else
    # fprintd reaches a reader's copy only through the host's files, so they stay for another try.
    echo -e "\e[31mfprintd could not finish deleting $fingerprint_user's fingerprints: $(tail -n 1 <<<"$delete_output")\e[0m"
    echo "Some may already be gone. Press Remove again."
    echo "If fprintd never recovers, this removes the files and leaves any copy on the reader out of reach for good:"
    echo "  sudo rm -rf -- /var/lib/fprint/$fingerprint_user"
    exit 1
  fi
fi

# The answer comes back on stdout, so a refused sudo cannot read as "no files".
if ! had_files=$(sudo sh -c 'if [ -e "$1" ]; then echo 1; else echo 0; fi' sh "/var/lib/fprint/$fingerprint_user"); then
  echo -e "\e[31mDeleting fingerprints needs administrator rights.\e[0m"
  exit 1
fi
if ! sudo rm -rf -- "/var/lib/fprint/$fingerprint_user"; then
  echo -e "\e[31mCould not remove $fingerprint_user's saved fingerprints, so the removal may be incomplete.\e[0m"
  exit 1
fi

if [[ $reader == deleted || $had_files == 1 ]]; then
  echo -e "\e[32mDeleted $fingerprint_user's saved fingerprints.\e[0m"
else
  echo "fprintd has no fingerprints on record for $fingerprint_user. A reader that refused an earlier delete may still hold its copy."
fi
case $reader in
absent) echo -e "\e[33mNo fingerprint reader is available now, so any fingerprints stored on the reader itself stay there.\e[0m" ;;
off) echo -e "\e[33mfprintd is off, so any fingerprints stored on the reader itself stay there.\e[0m" ;;
esac

echo
echo "Disk snapshots taken since you enrolled still hold a copy until they are deleted."
echo "\`sudo snapper -c root list\` shows the boot snapshots."
if [[ $reader != off ]]; then
  echo
  echo "Fingerprint login is still declared. Turn off services.fprintd (fprintAuth follows it), then Apply changes."
fi
```

```markdown
stay, and it does not ask for confirmation beyond `sudo`. If you change your mind, enrol again.

What it does not do:

- **Turn fingerprint login off.** That is still your configuration: turn off `services.fprintd`
  (`fprintAuth` follows it), then Apply changes.
- **Reach a disk snapshot.** Snapshots taken since you enrolled hold a copy until they are
  deleted. `sudo snapper -c root list` shows the boot snapshots.
- **Reach a reader that is not there.** With no reader attached it removes the files, and any
  copy on the reader itself stays there, with no way left to address it.
- **Press on after a real failure.** If fprintd refuses, the files stay, because they are how
  fprintd finds the reader's copy. Press Remove again.

If you already turned `services.fprintd` off, your templates are still on disk:

1. If the reader might store prints itself, or you are not sure, turn `services.fprintd` back on,
   Apply changes, press Remove, turn it off, and Apply changes again. Removing the files first
   leaves the reader's copy out of reach for good.
2. Otherwise: `sudo rm -rf -- /var/lib/fprint/<user>`, with the account written out. `$USER` is
   wrong in a root shell.

A factory reset keeps fingerprint templates, in the `/var/lib` it sets aside, and the reader keeps
its own, so run Remove first.
```
