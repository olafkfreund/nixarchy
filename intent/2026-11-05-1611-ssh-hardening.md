# Intent: Turning on SSH from the menu leaves password logins on

## Problem

Upstream's v4.5.0 `bin/omarchy-setup-security-sshd` authorizes a key, writes
`PasswordAuthentication no` and `KbdInteractiveAuthentication no`, checks they
took effect, and only then starts sshd. The machine never listens with
passwords on. Ours does none of that.

- `setup.security.sshd` runs `nixarchy-service-enable openssh`
  (`modules/apps.nix:898-899`), and `install.service.openssh` runs the same
  command (`modules/apps.nix:1092`). That command uncomments one line in
  `services.nix` (`modules/apps.nix:1764` onward). It asks for no key, and
  neither row opens a terminal.
- The catalogue's openssh row is `kind = "plain"`, so nixarchy adds nothing
  beside `services.openssh.enable = true` (`data/services.nix:11-16,73-81`).
- Nothing in `modules/`, `data/` or `installer/` sets `PasswordAuthentication`.
- nixpkgs defaults `PasswordAuthentication`, `KbdInteractiveAuthentication` and
  `openFirewall` to `true`
  (`nixos/modules/services/networking/ssh/sshd.nix:312-314,547-549,569-571` at
  the locked nixpkgs).

Measured with a minimal evaluation at that nixpkgs, `services.openssh.enable =
true` alone gives both settings `true` and PAM `unixAuth = true`. So after
Apply, port 22 is open and accepts the password of any account that has one,
except root (`PermitRootLogin` defaults to `prohibit-password`), with no rate
limit (`docs/manual/security.md:66-69`).

Our text tells the user the opposite, or describes a route that is gone:

- `data/services.nix:81` says "NixOS defaults to keys only, not passwords". That
  is false. It is the description on `install.service.openssh`
  (`modules/apps.nix:1098`) and a comment on the row in every generated
  `services.nix` (`modules/apps.nix:294`).
- `docs/manual/security.md:55-64` says the menu row is upstream's script and
  cannot finish, which #1304 changed. Its snippet leaves passwords on.
- `docs/manual/remote-desktop.md:45-50` sets the same line, then relies on a
  password login for `ssh-copy-id`.

## Proposed outcome

A user who turns on SSH from the menu ends up with a machine that takes key
logins and refuses password logins, and no one loses remote access they have
today because of it. Anyone who did not use the menu sees no change, including
a user who declared `services.openssh` and left passwords at the nixpkgs default.

## Affected users and systems

- Anyone using either menu row. This is opt-in: no default install enables sshd.
- **Turning it on at the machine with no key yet.** This is not a lockout: they
  had no ssh access to lose, and local login is not sshd. It is a trap. The
  documented way to add a key is `ssh-copy-id`
  (`docs/manual/remote-desktop.md:49-50`), which fails with passwords off, so
  they get a server nobody can reach until they are back at its console.
- **The real lockout: someone logging in over ssh with a password today.** Two
  cases: a machine that already enabled the row, and one that declared sshd in
  its own config, where the row is not dimmed because `disabled` reads only
  `services.nix` (`modules/apps.nix:900`).
- Users who declare `services.openssh.enable = true` themselves, as both manual
  pages tell them to.
- gliff users. The machine they connect to needs sshd, and the widget already
  requires a key (`docs/manual/remote-desktop.md:50-52`).
- sops users who want sshd only for its host key (`modules/secrets.md:91-104`).
  They have no client key to give and may use the menu row.
- MicroVM guests, where `services.openssh.enable` is a default from `sshPort`
  or set by the machine's own modules (`modules/services/microvm.nix:294-296`),
  and the `dev` account has no password.
- `omarchy-setup-security-sshd` run by hand. It stays vendored
  (`data/bin-ledger.nix:593-597`), and it cannot harden here. The NixOS
  `sshd.nix` has no `Include` or `sshd_config.d`, so if it gets past
  `omarchy-pkg-add`, `sshd -T` still shows passwords on, and it deletes its file
  and exits before starting sshd. A key it already wrote stays.

## Constraints

- **Must use `mkDefault`, and never override a user's setting (§7, §14).**
- **`mkDefault` alone does not satisfy "no change".** Measured, with a module
  setting `lib.mkDefault false`:

  | the user's own config | `PasswordAuthentication` |
  |---|---|
  | sets nothing | `false`: beats nixpkgs' option default, so a user relying on the default changes |
  | `= true` | `true` |
  | `= null` | `null` (PAM `unixAuth = false`) |
  | `= lib.mkDefault true` | evaluation error: same priority, conflicting values |

  So where the default applies decides who it reaches, and Mode A must stay
  untouched by anything opt-in (§7). A plain assignment in `services.nix` would
  also collide with a user's own `= true`.
- **The hardening covers both settings, as upstream's does.** Setting only
  `PasswordAuthentication = false` left `KbdInteractiveAuthentication = true`
  when measured. PAM's `unixAuth` went `false`, so a password should not work
  that way, but no real login was tried, and other PAM modules are not covered.
- **The row cannot carry the difference by itself.** Every existing
  `services.nix` already has the openssh row, commented out. The command matches
  that line and uncomments it (`modules/apps.nix:1803,1825`), and nothing
  regenerates the file, so a changed template reaches only new files. A line
  enabled today and one enabled after this change look the same to a rebuild,
  and to a user who uncommented it by hand.
- **A key check has to say which keys it can see.** sshd reads
  `%h/.ssh/authorized_keys` and `/etc/ssh/authorized_keys.d/%u` (measured), plus
  `authorizedKeysCommand` or custom `authorizedKeysFiles` if set. Evaluation
  sees only `users.users.<name>.openssh.authorizedKeys`. Upstream's check reads
  only the home file, which misses declared keys, and that file is not read at
  all under `authorizedKeysInHomedir = false` (`sshd.nix:444,886`).
- Coexistence (§14): the spec answers this with fixtures in
  `tests/coexistence/fixtures.nix` that can fail, for a user's own
  `PasswordAuthentication = true` and for question 4 below.
- A changed default is announced in the release notes and Discussions, with the
  migration step (§14).
- The false note and both manual pages are corrected in the same change.
- Upstream's `ufw limit` has no equivalent here. Rate limiting is out of scope.

## Open questions

The owner approved every recommendation below on 2026-11-05.

1. **Who gets the hardening?** Everyone with sshd through the nixarchy module,
   or only machines that turn it on through the menu? Recommended: only the menu
   route. The first changes Mode A users who rely on the nixpkgs default. The
   spec must show how a rebuild tells the two apart, given the constraint above.
2. **What happens with no key the machine can see?** Ask for one before turning
   on, as upstream does (GitHub username or paste), or turn on with passwords off
   and say how to add one? Recommended: ask, and do not turn on without one. The
   reason is not lockout: without a key the server is unusable, and the user finds
   out from another machine. It costs a terminal in the row, and sops-only users
   declare `services.openssh` instead.
3. **Machines already enabled from the menu:** change them on upgrade, or leave
   them and tell them? Recommended: leave them on passwords and announce the
   one-line change. This is the real lockout, and a silent one costs more than a
   delayed hardening.
4. **A user's own `lib.mkDefault true`:** accept the evaluation error, or use a
   priority weaker than `mkDefault`, which departs from §7's rule for scalars?
   Recommended: accept it and record it with a fixture. It is loud, overrides
   nothing, and needs a user who wrote exactly that and also used the menu.
