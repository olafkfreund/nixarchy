# Intent: `nixarchy-apply --home-plan`, a read-only answer to what apply will do with home.nix

Follows `intent/2026-11-16-1817-home-multiuser.md` (merged as #1820).

## Problem

Since #1820 what `nixarchy-apply` does with `~/.config/nixarchy/home.nix`
depends on the host's home owner: `snapshot_home`, `classify_home`,
`read_owner`, `home_decide` and the `render_user` rule in `modules/apps.nix`
decide `claim`, `copy`, `keep` or `refuse`. Nothing outside apply can see that
decision. The nixarchy-pkg panel needs it before it runs apply, to know whether
user scope is usable and which home import `nixarchy-pkg check` should
evaluate (olafkfreund/nixarchy-pkg#103). Copying `home_decide` into the plugin
would drift: #1820 already rewrote it once.

Two defects in the shared code surfaced while measuring the contract, and both
would make a plan wrong rather than merely apply wrong:

- `classify_home` treats every non-zero `cmp -s` as `edited`, including `cmp`
  failing to read the seed (a nonexistent template gives `state=edited`, rc 0).
- `valid_user` is applied to the render user only when it is non-empty, never
  to the caller, so a `keep` decision accepts a caller name apply would refuse
  to write.

## Proposed outcome

`nixarchy-apply --home-plan [--json]` prints the decision apply would take,
changing nothing. The binding contract is the approved section 1 of
olafkfreund/nixarchy-pkg#103 `spec/2026-11-17-103-follow-home-owner.md`
(quoted in the #1825 comment): a version 1 object with seven keys
(`version`, `owner`, `caller`, `state`, `action`, `renderUser`, `message`),
an error object `{"version":1,"error":...}` with exit 1, exit 0 for every
decision including `refuse`, exit 2 for any other flag combination. The state
word is `absent`, not `missing`. The two hardenings above land in the shared
code, so apply gets them too.

## Affected users and systems

- nixarchy-pkg (consumer), and anyone scripting against the output.
- `nixarchy-apply` itself: the same functions run in the same order; the
  function definitions move above the point where apply writes anything, and
  the flake-directory check moves before the `apps.nix` check.
- `modules/apps.nix`, `tests/home-selection.nix`, `docs/manual/configuration.md`,
  `modules/AGENTS.md`.

## Constraints

- Strictly read-only: no lock, no `mkdir` under `$base`, `~/.config/nixarchy`,
  `$applied` or `$XDG_STATE_HOME`, no write outside a private `mktemp -d`.
  It must not need `apps.nix` to exist, but does need the flake directory.
- Same functions as apply, not a copy (the plugin's reason for asking).
- The JSON is a stable contract: seven keys always present, extra keys allowed
  later without a version bump.
- Mode A (someone importing the module) is untouched: no option changes.
- The answer is advisory, not a reservation: the query takes no lock, so
  ownership or the source file can change before apply runs. Apply recomputes
  its decision under its existing lock, in its existing order; only function
  definitions move, never the calls. The docs say so.
- The query sits with the other read-only modes, before the branch guard
  (#1037): a deployment restriction must not stop a consumer from asking.
- Every failure under `--json` (including a failing `set -e` step) becomes the
  error object with exit 1, never an empty stdout.
- `--release-home` is not a `home_decide` decision and stays exempt from the
  new caller-name check, so a user whose name fails `valid_user` can still
  release. Such a user could never be an owner (`read_owner` applies the same
  check), but today can run apply with `keep`; the new check refuses that, and
  it is stated in the docs as the one deliberate tightening.
- A third hardening in the same spirit: `read_owner` hides a `grep` failure
  (unreadable `nixarchy-apps.nix`) behind `|| true` and then misreports it as
  "several owners" with bash integer errors. Exit above 1 must be reported as
  an unreadable file, not as a decision.
- An error is never reported as `action: "keep"`.

## Open questions

None. The contract is fixed by the consumer's approved spec; the optional
`--capabilities` marker from the issue body is out of scope (the object's
`version` field serves, and nixarchy-pkg's section 1 does not use one).
