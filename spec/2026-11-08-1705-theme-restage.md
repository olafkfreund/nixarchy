# Spec: a vanished or stale staged theme is put right on an existing home

## Design

Three pieces, following the intent's three decisions.

### 1. A vanished theme is repaired at every switch (`modules/home.nix`)

The first-run theme step in `activation.nixarchySeed`
(`modules/home.nix:1401-1414`) runs `omarchy-theme-set "${cfg.defaultTheme}"`
headless when `theme.name` is missing. It gains a second trigger in the same
block:

- `theme.name` holds a name, read with `$(<file)` (which drops the trailing
  newline) and stripped of surrounding whitespace, that is a directory in
  neither `${omarchyPath}/themes/<name>` nor `~/.config/omarchy/themes/<name>`.
  `theme.name` holds the directory slug (`bin/omarchy-theme-set:394,506`),
  so `-d` on each root is the existence test. `-d` follows a symlink, so a
  linked theme that resolves counts as existing and a dangling one does not.
- A `theme.name` that exists but is empty or whitespace takes the first-run
  path (apply `defaultTheme`, no notice), the same as a missing one. Today it
  takes neither path.

On that trigger it picks the fallback: `cfg.defaultTheme` if it exists in
either root, else `tokyo-night`. It runs the same headless `omarchy-theme-set`
call the first run uses, with the same `PATH` (the reason that `PATH` is
there, `:1404-1409`, applies unchanged). Then:

- **Success is checked, not assumed.** `omarchy-theme-set` has no `set -e`
  and has exited 0 with siblings missing (`:1404-1409`), so its exit status is
  not enough. Success means it exited 0 *and* `theme.name` now holds the new
  slug *and* the staged `current/theme/colors.toml` exists.
- **On success**, it echoes one activation-log line
  (`nixarchy: theme '<old>' no longer exists; applied '<new>' (#1705)`) and
  writes `~/.local/state/nixarchy/theme-fallback` holding `<old>` and `<new>`
  on two lines, for piece 2. The marker is written to a temporary file
  beside it and moved into place with `run mv`, after `run mkdir -p
  ~/.local/state/nixarchy`, so a dry switch creates neither, and the hook
  never reads half a file.
- **On failure** (any of the three tests), it echoes `nixarchy: could not apply '<new>' in place of
  vanished theme '<old>'; trying again at the next switch` to stderr and
  carries on. `omarchy-theme-set` writes `theme.name` last (`:506`), so a
  failed run leaves the trigger true and the next switch retries. This keeps
  the existing `|| true`'s job, which is that a theme failure never aborts a
  home-manager switch, without its silence.

When the theme exists, the block does nothing: two `-d` tests, no command,
no write. The block runs under `DRY_RUN` like the rest of `nixarchySeed`
through `run`, so a dry switch writes nothing.

### 2. The user is told at the next login (`modules/home.nix`)

A new post-boot hook, `omarchy/hooks/post-boot.d/theme-fallback`, gated like
its siblings on `osConfig.programs.nixarchy.enable`:

- If `~/.local/state/nixarchy/theme-fallback` exists, it sends one
  `notify-send` ("Theme changed: '<old>' is no longer installed, so
  '<new>' is in use. Pick another with Super + Ctrl + Shift + Space.") and
  removes the file only if `notify-send` succeeded, so a session that cannot
  notify tries again at the next login.
- Otherwise it exits 0.

The hook runs where the user-migrations hook already runs (#1610), inside a
session, so no new delivery mechanism is needed.

### 3. Staged code is dropped once (`data/user-migrations.nix`, a port)

`1787481315` moves out of `predates` into a row:
`decision = "ported"; run = "port";` with the reason "re-stage the current
theme once when its staged copy holds code, so an older install's staged code
is dropped (#1705)". The port is nixarchy's own script, not upstream's file,
for two reasons the reviews found:

- **Upstream's vanished-theme branch is dropped.** Piece 1 owns that case. Left
  in, it would apply Tokyo Night at login, with no log line and no notice,
  whenever piece 1's repair had failed.
- **It acts only when there is code to drop.** The port runs
  `omarchy-theme-refresh` only if the current theme exists *and* the staged
  `~/.local/state/omarchy/current/theme` holds a file upstream's staging now
  refuses (`*.lua`, `alacritty.toml`, `foot.ini`, `ghostty.conf`, `kitty.conf`,
  `vscode.json`; `bin/omarchy-theme-set:25-35,290-294`). A clean home sees
  nothing, as the intent's third outcome requires. The list is read from the
  pinned `omarchy-theme-set` rather than copied, if the spec's step can parse
  it cleanly; otherwise copied with a check that it still matches.

The runner (#1692) runs it once at the next login of every existing home, and
marks it done whatever it decided. A freshly seeded home has it marked done
from the runner's list (`modules/home.nix:1211-1214`).

## Alternatives rejected

- **Port `1787481315` only** (the issue's original proposal). It fixes the
  vanished theme once; the next upstream theme removal is the same bug again.
- **Do the repair in a post-boot hook instead of activation.** It would have a
  session to notify from, but the first-run theme step already lives in
  activation and runs the same command headless, and a login-time repair
  restages the theme in front of the user after the desktop is up.
- **Upstream's Tokyo Night as the fallback.** A home that configured
  `defaultTheme` expects that theme on a fresh start; using it here matches
  what this home's first run did.
- **Notify from activation directly.** Activation can run with no session
  (`nixos-rebuild` at boot, a remote switch), so a notification there is lost.

## Risks

- **A theme root briefly absent during a switch** would read as a vanished
  theme. `${omarchyPath}` is a store path that exists for as long as the
  generation does, and `~/.config/omarchy/themes` is the user's own. Neither
  changes mid-activation, so this needs no guard.
- **Piece 3 restages only a home whose staged theme holds code**, which
  retints its open apps once at that login (`omarchy-theme-refresh` waits for
  the retints and skips the background).
- **`notify-send` with no notification daemon** fails, and the marker stays.
  That is the designed retry, not a leak: the file is two lines.
- **Mode A** is untouched. Both pieces sit in code that is already gated on
  `programs.nixarchy.enable`, and the ledger row only changes what the runner
  runs on a nixarchy home.

## Coexistence

Nothing here sets an option a user also sets; `defaultTheme` is read, not
written. No fixture is needed in `tests/coexistence/`.

## Verification

- **`checks.home-activation-writes`**, a new section in the #1342 shape: the
  block between the first-run theme comment and its closing `fi`, taken from
  `nixarchySeed`'s generated text with `omarchy-theme-set`'s store path
  rewritten to a stub that records its argument and writes `theme.name`. Run
  under `set -eu`. Cases:
  1. `theme.name` missing, and separately empty, and whitespace → the stub is
     called with `defaultTheme`, with no marker (first-run behaviour).
  2. `theme.name` names an existing theme in `$OMARCHY_PATH/themes` → no
     call, no marker, no output.
  3. The same in `~/.config/omarchy/themes` → no call.
  4. `theme.name` names a vanished theme, and both `defaultTheme` (set to
     something other than `tokyo-night`) and `tokyo-night` exist → the stub is
     called with `defaultTheme`; the marker holds old and new; the log line is
     printed.
  5. Vanished theme and vanished `defaultTheme` → the stub is called with
     `tokyo-night`.
  6. The stub fails → the stderr line is printed, the block exits 0, no marker.
     And again with a stub that exits 0 but writes no `colors.toml` → the same.
  7. `DRY_RUN=1` with a vanished theme → no marker, no state directory, no
     success line.
  8. A symlinked theme directory that resolves → no call; a dangling one →
     repaired.
- **The hook**, in the same check: the marker plus a recording `notify-send`
  → one call, marker gone; a failing `notify-send` → marker kept.
- **`checks.user-migrations-ledger`** passes with the row, and
  **`checks.user-migrations`** gains a case for `1787481315`, three ways:
  staged `hyprland.lua` with an existing theme → `omarchy-theme-refresh`'s
  stub called once; a clean staged theme → not called; a vanished theme → not
  called. The migration's marker is set in all three. That the refresh then
  drops the code is upstream's staging, which this check does not run; it is
  named here as the one part not proved by a cheap check.
- §1 breaks, each shown failing: drop the vanished-theme trigger (case 4
  fails); swap the fallback order (case 4 fails, since both exist); drop the
  `colors.toml` success test (case 6's second half fails); remove the marker
  removal's success guard (the failing-notify case fails); drop the port's
  staged-code test (the clean-home case fails); restore `1787481315` to
  `predates` (the hyprland.lua case fails).
- Both Omarchy pins: the user-migrations case on `main` and on the edge carry,
  as #1709 did.
