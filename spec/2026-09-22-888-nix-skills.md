# Spec: the Nix skills in olafkfreund/nix-skills reach nixarchy's agents

Refs #888. Read against nix-skills at `8660959` (2026-09-22) and nixarchy `main`
at `e87452e`, both read rather than recalled.

## Design

### 1. Depend, and link through nixarchy's own loop (open question 1)

**Recommended: take nix-skills as an input, and have nixarchy's existing skill
relink step link from its package as a second source.**

This is neither of the intent's two options exactly, because reading the code
showed a third that keeps the advantages of both:

- nix-skills' package lays each skill out at `$out/share/nix-skills/<name>`
  (`nix/packages.nix`). Nothing is copied into nixarchy's tree, so **nix-skills
  stays the one source**, and a fix there arrives with an input bump.
- nixarchy's activation already links every skill into **the four directories
  its agents read** (`.agents/skills`, `.claude/skills`, `.codex/skills`,
  `.pi/agent/skills`; `modules/home.nix:973-989`). Feeding it a second source
  gives the six skills exactly the reach nixarchy's own have, pi included. That
  is the intent's "the same agents, and no fewer". nix-skills' own module does
  not know pi.
- **nix-skills' Home Manager module is not used.** Its `home.file` links would
  be a second definition of the same files for anyone who already enables
  `programs.nix-skills` themselves, and Home Manager refuses that. Activation
  links cannot collide that way.

The change, in the relink loop:

- **Cleanup:** besides `/nix/store/*/agents/skills/*`, it also removes a link
  into `/nix/store/*/share/nix-skills/*` before relinking. So turning the skills
  off takes them away on the next activation, and a bump moves them.
- **Link:** when the option is on, each `share/nix-skills/<name>` is linked
  after nixarchy's own, **but only where nothing else is already there**. A path
  that exists and is not a link nixarchy made is someone else's (a user's own
  `programs.nix-skills`, or a hand copy), and it is left alone. nixarchy's own
  skills keep today's `ln -sfn` unchanged.

Rejected for now: **vendoring**. It would be simpler for the counts and the
parity check, but it creates a second copy that drifts from the repository
created to be the source.

### 2. The devenv overlap: two skills with one boundary (open question 2)

Read side by side, they do not duplicate each other:

- nixarchy's `devenv` (284 lines) is **this machine's**: which rung a tool
  belongs on (project or machine), whether devenv is here, trusting a directory,
  and the traps specific to nixarchy.
- `devenv-project` (50 lines) is the **portable reference** for `devenv.nix`
  itself: languages, tasks, services, lockfiles, activation.

**Keep both, and give them one boundary.** nixarchy's `devenv` gains a hand-off
line in its existing *Hand-offs* section (`SKILL.md:252`): the syntax and options
of `devenv.nix` itself (languages, tasks, services) → `devenv-project`. Its
description keeps its machine scope. Nothing changes in nix-skills for this: the
portable skill is right to be portable.

Rejected:

- **Dropping `devenv-project` on nixarchy**, which throws away the reference half.
- **Merging the two**, which puts nixarchy's machine rules into a portable
  repository, or portable rules into ours.

### 3. Counted apart: sixteen, plus six (open question 3)

The built tree holds **16** `SKILL.md` today, and README, `docs/llms.txt` and
`docs/manual/ai.md` say *sixteen* (`readme-counts.sh:198`). Linked from their own
package, the six do not enter that tree. So:

- `skills` still counts nixarchy's own, and stays sixteen;
- a new quantity, **`nix-skills`**, counts the input's `skills.json` (six), and
  the docs say so separately: *"…and six Nix skills from
  [nix-skills](https://github.com/olafkfreund/nix-skills): the language,
  nixpkgs, Home Manager, microvm.nix, devenv and the wiki"*;
- the floor in `readme-counts.sh` moves by one per place the new number is
  stated. `word_for` already spells six.

This also avoids "twenty-two", which `word_for` cannot say (it stops at twenty),
and it tells a reader which skills are nixarchy's and which are general Nix.

### 4. On by default, with an off switch (open question 4)

`programs.nixarchy.nixSkills` is a NixOS option, **default `true`**, read in the
home module the way `mcp` is (`osConfig.programs.nixarchy.nixSkills or false`).
The case for on: the six are what an agent on NixOS most often gets wrong, and a
skill costs only its description until it is triggered. Off is one line.

Mode A is untouched. Everything is inside the home module's
`lib.mkIf cfg.enable`, and the `or false` makes a standalone home inert.

### 5. The input and the licence

- `flake.nix` gains `nix-skills`, pinned to a commit, with
  `inputs.nixpkgs.follows`.
- **Before the pin, a `LICENSE` lands in nix-skills** (a PR there). **MIT**, the
  owner's decision (2026-09-22), matching ai-mirror.

## Alternatives rejected

- **Vendoring the six into `pkgs/omarchy/skills`.** Above: a second copy of a
  repository created to be the only one.
- **Enabling nix-skills' Home Manager module.** A clash with any user who
  enables it themselves, and no pi.
- **Counting them into "twenty-two".** Hides which skills are general Nix, and
  needs `word_for` to learn a number past its table.
- **Teaching opencode here.** nixarchy does not seed opencode's skill directory
  for its own sixteen either. The six follow the same directories; opencode is
  a separate change for all twenty-two, if wanted.

## Risks

- **Skipping an occupied name could hide a stale user copy.** A user's
  hand-copied old `nix-language` would win over ours. That is the right side to
  err on (their file, their choice), and the activation prints one line naming
  each skip.
- **Cleanup by path pattern.** `/nix/store/*/share/nix-skills/*` could match
  another package laid out the same way. Only nix-skills uses that name, and
  the cleanup only ever removes symlinks, never files.
- **Six more skill descriptions in every agent's context.** Small, and the off
  switch exists. Option 4's default is the owner's to confirm.
- **An input bump can change a skill's text.** That is the point of depending.
  Bumps are reviewed like nixi's.

## Verification

Each check is broken first and seen red (AGENTS.md §1).

- **`tests/options.nix`, both states:**
  - with `nixSkills` on, the relink activation text names the nix-skills store
    path; off, it does not;
  - with nixarchy disabled, nothing (Mode A).
  - Break: wire the second source unconditionally.
- **The relink behaviour, as a stubbed `runCommand`** running the activation's
  loop against a fake home:
  - the six are linked into all four directories;
  - an occupied name (a real directory) is left alone and reported;
  - with the option off, a previous run's nix-skills links are removed and
    nixarchy's own sixteen stay.
  - Breaks: drop the "only where empty" guard, and the user's directory is
    replaced; drop the cleanup pattern, and off leaves the six behind.
- **`readme-counts.sh`:** the new `nix-skills` quantity passes, and goes red
  when a doc says *five*.
- **The devenv hand-off:** `grep` the built tree's `devenv/SKILL.md` for
  `devenv-project`, in `checks.patched-files`' style, so a skill rewrite that
  drops the boundary is caught.
