# Spec: hosts follow a green edge, with rollback

Approved by the owner (2026-11-26). The design is Codex's read-only pass, taken as written, with the owner's scope:

Owner decision (2026-11-26, "Phased"): build all of it, enable only the nixos_config bump and razer's unattended switch. p620's unattended switch is built but stays OFF (an option defaulting to false) until the runner-drain test the design names passes; turning it on is a later one-line change by the owner.

## Design

Use the existing `system.autoUpgrade` timers on p620 and razer, with a guarded upgrade script in `nixos_config`. Let hosted CI evaluate the lock bump, then have p620 build both exact toplevels before either host activates. Keep p620’s unattended switch disabled until a test proves that all four runners can stop accepting jobs without cancelling one. [nixarchy #1946](https://github.com/olafkfreund/nixarchy/issues/1946)

### 1. Promote the exact green edge commit

Add a scheduled workflow in `nixos_config`, with manual dispatch for recovery. Have nixarchy’s `omarchy-edge` workflow publish a small artifact containing the promoted candidate SHA and run attempt, only after promotion and reporting succeed. The downstream workflow reads `refs/heads/edge` and requires a completed, successful `omarchy-edge` run from `main` whose promotion artifact matches that exact SHA. The workflow’s own `head_sha` identifies its triggering checkout. The promotion step pushes the separately tested candidate. A successful dry run, a skipped promotion, or an edge head that moved during the update defers the bump. This also handles missed polls without a cross-repository dispatch credential. Run `nix flake update nixarchy` from fresh `nixos_config` main. Check that the new `locked.rev` matches the verified SHA, that only `flake.lock` changed, and that input changes are confined to nixarchy and its dependency graph. Keep one bot PR and make the same promotion check required for **any** PR that moves the nixarchy pin. The daily all-input updater can otherwise advance it independently. Require the existing three-host eval matrix on an up-to-date merge candidate and enable protected auto-merge with the repo’s PR bot credential. Evaluate p510 only. Hosted full-closure builds already failed repeatedly in this workflow, and the existing step named “Auto-merge” only prints instructions. ### 2. Build first, then switch inside the gates

Reuse `nixos-upgrade.timer` and replace its generated service script through a feature module enabled on p620 and razer. The shared config already enables a persistent 04:00 timer with jitter and no reboot. Its current network condition checks GitHub reachability. Replace that with a fresh resolution of `refs/heads/main` and build from the resulting immutable SHA with the committed lock file. The pinned NixOS service already has `restartIfChanged = false` and `X-StopOnRemoval = false`, useful for keeping the transaction alive across a switch. Keep p510’s explicit opt-out. [nixos_config `modules/nix/nix.nix`:7](/mnt/data/vmtest/cfg-1946/modules/nix/nix.nix:7) · [Pinned NixOS `auto-upgrade.nix`:241](https://github.com/NixOS/nixpkgs/blob/2786a2a72088ecf32aea5b3ec52099e6a7cff78f/nixos/modules/tasks/auto-upgrade.nix#L241) · [`hosts/p510/configuration.nix`:477](/mnt/data/vmtest/cfg-1946/hosts/p510/configuration.nix:477)

Stage and GC-root both closures on p620 under resource limits, deferring heavy builds while install or edge VMs are running. Razer resolves main itself and pulls the matching signed closure from p620’s Nix store over restricted SSH. Reuse the build and transfer pattern in `deploy-via-p620`. That recipe calls it a cache, but the repo documents that p620 has no HTTP binary cache. Start with p620 as the canary and release the matching razer closure after p620 passes health checks. If main advances during staging, defer the stale candidate. - **p620.** Query `gh api --paginate repos/olafkfreund/nixarchy/actions/runners` for the four configured runners. Defer on any busy runner, missing or unexpected offline runner, or unavailable API. Query job state for `install-check.yml`’s `install` and `omarchy-edge.yml`’s `verify`, and check the local maintenance lock for manual VM work. Both a poll and an immediate recheck leave an assignment race. Add a cooperative drain at the runner listener: stop taking new jobs, settle any in-flight poll, and acknowledge only when the dispatcher is idle. If a job was acquired during drain, let it finish normally and defer the upgrade. Require all four acknowledgements before switching and keep admission closed across activation and any rollback, including listener restarts. The existing `vm-host-free.sh` is a model for treating unknown status as busy, and it deliberately exempts one waiting install step to avoid a CI deadlock. Use a stricter deploy check. ### 3. Verify and roll back under one lock

Use one host-local deployment lock shared with the manual switch recipes. Immediately before activation, record the exact active closure, system profile generation, failed units, and critical service and session state. Pin the old closure and defer if the running and boot-default generations already differ. Activate the staged store path and allow a bounded settling period.

| Check | Decision |
|---|---|
| Activation and systemd | Verify `/run/current-system` and the system profile point at the candidate. Roll back for a failed activation or newly failed units. Compare the post-switch failed set against the baseline. An existing unit failure alone is logged and excluded, including when it accounts for an activation command’s degraded exit. |
| Home Manager and session | Check `home-manager-olafkfreund.service` for a successful result and exit status. If activation reran, verify the fresh invocation. For a previously running Hyprland session, verify the same session and a responsive `hyprctl` as the user. If logged out, check the greeter and leave session launch to the next login. |
| p620 runners and cluster | Verify all four systemd services and runner connectivity while admission remains closed. Check Docker and the k3d API’s `/readyz` if healthy in the baseline. Report a GitHub API outage as unknown and keep the candidate pending verification. A local runner startup failure is a rollback signal. |

On a regression, restore the **recorded** generation and activate its closure, then verify the running system, boot default and critical services. Record the failed SHA and pause automatic activation until the owner clears it. Persist transaction state before switching so an interrupted process can reconcile on its next invocation. Keep runners drained until either the candidate or the restored system passes local checks. ### 4. Notify, pause, and prove the behavior

Before either switch, read `#agents:freundcloud.org.uk`, defer for work in flight, and post the host, SHA and expected duration. Defer if the bus is unavailable. Post the outcome and write it locally. Send a desktop notification when a session is available, and create or update one GitHub issue per host and failed SHA with the failed checks and rollback outcome. Keep a persistent per-host pause flag checked again immediately before activation. Pausing the bump workflow separately stops new bot PRs. [Agent bus rules](/mnt/data/vmtest/cfg-1946/AGENTS.md:41) · [nixarchy durable failure record](/mnt/code/Source-home/nixarchy/modules/fleet.nix:94)

Reuse nixarchy fleet’s opt-in approach, fresh remote resolution, timer jitter and durable failure reporting. Its current wrapper sets `system.autoUpgrade` defaults and writes an `OnFailure` marker. The promotion consumer, runner drain, AC and idle policy, health checks, and rollback belong in `nixos_config`. Native systemd already provides the scheduler, so this design needs no comin daemon. [nixarchy `modules/fleet.nix`:63](/mnt/code/Source-home/nixarchy/modules/fleet.nix:63) · [Fleet manual](/mnt/code/Source-home/nixarchy/docs/manual/many-machines.md:111)

Use fixtures for stale or mismatched promotion evidence, busy or missing runners, API errors, idle/resume, AC loss, and duplicate invocations. In a disposable NixOS VM, exercise a healthy switch, a pre-existing failed unit, a new failed unit, Home Manager failure, and interruption during activation. Assert restoration of both the running and boot-default generation and suppression of retries for the failed SHA. In a test repository, submit a real runner job at the drain boundary and prove it either finishes normally or queues through maintenance. That test is the release gate for unattended p620 switches.

This was a read-only review. Live branch protection, runner drain behavior and hardware gates remain unverified. Even with the idle gate, a switch can interrupt a session or cluster workload, and generation rollback cannot recover unsaved work or undo application data migrations.
