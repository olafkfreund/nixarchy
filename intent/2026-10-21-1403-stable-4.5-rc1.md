# Intent: stable moves to Omarchy v4.5.0-rc1, for the owner's machine and the users who want 4.5 now

## Problem

Omarchy v4.5.0-rc1 shipped on 2026-10-20. It is the first feature release
since Quattro: new notifications, 50 languages, per-monitor workspaces,
floating workspaces with a dock, the Appearance menu, theme intros, and
speed-ups. Upstream calls it a release candidate ("run it on a test
machine").

nixarchy already runs it, but only on **edge**. Edge's quattro pin
0a7beb7 is rc1 + 1 commit, and edge has been green since run 39581384092.
Stable does not have it:

- `main` pins `github:basecamp/omarchy/v4.0.6` (`flake.nix:81`), with a
  second copy `omarchyVersion = "4.0.6"` at `flake.nix:540`.
- **Installed machines follow `release`, not `main`.** `release` is
  still on **v4.0.5**: v4.0.6 never reached it, because tag v4.0.6-1 was
  never cut (`nixarchy-channel`: "stable = the release branch (what
  installed machines follow)").
- Edge carries 51 commits over 40 files that main lacks. They are the
  NixOS adaptations to quattro: the setters, the browser guard, the
  notifications engine, agent accounts (#1386), the language picker
  (#1289), omasnap, and #1398's fixes.

The owner has decided that stable takes rc1 now. It goes to their own
machine and to a few eager users.

## Proposed outcome

- `main` carries Omarchy **v4.5.0-rc1**, pinned to the tag (03ff1eff) and
  built from edge's proven carries. Edge then differs from main by its
  quattro pin alone.
- A user who wants 4.5 now can get it with one documented step, and can
  get back to 4.0.6 with one documented step.
- Automation does not fight the RC:
  - the nightly bump does not propose a downgrade to 4.0.6;
  - it does propose 4.5.0 final, or rc2, when either ships;
  - the ISO label, the release tag check and the release notes accept an
    RC.
- Edge keeps publishing.

## Affected users and systems

- `main`: `flake.nix`, `flake.lock`, and the edge carries (about 40
  files).
- `.github/workflows/omarchy.yml` and `release.yml`: CI changes, merged
  by the owner (§11).
- `installer/cd.nix` (the volume label) and the docs
  (`docs/manual/omarchy-channels.md`, `README.md`).
- Installed machines on `release`: **only if question 1 says so.**

## Verified facts the design rests on

Two read-only plans (Codex gpt-6-sol, and agy with no model reported)
agree on the route. These are their load-bearing claims, each checked
here:

1. **`omarchy.yml` would downgrade.** It reads `releases/latest`, which
   excludes prereleases and answers v4.0.6, and compares with `!=`
   (:56-67). Its tag regex already accepts `-rc1` (:59).
2. **`sort -V` is a trap for the fix.** It ranks `v4.5.0` before
   `v4.5.0-rc1`, which would block the final release. Mapping `-` to `~`
   orders `4.5.0~rc1 < 4.5.0~rc2 < 4.5.0` correctly (measured).
3. **The ISO label breaks.** `cd.nix:588` turns only `.` into `_`, so
   `4.5.0-rc1` fails the `[A-Z0-9_]` assertion. The fix is upper-case
   plus `-`→`_`, giving `NIXARCHY_4_5_0_RC1`. Edge's special case for
   `edge-*` stays.
4. **`release.yml:79` rejects `v4.5.0-rc1-1`.**
5. **The one commit between rc1 and edge's pin (0a7beb7) changes two
   keybinding lines** (Super+Ctrl+Alt+C for the screenshot,
   Super+Shift+S back to Google Maps) plus the upstream manual. No
   nixarchy file names them, so pinning the tag instead of 0a7beb7 is
   expected to change no carry. The build proves it.
6. **#1400 (`appearance.*`) is after rc1** and stays out.

## Constraints

- **Pin the tag** (`v4.5.0-rc1`), not a quattro sha: the nightly bump,
  `review-pins` and the release notes all reason in tags.
- **Keep edge's history.** Merge edge into the task branch (a real merge,
  not a squash), so the nightly edge merge does not replay its carries.
  No force-push.
- **§1 for every check that changes:** the bump decision, the label and
  the tag guard each get a failing case first.
- **§11:** the workflow and release-script edits are CI changes, merged
  by the owner.
- Rolling back the NixOS generation does not undo what 4.5 writes to
  `~/.config`. The announcement says so.

## Open questions

1. **Who receives it automatically?**
   - **(a)** `main` only. You and the eager users opt in by pinning a
     nixarchy prerelease tag `v4.5.0-rc1-1`, or `main`. Installed machines
     stay where they are.
   - **(b)** Also move `release`. Every installed machine gets the RC at
     its next update.

   I propose **(a)**. You said "my machine and some other users that are
   eager", which is opt-in. (b) is one command later, once rc1 has run on
   your machine.
2. **Tag v4.0.6-1 first?** I propose yes, before main moves: it is
   pending anyway, and it gives the rollback instructions a fixed target.
   Whether `release` then moves to v4.0.6-1 is your separate decision, as
   it was before.
3. **The nightly bump while main is on an RC:** follow rc2 and later RCs,
   or only finals? I propose RCs too. You chose the RC track, and rc2 is
   where rc1's bugs get fixed. It means asking the releases list instead
   of `releases/latest`.
