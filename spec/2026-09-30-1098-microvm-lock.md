# Spec: Let MicroVM mutations wait out brief status probes

Refs #1098. The approved outcome is a bounded wait at the shared mutation lock. Status probes and the verifier remain unchanged. #1097 separately tracks CI hygiene, so this item does not close the #1098 batch or alter workflows.

## Design

1. In `pkgs/microvm.nix:328-334`, change only `lock_stopped_vm`'s `take_lock -n` to `take_lock -w 2`. `take_lock` at `:316-322` still opens the same `.lock` on fd 9, holds it across the mutation or runner lifetime, and prints exactly `nixarchy-vm: '<name>' is already running.` if the wait expires. After taking it, `unit_busy` still refuses an active, activating, or reloading detached unit with its existing stop-first message (`:170-185,330-333`). `run_vm`, `detach_vm`, `set_template`, and `rm_vm` all reach this one helper (`:356-360,379-382,419-432,461-472`), so the one change covers every mutation that used the immediate `-n` refusal. Do not change `launch_vm`'s separate 30-second handoff wait (`:363-370`).
2. Keep both nonblocking status probes: `lock_held` at `pkgs/microvm.nix:158-166` feeds text/JSON `list` and the detached-run poll (`:180-214,389-395`), and `pkgs/verify.sh:683-694` uses the same probe pattern. The only other `flock -n` instances relevant here are the external-holder fixtures in `tests/microvm-template.nix:692-693,862-863`; they are not mutation paths. The probe holds fd 8 only between a successful `flock -n` and immediate `exec 8>&-`, with no blocking call inside that interval. A waiting mutator does not need a response from the probe. Conversely, after obtaining fd 9, `lock_stopped_vm` calls `unit_busy`, which asks systemd and does not wait for a probe; `detach_vm` closes fd 9 before its readiness poll. There is no reciprocal wait cycle or deadlock between these paths.
3. Extend `tests/microvm-template.nix:675-730,840-875` with one deterministic short-holder fixture. Create a stopped disposable VM, have a child hold its `.lock` exclusively for less than two seconds and signal when ready, then invoke a mutation through the built `nixarchy-vm`. It must succeed only after that child releases the lock. Use the same helper for a truly held lock: a real competing holder remains beyond two seconds, and `run` refuses within a small bound with **exactly** `nixarchy-vm: '<name>' is already running.` on stderr, before any build begins. Keep existing stopped/running list JSON assertions and the active-unit handoff case. The fixture must wait for or terminate only its own child PID; it must not boot a VM.

## Alternatives rejected

- Replace status probes with `lslocks` or `/proc/locks` parsing: the owner chose the smaller bounded-wait fix. Path and permission interpretation would expand the behavior and test surface for a short race.
- Use a shared flock for status: it can still briefly block an exclusive mutator and changes the meaning of existing lock probes.
- Keep `-n` and ask users to retry: the panel polls list and a read-only query can spuriously refuse a legitimate command.
- Increase the wait beyond two seconds or alter the runner's lifetime lock: unnecessary for the measured probe window, and a truly running VM should still refuse promptly.

## Risks

- A mutation against a truly running VM now takes about two seconds to report the same error, rather than refusing immediately. A short probe should release well inside that bound; the check must measure both cases.
- Accidentally changing `take_lock` globally would also alter `launch_vm`'s 30-second handoff. Change only the call in `lock_stopped_vm`.
- Tests that check only a success exit can pass when the fixture holder never acquired its lock. Require a ready signal and prove the child holds the lock before invoking the mutator. An exact-message assertion must catch an unintended build or changed refusal.
