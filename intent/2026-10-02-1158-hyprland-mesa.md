# Intent: Hyprland starts whatever glibc nixpkgs' Mesa is built against

## Problem

Hyprland aborts while creating its backend whenever the system's Mesa is built
against a newer glibc than Hyprland is.

- **Hyprland's glibc.** Hyprland comes from hyprwm's own flake and
  deliberately does not follow our nixpkgs (`docs/internals/flake.md`, the
  hyprland section), so hyprland.cachix.org serves it prebuilt. Its nixpkgs is
  `e554fab` (2026-09-17): glibc 2.42.
- **Mesa's glibc.** The nightly bump (#1154) moves our nixpkgs to `c59305b`
  (2026-10-01): glibc 2.44. `hardware.graphics` builds `/run/opengl-driver`
  from that nixpkgs' Mesa 26.2.3, which needs glibc ≥ 2.43.
- **The failure.** Hyprland loads that Mesa into its own glibc-2.42 process:

  ```
  MESA-LOADER: failed to open dri: …glibc-2.42-84/lib/libm.so.6: version `GLIBC_2.43' not found
  terminate called after throwing an instance of 'std::runtime_error'
    what():  CBackend::create() failed!
  ```

- **A Hyprland bump does not help.** hyprwm's `main` (2026-10-01) still pins
  the same 2026-09-17 nixpkgs.

**It is live, not hypothetical.** p620 has run nixpkgs `c59305b` since
2026-10-02 04:25: Mesa 26.2.3 on glibc 2.44, beside a Hyprland built on glibc
2.42. Its session survives only because it started on 2026-09-22 with the old
Mesa still loaded. The next time Hyprland starts there, it is expected to
abort the same way. Any nixarchy machine that takes #1154 would do the same.

The general shape is that **two nixpkgs share one process.** Hyprland's
nixpkgs builds the compositor, and ours builds the GPU drivers it loads. They
will drift apart again every time glibc moves, and nothing here notices until
a session fails to start.

## Proposed outcome

- **Hyprland starts** on a machine whose nixpkgs has a newer glibc than
  Hyprland's: in `checks.session` with #1154's nixpkgs, and on p620.
- **The cache stays.** Hyprland still comes from hyprland.cachix.org; no
  machine compiles the compositor.
- **The next drift is caught by a check,** not by a session that fails to
  start. The check names both glibc versions, before the change reaches
  `main`.
- #1154, or the next nixpkgs bump, can merge.

## Affected users and systems

- Every installer-managed nixarchy machine: the GPU driver package behind
  `/run/opengl-driver`, both 64- and 32-bit.
- `modules/nixos.nix`, and possibly `flake.nix` if the Hyprland nixpkgs needs
  passing through.
- `docs/internals/flake.md`, the hyprland section.
- `tests/`: a check for the glibc relationship. `checks.session` already
  catches the crash, but only in the expensive tier.
- p620, razer and p510 through their own configs, when they take this
  nixarchy. p620 sets `hardware.graphics.extraPackages` with Mesa in
  `hosts/p620/nixos/amd.nix`, which may need the same treatment there. That
  repository is out of scope here, so the PR says what it needs.

## Constraints

- **Hyprland keeps its own nixpkgs and its cache.** No `follows` (the
  documented decision).
- **Mode A stays inert.** A configuration that only imports the module keeps
  its own `hardware.graphics`.
- **A user who sets `hardware.graphics.package` themselves wins.** Use
  `mkDefault`, not plain assignment and not `mkForce` (the header of
  `modules/services/default.nix`).
- **Follow hyprwm's own documented approach** rather than inventing one.
- **No posting upstream** (the owner's rule).
- **No local session runs while CI is busy** (§6 tiers). The session check is
  CI's.

## Open questions

1. **Mesa from Hyprland's nixpkgs** (the owner's choice, 2026-10-02) means
   every application gets that Mesa: slightly older, 2026-09-17. Applications
   built on a newer glibc load a driver built on an older one without trouble,
   but GPU support moves at Hyprland's pace, not nixpkgs'. Accepted as the
   cost, or should the spec look for a narrower fix, such as a
   compositor-only driver path?
2. **The new check.** A cheap evaluation check could assert that the glibc of
   `hardware.graphics.package` is not newer than Hyprland's. It would be red
   on #1154 today without this fix, and green with it. Is that the right
   layer, or is `checks.session` enough?

## Owner's answers (2026-10-02)

1. Accepted: every application uses Mesa from Hyprland's nixpkgs.
2. Yes: a cheap check on the glibc relationship, as well as checks.session.
