# Spec: Removing a fingerprint removes the fingerprint

## Design

The row runs upstream's script as far as its deletions, then stops. Everything
below them that is wrong on NixOS is cut out of the shipped file, so "must not
reach" holds because the text is not there, not because an `exit` sits above it.

### What ships in `omarchy-remove-security-fingerprint`

In `pkgs/omarchy/default.nix`:

1. `:1461` stops splicing the guidance. `1304-guidance-remove-fingerprint.sh` is
   deleted. The account lookup and its safety check (upstream `:9-22`) now run
   for real.
2. `remove_lock_fingerprint_pam` joins the function deletions at `:1357-1374`,
   with the same `grep` guard that a function has moved, and joins the survival
   check at `:1375`, which names the deleted functions separately.
3. From upstream's anchor `# fprintd finds no reader when it is off or
   unplugged:` to the end of the file is deleted with `sed`, and
   `pkgs/omarchy/1620-remove-fingerprint.sh` is appended in its place. That
   range holds `remove_pam_config`, `remove_lock_fingerprint_pam`,
   `remove_resume_hook`, the lifecycle hook and `omarchy-pkg-drop`. A `grep`
   before the `sed` fails the build if the anchor moved, and one after it fails
   if `omarchy-pkg-drop`, `omarchy-lifecycle-dispatch`, `/etc/pam.d` or a call to
   any of the three deleted functions survive. Their bodies went in step 2, so
   `/etc/pam.d` alone would not see upstream moving a call above the anchor.
4. The `--replace-fail` calls at `:1431-1436` go with their targets. The
   function deletions stay, because the drift guard's premise is unchanged.
5. The heading `echo` and `# omarchy:summary=` stop saying "from sudo, polkit,
   and lock screen", which this row does not do. Both become
   "Delete <user>'s saved fingerprints".

Upstream's privilege check (`:66-69`) stays as it is.

### The appended block

The plan holds the exact text. The logic, which the check pins:

```bash
reader=off had_files=0
if omarchy-cmd-present fprintd-delete; then
  # sudo's own stderr stays on the terminal; only fprintd-delete's output is captured
  if delete_output=$(sudo sh -c 'fprintd-delete "$1" 2>&1' sh "$fingerprint_user"); then
    if [[ $delete_output == *" deleted on "* ]]; then reader=deleted; else reader=none; fi
  elif [[ $delete_output == *"No devices available"* ]]; then
    reader=absent
  elif [[ -z $delete_output ]]; then
    # sudo refused, so fprintd-delete did not run: upstream's "needs administrator rights", exit 1, no rm
  else
    # report the last line, say what to do, exit 1, and do NOT run the rm
  fi
fi
sudo test -e "/var/lib/fprint/$fingerprint_user" && had_files=1
sudo rm -rf -- "/var/lib/fprint/$fingerprint_user" || { report; exit 1; }
# report, in this order: what went, what could not be reached, snapshots, login
```

`*" deleted on "*` is checked rather than the exit status because
`fprintd-delete` exits 0 for both "deleted" and "nothing to delete"
(`utils/delete.c:90-118`). With two readers, one line of each can appear, so
"deleted" is looked for first. If fprintd's wording ever changes, the row says
*less* than happened, which is the safe direction. The check also pins the three
literals against the real binary (Verification).

### Exit status

The status answers one question: did the deletion the person asked for run?
`omarchy-launch-floating-terminal-with-presentation` shows Done or Failed from
it, then waits for a key, so the text stays readable either way.

| state | `/var/lib/fprint/<user>` | says | exit |
|---|---|---|---|
| prints deleted, reader present | removed | deleted | 0 |
| only leftovers from an earlier reader | removed | deleted | 0 |
| nothing on record (second press) | no-op | none saved | 0 |
| no reader (`No devices available`) | removed | deleted if there were files, plus "any on the reader itself stay there" | 0 |
| `fprintd-delete` absent (row summoned by id or run by hand, fprintd off) | removed | same, plus "fprintd is off" | 0 |
| `fprintd-delete` fails for any other reason | the row runs no `rm`; fprintd itself may already have removed some or all | the reason, that some may already be gone, press again, the manual `rm` as last resort | 1 |
| `sudo` refused or absent, at the first prompt or a later one | not touched by the row | upstream's "needs administrator rights" | 1 |
| `rm` fails | possibly part removed | that removal may be incomplete | 1 |

Exit 0 despite login still being declared: the row deleted prints, it did not
turn fprintd off, and it says so. Exit 1 would show "Failed" after a successful
delete. `#1304`'s "explain and exit 1" meant "I did nothing", which no longer
applies. An absent reader is 0 because a machine with fprintd on and no reader
has nothing wrong with it.

### A failed delete does not run the `rm` (departs from upstream)

Upstream runs the `rm` regardless. Here that destroys the only route to the
reader's copy, because fprintd finds a device's prints **through the host's
files** (`src/device.c:2355,2380,2399`, `store.discover_prints`). With the files
gone, `user_has_print_enrolled` is false, fprintd answers `NoEnrolledPrints`, and
the print on the chip can never be addressed again. fprintd has no call that
clears a chip without one.

So on a real failure (a claim refused because something holds the device, a dead
daemon) the row stops and asks for another press. The last-resort `sudo rm -rf`
is printed for someone whose fprintd never recovers. Owner decision 1.

The same fact has two more consequences:

- **A failed delete can already have changed things.** fprintd treats a device
  error as non-fatal: it removes the host file and then returns
  `PRINTS_NOT_DELETED_FROM_DEVICE` (`src/device.c:2395-2480`). With two readers, the
  client can finish one and then fail on the next (`utils/delete.c:173`). So the
  failure message says some may already be gone and never that the files are intact,
  and the next press may see `NoEnrolledPrints`. The "none saved" wording must be
  "fprintd has none on record", with the caveat that a reader which refused an earlier
  delete may still hold its copy. It must never say the reader is empty.
- **Intent decision 4's route has an order.** See Docs below.

An absent reader still runs the `rm`, as the intent says. On an unplugged
match-on-chip reader that orphans the chip's copy, and the message says those
stay there. See Risks.

### Second press

`fprintd-delete` exits 0 with "No fingerprints to delete", `test -e` is false,
and the row says fprintd has none on record for this account, then prints the
snapshot and login lines, and exits 0. It repeats safely any number of times.

### How privilege is obtained

`sudo`, as upstream, in the floating terminal the row already opens, so the
prompt has a tty. Three calls, one authentication: `sudo -n true || sudo -v`,
then `fprintd-delete`, `test` and `rm` on the cached timestamp.

- `rm` and `test` need root regardless: `/var/lib/fprint` is `StateDirectoryMode=0700`.
- `fprintd-delete` run as the user would need polkit's `auth_self_keep`
  (`net.reactivated.fprint.device.enroll`) and an agent, for a second prompt.
  Under root, polkit authorizes by uid. That is read, not run (Verification).
- With fprintd on, `sudo` asks for a finger first (`pam_fprintd` is `sufficient`,
  evaluated). That works, and is released before the delete claims the device. If
  `timestamp_timeout=0`, the later calls ask again and fall through to `pam_unix`.
  So the delete's capture must not take `sudo`'s stderr with it: that would hide any
  prompt written there, and read a refused `sudo` as a failed delete saying some prints
  may be gone. Upstream's comment at `:64` knows the capture hides things.
- `sudo fprintd-delete` resolves through the caller's PATH as `sudo fprintd-enroll`
  already does in the setup row, which `security.md` says really enrols.

### No lock-out

After deleting, a machine with fprintd on is in the same state as one that never
enrolled. No new auth state is created. Evaluated on `reference` with
`services.fprintd.enable`:

| stack | auth lines |
|---|---|
| `sudo`, `polkit-1` | `sufficient pam_fprintd`, `sufficient pam_unix`, `required pam_deny` |
| `login`, `omarchy-lock-password` | `sufficient pam_fprintd`, optional `pam_unix`, optional keyring, `sufficient pam_unix`, `required pam_deny` |
| `omarchy-lock-fingerprint` | `sufficient pam_fprintd`, `required pam_deny` |

`pam_fprintd` answers `PAM_AUTHINFO_UNAVAIL` for no prints (`pam_fprintd.c:376`),
which a `sufficient` line passes over, so the first two rows reach `pam_unix`. The
third has no fallback, and is gated: the shell only opens it when the file exists
**and** `fprintd-list` shows a `- #n:` line (`Service.qml:727`,
`FingerprintModel.js:39-45`). "has no fingers enrolled" classifies as `no`, and
`Service.qml:178-183` then aborts the attempt.

The stacks are checked by evaluation. That `pam_fprintd` really returns that code
and the shell really falls back is read, not run.

### Messages

Always printed, in this order, whatever else happened (except on exit 1 before the `rm`):

1. What was deleted, or that fprintd has none on record.
2. What could not be reached (no reader, fprintd off).
3. **Snapshots:** "Disk snapshots taken since you enrolled still hold a copy until
   they are deleted. `sudo snapper -c root list` shows the boot snapshots."
   Printed unconditionally rather than detected. No retention period is claimed.
4. **Login:** "Fingerprint login is still declared. Turn off `services.fprintd`
   (`fprintAuth` follows it), then Apply changes."

## Alternatives rejected

- **Remove the early exit outright.** Reaches `rm /etc/pam.d/omarchy-lock-fingerprint`
  and `omarchy-pkg-drop`. Excluded by the intent.
- **Keep an `exit` above the unwanted lines rather than cutting them.** The ledger,
  `checks.menu-actions` and every reader would keep seeing writers that never run.
- **`--replace-fail` line by line instead of a range cut.** Longer, and a new
  upstream step below the anchor would silently ship and run. A range cut drops it
  and the edge review reads the diff. The cost is noted in Risks.
- **`pkexec` for the prompt.** Three separate dialogs, or a helper to wrap them,
  for no gain over a tty the row already has.
- **Detect snapshots before mentioning them.** A branch and a stat for a sentence
  that is true in the same words on every machine.
- **Run `rm` first or independently of `fprintd-delete`.** Orphans the chip's copy.
- **Extend `checks.menu-guidance`.** Its contract is "no writer called", the opposite
  of this row.
- **A `pkgs/verify.sh` section.** The only useful probe deletes the tester's real
  prints, so it stays a named by-hand step.

## Risks

- **A stale chip print.** No reader, or a device error, leaves a copy on a
  match-on-chip reader with no route left. Reported, not preventable from here.
- **Text matching.** Three `fprintd-delete` strings are matched. A nixpkgs bump that
  changes them fails the check, and at runtime errs towards saying less.
- **Range cut hides an upstream addition.** A new upstream step below the anchor is
  dropped silently, and an upstream security fix there would not arrive. Edge's
  classification of each quattro commit is the review point.
- **Reversal of #1304's "Nothing was changed".** Pressing the row is now destructive
  with no confirmation, as upstream's is. Re-enrolling is the undo. Owner decision 2.
- **`sudo` absent in Mode A** (doas): the row refuses honestly with exit 1.
- **A second press has no memory.** With two readers, if the first refused on the previous
  press, the next press can truthfully say "deleted" about the second with no caveat for
  the first. The previous press said so, and the row keeps no state to say it again.
- **Hardware unverified.** See below.

## Verification

### `checks.remove-fingerprint` (new, `runCommand`, cheap tier)

`tests/remove-fingerprint.nix`. Runs the **shipped** script under `sed` rewrites of
exactly two paths, `/run/current-system/sw/bin/id` to a stub and `/var/lib/fprint/`
to a fixture, as upstream's own test does. It asserts each rewritten string occurs
the expected number of times first, so a no-op rewrite cannot pass (§1). `sudo` is a
stub that logs and then execs; `rm` and `test` are real, against the fixture, and
the stub refuses `-n` and `-v`, or fails an `rm`, when a case asks it to, because a
real `rm` on a fixture does not fail on its own. Every other writer is a recording

and `test` are also logged. `generated-checks.sh` picks it up with no workflow
edit (§4).

### The virtual reader: a spike, not yet run

**Unrun.** CI had four runs in flight when this was written, so the tier rule (§6)
forbade the VM. Source reading says it should work. libfprint's
`virtual-device-storage.c` is enabled by `FP_VIRTUAL_DEVICE_STORAGE` naming a socket,
has a real `prints_storage` table and a real `dev_delete` (`:189-226`), and nixpkgs
builds it (`-Ddrivers=all`). Unproven: fprintd's unit sandbox letting the socket
through, and that enrolment can be scripted over it.

The plan's first step runs it once, as a throwaway test outside the tree, when
`gh run list` prints 0:

1. Set the environment on `fprintd.service`; enrol `alice` and `bob` over the socket
   with `SCAN` and known ids.
2. Press the shipped script as `alice` with passwordless test sudo.
3. Assert `/var/lib/fprint/alice` is gone, `/var/lib/fprint/bob` stays, and
   `fprintd-list alice` says no fingers.
4. Send `REMOVE <alice-id>` and `REMOVE <bob-id>`. The driver warns "not found in
   storage" (`virtual-device.c:184-185`). It must warn for alice's and **not** for
   bob's: bob's is the control, since a warning alone could mean the id was never stored.
5. `pamtester` on `sudo` and `omarchy-lock-password` reach the password.

Whichever way it goes, the result goes in the PR and in `tests/AGENTS.md`. If it fails,
say why and leave those rows unverified. Owner decision 3 covers keeping it permanently.

### Hardware, by hand

A section in `tests/AGENTS.md` beside "The hardware-only pair" names the hole: enrol on
a real reader, press Remove, `sudo ls /var/lib/fprint`, and confirm the finger no longer
verifies at `sudo`, then that the password does. A match-on-chip reader is the only
thing that can show the chip obeyed. Nobody here has one, and the PR says so.

### Not run

Only `nix eval` of the PAM stacks and snapper config was run for this spec. No real
fingerprint data was read, and no real reader was touched.

## Owner decisions

1. **On a real `fprintd-delete` failure, does the row still run `rm`?** Recommended:
   no, stop and report, because the host file is the only route to the chip's copy
   and a retry usually succeeds. The cost: a template stays on disk until a retry or
   the printed `rm`, and it departs from upstream. The alternative is upstream's
   behaviour: disk gone at once, chip's copy orphaned for good.
2. **Confirm before deleting?** Recommended: no, as upstream. The row is named Remove,
   a `sudo` prompt already stands in the way, and re-enrolling undoes it.
3. **If the virtual-reader spike works, keep it as a permanent check?** Recommended:
   yes, because nothing else can see polkit, D-Bus and fprintd on a nixpkgs bump. It
   is a VM, so it needs a job in `build.yml` beside `wifi-hwsim`, which is a CI-gate
   change a human merges (§11). If not: paste the one run in the PR and leave the hole
   named.
