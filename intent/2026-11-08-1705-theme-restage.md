# Intent: a vanished or stale staged theme is put right on an existing home

## Problem

Omarchy stages the current theme into `~/.local/state/omarchy/current/theme`
and records its name beside it in `theme.name` (`bin/omarchy-theme-set:12`). Two things
can leave that staged copy wrong on a nixarchy home, and nothing here repairs
either:

1. **The theme vanished.** An Omarchy release removes a bundled theme (v4.5.0
   dropped Osaka Jade, #1698). A home that had it selected keeps
   `theme.name` naming a theme found in neither `$OMARCHY_PATH/themes` nor
   `~/.config/omarchy/themes`, and its staged copy lingers with no source. A
   refresh or a re-select then has nothing to read from. #1698 fixed that one
   theme by bundling it again; the next removal will do the same thing.
2. **The staged copy holds code.** Older staging copied an installed theme's
   `hyprland.lua`, `gum_env.lua`, `neovim.lua` and terminal configs into the
   staged theme, which Hyprland requires at login and the terminals include at
   launch. Upstream staging drops those now (`bin/omarchy-theme-set:25-35,
   290-294`), but a home staged before that keeps them until the theme
   changes, which may be never.

Upstream fixes both once, with migration `1787481315`: re-stage the current
theme, or apply Tokyo Night if it no longer exists. nixarchy lists that
migration in `data/user-migrations.nix`'s `predates` ("in v4.0.6 already; every
nixarchy seed carries its effect"), so it never runs here. That holds for a
fresh seed and not for a theme removed after it.

## Proposed outcome

- A home whose current theme no longer exists anywhere ends up on a theme that
  does, and the user is told which and why. That stays true for removals in
  future Omarchy releases, not only the one already shipped.
- A home staged before upstream tightened staging loses the staged theme code,
  once, without changing which theme is selected.
- A home whose theme exists and is staged cleanly sees no change and no
  notification.

## Affected users and systems

- Every Mode B home (installer-managed) on an Omarchy theme, on `main`'s tag
  pin and on edge. Users on a theme of their own in
  `~/.config/omarchy/themes` are affected only by outcome 2.
- `modules/home.nix` (first-run theme activation), `data/user-migrations.nix`
  and the user-migrations runner (#1692), `checks.user-migrations`.

## Constraints

- Mode A: a configuration that imports `nixosModules.nixarchy` without opting
  in is untouched.
- Never replace a theme that exists, in either theme root.
- No network: the fix may only use what the home and the store already hold.
- A user's own theme directory is never modified or deleted.
- Must hold under both Omarchy pins (`main`'s tag and edge's quattro), the
  lesson of #1709.

## Open questions

1. **One-shot or recurring for the vanished theme?** Porting `1787481315`
   through the runner fixes the current state once. A check at home activation
   (beside the existing first-run theme step) would also catch the next
   removal. Recommendation: recurring for outcome 1, the ported migration for
   outcome 2.
2. **Which fallback theme?** Upstream applies Tokyo Night; nixarchy has
   `programs.nixarchy.defaultTheme`. Recommendation: the configured default,
   since that is what this home's first run would pick.
3. **How is the user told?** A desktop notification at the next login, or a
   line in the activation log only. Recommendation: a notification, because a
   theme changing without notice reads as a bug.
