# Spec: edge takes Omarchy quattro 155c4b4

Approved by the owner's standing pre-approval (2026-11-26). The design is Codex's read-only diagnosis, taken as written. Its noted limit is accepted: the skill-parity row holds for 155c4b4 and v4.5.0, not for the 3642699 fallback, which edge builds only when the new pin fails.

## Design

I traced all four failures in issue #1964 to the upstream diff from `3642699` to `155c4b4`. The smallest carry is a cache-tag retarget, a pin-aware agent count, one skill-parity update, and seven ledger entries. [Upstream comparison](https://api.github.com/repos/basecamp/omarchy/compare/3642699...155c4b4) · [CI run](https://github.com/olafkfreund/nixarchy/actions/runs/45855151315)

1. **`omarchy` package.** Upstream bumped the cache key from `v22` to `v23` when it started hashing Lua binding files and batched Hyprland state. The submap-filter insertion still matches. Add `23` to the existing substitution loop so the new pin writes `v23-submaps`, and retain the fatal guard. The old quattro pin uses `v22` and v4.5.0 uses `v19`. [Package substitution](/mnt/data/vmtest/wt-1964/pkgs/omarchy/default.nix:489) · [Upstream cache key](https://github.com/basecamp/omarchy/blob/155c4b4/bin/omarchy-menu-keybindings#L709-L742)

2. **`default-agent-routes`.** Upstream removed exactly `kiro-cli` and `commandcode`. The no-menu branch still expects 25 IDs and now extracts 23. Expect 23 when the upstream source contains the new `bin/omarchy-install-ai-cli` helper and 25 on the older quattro shape. Keep the 24-row menu branch for v4.5.0 and the existing port-side compatibility cases. I verified the helper is present only on the new pin among the three sources. 3. **`skill-parity`.** Upstream added a Polkit exception for installing curated Arch packages. Keep `Privilege Escalation` classified as `adapted`, retain its existing anchor, and update the reason to explain that Nixarchy uses declarative package installation. Set `upstream = "fde15ad3173f"` and `tag_upstream = "d4ded906a1a4"`. I ran the checker’s comparison in memory and got zero findings for `155c4b4` and v4.5.0 with those values. The same comparison fails on `3642699`, which is still `origin/edge`’s fallback pin. If this carry must pass on that fallback too, the checker needs an explicit digest for that revision.
