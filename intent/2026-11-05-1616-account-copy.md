# Intent: `omarchy agent account copy` works in every direction, and we know why

Part of #1610.

## Problem

#1616 says `omarchy agent account copy` fails against a NixOS machine, because
upstream hardcodes paths that don't exist there. **Measured, that is not true of
a default nixarchy destination.** The real problem is narrower: the command
works only because of envfs and the session environment, nothing says so, and the
proposed fix ("patch the paths") would break a direction that works today. #1610's
entry came from reading the files; nobody ran the command.

**How the command works.** The sender builds a shell command and SSH runs it on
the destination, with credentials on stdin. All citations to upstream are v4.5.0:

- `bin/omarchy-agent-account-copy:37-40` sends the bundle over `ssh -T`.
- `bin/omarchy-agent-account-transfer:352-358` builds the command from
  `/bin/bash`, `/etc/profile.d/omarchy.sh` and `/usr/bin/python3`.

These three strings are evaluated on the destination, but generated on the
sender, which can't know the destination's OS. This script is the only vendored
one that builds a remote command with these paths (`omarchy-theme-set-herdr-machines:76`
is the only other scripted `ssh`, and has no such paths on its command line).

**Why it resolves here.** `modules/nixos.nix:1580` defaults `services.envfs.enable`
to true, so `/bin` and `/usr/bin` resolve names through the calling process's PATH.
`modules/nixos.nix:1397` puts `python3` on the system PATH. `/etc/profile.d/omarchy.sh`
doesn't exist here, but upstream ignores that failure (`:357`). `OMARCHY_PATH` comes
from `environment.sessionVariables` (`modules/nixos.nix:1358-1359`), which reaches
`/etc/pam/environment`, and `sshd` here has `UsePAM yes`.

**Measurements, on p620 (envfs mounted), no real credential involved:**

| Case | Result |
|---|---|
| Fake Claude login, real `sshd` over loopback, fake `HOME` on the far side | exit 0, `Claude: copied Main`, credential files mode 600 |
| Receiver with only `/run/current-system/sw/bin` on PATH, empty stdin | Interpreters resolve; `invalid receiver bundle` (stops before import) |
| Fake login, receiver installed on PATH, `OMARCHY_PATH` unset | exit 1, `destination account backend is unavailable`; nothing written |
| Fake login, no receiver installed, `OMARCHY_PATH` unset | exit 0, copied by the in-memory fallback (`transfer:70-77`) |
| Receiver with neither `bash` nor `python3` on PATH | exit 127, `/bin/bash: No such file or directory`; stdin unread |
| Stub `python3` first on PATH, empty stdin | The stub runs instead of the system Python |
| `reference` config, evaluated | envfs on; `python3` and `bash` in `systemPackages` |

**Directions:**

| Direction | Today | Basis | What a sender patch does |
|---|---|---|---|
| NixOS → nixarchy | Works | Measured above | Nothing needed |
| Arch Omarchy → nixarchy | Should work | Same command text as above, from an unpatched sender; no Arch sender run | Can't help: we don't ship that sender |
| nixarchy → Arch Omarchy | Should work | We don't patch the command, and those paths are Arch's own; not run | **A store path or `/run/current-system` path breaks it** |
| Any → NixOS with envfs off, or plain NixOS | Fails | Read: `modules/nixos.nix:1577`. Nearest measurement is the exit 127 row | One probing the destination could help nixarchy senders only |

**Reachability.** Reachable from the CLI only: `omarchy agent account --help` lists
`copy`, and no menu row or panel calls it (`shell/plugins/agents/Panel.qml` calls
`add`, `rename`, `use` and `mode`, not `copy`). It is live on `main` too: the script
is byte-identical in v4.5.0-rc3, v4.5.0 and this host's tree below line 1, so this
doesn't wait for #1606.

**Why `bin-ledger` didn't flag it.** It can't see this class:

- A ledger row claims a file differs from upstream (`data/bin-ledger.nix:10-16`).
  This one is `vendor`, so it correctly has no row.
- `allow` groups (`.github/scripts/check-bin-ledger.py:85`) cover behaviour such as
  `systemctl` or writes under `/etc`, not interpreter paths.
- `patchShebangs` (`pkgs/omarchy/default.nix:2107`) fixes line 1, so the `#!/usr/bin/python3`
  was never the problem; only the strings at `:352` and `:358` survive.
- `checks.session` (`tests/session.nix:310-311`) probes `/bin/bash` and `/usr/bin/env`
  through envfs. Nothing probes `/usr/bin/python3`.

By §2, what we ship that names something else needs a list or a check. This has
neither. A check over the shipped tree is the layer that could see it.

**Scripts sharing the pattern**, excluding shebangs:

| Path inside a script | Upstream `bin/` | Shipped here |
|---|---|---|
| `/usr/bin/python3` | 6 files, 7 lines | 1 file (this one): `default.nix:861-866` patches the other 5 |
| `/bin/bash`, `/usr/bin/bash` | 11 files, 16 lines | 10 files, 15 lines |
| `/etc/profile.d` | 1 file | 1 file (this one) |

The shipped `/bin/bash` hits run locally through envfs, four are generated
scripts' shebangs, and some are patched already. Only this script's run on another
machine. Whether each local hit works is not checked here.

**Security.** This moves OAuth tokens for Claude, Codex and Grok (`transfer:32-36`).
What upstream gets right holds here too: credentials travel on stdin only, never in
arguments (`copy:35-40`). A failure before the importer runs writes nothing, but an
import that fails partway keeps the providers already done (`transfer:383-389`).

One upstream guarantee is weaker on nixarchy. `:355-356` pins absolute paths to
"avoid user profiles, BASH_ENV and home-directory Python modules while credentials
are on stdin". Under envfs those paths resolve through PATH, and the loopback SSH
session's PATH starts with `~/bin` and `~/.local/bin`. So a `python3` or `bash` in
those directories receives the credential stream, even if the import would then
fail, as the stub row shows. A broken `python3` there breaks the copy the same way.

That crosses no privilege boundary: the receiving code already runs as the account
the logins are being copied to. Upstream has similar exposure on every OS: the login
shell's startup files run with the stream on stdin, and `shutil.which` (`:52`) picks
the importer from PATH. So this is low severity, but it should be a stated decision
rather than an accident. The same envfs property is why two sudoers rules stay
`divergent` (`data/etc-overlay.nix:190`).

## Proposed outcome

- A copy from nixarchy or Arch Omarchy to a default nixarchy machine works, and
  nixarchy to Arch Omarchy keeps working.
- A destination that can't receive it (envfs off) fails with no credential written,
  and the docs say why.
- The reliance on envfs, `python3` on PATH and `OMARCHY_PATH` over SSH is written
  down and checked by running the generated receiver with a fake login, so losing
  any of them goes red rather than silently breaking logins.
- #1610's "confirmed gap" entry is corrected.

## Affected users and systems

- Anyone copying logins to or from nixarchy, on Claude, Codex or Grok.
- nixarchy machines with `services.envfs.enable = false`.
- Mode A machines (`programs.nixarchy.enable` off) and plain NixOS. They have no
  envfs, so they fail on `/bin/bash`. Omarchy's commands aren't what's missing: the
  in-memory fallback needs only the two interpreters, so any FHS machine can receive.
  The manual promises only "another Omarchy machine" (`manual/17-ai.md:65`).

## Constraints

- Must not break nixarchy → Arch Omarchy, which rules out naming a path that exists
  only on the sender's OS.
- Must not put credentials in arguments, logs, the store or test output.
- Must not widen trust on the destination beyond what it has now.
- A fix to how Omarchy itself behaves belongs upstream (§11), and we don't file there
  unprompted.
- Coexistence (§14): must not start overriding a user's `services.envfs` setting.

## Open questions

The owner approved every recommendation below on 2026-11-05.

1. **Do we change what the sender emits?** Recommend no. It solves nothing on a
   default destination and can't reach Arch senders. A simple path swap breaks
   nixarchy → Arch; one that probes the destination would only help nixarchy senders
   reach envfs-off machines.
2. **What must the guard prove?** Recommend the real receiver command, with a fake
   login, in an environment like an SSH session. A probe of `/usr/bin/python3` alone
   stays green with `OMARCHY_PATH` missing (§1). Whether to also watch the whole class
   on future bumps (about 11 ledger rows, if done there) is for the spec.
3. **Support destinations without envfs (envfs off, Mode A, plain NixOS)?** Recommend
   no: fail, and say so in the docs. Turning envfs off is an explicit choice, and the
   manual promises only Omarchy machines.
4. **Accept that the interpreter resolves through PATH?** Recommend accept and
   document, for the reasons under Security.

Not measured: Codex and Grok (only Claude was round-tripped); a real second machine;
any Arch end; login shells other than bash (PAM should supply `OMARCHY_PATH`
regardless, by reading); a machine with envfs actually off.
