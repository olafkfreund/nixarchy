## Design

### 1. The app skill patch, rebased with judgement

`pkgs/omarchy/1406-omarchy-app-nix-edge.patch` is regenerated against
`c6945de` with `diff -u` from upstream's files, not hand-edited. Its intent
stays what it was: the skill teaches building an app as a flake (`nix
develop`, `nix run`, `nativeCheckInputs`), never `omarchy-pkg-add`,
`/usr/lib`, or `cmake --install` into `~/.local`. Upstream's rewrite adds
three things the old patch never saw:

- **`scaffold`**, a new script in the skill directory. It writes every file
  from `templates.md` (which our patch already turns into a flake project),
  the LICENSE and `git init`, then runs `bin/test`. Its `#!/usr/bin/python3`
  shebang needs nothing: stdenv's fixup rewrites shebangs in every
  executable in the output, and the built scratch package already has a
  store `python3` there (Codex's review). Two things do need a patch,
  because a first run would fail on NixOS:
  - the generated `bin/build` and `bin/test` start `#!/bin/bash`
    (`templates.md:58,71` in the built package), and `bin/test` executes
    `bin/build` directly; NixOS has no `/bin/bash`. The templates' two
    shebangs become `#!/usr/bin/env bash`;
  - `scaffold` runs `git init` but tracks nothing, and a flake sees only
    tracked files (§5), so `nix develop` would not find the new
    `flake.nix`. `scaffold` gains `git add -A` after `git init`, and runs its
    test as `nix develop --command bin/test`, because `cmake` exists only
    inside the dev shell here.
- **`/usr/lib/qt6/bin/qmllint`** (SKILL.md:84): becomes `qmllint`, which the
  dev shell puts on PATH. The patch's template already lists
  `qt6.qtdeclarative` (`1406-omarchy-app-nix-edge.patch:198`), and the shell
  inherits it through `inputsFrom` (line 163).
- **`omarchy agent look app -- ./build/<name>`**: an upstream command that
  works on nixarchy unchanged, because it runs the built binary offscreen.
  Not patched, except where its build path differs from a `nix build`
  output, which the plan checks.

The line about `checkdepends` in omarchy-pkgs keeps the existing hunk's
replacement (`nativeCheckInputs` in `package.nix`). The SKILL.md line about
packages being "part of Omarchy" keeps the existing hunk's replacement.

`checks.skill-parity` passed at `c6945de` with the mechanical rebase, so
the section digests it compares are unaffected; it is re-run after the
rebase.

### 2. The theming.md rule follows upstream's text

`pkgs/omarchy/default.nix:1228`: the rule for the removed line is replaced
by one for the new step 1:

```
--replace-fail '(dark or light) from `/usr/share/omarchy/themes/` and change' \
               '(dark or light) from `$OMARCHY_PATH/themes/` and change'
```

The file's other three Arch paths (lines 68, 80, 89) still match the
existing rules. This line exists only at `c6945de`'s text, and `main`'s tag
pin still has the old line, so it must hold under both pins (§8). It becomes
a pin-conditional rule, written the way `default.nix` already picks the
edge and tag variants of `1406` (`if isEdge then … else …`).

### 3. Ledger rows

**`data/bin-ledger.nix`**. Upstream moved two commands into its new
`omarchy-device-*` family. The old `omarchy-toggle-hybrid-gpu` is now
`exec omarchy-device-gpu-hybrid "$@"`.

- `omarchy-keyboard-toprow` (an `edge = "only"` row): deleted. Quattro no
  longer ships it, and `main` never had it.
- `omarchy-device-keyboard-toprow`: new, `edge = "only"`, `vendor`,
  `allow = "initrd-boot modprobe"`, with the old row's reason carried over
  (it writes `/etc/modprobe.d`, sets `hid_apple`'s live `fnmode` and reruns
  `limine-mkinitcpio`; the declarative equivalent is
  `boot.extraModprobeConfig`), updated for the read-only sysfs handling
  upstream added.
- `omarchy-device-gpu-hybrid`: new, `edge = "only"`, `vendor`,
  `allow = "etc-write systemctl-system"`, with the old supergfxd reason.
- `omarchy-toggle-hybrid-gpu`: gains `edge = "absent"` and keeps its
  `allow`. `main`'s tag pin still ships the full script; on quattro it is a
  vendored one-line alias, which gets no row. `tag_allow` alone would not
  do: on edge the row would remain with no allowance, and
  `check-bin-ledger.py:324-337` rejects a bare vendor row ("a row for a file
  identical to upstream", measured in review).

**`data/omarchy-packages.nix`**: `raspberry-pi-4-bluetooth-firmware`,
`edge = "only"`, `skip = "Raspberry Pi 4 hardware (aarch64); this port
targets x86_64."`, in the house form of `asahi-bless`.

**`data/user-migration-commands.nix`**: `omarchy-agent-local-launchers`,
`edge = "only"`, `follow = true`, reason: writes one `.desktop` file and
a vendor-logo SVG icon under `~/.local/share` for each local model that is
set up, and removes those of models taken away. `follow = true` makes the
ledger triage every migration that calls it, which brings in a third
migration below.

**`data/user-migrations.nix`**, both `edge = "only"`, `run = "upstream"`:

- `1794931275`: `decision = "ported"`. It gives each agent harness already
  installed its own launcher in `~/.local/share/applications` through
  `omarchy-agent-launcher`, then redraws the icon set. It works on nixarchy
  as on Arch.
- `1794938310`: `decision = "ported"` (the approved herdr decision). It
  appends `[update] version_check = false` to `~/.config/herdr/config.toml`
  when the file exists, is not a symlink at any level, and has no `[update]`
  table. The reason names why it holds here: nixpkgs' herdr 0.9.5 leaves the
  check on, recognises a `/nix/store` binary, and tells the user to "update
  through Nix", a notice they cannot act on outside a rebuild. Its
  `python3` (for `tomllib`) is in Omarchy's `runtimeDeps`
  (`pkgs/omarchy/default.nix:284`), on the session PATH the migration hook
  keeps (`modules/home.nix:2601-2608`).
- `1794839007`: `decision = "ported"`. It runs `omarchy-agent-local-launchers`
  once, so models set up before launchers existed get theirs. Found in
  review: it is what `follow = true` on the command row brings in.

### 4. T3 Code gets `flock`

`modules/home.nix:1683-1689`: the activation's PATH for
`omarchy-theme-set-t3code` gains `pkgs.util-linux`, for `flock`, which
quattro's setter takes at line 25 to serialise theme writes. This holds under
both pins: `main`'s setter does not call it, and an extra PATH entry changes
nothing there. It goes in the carry with the rest, not in a separate `main`
PR, so the carry is one reviewable unit.

### 5. The pin

`flake.nix`'s input `url` and `omarchyVersion` move to `c6945de`
(`edge-20261118-c6945de`), and `flake.lock` with them, in the same carry as
the rows (§8).

## Alternatives rejected

- **Pin `419a5a7`**, the commit named in the intent: rejected by question 1.
  The rows would be stale on arrival.
- **Hand-edit the three failing hunks.** The patch would encode the old
  structure, and the new `scaffold` and `qmllint` lines would ship
  unpatched. A rebase against the new text is the only way the patch
  describes what users read.
- **Delete `omarchy-toggle-hybrid-gpu`'s allowance outright.** `main`'s tag
  pin still ships the full script, so its `bin-ledger` would go red at the
  next edge-to-main merge. `tag_allow` exists for this.
- **Decline the herdr migration.** Rejected by question 2.
- **Land the T3 Code PATH fix on `main` first.** Valid under both pins, but
  it splits one upstream change across two PRs and two reviews for no gain.

## Risks

- **The skill teaches something that does not run.** `scaffold` running
  `bin/test` through `nix develop` is the riskiest line here, because no
  check runs `scaffold`. The plan adds one: run `scaffold` against a
  temporary directory in a check, offline, as far as the dev shell allows. If
  that cannot work offline, the PR says so and a human runs it once.
- **Claimed VM checks never boot on quattro** (agent bus, #1543): edge's
  `verify` builds only generated checks. The commits touching keyboard setup
  under read-only sysfs make `keyboard-boot` the one to boot locally on the
  carry tree. `session` also boots, because the T3 Code and launcher changes
  run at login.
- **Main's pin.** Every non-VM check also runs on a scratch tree with
  `main`'s tag pin restored (§8, and #1752's lesson: pin-derived data
  beyond the ledgers goes red too).
- **Quattro moves during review.** The pin is frozen; a
  `from_candidate=true` dispatch keeps the carry's pin, and later commits
  are the next run's.
- Hosts: edge users only. p620 runs the local builds under §6's tiers.
