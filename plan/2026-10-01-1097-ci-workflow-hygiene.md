# Plan: Make CI workflow gates honest and keep forks off the install runners

## Approved decisions and owner boundary

All five #1097 findings are in scope. The approved fork rule is: an install-relevant fork PR fails its required `install` check on a hosted runner; an irrelevant fork PR gets the existing green no-op; same-repository PRs keep their normal install gate. For forks, the hosted gate runs the base branch's `.github/scripts/pr-touches-build.sh`, not fork code. Unknown relevance is relevant. A fork must not get a self-hosted job.

GitHub's [trusted-base event guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) says `pull_request` uses the PR merge commit's workflow, which a fork can edit, while `pull_request_target` uses the base branch workflow. Therefore `install-check.yml` must use `pull_request_target` for PRs, with explicit read-only token scopes, base-only code in its hosted gate, and no fork checkout. An `if:` inside the current `pull_request` workflow is not a security boundary. The owner must verify the repository's Actions event policy permits `pull_request_target` before applying; [GitHub warns](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) that a public-repo default policy may block this event. The owner may also require approval for all outside collaborators and restrict runner access; those settings are complementary and are not changed by this branch.

This plan's output is a **ready-to-apply branch**, not an automatically merged CI change. Root `AGENTS.md` §11 reserves CI-gate changes for the owner to review and merge. Implementation starts only after this plan is approved. The implementing agent writes and checks the patch locally, then stops for owner review; no deploy, push, PR or merge is authorized by this plan.

## Rollback

Before owner merge, discard the proposed workflow patch branch and leave `main` unchanged. After merge, revert the workflow and docs commit as one owner-reviewed change, restoring the previous triggers and gate semantics. If the trusted-base trigger is blocked by an Actions policy, the owner restores a working required `install` check before accepting further PRs; an absent required check must never be treated as green.
