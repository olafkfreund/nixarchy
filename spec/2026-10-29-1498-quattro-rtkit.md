# Spec: edge follows Omarchy quattro's rtkit change

## Design

Two changes on `main`, which reach edge with its next merge, and one carry on
edge.

### 1. rtkit on (`main`)

In `modules/nixos.nix`'s `security = { ... }` block (`:1800`), add
`rtkit.enable = lib.mkDefault true;`, with a comment naming upstream's base
package list and omacom/omarchy#9390. nixpkgs' PipeWire module then adds
`rtkit` to the daemon's groups itself (`pipewire.nix:490`).

### 2. Clients ask rtkit directly (`main`)

Upstream sets `module.rt.args = { rtportal.enabled = false }` in
`client.conf.d` and `jack.conf.d`. Decision 2 (install the files verbatim)
can't be built. nixpkgs refuses any `environment.etc."pipewire/..."` entry
with an assertion (`pipewire.nix:389-392`). Upstream's files also exist only
on quattro, so a module that links them would fail to build on `main`.

So the setting is declared instead, the alternative the intent offered:

```nix
services.pipewire.extraConfig = {
  client."50-omarchy-rtkit"."module.rt.args"."rtportal.enabled" = false;
  jack."50-omarchy-rtkit"."module.rt.args"."rtportal.enabled" = false;
};
```

These go inside the existing `pipewire = { ... }` block (`:1591`), as an
attrset with plain assignment, per §7. nixpkgs writes them to
`/etc/pipewire/{client,jack}.conf.d/50-omarchy-rtkit.conf`, the same paths
upstream uses. Because the setting is declared on `main` as well, the
running-session risk the owner accepted mostly goes away: a client never asks
the portal, so the portal's stale zero budget never reaches it.

### 3. Edge carry: the rows

These go on `edge-candidate` as one commit, then a `from_candidate`
dispatch:

- **`data/etc-overlay.nix`:** both files get `class = "native"`, with a
  reason naming `services.pipewire.extraConfig` and the `pipewire.nix`
  assertion.
- **`data/bin-ledger.nix`:** `omarchy-realtime-repair` gets
  `class = "vendor"`, a `pacman` reason, and
  `allow = "systemctl-system systemctl-user"`. The reason: only a migration
  and `omarchy-upgrade-to-quattro` call it, nixarchy runs neither, and
  `security.rtkit.enable` stands in for its install.

## Coexistence (§14)

- **A user sets `security.rtkit.enable = false`.** `mkDefault` yields to it,
  and the drop-in still applies. With no rtkit, a client then gets realtime
  only if its own limits allow it, never at a zero limit, which upstream
  describes as safe. No fixture: no failing case exists.
- **A user's own `services.pipewire.extraConfig.client.<name>`.** These are
  separate attrset keys, so they merge. A user who sets the same name
  `50-omarchy-rtkit` merges at key level, and a conflicting value fails
  evaluation loudly. A fixture would only restate the module system.

## Alternatives rejected

- **`installed`, verbatim (decision 2):** refused by nixpkgs' assertion, and
  quattro-only.
- **`services.pipewire.configPackages` linking upstream's files:** verbatim,
  but the files exist only on quattro, so the module line would also have to
  be an edge carry. Then `main` would get rtkit without the drop-in, which is
  the risk the owner flagged.
- **Patching or running `omarchy-realtime-repair`:** its whole job is a
  pacman install and limit repair on Arch. Declaring rtkit from boot means
  the zero budget never arises on a fresh boot.

## Risks

- **The switch that adds rtkit.** Processes started before it may still hold
  a hard `RLIMIT_RTTIME` of 0 they got from the portal. With the drop-in,
  PipeWire clients stop asking the portal, but a process that already holds
  the zero keeps it until it restarts. Release notes: "log out and in once
  after this update". This is the owner's accepted risk, now narrower.
- **PipeWire's drop-in override of `module.rt.args`.** Upstream relies on it
  in exactly this form, and nixpkgs' `extraConfig` writes the same key as
  JSON.

## Verification

- **`tests/options.nix`, using `etcNative` (`:616`), so both Mode A states
  are asserted:**
  - `etcNativeRtkit = etcNative (c: c.security.rtkit.enable) true;`
  - `etcNativeRtportal`, reading the client key, `false` on and absent off.
- **`checks.session` (§2, the highest layer):** the shell's process
  (`pgrep -o quickshell`) has a non-zero hard `Max realtime timeout` in
  `/proc/<pid>/limits`, and `systemctl is-active rtkit-daemon` succeeds once
  PipeWire has started.
  - Red proof: on a throwaway branch with `rtkit.enable` removed, the
    portal reports 0 and the hard limit reads 0. That is the zero upstream
    describes, measured here.
  - The drop-in only matters at the switch, and no VM boots through one.
    That hole is named in `tests/AGENTS.md`.
- **Edge:** a `from_candidate` dispatch of `omarchy-edge.yml` with the carry,
  where `bin-ledger`, `etc-overlay` and `verify` are green, and edge reaches
  quattro `8478247`.
- **Cheap tier:** `nix fmt -- --ci`, statix and deadnix.
