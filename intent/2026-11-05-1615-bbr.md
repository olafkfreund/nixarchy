# Intent: BBR and the fq qdisc reach nixarchy, and a `native` sysctl row can't go stale silently

Part of #1610.

## Problem

**Two values are missing.** Upstream's `etc/sysctl.d/99-omarchy-sysctl.conf`
sets `net.core.default_qdisc=fq` and `net.ipv4.tcp_congestion_control=bbr`
(lines 7-8). `data/etc-overlay.nix:228-231` classes that file `native` and says
"value for value". `modules/nixos.nix:2222-2237` sets neither.

Evaluating `nixosConfigurations.reference` confirms it: `boot.kernel.sysctl` has
no such keys, so a machine runs what systemd's `50-default.conf` and the kernel
choose (`fq_codel`, and `cubic` per `CONFIG_DEFAULT_TCP_CONG`).

This doesn't wait on #1606. `main` pins `v4.5.0-rc3` (`flake.nix:82`), and its
sysctl files hold the same keys and values as v4.5.0.

**Nothing noticed.** `tests/etc-overlay.nix:60-61` hands the check only the
manifest's row names, and it diffs them against the shipped file list
(`:76-77`, `:90`). A row's `reason` is checked only for length (`:44`). So an
edited file passes. `modules/AGENTS.md:451-453` already records this hole: the
check forces a decision "when a file is added or dropped, but not when one is
edited". `tests/options.nix:1200-1202` asserts 3 of the 13 keys, against values
written in the test rather than read from upstream.

### Measured drift

Compared against the reference configuration:

| Upstream file | Class | Keys | Match | Missing |
|---|---|---|---|---|
| `99-omarchy-sysctl.conf` | `native` | 11 | 9 | `default_qdisc`, `tcp_congestion_control` |
| `90-omarchy-arp.conf` | `native` | 4 | 4 | none |
| `90-omarchy-file-watchers.conf` | `covered` | 1 | 1 | none |

Those are the only sysctl files, and no value differs: the drift is the two
missing keys. The reasons for the other 20 `native` rows are prose about
non-sysctl files. A grep of the modules found matching values for the systemd,
logind, oomd, NetworkManager, sudo and Docker log rows. The `cups`, `nsswitch`,
`plymouth` and `sddm` rows were not compared.

### The obvious fix breaks a real machine

Adding the keys to the existing `mapAttrs mkDefault` block is what #1610
suggests. It gives a user's plain value the win, measured on `vm.swappiness`
(a plain 60 and a `mkForce 60` both give 60). But a user's own `mkDefault` is an
**evaluation error, even with the same value**: `lib.mkDefault 150` and
`lib.mkDefault 60` both failed against nixarchy's `mkDefault 150`, because
`sysctlOption` merges through `mergeOneOption` (nixpkgs
`nixos/modules/config/sysctl.nix:17`) and both definitions sit at one priority.

The owner's own config does exactly this: `modules/common/networking.nix:54-55`
sets both keys with `lib.mkDefault`. `p620` and `p510` also set them plainly and
would survive. `razer` imports `nixosModules.nixarchy` and has no plain value, so
it would stop evaluating. Any user who tuned BBR the same careful way would too.

### What was measured about the module

`tcp_bbr` and `sch_fq` are modules, not built in (`CONFIG_TCP_CONG_BBR=m`,
`CONFIG_NET_SCH_FQ=m`), and nixpkgs' `common-config.nix` doesn't change that.
They load on demand: the kernel requests `tcp_<name>` and the qdisc alias when
the sysctl is written (v7.0 `net/ipv4/tcp_cong.c:50-57`,
`net/sched/sch_api.c:221-233`).

`p620` runs the kernel the reference configuration evaluates to (same store path,
`linux-7.3.1`), sets both sysctls, and lists neither module in
`/etc/modules-load.d/nixos.conf`. It runs `bbr` and `fq` with both modules
loaded. So `boot.kernelModules` looks unnecessary on nixpkgs' kernel. That is one
machine, with no VM run. A user's own kernel without these modules is not measured.

## Proposed outcome

- A nixarchy machine with no opinion of its own runs `bbr` and `fq`, seen in
  `/proc/sys`, after a reboot.
- A machine with its own value keeps it, however it set it.
- When upstream's sysctl value changes or a key is added, a check fails and names
  the key, until someone decides. A deliberate difference is written down.
- `data/etc-overlay.nix:230` says what is true.

## Affected users and systems

- Every machine with `programs.nixarchy.enable`, on its next rebuild: TCP changes
  from `cubic` to `bbr`, on all connections, without being asked.
- Mode A with nixarchy off gains nothing: the block is inside `mkIf cfg.enable`
  (`modules/AGENTS.md:444`), and `etcNative` asserts both states.
- Owner's `razer`, as above. `p620` and `p510` keep their own values.
- `tests/coexistence/`, `tests/etc-overlay.nix` or a sibling check, and
  `data/etc-overlay.nix`.

## Constraints

- A user's value wins (§7, §14). §14 requires a Coexistence section in the spec,
  answered by a fixture in `tests/coexistence/fixtures.nix` that can fail (§1),
  and it must cover a user's own `mkDefault`, not only a plain value.
- A changed default a user commonly sets is announced in the release notes and
  the Discussions post, with the migration step (§14).
- The new check must fail on the bug as it stands today (§1), and must not trip
  on comments or key order in upstream's file.
- Edge pins newer upstream commits, so a value check also fires there. It has to
  be a decision edge can record, not a stop.
- Eval-only and cheap where possible: the whole `options` check needs about
  11.5 GB. A running value is only visible in a booted VM (§2).
- `modules/nixos.nix` is shared with #1611, #1612, #1613 and #1614. Stay inside
  the sysctl block there.
- Must work on both channels (`checks.stable-eval`).

## Open questions

1. **Does a user's own `mkDefault` have to survive for these two keys?**
   Recommended: yes. Otherwise `razer` and anyone like it fail to evaluate on the
   next update. The spec picks the mechanism.
2. **The other 13 keys have the same `mkDefault` collision today.** Fix them here,
   or only the two new ones? Recommended: only the two; file the rest if the owner
   wants it, since nobody has reported it.
3. **How far does the value check reach?** Recommended: the three `sysctl.d`
   files, whose `key=value` form can be compared mechanically. The other 20 `native`
   rows stay prose, named as a known hole in `tests/AGENTS.md` (§3).
4. **Kyber: stays declined?** Recommended: yes. Nothing measured changes the
   reason at `data/etc-overlay.nix:330`: `p620`'s NVMe disks do run `bfq`, and a
   udev rule still can't yield to a host's choice. But that row says "Tracked in
   #1386", which is closed and about mise wrappers, so nothing tracks it. Point
   it at #1610 here, and tick that box.
5. **Release note wording for BBR.** Recommended: state the change, and how to
   set `cubic` back.

Not verified: what `systemd-sysctl` does when the module is absent (a loud failed
unit or a quiet `cubic`), `security.lockKernelModules`, and microvm guests.
