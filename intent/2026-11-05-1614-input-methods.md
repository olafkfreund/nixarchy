# Intent: Omarchy's input methods can be chosen and used on nixarchy

## Problem

Omarchy 4.5 offers Japanese (Mozc), Korean (Hangul), Simplified Chinese (Pinyin),
Taiwanese (Zhuyin) and Hong Kong (Cangjie) typing under Setup > Typing
(`default/omarchy/omarchy-menu.jsonc:185-187`). On nixarchy none of them can work,
for two separate reasons.

**The engines are not installed.** `data/omarchy-packages.nix:341-363` says the
fcitx5 addons come from `i18n.inputMethod.enable`. `modules/nixos.nix:2290-2293`
sets only `enable` and `type`, and nothing sets `i18n.inputMethod.fcitx5.addons`.
Evaluated: the reference machine's addon list is `[]`. Nothing caught this because
`tests/omarchy-package-ledger.nix` does not check `module` rows; they are "read by
hand" (`data/omarchy-packages.nix:25-26`).

**The tools around the engines also fail here.** Installing addons alone leaves
these, all read in the v4.5.0 tree and in a built `omarchy-4.5.0-rc3`:

| Where | What happens on nixarchy |
|---|---|
| `bin/omarchy-setup-input:27` | Runs `omarchy-pkg-add fcitx5-mozc` under `set -e`. Our stub exits 1 for a name with no table row and no command (measured), so `omarchy setup input mozc` stops there, whether or not the engine is installed |
| `typing_setup.py:113` | When a chosen engine is not yet loaded, for example after a rebuild while fcitx5 is running, this asks `omarchy-pkg-present fcitx5-mozc`. Our stub exits 1 (measured), because no such command exists, so the picker reports "Install fcitx5-mozc" and never reaches the restart at `:119`. Whether a rebuild restarts the unit first is not measured |
| `default/input-methods/indicator.py:10` | Imports `gi`. Both `python3` builds in the closure fail with `No module named 'gi'` (measured). This process feeds the bar indicator and `Super+I` (`shell/Commons/InputMethodState.qml:9-19`), so neither can work with those builds, whatever PATH says |
| `typing_setup.py:19` | Reads `/usr/share/systemd/kbd-model-map`, which is absent; envfs serves only `/bin` and `/usr/bin`. The file exists at `/run/current-system/sw/share/systemd/`. Setup > Typing > Keyboard Layouts fails with a notification |
| No fcitx5 profile | `configure.py` aligns fcitx5's group with the machine's layout, but `pkgs/omarchy/enable-user-units.sh` omits upstream's `omarchy-input-method configure --defaults`, and `config/fcitx5/` ships no `profile`. What a non-US machine types after leaving an engine is not measured |

**The reported `/usr` paths: partly confirmed.** All of them exist and none is
patched; `pkgs/omarchy/default.nix:862-865` patches five `bin/` scripts only. Their
effect differs:

- `typing_setup.py:19` is a real failure (above).
- `typing_setup.py:59` is what both pickers run to apply each change. It names
  `/usr/bin/python3`, which envfs resolves through the caller's PATH
  (`modules/nixos.nix:1577-1580`). Whether python3 is on that PATH in a session is
  **not measured**.
- `InputMethodState.qml:19` names the same path, but fails on `gi` regardless (above).
- `configure.py:143` only compares a string, and has no effect.
- `org.fcitx.Fcitx5.service:4` is written only by `configure.py`'s
  `activation_default`, which nixarchy does not run.

The v4.5.0-rc3 pin on `main` has the same `default/input-methods/` as v4.5.0 (`diff
-rq` is empty), so this does not depend on #1606 merging.

The reported font gap is not one: `Noto Serif CJK` (`configure.py:232`) is already
in the reference machine's `fonts.packages`, through nixpkgs' defaults (evaluated).

## Proposed outcome

On a nixarchy machine with no input-method settings of its own:

1. Each of the five can be selected under Setup > Typing > Input Methods and is then
   usable without a rebuild, including straight after the rebuild that installs it.
2. Text composes in that engine, and `Super+I` and the bar indicator switch it.
3. On a fresh profile, tapping Shift alone leaves the engine for Latin input and
   returns (`config/fcitx5/config:14`). Leaving an engine types the machine's own
   layout, not always US.
4. `omarchy setup input mozc` succeeds. Choosing Japanese, Korean or Chinese under
   Setup > Language (`bin/omarchy-language:122-132` maps four; Cangjie is not one)
   leaves the engine selected, and keeps an engine the user already has.
5. Under Keyboard Layouts, selecting a layout applies it.
6. The ledger rows are true, and something fails if an engine goes missing again.

## Affected users and systems

- Everyone with `programs.nixarchy` on and fcitx5 in force, on install and on
  rebuild: this is new closure on machines that will never type CJK.
- The offline ISO, which carries the reference closure (`installer/cd.nix:655`).

### Closure cost, measured

Against a local reference toplevel on the same nixpkgs rev (17.9 GiB, not this
commit's, which is not built). NAR sizes from cache.nixos.org:

| Addon | Beyond the closure | Mostly |
|---|---|---|
| `fcitx5-mozc` | 33 MiB | `mozc-server` 28 MiB |
| `fcitx5-hangul` | 6.5 MiB | `libhangul` |
| `fcitx5-chewing` | 7.8 MiB | `libchewing` |
| `fcitx5-table-extra` | 43 MiB | the tables |
| `qt6Packages.fcitx5-chinese-addons` | 487 MiB | `qtwebengine` 418 MiB, `libime` 56 MiB |
| **All five** | **577 MiB (+3.1%)** | |

Mozc is not the large one; Pinyin's `qtwebengine` is 72% of the total, and nothing
else in that closure has it. All five are substitutable from cache.nixos.org at this
pin and evaluate with unfree off, so at this pin they download rather than compile,
and a machine with unfree off still gets them.

ISO: last night's `iso-budget` read 6.66 GiB of 7.50. At the whole-image 2.7x ratio
in `installer/cd.nix:653`, all five add about 0.21 GiB, to about 6.87 GiB. That ratio
was not measured on these addons, so only an ISO build can confirm it. `iso-net` (1.79
of 2.00 GiB) should not move, because `storeContents` is offline-only.

## Constraints

- **Coexistence (§14).** Evaluated today through `reference.extendModules`:

  | User sets | Result today | Must stay true |
  |---|---|---|
  | `type = "ibus"`, plain or `mkDefault` | ibus package, no `omarchy-fcitx5` unit | yes, with no addon built |
  | `enable = false` | no package, no unit | yes |
  | `fcitx5.addons = [ fcitx5-rime ]` | their list, alone | theirs joins ours |
  | Wanting none of ours | nothing to shed | possible, with `lib.mkForce` on a list (§7) |

  §14 requires each row to end up as a fixture that can fail (§1). The priority trap
  in `modules/AGENTS.md#default-environment-d-10-omarchy-fcitx-conf-plus-t` still
  applies to `enable` and `type`.
- **Mode A:** a user's own configuration is not changed by anything opt-in, and the
  off state stays asserted (`tests/options.nix:2204`).
- A changed default is announced with its closure cost in the release notes (§14).
- `modules/AGENTS.md:812-814` says `i18n.inputMethod` "builds fcitx5 with its addons",
  which is what the ledger misread. It must end up saying what is true.
- A user's existing choices stay: their hotkeys, their engine list, and any file they
  edited. `seed_dir` is `--update=none` (`modules/home.nix:1142`). Upstream's
  `configure.py` does edit an existing `config` and `pinyin.conf` (`:75`, `:123`), so
  adopting it is not automatically safe.
- **What each layer can prove (§2, §3):**
  - Static: the addons are set and the ledger rows are true.
  - `checks.session` boots a desktop but covers only compose today
    (`tests/session.nix:2364`). It can reach the daemon's engine list, the pickers, the
    indicator and composition. Every VM here has a US layout, so the non-US case
    needs varying on purpose.
  - Hardware only: physical 한/영 and 全角/半角 keys, and real toolkit apps. That is
    `pkgs/verify.sh`'s layer.
- `modules/nixos.nix` is shared with #1611, #1612, #1613 and #1615. #1613's intent
  defers to this one for the addon list, so these two must merge cleanly.

## Open questions

The owner approved every recommendation below on 2026-11-05.

1. **Which engines do all machines carry?** Upstream installs all five
   (`install/omarchy-base.packages:35-42`). *Recommended: all five, provided an ISO
   build stays within budget.* Every row in the menu then works, for 3.1% more closure.
   The spec should find out whether Pinyin can drop `qtwebengine`; this has not been
   tried. The alternative is the four small ones (90 MiB) with Pinyin opt-in, which
   leaves a menu row that fails for China's commonest input method.
2. **Does this task include the tools, or only the addons?** #1610 lists the `/usr`
   paths as a separate unconfirmed item. *Recommended: include them.* Without
   `Super+I`, the indicator, the command and the picker's first save, an installed
   engine is barely usable, so the outcome above is not reached.
3. **Do existing machines get the Shift toggle?** Their `~/.config/fcitx5/config` is
   kept, and upstream also skips hotkeys on an existing profile (`configure.py:103-105`).
   *Recommended: follow upstream*, with no migration and a line in the release notes
   saying how to add it.
