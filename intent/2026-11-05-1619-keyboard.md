# Intent: The installer's keyboard choice reaches the login screen and the session

## Problem

The installer asks for a keyboard layout and writes the answer to one option,
`console.keyMap` (`installer/template/host/configuration.nix:15`). Only the text
console reads it. Someone who chooses German gets German on the console, and US on
the login screen and in the desktop.

This is more than a wrong layout. The installer takes the account password under the
chosen layout (`loadkeys` at `installer/install.sh:627`, then `ask_password`). The
login screen and lock screen then take it under US. A German `y` is the physical key
that US reads as `z`, so a password containing it can fail on the first boot of a
machine whose owner typed it correctly twice. The same password is the disk passphrase
on an encrypted install (`install.sh:711-714`). On the interactive path `ask_keymap` runs
first (`install.sh:3235`), but `loadkeys`' failure is ignored. All of this follows from
reading the code and has not been run.

### What was measured

Measured on 2026-11-05 at v4.5.0's pin: `nixosConfigurations.reference` with one added
module, `console.keyMap = "de-latin1"`, which is the option the template sets. This is
not a flake generated by `mkFlake`. I built the generated files and read them. No VM
ran, because CI had three runs in flight (§6).

| Layer | What reads the layout | With `de-latin1` | Control |
|---|---|---|---|
| Console | `/etc/vconsole.conf` | `KEYMAP=de-latin1` and nothing else | |
| Option | `services.xserver.xkb.layout` | `us` | |
| Login screen | `weston.ini`, `[keyboard] keymap_layout` | `us` | Adding `xkb.layout = "de"` changes only `CompositorCommand`'s `weston.ini` path |
| Session | Upstream's `default/hypr/input.lua`, run with `hl` stubbed, against that `vconsole.conf` | `kb_layout=us` | `XKBLAYOUT=de` added prints `kb_layout=de`; `XKBLAYOUT=ru` prints `us,ru` with `grp:alts_toggle` |

So the bug is real at both layers, and the probe can tell the difference. What is still
not run is a booted machine with a key pressed.

### Corrections to what was reported

- **The login screen is not upstream's.** The issue's evidence cites
  `default/sddm/hyprland.lua`, which reads `/etc/vconsole.conf`. nixarchy installs that
  file (`pkgs/omarchy/default.nix:1769`), but nothing runs it: the generated
  `sddm.conf` has `CompositorCommand=…/weston --shell=kiosk`, unless a user overrides
  `wayland.compositorCommand` themselves. The comment there says
  upstream's `10-wayland.conf` refers to it, and this repo does not install that file.
  **The greeter and the session therefore read the layout from two different places**,
  and one setting does not fix both.
- **The session does not read `xkb.layout`.** Input comes from
  `~/.config/omarchy/keyboard-layouts`, then `XKBLAYOUT` and `XKBVARIANT` in
  `/etc/vconsole.conf` (`default/hypr/keyboard.lua:28-33`, `input.lua:14-15`). NixOS
  writes only `KEYMAP=` there (`nixos/modules/config/console.nix:29-33`). Variants matter:
  `dvorak`, `colemak`, `us-acentos`, `fr_CH-latin1` and `sk-qwerty` are not plain layouts.
- **A menu value is not an XKB name.** The menu holds console names: `uk`, `trq`,
  `sr-cy`. XKB calls these `gb`, `tr`, `rs`. Looking up all 43 menu entries in the first
  column of systemd's `kbd-model-map`, 36 have a row and 7 do not: `colemak`,
  `cz-qwertz`, `de_CH-latin1`, `il-heb`, `no-latin1`, `pl`, `se-lat6`. The answers file
  accepts any real keymap (#1120), so the choices go beyond the menu.
- **Non-Latin layouts need more than the name.** Upstream's two Lua files put `us` first
  for these, because bindings and a Latin password need it. Weston has no such logic. A
  naive `ru` on the greeter would be worse than today's `us`.

### Why nothing caught it

Every automated install answers `keymap=us` (`installer/vm.nix:84`,
`tests/install-iso.nix`, `tests/install-matrix.py:280` and the others), the one value
where all these layers agree. This is §3's held-constant variable. The non-US path has
never run in CI, so whether a non-US install stays offline-buildable is also unmeasured.

## Proposed outcome

Choosing a layout in the installer, by menu or by answers file, gives a machine where:

1. For a Latin choice, the login screen types that layout and variant.
2. For a Latin choice, the Hyprland session and the lock screen type that layout and
   variant.
3. A non-Latin choice starts on `us` at the login screen and in the session, so a Latin
   password and Omarchy's bindings work, and reaches the chosen layout with Left Alt +
   Right Alt, as on upstream.
4. All 43 menu entries reach their desktop layout. The 7 without a `kbd-model-map` row
   are not an exception, because each has an XKB equivalent. An answers-file keymap
   outside the menu with no equivalent still installs and boots on `us`, and the
   installer's summary says so before the disk is touched.
5. The password set during installation works at every prompt that asks for it on that
   machine: the login screen, the lock screen, and the disk unlock on an encrypted
   install.
6. A US install is unchanged.

A check that varies the keymap fails if any layer goes back to US.

## Affected users and systems

- **Everyone who picks a non-US entry:** 42 of the 43 menu entries. `dvorak`, `colemak`
  and `us-acentos` count too, as US variants. Each new install from the ISO.
- **Machines already installed this way:** they have the same bug and their
  `configuration.nix` is theirs. They hold only `console.keyMap`. See Open questions.
- **Encrypted installs:** the first prompt is the disk unlock, using the same password.
  Autologin then enters an unlocked session (template line 22). The greeter still appears
  after a logout, because `sddm.autoLogin.relogin` defaults to false. Measured:
  `console.earlySetup = false`, Plymouth on, `/etc/vconsole.conf` present in the initrd.
  Whether Plymouth's prompt honours the keymap is not known. The optional recovery
  passphrase (`ask_recovery`) has the same question at the emergency prompt.
- **`--from` installs:** `install.sh:3216` asks for the password and never runs
  `ask_keymap`, so it is typed under the live image's US console. If the repository's host
  declares another layout, fixing the desktop creates the reverse mismatch. Answers-file
  installs type no password and are not exposed.
- **The offline ISO:** a non-US answer changes `weston.ini`, so its closure differs from
  the baked one (§3, `iso-budget`, `install-iso`).
- **#1614** (input methods; spec and plan approved, implementation under way). Its spec
  §6 and open decision 2 name this gap and leave it out of scope. Its spec names
  `modules/nixos.nix`, `pkgs/omarchy/default.nix`, `tests/coexistence/fixtures.nix`,
  `tests/options.nix` and `tests/install-matrix.py`, so this task's spec may touch the
  same files, and whichever lands second rebases (§9). No behaviour here needs it first:
  until it lands, the engines it adds are not on the machine. Three contact points:
  - Its Keyboard Layouts picker writes `~/.config/omarchy/keyboard-layouts`, which
    outranks the installer's choice. That is the right order.
  - It takes the machine's layout from `hyprctl` at run time, once, on a stock profile.
    A fresh install follows this fix without an edit.
  - It fixes the path to `kbd-model-map`, which this task may also want.

## Constraints

- **Coexistence (§14).** The spec needs a Coexistence section answered by a fixture in
  `tests/coexistence/fixtures.nix`. What must keep winning:
  - a user's own `services.xserver.xkb.*`, in the generated config or in Mode A;
  - `~/.config/hypr/input.lua` (`hl.config`) and `~/.config/omarchy/keyboard-layouts`;
  - a user's own `services.displayManager.sddm.wayland.compositor`, or another greeter
    under `programs.nixarchy.displayManager = false`;
  - a Mode A user's `console.useXkbConfig = true`, which derives the console from XKB.
    On a generated host it already conflicts with the template's normal-priority
    `console.keyMap` (read: `console.nix:144-149`), and the spec says whether that stays.
- **Mode A is untouched.** A machine importing `nixosModules.nixarchy` with no installer
  answers keeps its layout. Both states asserted in `tests/options.nix` if an option is
  added (§7).
- **§7 priorities.** `lib.mkDefault` on scalars. The user's file must win without
  `mkForce`.
- **A US install changes no closure that the ISO carries**, and non-US stays offline
  installable. Both measured, not assumed.
- **No new patch to upstream's Lua unless the spec shows no other route** (§11).
- **Prove the check fails (§1, §3).** It must vary the keymap, include a non-Latin entry
  and a name that differs between namespaces such as `uk`, and go red when the fix is
  reverted. A check that greps for the key proves only that it was written (§2). A real
  keypress at the greeter, in the session and at the lock screen, in a VM, is the final
  evidence.
- **Local builds by §6 tier.** VM checks only when nothing is in flight.

## Open questions

The owner approved every recommendation below on 2026-11-05.

1. **What about machines already installed?** Their file has only `console.keyMap`.
   *Recommended: a release note and Discussions post with the lines to add, no
   migration.* Deriving the layout in the module would reach them, but it would change
   Mode A machines and a layout the owner may have worked around.
2. **Which greeter?** Keep nixpkgs' weston and set its layout, or run upstream's
   `default/sddm/hyprland.lua`. The second brings Latin-first logic and one source for
   both layers, but changes the first screen of every machine, and of the ISO's closure.
   *Recommended: let the spec measure both, leaning to weston as the smaller change,
   and delete nothing here.* The spec reports what `hyprland.lua` costs.
3. **Is the LUKS prompt in scope?** A passphrase typed under `de` and asked for under
   `us` locks the owner out of their disk, which is worse than this issue's symptom, and
   it is the first prompt on an encrypted machine. Outcome 5 includes it.
   *Recommended: in scope. Measure it in a VM first. If the fix is large, split it into an
   issue the same day and narrow outcome 5, with the owner's say.*
4. **`--from` installs.** Should the installer load the repository host's layout before
   asking for the password? *Recommended: the spec answers it, since it depends on where
   the layout ends up living. Otherwise a warning at that prompt.*
