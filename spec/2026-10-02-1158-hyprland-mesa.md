# Spec: Hyprland and its GPU drivers come from the same nixpkgs

## What was measured before writing this

Evaluated against `main` (`70e56005`, nixpkgs 2026-09-28):

| | glibc | Mesa |
|---|---|---|
| Hyprland (`inputs.hyprland.packages.<system>.hyprland`) | 2.42 | -- |
| Hyprland's nixpkgs (`inputs.hyprland.inputs.nixpkgs`) | 2.42 | 26.2.3, and an i686 build exists |
| Our nixpkgs on `main` | 2.42 | -- |
| Our nixpkgs on #1154 (`c59305b`) | 2.44 | needs ≥ 2.43 |

- **Today's agreement is a coincidence of timing.** `main` is fine only
  because our nixpkgs has not yet moved past Hyprland's glibc. That is what
  #1154 changes.
- **The module can reach the inputs.** `modules/nixos.nix` takes the flake
  `inputs` as its outer argument (`modules/nixos.nix:1`), so
  `inputs.hyprland.inputs.nixpkgs` is reachable without a `specialArgs`
  change.
- **Nothing collides with it.** nixarchy sets nothing under
  `hardware.graphics` today (no match in `modules/`).

## Design

### D1. Mesa from Hyprland's nixpkgs, as hyprwm document

In `modules/nixos.nix`, inside the existing `config = lib.mkIf cfg.enable`:

```nix
hardware.graphics = let
  hyprPkgs = inputs.hyprland.inputs.nixpkgs.legacyPackages.${pkgs.stdenv.hostPlatform.system};
in {
  package = lib.mkDefault hyprPkgs.mesa;
  package32 = lib.mkDefault hyprPkgs.pkgsi686Linux.mesa;
};
```

- **Why this.** It is hyprwm's documented NixOS setup for a configuration that
  does not override Hyprland's nixpkgs, which is exactly nixarchy's. The
  driver Hyprland loads is then built against the glibc Hyprland was built
  against, whatever our nixpkgs does.
- **`mkDefault` on both:**
  - a machine that sets its own `hardware.graphics.package` wins;
  - both are scalar options, so `mkDefault` is the repo's rule for them
    (`modules/services/default.nix` header).
- **`package32` only matters with `enable32Bit`.** Setting it
  unconditionally costs nothing when 32-bit is off, because the option is not
  realised then.
- **A one-to-three-line comment at the site.** It says the two nixpkgs share
  Hyprland's process and points to `docs/internals/flake.md`.

### D2. `checks.graphics-glibc`: `tests/graphics-glibc.nix` (new, evaluation-only)

- **The comparison.** At evaluation time, from
  `nixosConfigurations.reference.config`, read the glibc versions behind:
  - `hardware.graphics.package` (`.stdenv.cc.libc.version`);
  - and, when `hardware.graphics.enable32Bit` is on, `package32`;
  - and `programs.hyprland.package`, or whatever package the module starts
    as the compositor (the plan pins the exact attribute).
- **The result.** A `runCommand` echoes all of them, and fails, naming both
  versions and the fix, if a driver's glibc is newer than the compositor's
  (`builtins.compareVersions` > 0).
- **Why evaluation.** Every value is a derivation attribute, so the check is
  cheap: no closure is built. It still sees exactly the drift that killed
  #1154's session.
- **Built-in negative control.** In the same check, evaluate a variant of the
  reference with `hardware.graphics.package = lib.mkForce pkgs.mesa` (our
  nixpkgs' own Mesa).
  - On `main` that variant **agrees** (both 2.42), so the control cannot be
    "must fail" here.
  - Instead, the §1 proof is shown once in the PR, by evaluating this check
    on #1154's lock without D1, where it must go red.
  - The check's comment says why there is no permanent negative control: the
    drift is a property of two moving inputs, not of our code.
- **Wiring.** A `checks.graphics-glibc` entry; CI runs it with no workflow
  edit (§4).

### D3. Docs

- **`docs/internals/flake.md`'s hyprland section** gains a paragraph:
  - Hyprland's own nixpkgs also supplies the GPU drivers, and why (#1158,
    with the `GLIBC_2.43` line);
  - the cost: drivers move at Hyprland's pace;
  - `checks.graphics-glibc` is what notices the next drift.
- **`modules/AGENTS.md`**, if it lists what the module sets system-wide:
  `hardware.graphics` gets its row.

### D4. Proving it on #1154 itself

- **Once D1–D3 land on `main`,** #1154 rebases onto it and its
  `checks.session` must go green. That is the real end-to-end proof.
- **Before merging this,** the PR shows two things, so the fix is proven
  before it ships rather than after:
  1. `checks.graphics-glibc` red on #1154's lock without D1, green with it;
  2. a `checks.session` run with #1154's `flake.lock` plus D1, on a throwaway
     branch through CI.

## Alternatives rejected

- **Hyprland `follows` our nixpkgs.** It forfeits hyprland.cachix.org, so
  every machine compiles the compositor (the documented decision).
- **Hold nixpkgs back.** That stops every app update until hyprwm moves, and
  then the drift recurs.
- **A compositor-only driver path,** e.g. wrapping Hyprland with its own
  `LIBGL_DRIVERS_PATH` / `__EGL_VENDOR_LIBRARY_FILENAMES` and leaving
  `/run/opengl-driver` on our Mesa. It is narrower, but every application
  Hyprland launches inherits the variables, and it is not hyprwm's documented
  route. The owner accepted the system-wide Mesa (intent, answer 1).

## Risks

- **Two Mesa stacks on disk.** Applications from our nixpkgs that link
  `libgbm` or `mesa` directly still pull our Mesa, beside the driver Mesa.
  - Cost: closure and ISO size (`checks.iso-budget`, nightly).
  - The plan measures the toplevel closure before and after, and names the
    delta in the PR.
- **Driver age.** New GPUs wait for Hyprland's nixpkgs to move. Hyprland's
  input already tracks a branch (`docs/internals/flake.md`), so the lag is
  usually days.
- **p620's own `hardware.graphics.extraPackages`** lists `mesa` from *its*
  nixpkgs (`hosts/p620/nixos/amd.nix`, in the separate config repo). That puts
  a second Mesa into `/run/opengl-driver` and can bring the mismatch straight
  back. Out of this repo's scope: the PR says exactly what p620's config should
  drop.
- **A user's own `hardware.graphics.package`** wins through `mkDefault`, and
  with it the mismatch, if theirs is newer. `checks.graphics-glibc` covers
  only the reference machine. The option description and the docs say so.
