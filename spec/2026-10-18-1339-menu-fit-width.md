# Spec: the Omarchy menu is wide enough to show its labels

## Design

One carried `--replace-fail` substitution on `shell/plugins/menu/Menu.qml`,
in `pkgs/omarchy/default.nix` beside the #1305 substitutions on the same file.

**Anchor:** upstream's one `cardWidth` line (v4.0.5, line 112):

```qml
  property int cardWidth: Math.min(root.dmenuActive ? Style.space(root.dmenuWidth) : ((root.activeMenu === "trigger.capture.screenrecord" || root.activeMenu === "style.font") ? Style.space(520) : Style.space(300)), panel.width - Style.gapsOut * 2)
```

**Replacement:** in `pkgs/omarchy/1339-menu-fit-width.qml`. Multi-line text
lives in a file for the reason pkgs/AGENTS.md gives for the 1305 files:
inline, `nix fmt` re-flows the whole `installPhase`.

```qml
  property int cardWidth: Math.min(Math.max(root.fitWidth, <upstream's expression, unchanged>), Style.space(640), panel.width - Style.gapsOut * 2)
  // Width that fits the widest label of the open menu (#1339). It only grows
  // while the menu is open, so filtering does not make the card jump.
  property int fitWidth: 0
  onActiveMenuChanged: fitWidth = 0
  onDmenuActiveChanged: fitWidth = 0
  onLayoutSerialChanged: {
    var widest = 0
    for (var i = 0; i < displayModel.count; i++) {
      labelMetrics.text = displayModel.get(i).label || ""
      widest = Math.max(widest, labelMetrics.advanceWidth)
    }
    var chrome = root.rowReservedBorderLeft + Style.space(8 + 36 + 6 + 6 + 14 + 12) + card.contentLeftInset + card.contentRightInset
    fitWidth = Math.max(fitWidth, Math.ceil(widest + chrome))
  }
  TextMetrics {
    id: labelMetrics
    font.family: root.fontFamily
    font.pixelSize: Style.font.heading
    font.weight: Font.Medium
  }
```

Why it works:

- **`layoutSerial` is the hook.** Upstream bumps it at the end of every
  rebuild of `displayModel`: menu rows, app rows and dmenu rows (`rebuildDisplay`,
  `rebuildDmenuDisplay`). So it fires once per list change, after the rows exist.
- **The floor is upstream's own expression**, kept verbatim inside `Math.max`.
  Short menus, the two 520 exceptions and a caller's dmenu `width` look as
  they do today.
- **The metrics match the row label:** same family, `Style.font.heading`,
  `Font.Medium`, as the delegate's `labelText`.
- **`chrome`** is the row's fixed horizontal furniture, read off the delegate:
  border reserve, the 8 + 36 icon column, 6 gap, 6 right margin, the 14 trail
  chevron, plus 12 slack, plus the card's insets.
- **Grow-only:** reset on menu change or dmenu change, never on filter. The
  first rebuild of a menu has the full list, so it sets the width, and
  narrowing filters cannot shrink it.

**Decisions taken on the intent's open questions** (the intent was approved
without answers, so these are the defaults; change them at spec review):

1. **Cap: fixed `Style.space(640)`**, as in the prototype. The existing
   `panel.width - Style.gapsOut * 2` term still bounds it on small screens, so
   a fraction-of-screen cap adds a second rule for no case we have seen.
2. **Upstream: not part of this change.** Like the #1305 patches, it is
   CARRIED. Filing it at omacom/omarchy is the owner's call, and can be done
   later from the same text.

**Docs:** a `pkgs/AGENTS.md` entry, "The menu fits its widest label (#1339)",
with an anchor, linked from a `# Why:` line above the substitution, matching
the #1305 and #1313 entries.

## Alternatives rejected

- **A bigger fixed width** (e.g. 420 for every menu). Short menus like Power
  become needlessly wide, and long web-app names still elide.
- **An option** (`programs.nixarchy.menu.width`). The intent rules out a new
  option: the right width depends on the labels, not on the user.
- **Measuring the filtered list each keystroke.** The card would jump
  narrower and wider while typing.
- **Measuring with `implicitWidth` of the delegates.** A `ListView` only
  instantiates visible rows, so off-screen long labels would not count.
- **Telling users to clone `omarchy.menu`.** That freezes the menu against
  upstream and against our #1301 and #1305 patches (the prototype did this).

## Risks

- **An upstream bump rewords the anchor line.** The build fails, by design.
  Refresh the anchor and replacement together.
- **Interaction with #1301 and #1305.** None of their anchors overlaps line 112,
  and the substitution is applied after them. The build proves it: an
  overlapping `--replace-fail` fails.
- **Cost.** A `TextMetrics` pass over the list on each rebuild. That is about
  360 rows for Apps on p620, measured once per keystroke at most. The
  prototype showed no visible lag.
- **An unexplained failure on razer during prototyping.** A clone loaded
  into razer's shell reported `Syntax error` at a line of upstream code. That
  shell was running an older tree than the installed one, a stale session.
  The same text loads cleanly on p620. The headless test below loads the
  shipped `Menu.qml`, so a real syntax problem fails CI, not a session.
- **The headless window has no screen width.** The harness's `FloatingWindow`
  may be narrow, so `panel.width - gaps` would clamp everything. The test sets
  an explicit window width.

- **Extend `tests/menu-keys` (`checks.menu-keys`)**, the existing headless
  harness that loads the real patched `Menu.qml`:

  - the fixture gains a submenu whose one row has a long label;
  - the harness window gets an explicit width (1920);
  - assertions:
    1. the short `probe` menu keeps upstream's width;
    2. the long-label menu is wider than that, and no wider than
       `Style.space(640)`;

    4. reopening `probe` returns to upstream's width.
- `nix flake check` for the menu checks (`menu-keys`, `menu-model-merge`) and
  `nix fmt -- --ci`.
- **On p620:** after deploying, delete the prototype clone, open Apps with
