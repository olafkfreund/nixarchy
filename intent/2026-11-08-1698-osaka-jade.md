# Intent: a machine on Osaka Jade keeps a working theme after Omarchy dropped it

## Problem

Omarchy replaced the bundled Osaka Jade theme with Jade Horse on 2026-10-25
(basecamp/omarchy a1ea6096d, #16594). The v4.5.0 `main` pins has no
`themes/osaka-jade`, so a nixarchy machine whose
`~/.local/state/omarchy/current/theme.name` reads `osaka-jade` names a theme
that no longer exists in `$OMARCHY_PATH/themes`.

What such a user sees today: the staged copy under `current/theme` keeps the
desktop looking right. But the theme menu no longer lists it, and anything
that re-stages the theme (`omarchy-theme-refresh`, a font or background
change) has nothing to re-stage from.

Upstream repairs this with two migrations:
- `1787481315` (in v4.5.0) re-stages the current theme, or applies Tokyo
  Night when it no longer exists. nixarchy lists it in `predates`, so it
  never runs here.
- `1787481314` (quattro only) clones
  https://github.com/omacom/omarchy-osaka-jade-theme into
  `~/.config/omarchy/themes/osaka-jade` for anyone still on it, and
  otherwise applies Jade Horse.

The post-boot hook that runs ported migrations has no `git` on its PATH, so
the edge carry declined `1787481314` (#1696).

## Proposed outcome

- A machine on Osaka Jade ends up on a theme that exists: Osaka Jade
  itself, from its own repository, or Jade Horse, its replacement.
- It happens once, at login, without the user doing anything, and the user
  is told when their theme changes.
- A machine on any other theme is untouched.

## Affected users and systems

- Anyone who chose Osaka Jade before v4.5, on `main` today and on edge.
- `pkgs/omarchy/nix-bin/omarchy-migrate-user` (the hook's PATH),
  `modules/home.nix`, `data/user-migrations.nix`, and the `1787481314` row.

## Constraints

- Mode A: nothing outside `cfg.enable`.
- A login hook must not block on the network. A clone that hangs must not
  delay the session or stop the other migrations (the runner stops at the
  first failure, so a failure here would hold back every later id).
- Never change a user's theme silently. Upstream's fallback notifies on the
  console only, which nobody sees at login.
- `1787481314` is quattro-only; on `main` the row would be stale (the
  ledger fails a row for a migration the pin lacks), so the `main` fix
  cannot simply port that row.

## Decisions (owner, 2026-11-08)

1. **(b): package the theme.** The Osaka Jade theme repository
   (omacom/omarchy-osaka-jade-theme), pinned by hash, ships as a
   nixarchy-provided theme, so it works offline, stays selectable, and a user
   on it keeps the theme they chose. No clone at login.
2. **`1787481315` is out of scope here** and tracked in #1705, so this task
   stays the Osaka Jade case.

## Open questions (as drafted)

1. **How the theme returns.**
   - (a) Port upstream's migrations: add `git` to the hook's PATH, run
     `1787481314` on edge and an equivalent on `main`. That means a network
     clone at login.
   - (b) Package the Osaka Jade theme repository, pinned by hash, as a
     nixarchy-provided theme in `$OMARCHY_PATH/themes` (or beside it). No
     network, and it stays selectable for everyone.
   - (c) Apply Jade Horse with a notification and nothing else.

   The recommendation is (b): offline, deterministic, and the user keeps the
   theme they chose.
2. Should `main` also run the `1787481315` re-stage (currently in
   `predates`), so any other theme a user had that disappeared falls back to
   the default rather than lingering?
