# Spec: Factory reset tells the truth, and does all of it or none of it

Written from reading the source. Neither `omarchy-system-factory-reset` nor
`nixarchy-factory-reset.service` was run. Kernel claims not yet measured are
marked and collected under "Unverified"; `checks.factory-reset` settles them.

## Design

### 1. The unit: everything fallible first, then two exchanges

Line numbers are `installer/host.nix` today.

The current order has three fallible steps after the first visible change: `mv`
at `:514`, the snapshot at `:529`, and `mv` at `:530-531`. The new order does all
the staging first, then uses `exch` from util-linux. It calls
`renameat2(RENAME_EXCHANGE)`, and is already in the unit's `path` (2.42.4 on the
reference pin, `bin/exch` present).

```
stamp=$(date ...)
trap on_exit EXIT                          # phase=guard
mv "$request" "$failed"                    # was rm -f, :469
mount the top level

guard @factory, @factory-home, @home are subvolumes     # was -d, :487-492
guard "$oldvar" and "$oldhome" do not exist
phase=stage

# STAGE: nothing the machine uses changes
cp -a --reflink=auto "$top/@factory/var/lib" "$oldvar"  # was :512
write the success receipt into "$oldvar/nixarchy/"      # was :537-560
btrfs subvolume snapshot "$top/@factory-home" "$oldhome"   # was :529
btrfs filesystem sync "$top"

# COMMIT
exch "$top/@home" "$oldhome";  phase=home-swapped        # was :530-531
exch /var/lib "$oldvar";       phase=done                # was :513-514, the commit point
btrfs filesystem sync "$top" || true
```

`oldvar=/var/lib.before-reset-$stamp` and `oldhome=$top/@home-before-reset-$stamp`.
Both are the names the existing receipt and the command's text already promise.
Each starts out holding the fresh factory copy, and the exchange leaves the old
data under that name. So no rename follows the commit, and no step can fail
between the swap and the final names.

What each change buys:

| line today | failure today | after |
|---|---|---|
| `:469` request deleted | no trace, no retry | One rename removes the trigger and creates the failure marker, so a crash still leaves a record. A failed `mv` leaves the request, and the boot retries; `rm -f` failing does the same today. |
| `:511` `rm -rf /var/lib.factory-new` | | Removed. That fixed name would hold the user's `/var/lib` if a crash landed mid-swap. No path that existed before this run is ever deleted. |
| `:513-514` | no `/var/lib` | Gone: an exchange never leaves the name empty. |
| `:529` | `/var/lib` reset, `/home` not | Runs in staging, whatever the errno. Nothing has changed yet. |
| `:530` | as above, plus a stray | First exchange fails: nothing has changed. |
| `:531` | no `@home`, boot stops | Gone: `@home` always resolves. The `@home` guard also refuses cleanly if it is already missing. |
| `:537-538` | reset done, receipt missing or truncated | The receipt is written while staging and arrives inside the same exchange that commits, so a failed write stops the reset before anything changes. |

**The second exchange is the commit point, and rollback is what keeps the
promise.** If `exch /var/lib` fails, the EXIT trap exchanges `@home` back. That
is why `/home` goes first: the swap carrying the success receipt comes last, so
`.done` is present only if both happened.

**The trap may delete only what it staged.** `phase` is set after each exchange
succeeds, and logged, so the trap acts on what happened:

| phase | what the trap does |
|---|---|
| `guard` | removes nothing. Either name may already exist and hold a person's data: the stamp has one-second resolution from a clock that can be wrong early in boot, and the guard exists for that collision |
| `stage`, including a failed first exchange | removes `$oldvar` and `$oldhome`, which this run created and which hold only factory copies |
| `home-swapped` | exchanges `@home` back; only if that succeeds, removes both. **If it fails, `$oldhome` holds the user's home and nothing is removed** (case 5) |
| `done` | nothing: both names hold the user's data, and must never reach cleanup |

A signal landing between an exchange and its `phase=` is outside the promise,
which covers command failures. `set -e` still applies inside the trap, so its rollback
and removals are tested explicitly and a failed removal is only logged: otherwise the
trap would stop before writing the report.

**The promise, stated exactly:** a single failing command leaves `/home` and
`/var/lib` both reset or both untouched. A second failure, in the rollback, is
outside it, and is reported with the exact state and the repair. The comments at
`:395`, `:453-456` and `:520` are rewritten to say this.

**Power loss is not promised (owner, 2026-11-05).** The reorder does narrow it:
the snapshot no longer commits a half-done swap, and the sync before the commit
makes it likely, though not certain, that the two exchanges share one btrfs
transaction. This is inferred from the commit model and unmeasured. A power cut
can still leave `/home` reset and `/var/lib` not, and then the empty marker
reports it (section 3).

**The unit moves to `installer/factory-reset.nix`**, imported by `host.nix`, so
the VM check imports the shipped script rather than a copy. `host.nix` is imported
only by flakes the installer generated, so the Mode A gate stays structural.
`tests/options.nix:5043` reads the generated unit file and is unaffected.

### 2. The command: "I could not ask" is its own answer

Line numbers are `pkgs/omarchy/nix-bin/omarchy-system-factory-reset` today.

Replace `baseline_subvolumes` and `has_baseline` (`:96-105`) with one function
that has three outcomes. It takes the exit status of the `btrfs` call rather
than discarding it:

```
out=$("$BTRFS" subvolume list -r / 2>&1) || → unknown (keep $out for the message)
both names present → yes;  otherwise → no
```

`command -v "$BTRFS"` failing is also `unknown`. Per §5, the `|| ` must be on the
assignment: `set -e` does not reach inside `$(...)`.

**The `--check` route, unprivileged.** It never elevates, because it is what a
menu `when:` or a test would call, and it prints nothing.

| exit | meaning |
|---|---|
| 0 | managed, and the baseline is there |
| 1 | not managed, or the filesystem answered and there is no baseline |
| 3 | managed, and the question could not be asked |

An unprivileged `--check` on a real machine therefore exits 3, not a false 1.
`--help` (`:120-124`) is rewritten to say so. Only tests call `--check` today, so
widening its codes breaks no caller (§4: grepped, `tests/options.nix` only).
Those tests use `|| {` and `if`, which read 3 as "no"; the plan names exit 3
where it matters.

**Elevation.** The menu row's action does not change. The command elevates itself,
as upstream's does, so a bare shell run and the menu behave the same:

```
unknown and EUID != 0:
  self=$(readlink -f "${BASH_SOURCE[0]}")
  case $self in /nix/store/*) ;; *) refuse "run the installed command" ;; esac
  exec sudo "$self" "$@"
EUID == 0, at the top of the script:
  export PATH=/run/wrappers/bin:/run/current-system/sw/bin
unknown and EUID == 0:
  "Could not ask whether this machine has a factory snapshot:" + $out; exit 1
```

- Elevation is triggered by *unknown*, not by `EUID` alone, so the unprivileged
  fake-`btrfs` cases at `tests/options.nix:5094-5175` keep working unchanged.
- Upstream's three fixes, each accounted for. #13047 pinned elevation to the
  packaged command: the `/nix/store` case does that, since a store path is
  root-owned and immutable. #13316 forwards `GUM_*`: **not copied**. gum reads a
  variable per flag, so a forwarded `GUM_INPUT_VALUE` or timeout changes the
  prompts this issue must not weaken; the cost is unthemed prompts. #16032 exported
  `OMARCHY_PATH` for `omarchy-i18n`: this script uses neither.
- `PATH` is pinned because `bin/` is a symlink farm rather than wrapped
  (`pkgs/omarchy/default.nix:458`), so every tool comes from `PATH`. A missing
  `gum` fails closed at the existing `:300-304`.

**Why the confirmations are not weakened:** elevation happens before the prompts,
and passes only the caller's own arguments. Nothing from the caller's environment
is forwarded, sudo's `env_reset` drops the `NIXARCHY_*` seams, and a root run pins
`PATH`, so a caller's `gum` cannot answer the questions and the elevated run asks
the real filesystem. `--force` is never added. Both `gum` questions and typing `RESET` (`:299-321`) run as root
unchanged. A cached sudo timestamp skips the password and nothing else. A failed
sudo prints sudo's own message and never reaches a refusal about snapshots. The
"Reboot now?" confirmation stays too.

The ownership refusal (`:146`) still runs first, with no sudo: it does not need
root, and a Mode A machine should not be asked for a password to be told no.

### 3. Failure is reported on the next run

The owner chose a receipt shown when the command next runs, with no login
notification and no manual page.

`/var/lib/nixarchy/factory-reset.failed` is the renamed request (0600, root, the
existing mode) and the EXIT trap fills it in. It is present in the live `/var/lib`
exactly when the most recent reset did not commit, because a committed one swaps
to a `/var/lib` that never had it.

| contents | written by | machine state | what it tells the user |
|---|---|---|---|
| `nothing changed` + reason | trap, in staging or on a failed first exchange | untouched | why, and to run the command again |
| `rolled back` + reason | trap, after a successful rollback | untouched | same |
| `rollback failed` + reason | trap | `/home` reset, `/var/lib` not | the exact repair, below |
| empty | nobody | unknown: a crash, a power cut, or a report that could not be written | no cause claimed; how to look, section 4 |

The command prints it after elevation, before the baseline answer, so a machine
that reset badly says so first. **It then stops, `--force` included, until the
person has run the `sudo rm <path>` it ends with.** That is one refusal instead of
more code: a new request would otherwise overwrite the only record of where a
failed rollback left things. If the disk is so full the trap
cannot write, the marker stays empty and the journal has the reason (`|| true`
on the write: a failed report must not change the unit's result). `--check` never
prints it.

Staged in the success receipt, unconditionally: an earlier failed attempt can
leave further `before-reset` names, so it says how to list them.

### 4. How preserved data is reached, and recovery with no re-run

The success receipt's commands stay, and the check runs them. Everything is on the
same filesystem, reached through the top level:

```
sudo mount -o subvol=/ <device> /mnt
ls /mnt/@home-before-reset-<stamp>         # the old home
ls /var/lib.before-reset-<stamp>           # the old service state
```

| state | how you get there | repair, no re-run needed |
|---|---|---|
| untouched | any single failure | none; the data never moved |
| `/home` reset, `/var/lib` not | rollback failed, or a power cut | mount as above, then `sudo exch /mnt/@home /mnt/@home-before-reset-<stamp>`, reboot |
| **no `/var/lib`** | a past `:514` failure on the old code | The next activation recreates an empty one, the request cannot exist, and the unit will not start. `sudo mv /var/lib /var/lib.empty && sudo mv /var/lib.before-reset-<stamp> /var/lib`, reboot |
| **no `@home`** | a past `:531` failure on the old code | `/home` has no `nofail`, so the boot stops (inferred, unrun). The emergency root is locked (`tests/install.nix:818-820`), so from the ISO: mount `subvol=/`, `mv @home-before-reset-<stamp> @home`, reboot |

The last two rows are for machines already in that state. New code cannot produce
them, and they go in the PR and `installer/AGENTS.md` rather than in any text the
command prints, since that machine may not boot to run it. A re-run from
`@home`-missing is also now safe: the guard refuses, and nothing moves.

Once the marker is dismissed, a re-run from a rolled-back state simply works. A
re-run after `rollback failed` works too, but puts the factory home under a second
`before-reset` name, so the marker says to repair first.

## Alternatives rejected

- **Only moving the snapshot before `:513`.** Fixes `:529` and leaves both worse
  states: `mv` at `:514` and `:531` can still fail between their two renames.
- **Exchange, then rename the old copy aside.** Two more fallible steps after the
  commit, and it needs a fixed staging name that a stale run could then delete.
- **Plain renames with rollback, instead of `exch`.** A window with no `@home`
  remains, for no saving. It is the fallback only if the check shows the kernel
  refuses to exchange subvolumes, and that needs this spec amended.
- **A `/var/lib` subvolume**, to swap like `@home`. Changes the layout of every
  installed machine for a rare failure.
- **Writing a `baseline` marker file at install**, so an unprivileged run can read
  an answer. A second source of truth about a snapshot someone could delete, and
  pre-#172 machines would still need the distinction.
- **`sudo` in the menu row string only.** Fixes the menu and leaves the shell
  telling the same untruth; it also means patching an upstream row.
- **`pkexec`.** NixOS ships no setuid pkexec (`tests/options.nix`, the
  gpu-screen-recorder note).
- **Keeping the request until success.** Retries on every boot, which the intent's
  constraint forbids.
- **Refusing if a mount sits under `/var/lib`.** Not installer-laid; see Risks.
- **A doctor row reading the marker, as `upgrade-failed` has.** Not asked for.

## Risks

- **An exchange needs metadata space, including the rollback.** On a disk that is
  truly out of metadata, the first exchange fails safely, but the rollback after
  a successful first exchange could fail too. That lands in `rollback failed`,
  reported and repairable, not lost. No rate has been measured. This is the
  realistic way past the promise, and it is why a full disk is named here.
- **Staging can now fail where the old code got further.** Copy and snapshot both
  happen before anything moves, so a nearly full disk refuses more often. Correct,
  and it says so.
- **A user's own mount under `/var/lib`** (not installer-laid). If it is mounted
  before the unit runs, it should follow the old directory and appear at the
  `before-reset` path until next boot. Unverified. `/var/lib` itself being a mount
  point should fail the exchange with `EBUSY`, which rolls back and reports.
- **Only reset machines change.** The unit is conditioned on the request, so no
  ordinary boot runs any of the new code. The new module changes the closure of
  every installer-laid machine, which rebuilds it once.
- **Elevation opens a destructive path from the menu for the first time.** The
  owner accepted this, guarded by sudo and all the confirmations.
- **`git -C /etc/nixos` under sudo** (`:276`). Git accepts `SUDO_UID` as owner, so
  the "system half" text should stay right; from memory, so the check asserts it
  by way of the elevated output. If wrong, the text claims "no commits", a false
  statement this issue exists to end.
- **Mode A:** unaffected. No *Coexistence* fixture (§14): this sets no option a
  user also sets, and the unit stays absent there, as `tests/options.nix:5030`
  asserts.

## Verification

Every check proves one outcome, by way of a named break (§1). Each break's failing
output goes in the PR. A VM runs only when `gh run list` shows nothing in flight.
Nothing here runs on a real host.

**`checks.factory-reset` (new): a NixOS test VM with a real btrfs root.** It lays
out `@` and `@home` at the top level, takes real read-only `@factory` and
`@factory-home`, and imports `installer/factory-reset.nix`. Each case writes the
request, reboots and inspects. KVM needed, so it goes in the `claimed` list and a
KVM job, as `wifi-hwsim` does; that workflow edit is a CI-gate change for a human
to merge (§4, §11). About 10-20 minutes per pull request, as the owner accepted.

| # | setup, then reboot | proves | break that must make it fail |

| 2 | `chattr +i /var`, so the copy cannot start | staging failure: both untouched, `.failed` says nothing changed, boot reaches multi-user, no retry on the next boot | move `cp` after the first exchange |
| 3 | `chattr +i` the top-level root, so the snapshot fails after the copy exists (the `:529` state) | `/var/lib` not reset, and `$oldvar` removed | put the snapshot after the `/var/lib` exchange; separately, remove the trap's cleanup |
| 4 | `chattr +i /var/lib`, so the second exchange fails; the journal must show `phase=home-swapped` and `exch` failing on `/var/lib`, or the case fails | rollback: `@home` back, both untouched, `.failed` says rolled back | remove the rollback line |
| 5 | an `exch` wrapper on the unit's `path` that fails from a chosen call on | rollback failure: **the user's home still exists at `@home-before-reset-*`**, `.failed` gives the repair | let the trap delete staged names unconditionally |

| 9 | as root, `NIXARCHY_BTRFS=false` | root + unknown: "could not ask", exit 1, not "no snapshot" | treat unknown as no |
| 10 | case 2's `.failed`, then run the command | the receipt is shown first | delete the print |

`chattr +i` gives a real refusal from the real kernel at the real step. The
wrappers in cases 5 and 11 are the only stubs: no filesystem state makes one rename
succeed and its exact reverse fail, and a clock cannot be made to repeat a second.

**`checks.install` (one assertion, no new boot).** After the existing reset, or
before it where the machine is ready: as the installed user,
`omarchy-system-factory-reset --check` exits 3. This is the shipped machine rather
than a fixture. Break: restore the old discard and it exits 1.

**`tests/options-*` (cheap; §5: no heredoc in the indented string).** A refusing
fake `btrfs` plus a fake `sudo` on `PATH` that records its arguments and exits:

- `--check` exits 3 and prints nothing;
- the command execs `sudo` with the store path and the same arguments, no
  `--force`, and the output has no "no factory snapshot". Break: treat unknown as
  no;
- an empty but successful answer still gets the true refusal (the existing case 2,
  which stays). Break: treat no as unknown;
- the request directory is left alone in all of these.

**Not covered, and said so (§3).** Real metadata exhaustion and a real power cut:
no layer here can produce them on demand. The exact states are written down
above, a row goes in `tests/install-matrix.py` and `tests/AGENTS.md`, and the
empty-marker branch is reached by case 10 with an emptied file.

## Unverified

Each is a claim about the kernel, and the check will answer it. **None was run for
this spec:** CI had jobs in flight every time it was checked, so the VM rule said no.

| item | why it matters now | settled by |
|---|---|---|
| Exchanging two subvolumes at the top level works | **The design depends on it.** Read, not run: `btrfs_rename_exchange` (`fs/btrfs/inode.c`, kernel master) refuses only exchanges across subvolumes unless both sides are subvolume roots, says two subvolumes "can be exchanged", and has branches for it. Here both parents are the top level, so that test does not even apply. `/var/lib` and `$oldvar` share `/var`. If case 1 disagrees, this spec comes back. | case 1 |
| Metadata fault at `:529`, after `:512` (intent) | **No longer matters for the promise:** any staging failure, whatever its cause, is before the first change. What remains is an exchange hitting `ENOSPC`, under Risks. | not testable on demand |
| `EBUSY` from a mount under `/var/lib` (intent) | **Only a `/var/lib` mount point itself should give it**, and then rollback handles it. A mount below it should not block the rename, and travels with it. | not in the check, because not installer-laid; a VM run if the owner wants it |
| Nested-subvolume delete (intent) | Docker's btrfs driver or `machinectl` can nest subvolumes in `/var/lib`, so the receipt's `rm -rf` may fail on them. `@home` has none by layout: `@home-snapshots` is top-level. Out of scope per the intent; nothing is lost, the delete only stops. | the receipt could add `btrfs subvolume list`, a plan-level note |
| `chattr +i` makes each step fail where cases 2-4 need it, and does not stop an earlier step | If not, those cases cannot fail as written: §1 applies to the setup too. | each case asserts in the journal that the expected step failed |
| Unprivileged `btrfs subvolume list` exits non-zero | Read in btrfs-progs v7.1: `btrfs_list_subvols` errors out of `list_subvol_search`, a tree search, which is privileged. | case 8 |

## Review

Codex (gpt-6-sol) and a second Claude Opus reader reviewed this read-only, **not
agy**. Each finding was checked against the source and this draft includes the confirmed
ones. Neither reader nor the author ran the command or the unit.

agy was not obtained, verbatim, on the first try: `Individual quota reached. Please upgrade your
subscription to increase your limits. Resets in 23m21s.` (exit 3, code 429). On the
second: `print timeout after 10m0s with the turn still in progress; the response is partial`
(`DEADLINE_EXCEEDED`).

- **Confirmed:** forwarding `PATH` let a caller's `gum` answer the questions, and
  `GUM_*` can change the prompts. Not an escalation, since the caller already holds
  sudo, but it broke the claim that confirmations are unchanged: neither is
  forwarded now. Case 2's cleanup break could not fail, because the copy never
  started: moved to case 3. Case 4 needs proof it reached the second exchange. An
  empty marker has more causes than a power cut. `mv -f` overwrote an earlier
  failure record: the command now refuses until it is dismissed. Cleanup after
  commit needed an explicit rule: the phase table.
- **Confirmed (Opus):** the trap was set in phase `stage` before the guards, so a
  name collision, or a failed `mv` with `$top` not yet set, would have removed a path
  this run did not create. That is the one route found to losing a person's data, and
  `phase=guard` closes it, with case 11. `set -e` inside the trap could skip the report.
  Case 8's fake `gum` had no break, and two properties hold it.
- **Read and upheld (Opus):** the exchange's kernel path, the commit order, the phase table for
  `home-swapped` and `done`, that no later step deletes user data, and that the menu row has a
  terminal and no `--check` in its `when`.
- **Refuted:** none.
- **Unverified (Codex):** kernel exchange of subvolumes, exactly where `chattr`
  fails, sudo and gum behaviour. All are in the table above. That gum reads
  `GUM_INPUT_VALUE` is from memory of its per-flag variables, unrun.
