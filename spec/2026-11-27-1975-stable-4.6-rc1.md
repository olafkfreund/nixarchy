# Spec: stable moves from Omarchy v4.5.0 to v4.6.0-rc1

Revision 2. Revision 1 chose route (a), main first. The Codex and agy reviews of
its plan (2026-11-27) showed that it cannot hold. After a main-first merge,
`main` pins rc1 and `edge` pins quattro `155c4b4`, so two pins that both read as
quattro would ship different content. `skill-parity` has one `upstream` hash per
section for quattro, `mise-free` one line set, and `omarchy-package-ledger` one
`edge` marking per package. Twenty packages that rc1 dropped (`base`, `limine`,
`pipewire` and others) cannot be marked to pass both. Route (b) puts both
branches on the same upstream commit before `main` moves, so no ledger ever has
to tell two quattro commits apart.

## Design

### Phase 1: edge moves to rc1's commit

A carry on `edge-candidate` (branch off `origin/edge`), pushed and dispatched
with `from_candidate=true` the way #1964's carries were, pins quattro
`745271ccd293fc2e7a233b269004a9926a5c6cb4`. That is the commit the
`v4.6.0-rc1` tag names, 33 commits past `155c4b4`. The carry pins both
`flake.nix` copies and `flake.lock` (§8). It classifies the 33 commits in the
model edge already has: quattro (now rc1's content) against `main`'s v4.5.0
tag, which edge's `main-pin` job still builds.

The trial tree (`/mnt/data/vmtest/rc1-trial`, rc1 on `main`) found these, and
the reviews corrected them:

- **Commit-keyed rungs.** `pkgs/omarchy/default.nix` (`1625-no-mise-edge.patch`,
  `1923-reaper-check-155.patch`) and `tests/mise-free.nix:11`
  (`isLatestEdge = hasSuffix "-155c4b4"`) select the newest quattro's
  variant by commit. Each moves to `745271c`. If the variant no longer applies
  there, the build says so, and the old one is checked against the new tree.
- **Fingerprint (PAM moved into `omarchy-apply-fingerprint-pam`).**
  - The old `setup_pam_config` handling is chosen by **whether the file still
    defines the function**, not by pin. The 4.5 tag defines it and rc1 does not.
    The post-delete assertion stays.
  - `omarchy-apply-fingerprint-pam` is replaced, when shipped, by
    `pkgs/omarchy/1975-apply-fingerprint-pam.sh`. It exits 0 only when sudo and
    polkit-1 each have an active `auth` line whose module is exactly
    `pam_fprintd.so`, given bare or as a store path. Comments and look-alikes do
    not count. Otherwise it names the NixOS options and exits 1. It only reads,
    and it builds the stack path from a variable, because the drift guard
    refuses a literal one.
  - `omarchy-setup-security-fingerprint-enroll`, the panel's root helper run
    through pkexec, gets the port `omarchy-apply-lock` already has: it no longer
    resets `PATH` and `OMARCHY_PATH` to `/usr`. Its `pacman -Qqo` and
    `omarchy-pkg-missing`/`pacman -S` branch becomes the `fprintd-enroll`
    preflight that `quattro-script-ports.sh` gives the terminal setup.
  - The panel surfaces `fail secure` from the helper. The options text then
    reaches the owner through the panel's log, and the plan checks that it does.
  - `menu-guidance` is read under rc1. Its stub must answer the literal `ok`
    that the setup expects from `omarchy-shell shell summon`, or pass
    `--terminal`, so the test reaches the code it means to test.
- **Ledgers, two-state as today:**
  - `bin-ledger`: rows for the two new scripts.
  - `etc-overlay`: classify `systemd/logind.conf.d/30-lid-external-power.conf`
    (`edge = "only"`). The ZBook rule rc1 dropped becomes `edge = "absent"`.
  - `omarchy-package-ledger`: the 20 dropped names become `edge = "absent"`.
    They are still in the 4.5 tag and gone from quattro.
  - `user-migrations-ledger`: classify 1795709363. Rows for migrations rc1
    dropped are marked to match.
  - `skill-parity`: the two rewritten sections get `upstream` set to rc1's
    hashes, with `tag_upstream` holding the 4.5 tag's.
  - `autostart-runtime`: the herdr row is marked absent on quattro.
  - `mise-free`: the new and stale lines go under the variant that `isLatestEdge`
    selects.

### Phase 2: main moves to the tag

Route (a)'s sequence on `chore/1975-stable-4.6-rc1`, now with no
classification left in it. Merge `main`, merge the published `edge` for real,
then pin `github:basecamp/omarchy/v4.6.0-rc1` (rev `745271c…`, narHash
`sha256-0tGp3frcYptp7b40nb8UO+mcol3JZTm1UZYUUxC8jio=`). Edge and the tag are
the same tree, so every row from Phase 1 is right for both.

- **One predicate**, `pkgs/omarchy/is-quattro.nix`:
  `lib: version: lib.hasPrefix "edge-" version || lib.versionAtLeast version "4.6.0"`.
  Nix sorts `4.6.0-rc1` above `4.6.0`, so the threshold is the release itself.
  Evaluated: 4.5.0, 4.5.1 and 4.5.9 give tag. 4.6.0-rc1, 4.6.0-rc2,
  4.6.0-beta1, 4.6.0, 4.6.1, 4.10.0, 5.0.0 and edge-… give quattro.
  The 28 sites that test `hasPrefix "edge-"` on an Omarchy version call it.
  Names stay. The `dev-YYYYMMDD-<rev>` version an `--override-input` gives
  reads as tag, as it does today.
- **One exception:** `installer/cd.nix`'s ISO label keeps its own
  `hasPrefix "edge-"`. It parses the version string's shape, and a tagged
  ISO's label must stay `NIXARCHY_4_6_0_RC1…`.
- `readme-counts.sh --fix` after the pin (#1537).
- The PR merges with `gh pr merge --merge`.

### Coexistence (§14)

No new option, and no changed default a user sets. The PAM replacement only
reads. `modules/nixos.nix` installs only what a `covered`/`shipped` row says.

### Afterwards

Close #1972. Edge's next scheduled run asks for the newest quattro. If that
commit is past `745271c`, edge holds it the usual way (#1964), and that is
ordinary edge work.

## Alternatives rejected

- **Route (a), main first.** It needs three-state ledgers for the two quattro
  commits. Both reviews found the cases (skill hashes, mise lines, 20
  package rows).
- **Three-state ledgers** (tag, quattro `155c4b4`, rc1). Correct, and a new
  mechanism in six checks for a state that lasts one edge run.
- **Edge to the newest quattro instead of `745271c`.** It adds whatever came
  after rc1 to the same carry, and edge and the tag would differ again.
- **A predicate threshold of `4.6.0-rc1`.** That makes final 4.6.0 read as a
  tag.
- **Patching #1972's branch, or renaming `isEdge`.** Same reasons as
  revision 1.

## Risks

- **Edge's `verify` boots rc1's content first.** A red VM check is a carry in
  Phase 1 with its own §1 proof.
- **The carry is checked under both pins locally:** quattro `745271c`, and
  `main`'s 4.5 tag in a scratch tree, exactly as `omarchy-edge.yml`'s
  `main-pin` job does (copy both pin fields from `origin/main`, then
  `nix flake update omarchy`).
- **The fingerprint panel cannot be exercised without a reader.** The script is
  tested with stub stacks, and the helper under a cleared environment with
  stubbed `fprintd-enroll`. A real enrollment is a hand test.
- **The merge must stay a merge** (§8).

## Verification

- §1 for each guard this touches: drop the PAM install line and the drift guard
  fails. Make the matcher loose and the stub-stack test fails on the commented
  and look-alike fixtures. Remove the predicate on the Phase 2 tree and the
  webapp patch fails.
- Phase 1, before the push: every generated check, and the claimed non-VM
  checks `main-pin` builds, under quattro `745271c` and under main's tag. Also
  statix, deadnix, `nix fmt -- --ci` and `readme-counts.sh --check`. The VM
  tier (`session`, `options-files`) runs when no runner is busy. Then the edge
  run must publish `745271c`.
- Phase 2, before the push: the same checks under the rc1 tag. CI's `build`
  and `install check` must be green on the PR head. After merge, main's runs
  are green, and edge's next merge of main is clean.
