# Spec: The system profile carries fcitx5's themes, and nothing else of fcitx5's

The owner approved the intent and its three recommendations on 2026-11-05: link only the themes, do
not repair existing machines on upgrade, land after #1634.

## Design

**One line, `modules/nixos.nix`, `environment.pathsToLink` (`:1379-1384`):**

```nix
++ lib.optional usingFcitx5 "/share/fcitx5/themes"
```

`usingFcitx5` is already defined at `:142`. The patch at `pkgs/omarchy/default.nix:906-908` stays. Its
path then resolves, and the symlinks the script writes name the system profile rather than a store
path, so they follow the current system across rebuilds and garbage collection.

**Three checks, each of which can fail (§1, §2):**

1. **`tests/input-methods.nix`,** which #1634 adds and which already holds `reference` and the real
   package: build a small `pkgs.buildEnv` of that package with `pathsToLink =
   reference.config.environment.pathsToLink`, and assert `share/fcitx5/themes/default/prev.svg` exists and
   `share/fcitx5/addon` does not. That measures the real list and the real package, including the
   constraint against linking the whole directory. Not `${reference.config.system.path}`: that is every
   desktop package, in a check the `omarchy` job builds before the system closure is warm.
2. **`tests/options.nix`,** a case `fcitx5ThemesLinked`: `on` reads the entry from the adopter's
   `environment.pathsToLink`, `off` from the same list on a Mode A machine that turns fcitx5 on itself:
   `modeAOff` with `i18n.inputMethod = { enable = true; type = "fcitx5"; }`. `loaderOff` has no input method,
   so moving the entry outside `cfg.enable` would stay green there. The `usingFcitx5` half is the coexistence
   fixtures below.
3. **`tests/session.nix`,** beside the existing `#1614` steps: remove
   `~/.local/share/fcitx5/themes/omarchy/prev.svg`, because `omarchy-theme-set` has already written it by
   then, run `omarchy-theme-set-fcitx5 --activate` as the desktop user, then assert `test -e` on it. `-e`
   follows the link, so a dangling one fails. This is the highest layer that can see the user's result. Nothing
   here looks at the rendered window, which stays a hole: the `Image=` lookup is fcitx5's.

**Docs:** the release note says the glyphs arrive at the next theme change, and gives the command for
someone who does not want to change theme:

```bash
omarchy-theme-set-fcitx5
```

## Coexistence

- **A user's own `environment.pathsToLink`:** a list option, so the entry merges, and §7's plain
  assignment applies. A user who already lists `/share/fcitx5` gets the whole directory, by their choice.
- **A user who picked ibus, or turned input methods off:** #1634 already adds `input-own-ibus`,
  `input-default-ibus` and `input-disabled` to `tests/coexistence/fixtures.nix`, and they are the only
  ones covering each half of `usingFcitx5`. Extend their assertions in `tests/coexistence/default.nix` so the
  entry is absent in all three. No new fixture. Break: drop the `optional`.
- **A user's own fcitx5 theme package in `systemPackages`:** now appears under
  `/run/current-system/sw/share/fcitx5/themes`, on `XDG_DATA_DIRS`, so fcitx5 can list it. A theme with
  the name `default` is the only collision. `system.path` resolves it silently by priority (§14), and the
  glyphs would then come from theirs. Accepted, with no fixture: nothing fails, and it is what they installed.

## Alternatives rejected

- **Link all of `/share/fcitx5`.** Exposes every addon's `.conf` on `XDG_DATA_DIRS`, to any fcitx5,
  including the stale addon-less daemon #1614 tests.
- **Patch in a store path.** Dangles after garbage collection, until the next theme change.
- **`OMARCHY_FCITX5_PACKAGED_THEME` as a session variable.** Upstream reads it, but it names a store path
  too, so it has the same defect, and it is stale in a session started before a rebuild.
- **An activation hook to repair existing machines.** The owner declined it.

## Risks

- **Closure:** `system.path` gains links, not packages. `reference-toplevel` changes only in that
  derivation, and the installer's seeded closure takes it from the same place, so `install` is the proof.
- **Nested `pathsToLink`:** `/lib/omarchy-hyprland-titlebars` already uses two segments, but three under
  a real sibling are not yet measured here. Check 1 is the measurement: it fails if the entry links
  nothing, or too much.
- **`iso-budget`:** symlinks only, so no measurable growth.

## Verification

- `checks.input-methods`, `checks.options-system`, `checks.coexistence`, `checks.session` by §6's tiers.
- Breaks: remove the line, and check 1's `prev.svg` assert and the session step fail; widen it to
  `/share/fcitx5`, and the `addon` assert fails; make it unconditional, and the coexistence assertions fail;
  move it outside `cfg.enable`, and the options case fails.
